## 0. 文档宪法

### 0.1 规范词与优先级

本文中的 **MUST / MUST NOT / SHOULD / SHOULD NOT / MAY** 是规范词：

- **MUST / MUST NOT**：满足对应 conformance profile 的实现必须遵守；
- **SHOULD / SHOULD NOT**：除非有被记录、可审计的充分理由，否则必须遵守；
- **MAY**：允许的实现选择，不构成兼容性承诺。

发生冲突时，优先级如下：

1. 本文带唯一 ID 的规范条款；
2. 本文状态机、事务语义与错误语义；
3. 议题 27 的设计理由；
4. v0.1–v0.4.1 与议题 1–26 的历史设计；
5. 当前原型实现。

旧实现与本文冲突时，必须登记为实现缺口，不能用“代码已经这样做”反向改写规范。

### 0.2 规范、理由、理论和证据分离

| 层 | 可以声称什么 | 不得声称什么 |
|---|---|---|
| Normative Spec | 必须遵守的接口、不变量、状态机和错误 | 已经实现或已经验证 |
| Rationale / ADR | 选择理由、替代方案和权衡 | 设计决定天然正确 |
| Theory | 定义、假说、反例和证明义务 | 未形式化结论已获证明 |
| Evidence | 特定环境中的观察、测试和限制 | mock/单机结果等于生产事实 |

`[DOC-CLAIM-001]` 每个关键 claim MUST 有唯一 ID；在首次 `AssuranceLevel=CONFORMANT` 发布前，registry 还 MUST 为每项补齐类型、规范状态、适用范围/profile、证据方法、结果、限制和制品引用。

```yaml
id:
kind: vision | requirement | design | hypothesis | observation
normative_status: draft | candidate | stable | deprecated
scope: unit | process | node | real-provider | distributed | production
evidence_method: proof | property-test | mock | simulation | integration | field
result:
limitations:
artifacts:
supersedes:
```

`[DOC-CLAIM-002]` “设计已规格化”“原型测试通过”“生产不变量成立” MUST 被视为三个不同状态。

`[DOC-SOURCE-001]` v0.5 正文 MUST 只给出一个当前答案，不得继续采用“旧正文 + 多层修订注”的叠加维护方式。

### 0.3 当前合规状态

本文定义的是目标架构及其可测试契约。目前仓库中的实验最多提供局部、单机或模拟证据。因此：

- v0.5 条款当前总体状态为 `design/candidate`；
- `[DOC-CONFORM-001]` 任何未通过相应 profile 测试的实现 MUST NOT 宣称符合 v0.5；
- 本文中的未来对象和接口是演进约束，不表示已经交付；
- 负面实验是规范输入，不是需要隐藏的失败。

# 第一部：最高目标与核心设计哲学

## 1. NLOS 宪法

### 1.1 不可变最高目标

`[NLOS-GOAL-001]` llmos 的最高目标 MUST 保持为：构建达到 Windows/macOS 级别的通用、现代、系统级 NLOS。

这里的“级别”指系统完整性，而非第一天重写硬件内核：

- **通用性**：第三方能开发、安装和运行设计者事先没有预见的应用，无需修改内核；
- **系统权威性**：执行、身份、能力、资源、通信、持久状态、生命周期和副作用由系统统一裁决；
- **现代性**：原生考虑本地、多设备、云边、分布式、联邦身份、迁移、恢复和持续升级；
- **完整人机界面**：自然语言 Shell、Task Space、Task Manager、Resource Monitor、窗口、通知、权限确认、设置和多模态交互；
- **自动与手动控制并重**：自然语言可从顶层操作完整 Application，用户也可沿 System/Application/Task/Process/Agent/Resource/Topic 各层直接观察和调度；
- **开发者平台**：稳定契约、SDK、调试、包、驱动、测试、文档和迁移工具；
- **应用生态**：发现、获取、安装、组合、授权、更新、回滚和卸载；
- **海量 Agent 系统性**：像现代 OS 管理进程/线程一样，以层级任务域管理大量 Agent 的执行、资源、取消、故障与共享状态；
- **现代资源平面**：统一管理 CPU、内存、存储、I/O、网络、加速器、能源、费用、模型上下文、消息容量与人类注意力；
- **长期品质**：安全、隐私、性能、可访问性、离线、恢复、审计和兼容性。

`[NLOS-SCOPE-001]` 启动微内核、reference monitor 和单机纵切面 MUST 被描述为 bootstrap，而不是最终产品定义。

`[NLOS-GEN-001]` “未预见第三方应用能否在不改内核的前提下运行” MUST 成为通用性的最终验收问题。

`[NLOS-COMPAT-001]` 兼容性机制 MUST 从第一版契约开始存在，不得推迟到生态形成之后。

`[NLOS-SCALE-001]` NLOS MUST 能通过 TaskPlan/TaskNode 惰性物化、Context residency、层级 TaskGroup/TaskAttempt、Global/Cell/Worker Scheduler、Cell 分片和局部权威扩展到海量 Agent；不得依赖每 Agent 一个宿主 PID、单一全局 prompt、可变 Blackboard、全局锁或“所有 Agent 持有相同信念”。

`[NLOS-CONTROL-001]` 自然语言、可信 GUI、CLI 和结构化 API MUST 收敛到相同 typed Intent/TaskPlan/ControlCommand、Capability、Resource 和 Receipt 路径；任一交互形式都不得获得绕过系统不变量的特权后门。

`[NLOS-RESOURCE-001]` NLOS MUST 具备现代系统级 Resource Manager；金钱/token Budget 只是资源平面的一个维度，不能代替 CPU、内存、I/O、存储、网络、accelerator、energy、capacity、rate 和 attention 的各自控制器。

### 1.2 NLOS 主权域

**NLOS 主权域（NLOS Sovereignty Domain）** 是一组由同一 NLOS reference monitor 实际控制的工作负载、资源和副作用边界。

`[NLOS-AUTH-001]` 在 strict 主权域内，以下权威 MUST 由系统拥有：

1. Principal 与 Process 身份绑定；
2. Capability 与 Namespace 裁决；
3. Process 生命周期、隔离和故障域；
4. ResourceAccount 的预留、消费和结算；
5. Channel 与受保护 I/O；
6. 系统可见持久对象与审计锚点；
7. 外部副作用的 Driver 中介；
8. Package、Application 与更新信任链。

`[NLOS-HOST-001]` NLOS MAY hosted 于 Linux、Darwin、Windows、容器、WASM、云或 Kubernetes。是否裸机不得作为其 OS 身份的唯一判据。

`[NLOS-HOST-002]` 不能实际阻止旁路的部署 MUST 标记为 `COOPERATIVE`，不得宣传 strict 系统权威。

### 1.3 自然语言的系统位置

自然语言是 NLOS 的首要交互方式和意图来源，但不是未经约束的机器 ABI。

```text
Natural Language / GUI / API
          ↓
typed Intent
          ↓
proposed Actions + effects + cost + provenance plan
          ↓
consent / policy / authorization
          ↓
execution through capabilities and reservations
          ↓
Receipt + Artifacts + provenance + undo/compensation
```

`[NLOS-NL-001]` 任何产生系统或外部副作用的自然语言请求 MUST 在执行前编译为版本化、类型化、可授权、可计量、可审计的 Intent 和 Action。

`[NLOS-NL-002]` 原始自然语言 MUST NOT 直接成为 KABI syscall 参数或权限依据。

`[NLOS-NL-003]` 用户 MUST 能在高风险 Action 执行前看到其目标、主要副作用、权限、预算上界和可撤销性。

`[NLOS-NL-004]` 图形化、结构化、实时和后台应用 MUST NOT 被强迫表现为聊天机器人。

## 2. 核心思想与方法论

### 2.1 概率智能在用户态，确定性不变量在系统边界

llmos 的核心原则是：

> **模型负责理解、规划与提出行动；内核不相信模型的自律，只在不可绕过的边界上强制身份、权力、资源、生命周期和证据结构。**

```text
智能    = 不可信的用户态策略
权力    = Principal + Capability + Namespace
资源    = quote + reserve + consume + finalize
执行    = Process + Driver + Operation
知识    = immutable events + signatures + policy-relative views
委托    = attenuated capabilities + budget + immutable obligation
```

`[PHIL-BOUND-001]` 系统安全 MUST NOT 依赖 prompt 要求 Agent “自觉”遵守预算、权限、审计或取消。

`[PHIL-CTRL-001]` 内核控制 SHOULD 尽量不理解自然语言内容；它只判断 handle、权利、额度、期限、状态迁移和结构化证明。

`[PHIL-MECH-001]` Kernel MUST 实现最小、不可绕过、必须原子的机制；可替换策略 MUST 位于用户态或可信系统服务。

`[PHIL-EVID-001]` 每项设计 MUST 同时通过两道门：

1. **证据门**：当前证据是否支持所声称的不变量；
2. **演进门**：该设计是否保留通往通用应用、完整桌面和第三方生态的路径。

### 2.2 受约束的历史类比

OS、Unix、ELF、虚拟内存、BFT、Rice 定理和信息论可提供设计启发，但不自动构成证明。

`[THEORY-LIMIT-001]` “Agent 类似 Byzantine 节点” MUST 只作为威胁模型类比，不得自动继承 `3f+1` 等结论。

`[THEORY-LIMIT-002]` “意义 = 压缩” MUST 标记为研究启发式，不得作为已证明的语义定律。

`[THEORY-LIMIT-003]` “语义图灵完备”在 v0.5 中统一降级为“知识变换工作流可表达性假说”。

`[THEORY-LIMIT-004]` “不可命名 = 不可想象”统一改为可检验的“不可命名 = 在该 Namespace 中不可寻址、不可行动”。

`[THEORY-LIMIT-005]` Provenance MUST 表述为系统捕获或主体签署的 attestation，不得宣称覆盖模型预训练知识或全部隐式世界知识。

### 2.3 现代系统机制迁移方法

Agent 系统正在重现传统计算系统面对过的核心矛盾：有限资源上的并发、隔离、共享、一致性、故障、部署和人机控制。NLOS 不应逐个重新发明答案，而应先从现代 OS、runtime、数据库和分布式系统迁移已经验证的机制，再处理 Agent/模型带来的语义差异。

采用分为三类：

| 类别 | 含义 | 例子 |
|---|---|---|
| A 直接迁移 | 不变量和机制基本不变，只更换对象类型 | process isolation、capability、queue、backpressure、WAL、MVCC、lease/fence、cgroup、job control |
| B 语义适配 | 机制保留，但资源、状态或失败语义需要扩展 | Context paging、token/model slot、Topic interest、semantic cache、Agent checkpoint、human attention |
| C NLOS 新机制 | 传统系统没有对应的完整语义，必须新增 | typed Intent、IntentSpec、semantic provenance/view、EffectPermit、模型不确定性边界 |

`[PHIL-TRANSFER-001]` 新增 NLOS 抽象前，设计者 MUST 记录：最接近的现代系统机制、可直接继承的不变量、因 Agent/模型产生的语义断裂、为何现有机制无法无损组合，以及对应 conformance/故障测试。没有完成该分析不得直接扩张微内核。

`[PHIL-TRANSFER-002]` 迁移对象是**控制回路、隔离边界、状态机和失败语义**，不是术语。不得因为把 Agent 命名为“进程”就声称已经获得地址空间隔离，也不得因为使用 Topic/CRDT/consensus 名称就声称获得对应复杂度或一致性保证。

`[PHIL-HOSTED-001]` NLOS 采用双层系统模型：宿主 OS/runtime 负责 CPU thread、地址空间、页、FD、网络和最终强杀；NLOS 负责 Application、Task、Agent、Context、模型/工具、资源合同、语义提交和用户控制。两层责任必须通过可验证 binding/Receipt 连接，不能只靠约定。

### 2.4 现代系统机制迁移矩阵

| 领域 | 现代系统成熟机制 | NLOS 对应物 | 关键适配/边界 |
|---|---|---|---|
| 执行层级 | Application → Process → Thread → Coroutine/Fiber | Application → Process → AgentInstance → ExecutionFiber/Activation | AgentInstance 是 thread/actor 式身份；Fiber 是用户态可恢复执行流；强隔离仍在 Process/IsolationUnit |
| CPU/运行调度 | preemption、time slice、priority、EDF、fair-share、affinity、work stealing | Process/Agent/Fiber queue、deadline/QoS、Cell/Worker scheduler、model slot | LLM/Tool wait 与 CPU run 分维计量；pure-code 最终依赖宿主抢占 |
| 异步执行 | event loop、future/promise、interrupt、completion queue | Operation、stream、callback fence、Fiber WAITING/READY | callback 必须绑定 generation、cancel epoch 和 OperationId |
| 内存 | virtual memory、page fault、working set、page cache、COW、swap、OOM | Context residency、RAG page-in、KV/prefix cache、TaskSnapshot、checkpoint/evict | Artifact 是数据本体；回收派生 Context 不得改变逻辑读集 |
| 资源隔离 | cgroup/job object、quota、reservation、QoS、pressure/reclaim | ResourceGroup、ResourceContract、AdmissionPlan、Allocation/Lease | token/cost 与 CPU/memory 分维；余额不能冒充物理隔离 |
| IPC | pipe/socket/shared memory、bounded buffer、signal | Channel、Message、Topic、Blackboard、CancellationScope | Topic 匹配和语义 reducer 属于服务层；内核只保留通用 I/O 锚点 |
| 并发控制 | mutex/semaphore、futex、actor mailbox、structured concurrency | TaskGroup、Agent mailbox、EffectSlot、TaskControlRecord | 不鼓励跨 Agent 共享可变内存；共享必须显式 consistency contract |
| 持久化 | WAL、fsync、snapshot、journal、event sourcing | durable Ledger、Artifact revision、SemanticEvent、Task/Effect history | flush 不是 durability；未知副作用不能改名为失败 |
| 数据一致性 | transaction、MVCC、CAS、serializable、RCU、CRDT | TaskSnapshot/WriteSet、TaskHead CAS、consistency mode、Authority View | embedding/LLM 输出不能直接充当授权线性化点 |
| 分布式一致性 | consensus、lease、fencing、epoch、quorum、anti-entropy | TaskAuthority、Quota/CapacityLease、Cell epoch、takeover barrier | 认识论 quorum 按独立 ControlDomain，而非复制 Agent 数 |
| 分布式部署 | control/data plane、cell/shard、service discovery、placement、migration | Global/Cell/Worker、ServiceDirectory、Namespace、Process migration | 正常热路径不得全局扫描或依赖单点 prompt |
| 流量治理 | load balancing、rate limit、circuit breaker、bulkhead、retry/backoff | provider pool、Topic throttle、ResourceGroup bulkhead、Driver retry policy | retry 必须保留原幂等身份；模型/工具 storm 由 payer 与 admission 约束 |
| 生命周期 | init/systemd、service manager、job control、signal、supervisor tree | Application service、TaskGroup、Process supervisor、CancellationScope | daemon/UI 不必伪装成 Task；detached child 必须有新 owner 和资源域 |
| 安全 | user/role、capability、namespace、sandbox、MAC、secret store | Principal、Capability、Namespace、IsolationDomain、Keychain/Driver custody | prompt 不构成权限；credential 不进入不可信 Process |
| 可观测性 | metrics/log/trace/profile/core dump/audit | Task/Agent/Operation trace、Resource metrics、Semantic provenance、Receipt | 聚合和采样必须保留可下钻的权威关联；日志内容视为不可信输入 |
| 软件交付 | package、ABI、loader、signature、update/rollback | Package、Installation、Application、Executable、SABI/KABI | memory seed 与用户数据分离；升级不能静默改变已冻结 Task |
| 人机控制 | desktop、task manager、activity monitor、settings、CLI/API | NL Shell、Task Space、SystemControl、Task Manager、Resource Monitor | NL/GUI/CLI/API 进入同一 typed ControlCommand 和 Receipt |

`[PHIL-MATRIX-001]` 每个阶段路线和实现切片 MUST 从该矩阵选择需要兑现的机制，并为“不采用”的成熟机制记录理由；项目不得在调度、缓存、一致性或故障恢复问题上默认从零发明。

`[PHIL-MATRIX-002]` 现代机制的采用 MUST 保持 NLOS 微内核边界：scheduler policy、Context replacement、Topic predicate、CRDT merge、Planner 和语义监督通常位于系统服务/用户态；只有不可绕过且必须原子的 enforcement 进入 KABI。

# 第二部：对象模型与系统边界

## 3. 一等对象模型

### 3.1 身份和生命周期必须分离

`[MODEL-ID-001]` 下列 ID MUST 是不同的名义类型，不得互相复用：

```text
PrincipalId       ApplicationId      PackageId
InstallationId    ExecutableId       ProcessId
AgentRoleId       AgentInstanceId    ExecutionFiberId
ActivationId      TaskGroupId        TaskId
TaskAttemptId     IsolationDomainId  TaskPlanId
TaskNodeId        SchedulerDomainId  TaskSnapshotId
TaskCommitId      CancellationScopeId CommitPermitId
EffectPermitId    TaskAuthorityAssignmentId LogicalEffectId
IntentId          ActionId           ControlCommandId
OperationId       ReceiptId
ArtifactId        ContextId          WorkspaceId
SessionId         NamespaceId        CapabilityId
ResourceAccountId ResourceGroupId    ResourceAllocationId
ResourceControllerId ControllerBindingId AdmissionPlanId
AdmissionDecisionId ReclaimRequestId
QuotaLeaseId      CapacityLeaseId    ExclusiveDeviceLeaseId
ReservationId
EscrowId           ExpireRequestId
ChannelId         DeviceId           DriverId
SemanticEventId   ContentDigest      ControlDomainId
```

`[MODEL-ID-002]` 稳定 ID MUST NOT 编码机器地址、节点位置、数据库主键或当前网络路由。

`[MODEL-ID-003]` 所有可迁移运行对象 MUST 另带 `generation/epoch`，旧 generation 的 handle 与回调 MUST 被拒绝。

时间使用不同名义类型：

```text
MonotonicDeadline {boot_epoch, ticks}
UtcInstant         # 声明、展示和跨域排序提示
AuthorityInstant   # 由指定权威时钟、epoch 与签名解释
AuthorityExpiry    # 由签发者、epoch 与接收域 policy 解释
Duration
```

`[MODEL-TIME-001]` 本机 cancel/deadline MUST 使用 MonotonicDeadline；持久 Spec、Lease 和 Capability expiry MUST 使用明确 authority/epoch 的 AuthorityExpiry；生产者 `issued_at` 只是其签名声明，接收域 Admission time 才是本域观察事实。

### 3.2 对象定义

| 对象 | 规范定义 | 最小权威 |
|---|---|---|
| Principal | 用户、组织、应用、服务、设备或受委托主体 | 身份与授权链 |
| Application | 安装、授权、更新、卸载和数据所有权单位 | 稳定应用身份 |
| Package | 不可变、可签名、可分发制品 | digest 与签名 |
| Installation | Package 在 Workspace/Device 上的安装记录 | 授权与版本绑定 |
| Executable | Package 中可加载的代码、Agent、服务或驱动组件 | 加载约束 |
| Process | 调度、隔离、故障和生命周期单位 | 宿主可强制执行 |
| Agent Role | 自主语义角色，可跨一个或多个 Process | 用户态语义 |
| Agent Instance | AgentRole 在某 TaskAttempt/Process incarnation 中的一次可调度执行 | attempt + process binding |
| Execution Fiber | AgentInstance 内可挂起、恢复的用户态 coroutine/fiber/continuation | runtime-local scheduler + parent binding |
| Activation | AgentInstance/Fiber 的一次 dispatch quantum/turn | scheduler decision + metering interval |
| TaskGroup | 层级资源、取消、失败传播和共享范围的结构化并发域 | durable group policy |
| Task | 用户可见、可持续、可委托的义务 | 独立于聊天和进程 |
| TaskPlan | 自然语言或结构化目标编译出的版本化执行图 | issuer、compiler、plan digest |
| TaskNode | TaskPlan 中尚可保持纯逻辑状态、按需物化的工作节点 | dependency、admission、materialization generation |
| TaskAttempt | Task 的一次授权执行 generation；语义快照、资源与提交隔离单位 | immutable attempt contract |
| SchedulerDomain | system/Cell/Workspace/Application/TaskGroup/Worker 的分层队列与调度权威 | policy digest、generation、capacity view |
| IsolationDomain | 执行、Namespace、资源、数据、网络、secret、取消和故障隔离的组合边界 | generation + fence |
| TaskSnapshot | TaskAttempt 的 causal-closed 不可变输入切面 | revision/checkpoint digest |
| TaskControl/CommitPermit | winner、取消、副作用和 canonical commit 的线性化控制对象 | authority term + epoch CAS |
| Intent | 用户或应用请求的类型化目标 | 可审计提议 |
| Action | 已解析的具体副作用计划 | 授权与预算 |
| Operation | 异步执行实例 | progress/cancel/deadline |
| Receipt | 已发生事实、成本和结果的不可变回执 | 签名与关联 |
| Artifact | 用户或应用持久拥有的内容、文档或结果 | handle、版本、所有权 |
| Context | 为一次执行构造的派生输入视图 | quota、快照、映射 |
| Workspace | 用户/组织数据、应用和权限的协作边界 | namespace root |
| Session | 交互、桌面和设备临时状态 | 可恢复交互 |
| Capability | 对对象执行一组操作的不可伪造权力 | 衰减、租约、撤销 |
| ResourceAccount | fungible credit、费用与计量归属的权威账本账户 | 原子守恒 |
| ResourceGroup | CPU/memory/I/O/accelerator 等调度、容量、压力和回收的层级隔离容器 | host controller binding |
| ResourceController | 某类容量/速率/计量/排他资源的不可绕过强制器 | signed manifest + generation |
| AdmissionPlan/Decision | 多 controller 工作在 dispatch 前的 prepare/commit/abort 决定 | durable decision + barrier |
| ResourceAllocation/Lease | 对本地容量、独占设备或分布式配额的有界授权 | generation、expiry、reclaim、fence |
| Channel | 有序、可取消、有背压的通信原语 | commit + wakeup |
| Device/Driver | 外部能力及其可替换实现 | 不可绕过调用边界 |
| Semantic Event | 断言、判断、验证、撤回或规格事件 | 身份、签名、顺序 |

`[MODEL-AGENT-001]` `Agent` MUST NOT 再同时表示 Application、Package、Executable、Principal 和 Process。兼容代码中若保留 Agent 运行对象，其内核含义只能等价于 Process；人格和职责使用 AgentRole 表达。

`[MODEL-ART-001]` Artifact 是用户数据本体；Context 是针对执行生成的派生视图。二者 MUST NOT 合并。

`[MODEL-HUMAN-001]` Human Principal 与其手机、审批终端或消息端点 MUST 分离；“人是 Device”不得成为唯一人类模型。

`[MODEL-RESOURCE-001]` ResourceAccount 与 ResourceGroup MUST 分离：前者表达钱/可转移额度/权威核算，后者表达 cgroup/job 式调度与容量隔离。一个 TaskAttempt 通常同时绑定二者；实现不得用账户余额冒充 CPU/memory isolation，也不得用 scheduler counter 直接改写信用账本。

`[MODEL-AGENTINST-001]` AgentRole 只表达角色；每次可调度 Agent 执行 MUST 有独立 AgentInstanceId，并绑定 TaskAttemptId、ProcessId/incarnation、ContextId 与 producer ControlDomain。AgentInstance 类似 thread/actor，不是硬安全边界；互不信任的实例必须进入不同 Process/IsolationDomain。

`[MODEL-EXEC-HIER-001]` 执行层级 MUST 明确为 `Application ⊇ Process ⊇ AgentInstance ⊇ ExecutionFiber/Activation`。一个 Application MAY 拥有多个 Process；一个 Process MAY 承载多个 AgentInstance；一个 AgentInstance MAY 以一个或多个 Fiber/Coroutine 在宿主线程/event loop 上 M:N 复用。任何层级都不得因名称相似而自动继承上层的安全或资源隔离。

`[MODEL-FIBER-001]` ExecutionFiber 共享所属 Process 的地址空间、FD 和崩溃域，并继承 AgentInstance/TaskAttempt 的 Capability、Context、ResourceGroup 和 CancellationScope。Fiber 不是 Principal、Application、Task、Process 或强隔离边界；互不信任代码不得仅靠不同 Fiber 隔离。

`[MODEL-ACTIVATION-001]` Activation 是一次可计量调度片段，不是持久义务或资源所有者。它 MUST 绑定 AgentInstance/Fiber generation、SchedulerDomain、dispatch reason、start/end、CPU/model/tool wait 分类、cancel epoch 和 usage；重调度创建新 Activation，不得覆盖历史计量。

`[MODEL-ISODOM-001]` IsolationDomain MUST 是名义对象并分别声明每个隔离维度及其 enforcement status；不得用单一 `isolated=true` 代替 Namespace、Capability、resource、data、network/device、secret、cancel 和 failure-domain 证明。

### 3.3 关键关系

```text
Principal ─owns/delegates→ Application / Workspace / Capability
Application ─installed-as→ Installation ─selects→ Package
Package ─contains→ Executable / Driver / UI Surface / Migration
Executable ─spawned-as→ Process ─hosts→ AgentInstance ─implements→ AgentRole
AgentInstance ─runs→ ExecutionFiber ─dispatched-as→ Activation
Task ─owns→ root TaskGroup ─contains→ child TaskGroup / TaskAttempt
Task ─runs-as→ TaskAttempt
Task ─bound-to→ IntentSpec ─authorizes→ Action ─runs-as→ Operation
TaskAttempt ─binds→ IsolationDomain + TaskSnapshot + ResourceGroup + ResourceAccount
IsolationDomain ─contains→ AgentInstance + Process
Task ─planned-as→ TaskPlan ─contains→ TaskNode
TaskNode ─materializes-as→ TaskAttempt + Process + AgentInstance
SchedulerDomain ─admits/dispatches→ TaskNode / TaskAttempt / Process
Operation ─uses→ Capability + Reservation + Context
Operation ─produces→ Receipt + Artifact + SemanticEvent
Artifact ─projected-as→ Context
```

`[MODEL-TASK-001]` Task MUST 独立于 Session、聊天窗口和单个 Process 的存活。

`[MODEL-TASK-002]` Task 是持续义务，TaskAttempt 是一次不可变输入/权力/资源绑定下的执行尝试；retry、recovery、spec refinement 和并行候选 MUST 使用不同 TaskAttemptId/generation，不能覆盖旧 attempt 的 Receipt。

`[MODEL-TASK-003]` 每个 TaskGroup MUST 属于且只属于一个 Task generation，并形成该 Task root 下的结构化并发树；跨 Task 协作使用显式 Task dependency/Channel，不把多个 Task 偷塞进一个 group。TaskGroup 不是聊天标签，其 cancellation、ResourceGroup/Account、Namespace、failure policy 和 child admission MUST 由系统服务持久化。

`[MODEL-PLAN-001]` TaskPlan/TaskNode 是可持久、可检查、可手工编辑的逻辑执行描述，不是已经存在的 Process 或 AgentInstance。系统不得仅因计划包含十万节点就提前创建十万个宿主进程、模型会话、Context 或工具连接。

`[MODEL-SCHED-001]` SchedulerDomain 只拥有其被授权层级内的队列、权重、并发槽和 placement policy；下级不得绕过上级 hard capacity，手工或自然语言控制也不得伪造调度权威。

`[MODEL-OP-001]` 所有潜在长操作 MUST 拥有 OperationId、状态、progress、cancel、deadline、部分失败语义和最终 Receipt。

## 5. 微内核驻留判据

一个机制只有同时满足以下五项，才应进入微内核：

1. 被绕过会破坏隔离、授权、核算或生命周期正确性；
2. 必须与权威状态迁移原子完成；
3. 不需要理解自然语言内容；
4. 与模型、provider、协议和应用类型无关；
5. 无法由更小的内核原语无损组合。

`[KERN-BOUND-001]` 每个新 KABI 入口 MUST 在 ADR 中逐项通过上述判据。

`[KERN-MIN-001]` syscall 数量 MUST NOT 被用作最小性证明；正交性、可组合性、失败语义和 conformance test 才是判据。

### 5.1 内核保留的机制

- Principal/Process 的认证绑定；
- Process 生命周期、宿主隔离、等待、取消与故障域；
- Namespace handle 与 Capability 的派生、委托、撤销和检查；
- ResourceAccount 的原子转移、预留、消费和结算；
- 通用异步 I/O、背压、poll、cancel 与 commit/wakeup；
- Checkpoint/Restore 的一致性锚点和 generation fencing；
- 不可伪造的内核审计锚点；
- Driver 调用的强制中介。

### 5.2 稳定系统服务保留的策略

- 登录、目录、联邦身份与权限提示；
- 应用发现、安装、更新、迁移、回滚和卸载；
- TaskPlan 分解、Dependency Resolver、惰性物化、模型选择、分层调度 policy 和验收解释；
- Artifact、Context/RAG、Search、同步和版本管理；
- Topic broker、Blackboard、Message；
- Semantic graph、embedding、TrustPolicy 与 View；
- Escrow 条件解析、定价、合同和信誉；
- SystemControl、Task Manager、Resource Monitor、Notification、Shell、Desktop、窗口和设置。

# 第三部：信任、身份与执行

## 6. TCB 与不可绕过条件

### 6.1 分域 TCB

| TCB | 最小组成 |
|---|---|
| Safety TCB | 宿主隔离、NLOS 微内核、Process supervisor、sandbox/egress、可信时钟、identity key store、capability、ledger/consensus store、lease/fence authority、gateway fence state、enforcement driver |
| Epistemic TCB | canonicalizer、append-only event store、签名校验、verifier registry、Trust View engine |
| Update TCB | Package 验签、installer、migration runner、updater、rollback anchor |
| Data/Service TCB | Artifact ACL/加密/持久化、Task/Receipt 权威状态、Application data container、Keychain、service manager |
| Trusted UI TCB | 登录、权限提示、密钥确认、系统级 chooser 和安全状态展示 |

`[TCB-LIST-001]` 每个 deployment profile MUST 列出具体 TCB 组件、版本和信任假设。

`[TCB-BYPASS-001]` 任一 untrusted Process（包括 Agent、纯代码 worker 和第三方 Application）中 MUST NOT 暴露原始 provider、工具、云账户或控制面 credential。

`[TCB-EGRESS-001]` strict domain 的网络 MUST 默认拒绝；DNS、loopback、Unix socket、云 metadata、代理变量、子进程、本地浏览器、继承 FD、SCM_RIGHTS、ptrace/debug entitlement、共享内存、动态加载器、设备节点和 GPU runtime 均 MUST 纳入旁路分析。

`[TCB-ENDPOINT-001]` 所有真实成本、canonical write 或受保护副作用端点 MUST 校验 Principal、ProcessId + incarnation epoch、Capability、Operation-bound Reservation；Task activity 还必须校验 TaskAuthority term/control epoch、Task/Attempt generation、IsolationDomain fence、cancel epoch、Commit/EffectPermit epoch；分布式场景再校验 node boot generation/lease epoch/fencing token。

`[TCB-TOOL-001]` 能直接读取宿主密钥、访问网络或控制 socket 的 Tool MUST 被独立沙箱化；否则整个 Tool 必须列入 Safety TCB。

`[TCB-DOWNGRADE-001]` 任一未被完全中介的路径 MUST 降低 GuaranteeTier，并在 Receipt 和 UI 中可见。

`[TCB-AUDIT-001]` 审计日志不得代替同步强制；“记录了越权”不等于“阻止了越权”。

### 6.2 正交合规维度

合规不能压缩成单一高低档位。v0.5 使用三个正交维度：

| 维度 | 枚举 | 含义 |
|---|---|---|
| EnforcementProfile | `COOPERATIVE` / `ENFORCED_SINGLE_NODE` / `ENFORCED_DISTRIBUTED` | 系统实际拥有多强的不可绕过权威 |
| SurfaceProfile | `KERNEL` / `APPLICATION_PLATFORM` / `DESKTOP` | 实现提供到哪一层稳定产品表面 |
| AssuranceLevel | `DESIGN` / `TESTED` / `CONFORMANT` / `PRODUCTION_EVIDENCE` | 声称由何种范围的证据支持 |

另声明部署形态：

```text
DeploymentMode =
  LOCAL_SINGLE_NODE | CONNECTED_CELL | HEADLESS_CELL

ImplementationManifest {
  schema
  implementation_id
  build_digest
  enforcement_profile
  surface_profile
  assurance_level
  deployment_mode
  feature_registry_digest
  operation_registry_digest
  resource_controller_manifest_refs
  concrete_tcb_components_and_versions
  host_enforcement_assumptions
  evidence_registry_checkpoint
  signer
  signature
}
```

`[PROFILE-ORTHO-001]` 实现 MUST 分别声明 EnforcementProfile、SurfaceProfile、AssuranceLevel 和 DeploymentMode，不得用“production”一词同时代替分布式、桌面和证据状态。

`[PROFILE-IMPL-001]` 每个可部署 build MUST 发布签名 ImplementationManifest；profile、feature、operation、Resource controller、TCB 与证据 checkpoint 均以该 immutable manifest 为 conformance 输入。运行时发现的宿主/controller 能力低于 manifest 时必须 fail deployment 或发布新的降级 manifest，不能静默保留原保证。

`[TCB-PROFILE-001]` 未达到某一 profile/assurance 的实现 MUST NOT 使用该保证措辞。

默认适用映射：

| 条款范围 | 默认适用性 |
|---|---|
| `NLOS-*`, `PHIL-*`, `THEORY-*`, `ROAD-*` | Project Charter；约束项目方向，不是单个二进制的功能清单 |
| `DOC-*`, `PROFILE-*`, `EVID-*`, `SLICE-*` | Project Release Process；约束规范、证据和里程碑发布 |
| `MODEL-*`, `LAYER-*`, `COMPAT-*`, `TYPE-*` | 所有 advertised SurfaceProfile/contract |
| `KERN-*`, `TCB-*`, `ID-*`, `NS-*`, `CAP-*`, `PROC-*`, `KABI-*`（排除 `KABI-ESCROW-*`）, `IO-*`, `BUD-*`, `DUR-*`, `DRV-*` | `SurfaceProfile=KERNEL+`；对三个 EnforcementProfile 均适用。条款正文中的 `if ENFORCED`、`STRICT` 等是可判定前置条件，不是隐含的 applicability 例外 |
| `RSM-*` | `SurfaceProfile=KERNEL+`；对 ImplementationManifest 中 advertised 的每个 resource class 适用 |
| `LEASE-*`, `DIST-*` | `EnforcementProfile=ENFORCED_DISTRIBUTED` 或 advertised distributed feature |
| `SABI-*`, `PKG-*`, `ART-*`, `CTX-*`, `TOPIC-*`, `BB-*`, `MSG-*`, `TASK-*`, `CONS-*`, `NL-*`, `RCPT-*`, `CTRL-*` | `SurfaceProfile=APPLICATION_PLATFORM+` |
| `WD-L0-*` | `SurfaceProfile=KERNEL+` |
| `WD-SEM-*`, `WD-EMPTY-*`, `WD-CAP-*` | `SurfaceProfile=APPLICATION_PLATFORM+` 且 advertised supervision feature |
| `TUI-*` | `SurfaceProfile=APPLICATION_PLATFORM+`；可信授权/chooser UI 可以由本地或远程可信客户端呈现 |
| `DUI-*` | `SurfaceProfile=DESKTOP` |
| `KABI-ESCROW-*` | `SurfaceProfile=KERNEL+` 且 advertised `RESOURCE_ESCROW` feature |
| `RESCROW-*` | `SurfaceProfile=KERNEL+` 且 advertised `RESOURCE_ESCROW` feature |
| `SEM-*`, `SPEC-*`, `ESC-*` | `SurfaceProfile=APPLICATION_PLATFORM+` 且 advertised `SEMANTIC_SETTLEMENT` feature；该 feature MUST 声明依赖 `RESOURCE_ESCROW` |
| `PERF-*` | 每个 advertised KABI/SABI/Driver operation，按其 workload class 适用 |

以上各行定义互斥闭集；通用 `KABI-*` 行显式减去 `KABI-ESCROW-*`。`KERNEL+ = {KERNEL, APPLICATION_PLATFORM, DESKTOP}`，`APPLICATION_PLATFORM+ = {APPLICATION_PLATFORM, DESKTOP}`；`distributed feature`、`supervision feature`、`RESOURCE_ESCROW`、`SEMANTIC_SETTLEMENT` 和 advertised operation 都必须来自同一版本化 FeatureRegistry，不能由文档解释器猜测。

```text
applicability(requirement_id, implementation_manifest):
  1. 精确匹配 requirement-level override registry；没有则继续
  2. 匹配上表唯一的互斥 prefix set
  3. 将 SurfaceProfile、EnforcementProfile、FeatureRegistry
     和 OperationRegistry 代入该行的布尔表达式
  4. 未匹配、多匹配、未知枚举或未知 feature => LINT_FAILURE
```

v0.5 的 requirement-level override registry 是空集。任何后续例外 MUST 以
`RequirementId -> ApplicabilityExpression` 的显式记录加入 registry；不得用“基础规则”
“适当安全条款”或其他自然语言集合充当可执行映射。

`[PROFILE-MAP-001]` 每条 requirement MUST 由上述闭集算法得到唯一 applicability；条款正文中的条件分支只决定适用条款内的预期行为，不改变 requirement 本身是否适用。

`[PROFILE-LINT-001]` 任一 requirement ID 若未映射、多重映射、映射到不可求值的 applicability expression，依赖未声明 feature/operation，或实现 manifest 缺少四个正交维度，MUST 视为规范 lint failure 并阻止 `AssuranceLevel=CONFORMANT`。CI 必须对每个 ID 输出 `APPLIES` 或 `DOES_NOT_APPLY` 及命中的规则；不得调用自然语言分类器。

`[PROFILE-LOCAL-001]` `LOCAL_SINGLE_NODE + APPLICATION_PLATFORM` MUST 能在离线状态运行 Identity、Application、Artifact、Task、Settings、Search、Keychain 和本地 Process；远程模型/服务不可用时必须显式降级，同步不得成为本地数据存在的前提。

## 7. Principal、Namespace 与 Capability

### 7.1 身份来源

`[ID-AUTH-001]` Principal、ControlDomain、Process、Driver 和 Verifier 身份 MUST 来自认证会话、受信启动、capability 或 attestation，MUST NOT 接受调用者提交的自由字符串作为事实。

`[ID-KEY-001]` 签名 key MUST 绑定 Principal、用途、有效期、generation 和撤销状态。

`[ID-DOMAIN-001]` ControlDomainId MUST 表达共同控制关系，用于阻止同一控制者通过多 key、多进程或多事件伪造独立 quorum。

`[ID-DOMAIN-002]` ControlDomain 必须由 Identity authority 在版本化 identity snapshot 中创建和维护；merge/split/revoke MUST 产生新 snapshot 与 effective time，历史 View 必须引用当时 snapshot，不能用当前关系静默重写历史 quorum。

### 7.2 发现与授权分离

`[NS-DISC-001]` 全局资源发现目录与 Process 已授权 Namespace MUST 分离。

`[NS-NAME-001]` 对某 Process 不可命名的对象 MUST 在该 Namespace 中不可寻址和不可行动；这不意味着可信系统 UI 或授权服务也不可发现它。

`[NS-NOENT-001]` Namespace 外对象默认返回 `E_NOENT`，不得泄露对象是否在全局存在。

### 7.3 Capability 规则

`[CAP-UNFORGE-001]` Capability MUST 不可伪造并绑定 object、rights、scope、generation、issuer、holder 和可选 expiry。

`[CAP-ATTEN-001]` derive/delegate 只能衰减 rights、Namespace、Resource 调用上限/账户访问权、deadline 和再委托深度。Capability 不能复制 fungible credit；实际额度划拨只能由 Ledger transaction 完成。

`[CAP-REVOKE-001]` revoke MUST 通过 generation 或 revocation epoch 使旧 handle 失效；仅从目录隐藏不构成撤销。

`[CAP-DELEGATE-001]` 委托 MUST 产生不可变 Receipt，记录授权者、接收者、衰减结果、用途和期限。

`[CAP-PURPOSE-001]` 高风险 Capability SHOULD 绑定 purpose 与 Task/Intent；purpose 不能由自由文本替代可机械检查的 scope。

## 8. Process、抢占与恢复

### 8.1 Process 状态机

```text
CREATED → RUNNABLE ↔ RUNNING ↔ BLOCKED
   │          ↑          ↓
   │          └── SUSPENDED ← SUSPENDING
   │
   └→ FAILED_TO_START

任一 live state → TERMINATING → EXITED
任一 live state ─host loss→ LOST → RECOVERING → RUNNABLE | EXITED
```

`[PROC-HOST-001]` Process MUST 映射到可被宿主强制抢占的 IsolationUnit；IsolationUnit MAY 是 OS process、容器、VM、WASM task 或等价宿主实体，不要求与 Process 一一对应。

`[PROC-PREEMPT-001]` 安全性 MUST NOT 依赖 Agent 主动 yield、heartbeat 或 LLM trap。

宿主层负责 CPU、内存、FD、PID、wall deadline、网络隔离和最终强杀；NLOS 层在 syscall、stream chunk 和 metering 边界拒绝新 I/O、撤销 handle、冻结 Budget 并传播取消。

### 8.2 LaunchGrant 与原子出生

```text
ActivityContext =
  TaskActivity {
    task_group_id,
    task_id,
    task_attempt_id,
    attempt_generation,
    agent_role_id,
    agent_instance_id,          # BirthDecision 分配，runtime 注入
```

`[PROC-SPAWN-001]` ResourceAccount 划拨、ResourceGroup/host controller 绑定、Namespace 衰减、Capability 构造、Activity/可选 obligation 绑定和 Process identity 分配 MUST 在 child 进入 `RUNNABLE` 前形成一个原子 BirthDecision。DELEGATED_TASK 还必须绑定完整 TaskLaunchBinding、由系统分配的 AgentInstance identity 与其权威注册；调用者不得自报 AgentInstanceId。

`[PROC-SPAWN-002]` 普通 Application、daemon、UI、Device service 和可信维护 Process MAY 没有 IntentSpec 或 Task，但仍必须使用 ApplicationActivity/SystemActivity/SessionActivity 形成审计上下文；`launch_kind=DELEGATED_TASK` 时 activity_context MUST 是完整 TaskActivity，task_launch_binding MUST 存在且匹配 durable TaskAttemptContract/SnapshotReceipt/membership/domain/cancel/authority，obligation MUST 是不可变 IntentSpec，且 Process authority 不得跨 attempt generation 复用。

`[PROC-SPAWN-003]` 任一步失败 MUST NOT 留下半授权 child、孤立额度或不完整 obligation。

`[PROC-BIRTH-001]` 若 Ledger、Resource controller、Capability、Spec/TaskSnapshot、TaskGroup membership、IsolationDomain、CancellationScope、AgentInstance registry 和 Process identity 不在同一事务域，各域 MUST 先生成绑定同一 launch_grant_digest 的不可使用 durable prepare；只有协调者的 BirthDecision COMMIT 后才可原子激活 membership/domain/identity 并令 child RUNNABLE。超时或未知决定必须冻结并查询，不能单方面撤销；只有 durable ABORT decision 才能释放 prepare。

`[PROC-SPAWN-004]` 宿主启动只能发生在 BirthDecision durable COMMIT 后；启动失败必须产生 `FAILED_TO_START` 终态并返还未占用资源。

### 8.3 Suspend、cancel、kill

`[PROC-SUSPEND-001]` `suspend` 成功 ACK 前，系统 MUST 确认宿主执行已停止且新受保护 I/O 已封锁。

Suspend 模式：

- `DRAIN`：等待可完成操作并结算；
- `CANCEL`：取消在途操作后进入静止点；
- `FREEZE`：宿主立即冻结，只能声称 crash-consistent。

`[PROC-KILL-001]` `kill` MUST 幂等执行：封锁新 I/O、传播取消、宽限期终止、宿主强杀。

`[PROC-KILL-002]` Process 退出、超时或失联时，相关 Reservation MUST 在 reconciliation/finalize 前保持冻结。

`[PROC-CANCEL-001]` LLM/tool trap 是 cooperative safe point；长流操作 MUST 另有可取消 OperationId。

### 8.4 Checkpoint、restore、branch 与 join

`[PROC-CKPT-001]` Checkpoint 必须标记 `QUIESCENT` 或 `CRASH_CONSISTENT`，并记录不可 checkpoint 的 pinned Driver session。

`[PROC-RESTORE-001]` restore 是同一 ProcessId 的灾难恢复/接管，MUST 获得新 generation 并 fence 旧 generation、旧回调和旧 lease token。

`[PROC-RESTORE-002]` Checkpoint MUST NOT 序列化可直接复用的 Capability handle、active Reservation 或 Lease；proc_restore 只能在旧 incarnation fence barrier 完成后，通过 fresh_authority_binding 重新绑定 Namespace/Capability/Resource authority。无法 fence 时，新实例不得进入 RUNNABLE。

`[PROC-BRANCH-001]` branch/fork MUST 通过 `proc_spawn(launch_kind=BRANCH, initial_checkpoint_h=...)` 创建新 ProcessId，并单独划拨 Capability、ResourceAccount 和可选 obligation；禁止用同一 Checkpoint 的多次 restore 复制权力或额度。

`[PROC-JOIN-001]` 内核 join 语义仅等价于等待生命周期终态并返回 exit reason、output handles 和 accounting status；比较结果、投票和选 winner 属于用户态服务。

### 8.5 AgentInstance、Fiber 与异步运行时

```text
CREATED → READY ↔ RUNNING ↔ WAITING_IO | WAITING_MODEL | WAITING_TOOL
             ↑          ↓
             └──── SUSPENDED

任一非终态 → COMPLETED | FAILED | CANCELLED
```

ExecutionFiber 是 AgentInstance 内的用户态执行流；宿主线程/event loop 是承载它的物理调度资源；Activation 是一次实际获得执行权的有界 turn/quantum。三者不得混为同一个计数。

`[FIBER-MN-001]` runtime MUST 支持多个 ExecutionFiber 在有限宿主线程/event loop 上 M:N 复用；处于模型、工具、网络或定时器等待中的 Fiber 不得独占一个宿主线程。runtime 必须公开 runnable、waiting、active host thread 和 queue latency 的分离计量。

`[FIBER-AWAIT-001]` 每次外部 await MUST 关联稳定 OperationId。完成事件必须验证 Fiber/AgentInstance/Process generation、OperationId、cancel epoch 与 deadline 后才能令 Fiber 回到 READY；迟到或重复 callback 必须幂等丢弃或进入 reconcile，不能复活旧执行。

`[FIBER-CANCEL-001]` Fiber MUST 属于 TaskGroup/CancellationScope 的结构化并发树。父 scope 结束前必须 join、cancel 或显式 detach 全部 child；detached Fiber 必须转移到新的 owner、ResourceGroup、deadline 和 supervisor，不得成为无主后台工作。

`[FIBER-PREEMPT-001]` cooperative yield/await MAY 用于低开销公平调度，但安全和资源上界 MUST 由宿主抢占、Process freeze/kill、I/O reference monitor 和 Resource controller 保证。未主动 yield 的代码不得无限绕过 CPU quota、cancel 或 deadline。

`[FIBER-FAIL-001]` Fiber failure 的默认传播策略 MUST 由 TaskGroup supervisor policy 声明；由于 Fiber 共享 Process 故障域，内存破坏、runtime panic 或宿主线程致命错误 MAY 终止整个 Process。系统不得把 Fiber 级错误处理宣传为 Process 级隔离。

`[FIBER-METER-001]` Activation 计量 MUST 至少区分 active CPU、scheduler wait、model wait、tool/I/O wait、blocked-on-backpressure 与 suspended time，并归集到 Fiber → AgentInstance → Process → TaskAttempt/TaskGroup → Application/Workspace 的层级 ResourceGroup。等待时间可影响 deadline/SLO，但不得冒充 CPU consumption。

## 9. 兼容契约

v0.5 区分三类契约：

1. **KABI**：微内核、可信系统服务和受控 Driver 之间的对象能力 ABI；
2. **SABI**：第三方 Application 使用的稳定系统服务 API；
3. **Package/Driver ABI**：安装、加载、协商、更新和生态契约。

`[COMPAT-VER-001]` 每个 envelope/schema MUST 包含 schema name、major、minor 和扩展规则。固定布局 ABI 还 MUST 包含 struct_size 与 flags；自描述 CBOR schema MUST 区分 critical 与 non-critical extensions。

`[COMPAT-VER-002]` 未知 major MUST 返回版本错误；未知 critical field/flag MUST 拒绝；未知 non-critical 扩展 MAY 忽略但 MUST 保留 round-trip 语义。

`[COMPAT-DEPRECATE-001]` 稳定契约 MUST 定义弃用期、能力协商、迁移路径和 conformance vectors。

`[BUD-INT-001]` 权威账本中的离散资源 MUST 使用整数最小单位；浮点数 MUST NOT 进入权威状态。

`[BUD-ALG-001]` 每个 resource dimension MUST 在 unit registry 中声明单位、类型、可转移性、比较/加法规则、reserve/finalize 语义和 overflow 行为。守恒等式只适用于 fungible amount；capacity、cumulative meter 和 rate policy 必须分别验证容量、单调计量和窗口不变量。

### 10.0 现代系统方法与 NLOS 资源平面

NLOS 的资源管理目标不是发明一个万能 credit，而是继承现代 OS 的成熟控制回路，并增加 Agent/模型/外部服务特有资源。宿主内核负责最底层物理强制；NLOS Resource Manager 负责跨 Process、Application、Task 与 Cell 的统一政策和可审计契约。

| 资源域 | 现代系统常用管理方法 | NLOS 预计方法 | 主要强制层 |
|---|---|---|---|
| CPU / 执行时间 | 抢占式调度、时间片、优先级、fair-share、deadline、affinity、CPU quota | IsolationUnit 映射宿主调度实体；按 Principal/Application/TaskGroup 分层权重、quota、deadline 与 scheduling class；LLM provider wait 与 pure-code CPU run 进入同一核算体系但分维计量 | 宿主 scheduler + NLOS admission/accounting |
| 内存 | 虚拟内存、地址空间保护、working set、memory cgroup、pressure、swap、OOM | 每 Process/TaskAttempt 的 CapacityDemand + ResourceAllocation；Context/KV cache 单独计量；pressure event、分级 reclaim、checkpoint/evict，最后才按可审计策略 OOM kill | 宿主 VM/cgroup + NLOS reclaim policy |

| 消息 / fanout | socket buffer、队列容量、backpressure、traffic shaping | Channel/Topic queue、retention、fanout 上界和 payer 预留；慢消费者隔离，禁止无人承担的无限广播 | Channel + Topic service |
| 并发 / 速率 | semaphore、token bucket、quota、admission control | concurrency slot 属于 capacity lease；request/message rate 属于窗口 policy；不得与 fungible credit 混算 | Resource Manager + endpoint |
| 人类注意力 | notification priority、focus mode、rate limit | ConsentPrompt/Notification 的不可交易 attention rate policy、合并/节流/quiet hours、可信高风险通道；不可由 Agent 自行扩额 | Trusted UI + user policy |

`[RSM-SEPARATE-001]` ResourceGroup、ResourceAccount、ResourceContract 与 ResourceAllocation/Reservation/Lease/Meter MUST 是不同对象：ResourceGroup 不转移 credit，ResourceAccount 不充当 scheduler queue，ResourceContract 不证明已经分配，meter observation 不自动成为账本扣款。

`[RSM-ALG-001]` Resource Manager MUST 按资源真实代数选择控制器：fungible amount 用守恒账本，capacity 用 grant/lease，cumulative work 用单调 meter，rate 用窗口/token bucket，独占 Device 用排他/分片 lease。不同类别不得只因 UI 都显示“预算”而互换。

`[RSM-TYPE-001]` 每个 dimension MUST 选择上面的 ResourceDemand tagged variant；requested/effective demand 必须保持可验证的同类或走显式、已授权 fallback。同一物理资源 MAY 同时有多个正交维度，例如 CPU parallelism、cpu_ns 与 quota/period；unit、window、burst、reclaimability、durability、partition 与 exclusivity 不得被通用 minimum/desired/maximum 抹去。

`[RSM-HIER-001]` ResourceGroup MUST 形成 `system → tenant/user → Application → TaskGroup/TaskAttempt → Process/Operation` 的 scheduler/capacity 层级；ResourceAccount MAY 形成独立的 payer/ledger 层级。二者必须以 typed binding 关联而不能合并；子级硬上限不得超过祖先 grant，统计聚合不得把同一 usage 在父子层重复扣除。

`[RSM-HIER-002]` 每个 parent/controller/dimension MUST 在同一权威 capacity transaction 中保持：`sum(child PREPARED + ACTIVE strict guarantees) + parent_local_committed + system_reserve <= parent_effective_allocatable_capacity`。RateDemand 必须分别约束 sustained/window/burst，ExclusiveDemand 的同一 device/partition epoch 至多有一个 PREPARED 或 ACTIVE holder；weight 与可超售 BEST_EFFORT share 不进入 strict 加法，但仍受祖先 hard cap、pressure 与 reclaim policy 约束。

`[RSM-GROUP-001]` 每个 Process 在每个 advertised hard controller 的层级树中 MUST 恰好属于一个 leaf ResourceGroup。迁组必须原子更新宿主 enforcement binding、ResourceGroup generation 和 accounting high-water；旧 group 的 handle/usage callback 必须 fence，禁止通过反复迁组逃逸限制。

`[RSM-ADMIT-001]` spawn、Driver invoke、Context pin、Topic fanout，以及每次增加 durable physical usage 的 Artifact/metadata/index commit MUST 在不可逆工作开始前完成对应 admission/reserve/grant；小写入必须由已预留的有界 write window 覆盖，不能靠拆小绕过 storage admission。系统 MAY overcommit 可回收或 best-effort 容量，但 MUST 声明策略，且不得对 overcommitted 资源承诺 strict availability。

`[RSM-ADMIT-002]` 同一工作需要 CPU、memory、accelerator、Context pin、concurrency slot、storage、fungible Reservation 或 Lease 时，MUST 先构造带唯一 PlanId/digest/control epoch、完整 participant proposal root 的版本化 AdmissionPlan。participant 使用严格 tagged ALLOCATION/RESERVATION/LEASE proposal 与 PreparedParticipantReceipt，不能让 Ledger Reservation 冒充 ResourceAllocation。单事务域内全部资源原子 COMMIT；跨 authority 时唯一 Admission authority 只有在完整 proposal set 全部 PREPARED 后才能以 CAS 写 COMMIT，否则写覆盖完整 proposal root 的 ABORT。Process 进入 RUNNABLE 或 Operation dispatch 前，必须收齐 COMMIT 所列全部 participant 的 ACTIVE receipt。

`[RSM-ADMIT-003]` PREPARED participant MUST 计入对应 account/capacity/lease committed state且不得供其他 plan 使用；它只能消费 plan digest、complete participant root 和 admission epoch 精确匹配的 durable AdmissionDecision 转为 ACTIVE/ABORTED/FENCED。本地 timeout、coordinator 断线或“未查到决定”只能进入 RECONCILING 并继续冻结，禁止单方面释放；每个 authority MUST 提供 `admission_get(PlanId, DecisionId?)`，重复决定返回原结果。

`[RSM-ADMIT-004]` coordinator/participant 恢复 MUST 从 AdmissionRecord、PreparedParticipantReceipt 和 decision log 重放：COMMIT 后即使 ACK 丢失也按当前 admission epoch 幂等激活；ABORT 后幂等释放；UNKNOWN 保持冻结。若 COMMIT participant 永久无法激活，dispatch barrier 不得打开；Admission authority 必须以更高 epoch CAS 写覆盖完整 participant root 的不可逆 COMPENSATE_FENCE decision。全部 participant（包括离线 PREPARED 和曾 ACTIVE 者）恢复或执行任何 endpoint action前都必须查询最新 epoch、拒绝旧 COMMIT、fence/cleanup；只有逐项取得 fence/cleanup/reconcile Receipt 的资源才可释放，未响应者保持 QUARANTINED。不得把失败 COMMIT 改写为 ABORT，也不得在没有全体 fence proof 时重用容量。

`[RSM-ADMIT-005]` AdmissionDecision 提交时 MUST 原子关闭 plan_fence_epoch。关闭后到达的 prepare 请求不得新建孤儿 PREPARED：participant authority 必须返回相同 ABORT/COMPENSATE tombstone；若跨域竞态已先 durable prepare，则该 receipt 仍由覆盖 complete proposal root 的终态 decision 自动吸收并立即 ABORT/FENCE。COMMIT 的 prepared receipt set 必须与完整 proposal set 一一对应；ABORT/COMPENSATE 绑定完整 proposal root而不只绑定当时已返回的 receipts。部分准入只允许选择 AdmissionPlan 中预授权的完整 fallback plan，并在改变结果语义、成本或 deadline 时重新授权。

`[RSM-SCHED-001]` Resource Manager MUST 支持上述 scheduling class、层级权重、硬 quota 与 deadline；SYSTEM_CRITICAL 必须有独立保留量。只有 ResourceContract 写明可测 latency_slo、容量前提与 achieved guarantee 时，INTERACTIVE 才能声称有界延迟；DEADLINE 必须带 miss policy。BATCH/BACKGROUND 必须给出 starvation bound，或显式降为 BEST_EFFORT。语义重要性只能提出 priority proposal，最终优先级必须由授权 policy 裁决。

`[RSM-AUTH-001]` ResourceContract MUST 分离 requested 与 effective scheduling class/priority，并绑定裁决 authority、policy digest、generation 和 validity。不可信 Agent/Application 不得自行获得 SYSTEM_CRITICAL、实时优先级、不可回收 capacity 或系统救援保留量。

`[RSM-CONTROLLER-001]` 每个 advertised controller MUST 在签名 ResourceControllerManifest 中逐项声明 unit/type、宿主 enforcement mapping、支持的 prepare/commit/abort/attach/update/freeze/throttle/reclaim/fence/cleanup/meter/query/recover 操作、generation、fail-closed 行为与证据；缺少某项能力时该项不得被 OperationRegistry 广告，不能由通用 mock 或 meter 推断支持。

`[RSM-CONTROLLER-002]` attach/update/migrate MUST 通过 ControllerBinding 的 generation/epoch CAS，并返回可恢复 Receipt。controller/host restart 后，在重放 binding、验证宿主真实状态、恢复 meter high-water 与 fence 旧 boot generation 前不得重新 admission；无法确认强制状态的 binding 进入 QUARANTINED，其容量不得重发。

`[RSM-ENFORCE-001]` 每个 hard limit MUST 在 ImplementationManifest 中列出不可绕过 enforcement point、宿主映射和失败行为。只有 meter/告警/Agent 自律而没有强制点时，该 dimension 最多声明 `OBSERVED`，不得声称 hard quota、strict isolation 或 strict availability。

`[RSM-PRESSURE-001]` CPU saturation、memory/storage pressure、queue backlog、accelerator contention、network congestion、energy/thermal throttling 和 provider rate limit MUST 产生 typed PressureEvent，至少包含 scope、resource、severity、high-water、可重放时间和建议动作；不得只向 Agent 注入一段自然语言警告。

`[RSM-PRESSURE-002]` PressureEvent MUST 绑定 controller、ResourceGroupId/generation、dimension、severity、monotonic seq、observed high-water、threshold policy digest 与 MonotonicDeadline/observation time。通知本身不是正确性边界；CRITICAL pressure 必须允许 reference monitor 直接 throttle、reclaim、freeze 或 fence。

`[RSM-RECLAIM-001]` 回收顺序 MUST 由版本化 policy 决定，默认先回收可重建 cache/embedding/Context，再降级后台 QoS，再 checkpoint/suspend，最后才 kill。Artifact 本体、未结算 Operation、active Escrow/Reservation 和系统保留量不得被普通 reclaim 当作缓存删除。

`[RSM-RECLAIM-002]` 每个 allocation MUST 标记 `RECLAIMABLE | CHECKPOINTABLE | PINNED | NON_RECLAIMABLE | SYSTEM_RESERVED` 并使用完整 ReclaimRequest、acknowledgement/force deadline、controller/domain generation；PINNED_TEMPORARY 必须说明原因和最晚重试时间，但不是终态。强制动作必须产生数据/副作用风险 Receipt；QUARANTINED 容量在 holder 停止、内容清理与 fence/reconcile 前不得重新发放。回收不得修改冻结 Context 的逻辑内容、删除 Artifact 或释放 active Reservation/Escrow。

`[RSM-RECLAIM-003]` 无 ACK、PINNED 超期或 CRITICAL pressure 超过 force deadline 时，reference monitor MUST 按预授权 policy 进入 FORCE_PENDING，封锁新 dispatch，随后执行 Process/Device/Controller fence、kill/reset/evict 与 CLEANING。只有同时取得 holder fenced/terminated proof、controller cleanup/zeroization Receipt 和 capacity high-water reconcile 后才能进入 RELEASED；任一证明缺失进入 QUARANTINED，不能因“已发 kill”立即重复分配。

`[RSM-CAPACITY-001]` REVOCABLE/DURABLE/EXCLUSIVE allocation MUST 使用 ResourceAllocationState。expiry 只禁止续用和新准入；holder 尚未停止、设备/内存尚未清理或 fence barrier 未完成时，物理容量不得再次授予。DURABLE_CAPACITY 不得因普通 pressure 被静默回收。

`[RSM-OOM-001]` 内存或容量耗尽时 MUST 保留 reference monitor、Ledger、Identity、storage recovery 和 Trusted UI 的救援资源；OOM victim 选择必须绑定 ResourceContract、优先级、可恢复性和已发生副作用，产生 Receipt，并避免选择持有无法 fence 的 active effect 的 Process。

`[RSM-RESERVE-001]` Ledger/WAL、Identity/key state、Resource metadata、crash recovery、audit checkpoint 与 Trusted UI MUST 具有普通 Application 不可消费的 memory/storage/FD/system-reserved pool；ENOSPC/OOM 时首先停止新 admission，不能因清理普通任务而删除权威恢复记录。

`[RSM-FAIR-001]` 调度器 MUST 定义 starvation bound 或明确 BEST_EFFORT；共享锁/Device/accelerator queue MUST 有 priority inheritance、priority ceiling 或等价反转控制。多资源原子请求必须使用全序 acquisition、事务 reservation 或 timeout/rollback，防止 Agent 以循环等待占死系统。

`[RSM-FAIR-002]` 每个 scheduler MUST 声明 weight、floor、cap、burst、admission class 与可测 starvation bound。Priority donation/inheritance 必须有界且只能影响调度，MUST NOT 扩张 Capability、ResourceAccount credit 或 hard quota；非抢占 Device 的优先级反转必须在 admission 阶段用 reservation/gang scheduling 避免。

`[RSM-METER-001]` usage accounting、scheduler metric 与 billable ledger MUST 分层：观测计数可近似，权威扣账必须 durable、幂等并绑定 Operation；采样指标不得直接铸造/销毁 credit 或升级 GuaranteeTier。

`[RSM-METER-002]` CPU run/runnable/blocked/queue/provider-wait、memory committed/resident/pinned/cache/swap、GPU active/queue/VRAM、I/O bytes/ops/queue-wait、network ingress/egress/payload/overhead、storage logical/physical/snapshot/index/temp、energy_mJ/power_mW/thermal-throttle time 与 model billed/visible token MUST 分维报告；blocked wall/provider wait 不得计作 cpu_ns。共享 cache、batch、Topic fanout 或复用连接的成本 MUST 使用版本化 AttributionPolicy，且“各归属项 + 未分配系统开销”精确等于可信总 meter，不得在共享者间重复全额扣除。

`[RSM-HUMAN-001]` 人类注意力、隐私风险和授权疲劳默认不是 fungible commodity。系统 MAY 设 notification/consent rate policy 和 quiet hours，但 Agent 不得通过支付普通 credit 绕过用户拒绝、静默模式或 Trusted UI 高风险确认。

`[RSM-ENERGY-001]` thermal/battery safety MAY 抢占任务，但由此触发的模型降级、provider 切换、精度下降或 deadline 放宽必须属于已授权 fallback；否则 Task 进入 WAITING_RESOURCE/FAILED，不得静默改变结果语义。

`[RSM-ATTN-002]` Notification 与 authorization Consent MUST 使用不同队列和失败语义：普通通知 MAY 合并、节流或按 policy 丢弃；安全授权提示不得因 rate limit 自动同意，无法可信展示时 Action 必须等待或 fail-closed。Agent 自报“紧急”只能是提议。

`[RSM-DIST-001]` 跨 Cell 调度 MUST 先考虑 capability/data/accelerator locality，再以预付 QuotaLease 分配可消费额度；分区时不得凭中央旧快照超卖。全局 scheduler 的建议不替代节点本地 admission、boot generation 和 fencing 校验。

`[RSM-DIST-002]` 可转移 fungible credit 使用 QuotaLease；memory、GPU slice、concurrency slot 等可分容量使用 CapacityLease；排他设备使用 ExclusiveDeviceLease。三者 MUST 使用不同 state/reconciliation。Capacity/Device lease MUST 绑定 resource identity、amount、placement、holder ResourceGroup、source workload/boot generation、expiry 和 reclaim/fence protocol；source workload 与全部 enforcement endpoints 未 fence 前不得在 target 重发，且不得把“尚有钱”解释为某节点仍有物理容量。

`[RSM-FANOUT-001]` Topic publish MUST 在首次入队前绑定 max recipients、delivery attempts、cascade depth、retained bytes/time、payer 和 idempotency scope；每级再发布消耗父级 cascade budget，慢消费者必须隔离，Topic 环不得形成无限成本。

`[RSM-RECEIPT-001]` grant、reservation、quota denial、reclaim、preempt、OOM、lease move 和 final reconciliation MUST 产生可关联 TaskAttempt/Process/Operation 的 typed Receipt；用户和系统服务必须能解释“谁获得/失去何种资源、依据哪项 policy、是否可重试”。

### 10.1 权威位置与守恒

每个 fungible unit 在任一时刻必须且只能位于：

```text
AVAILABLE(account)
RESERVATION(reservation_id, limit, consumed)
RISK_RESERVATION(reservation_id, loss_bound)
ESCROW(escrow_id)
LEASE(lease_id)
SPENT(sink)
QUARANTINED(reason)
```

封闭预算域：

```text
MINTED + INBOUND
= AVAILABLE
+ RESERVATION.limit
+ RISK_RESERVATION.loss_bound
+ ESCROW
+ LEASE
+ SPENT
+ QUARANTINED
+ OUTBOUND
```

`[BUD-CONS-001]` 实现 MUST NOT 通过余额截零、事后负账或父子账户重复计数伪造守恒。

`[BUD-CONS-002]` Process/Application 的 ResourceAccount MUST NOT 为负。超过用户 Reservation 的真实成本必须优先由预留的 operator RiskAccount 支付；仍未覆盖的部分记录为域外 `EXTERNAL_DEBT` liability 并隔离 Driver，MUST NOT 伪造为新 credit 或追加到用户负余额。


状态机：

```text
NEW → RESERVED → ACTIVE → CLOSING → FINALIZED
        │          │         │
        └──────────┴─────────┴→ UNCERTAIN
                                  ↓
                           FINALIZED | QUARANTINED
```

`[BUD-QUOTE-001]` Driver `quote` MUST 返回上述签名 Quote；Reservation 和 invoke MUST 绑定同一 quote_id、operation proposal digest、PricingVersion 与有效期，禁止 reserve 后替换 SKU/model/effect。

`[BUD-RES-001]` `reserve(account, quote, upper_bound, preallocated_operation_id)` MUST 线性化执行 `AVAILABLE -= upper_bound` 并创建等额 Reservation；BOUNDED_RISK 还必须同时从 operator RiskAccount reserve `max_external_loss`。

`[BUD-RES-002]` durable reserve 成功之前，Driver MUST NOT 发起 provider/tool 调用或任何受保护副作用。

`[BUD-RES-003]` 并发调用 MUST 在权威事务层串行化，禁止“读余额 → 外部调用 → 事后扣账”。

`[BUD-BIND-001]` 一个 Reservation MUST 只绑定一个 CallId、OperationId、DeviceId、DriverId 和 QuoteId。`RESERVED → ACTIVE` 必须由 `io_submit`/reference monitor 使用一次性 CAS durable 激活；激活提交前不得 dispatch，重复激活只能返回同一 Operation。

`[BUD-ATTEMPT-001]` provider retry 必须传播同一 provider idempotency key；无法安全复用时，每个 attempt 必须有独立 Reservation。多个 Operation 不得共享 Reservation handle。

`[BUD-CONSUME-001]` `consume(reservation, seq, cumulative_usage)` MUST 使用单调序号和累计用量；重复相同报告幂等，相同 seq 对应不同内容必须视为 Driver 故障。

`[BUD-CONSUME-002]` `STRICT` MUST 满足 `reported_actual <= user_limit`。BOUNDED_RISK/OBSERVED MAY 观察到超限或 UNKNOWN_USAGE；账本仍必须 ingest 该报告，但 `chargeable_to_user` 永远不超过 user_limit。

结算量：

```text
observed_actual    = price(reported_usage) | UNKNOWN_USAGE
covered_by_user    = min(observed_actual, user_limit)
user_refund        = user_limit - covered_by_user
excess             = max(0, observed_actual - user_limit)
covered_by_risk    = min(excess, risk_reservation)
external_debt      = excess - covered_by_risk
```

若 observed_actual 为 UNKNOWN_USAGE，user Reservation 与 RiskReservation 必须保持冻结，直至权威回报、按全部上界保守结算或进入 QUARANTINED；不得用未知值计算退款。

`[BUD-FINAL-001]` finalize MUST 以双重记账 legs 保持来源：`AVAILABLE(user_account) += user_refund`、`AVAILABLE(operator_risk_account) += unused_risk`、`SPENT(user_leg) += covered_by_user`、`SPENT(risk_leg) += covered_by_risk`，并记录可选 EXTERNAL_DEBT liability。用户和风险退款不得合并到同一未知账户；一个 Reservation 只能有一个最终状态。

`[BUD-CLOSE-001]` `ACTIVE → CLOSING → FINALIZED` MUST 消费 endpoint/enforcement gateway 签名的 `effect_closed + final_usage + final_seq` Receipt，并同时满足 `final_seq >= high_water.seq`、`final_usage >= high_water.usage`（逐维）和 `price(final_usage) >= price(high_water.usage)`。向下修正只能走 Correction/Rebate；无法证明 effect 已关闭时只能按上界保守结算或进入 QUARANTINED。

`[BUD-LATE-001]` finalize 后所有迟到 consume/callback MUST 被识别并拒绝改变已提交账本；若迟到权威 Receipt 证明少收，只能走受限 rebate。

`[BUD-CANCEL-001]` 客户端断流、超时、取消和 Process 退出 MUST 先停止或隔离外部执行，再按已发生用量 finalize；不得直接全额退款。

`[BUD-UNCERTAIN-001]` provider 状态不明时 MUST 进入 `UNCERTAIN` 并冻结全部 Reservation；仅凭超时 MUST NOT 退款。

`[BUD-RECON-001]` 无权威最终回报时 MAY 按 user + risk Reservation 全额保守结算；后续只能用独立 rebate 返还，MUST NOT 再向用户追加超过 Reservation 的扣款。

本规范 v0.5 中所有公式里的 `H(x)` 都固定表示 `SHA-256(x)`；`||` 表示无歧义的
长度前缀字节连接，结构值使用 deterministic CBOR。后续版本若更换算法，必须更换
domain tag/schema major version，不能把其他算法产生的字节标记成 `SHA256`。

```text
RebateId =
  H(
    "llmos/rebate/v1"
    || deterministic_cbor([
         reservation_id,
         authoritative_receipt_id,
         receipt_version
       ])
  )
```

`[BUD-REBATE-001]` Reconciliation Receipt version MUST 形成单调 supersession chain，但 PROVISIONAL version 只能更新 projected rebate，不能移动资金。只有唯一 `FINAL/NON_SUPERSEDEABLE` 权威 Receipt 可触发 rebate；账本据此计算 `target_total_rebate = max(0, original_settled_amount - final_authoritative_actual)` 与 `delta = target_total_rebate - already_rebated`，并要求 `delta >= 0`。

`[BUD-REBATE-002]` Rebate MUST 以 RebateId 去重并按 Reservation CAS，逐笔反向冲销原始 user/risk debit legs；累计 rebate 不得超过对应 leg 的既有 SPENT，已消费的 FINAL Receipt/high-water 必须持久保存。所谓 FINAL 之后的向上成本修订只能进入独立 dispute/clawback/operator loss，不能静默撤回已返用户额度或追加用户扣款。

### 10.3 流式与隐藏成本

`[BUD-STREAM-001]` 流式调用 MUST 预留完整可执行上界，或采用 durable 预付窗口；下一窗口在 reserve 成功前不得下发。

`[BUD-STREAM-002]` chunk 是 usage 报告和 cooperative cancel 点，不天然是成本边界。

`[BUD-USAGE-001]` usage vector MUST 按同一 PricingVersion 报告 provider 可观察的 prompt、completion、cached、reasoning/hidden、tool、multimodal 等计价维度；无法观察的维度必须标为 `UNKNOWN_USAGE`。STRICT 必须覆盖全部实际计价维度，否则请求必须拒绝。

`[BUD-PRICE-001]` 动态价格、隐藏 token 或 Tool 副作用无法给出上界时，系统 MUST 拒绝 strict 请求，或按声明的最坏值预留。

### 10.4 外部保证档位

| GuaranteeTier | 可承诺内容 |
|---|---|
| OBSERVED | 只保证 NLOS 内部观察与核算，不保证外部支出上界 |
| BOUNDED_RISK | 通过预付账户、短期 credential 或 gateway 给出最大运营损失 |
| STRICT | 所有计价维度均有调用前上界，且 endpoint 可物理强制 |

`[BUD-TIER-001]` 请求 `STRICT` 时 MUST NOT 静默降级。

`[BUD-TIER-002]` 只有 `STRICT` 可声称 `external_cost <= reservation`；`BOUNDED_RISK` 只能声称 `external_loss <= declared_bound`。

`[BUD-TIER-003]` Driver 自报 usage 本身不构成严格保证；在 ENFORCED profile 中，enforcement shim MUST 与不可信 provider adapter 分离。

```text
          durable_notice_at, signature}))

ResourceCommandIntentDigest =
  H("llmos/resource-escrow-command-intent/v1"
    || deterministic_cbor(ResourceCommandIntent))

ExpireRequestId =
  SignedObjectId(
    "llmos/resource-escrow-expire-intent/v1",
    ResourceEscrowExpireIntent minus
      {expire_request_id, requester_signature})

CommandBodyDigest =
  H("llmos/resource-escrow-command-body/v1"
    || deterministic_cbor(ResourceEscrowCommandBody))

CommandId =
  H("llmos/resource-escrow-command/v1"
    || deterministic_cbor([
         CommandBodyDigest,
         canonical_authorization_bundle
       ]))

ResourceEscrowRecordDigest =
  H("llmos/resource-escrow-record/v1"
    || deterministic_cbor(ResourceEscrowRecord))

SettlementAttemptHistoryRoot =
  H("llmos/resource-escrow-attempt-history/v1"
    || deterministic_cbor(
         settlement_attempt_history sorted by attempt_seq))
```

其中 unsigned body 是移除本对象自身 id 与全部 signature 字段后的完整 schema；type tag 的
ASCII bytes 逐字固定为：

- `llmos/resource-escrow-open/v1`
- `llmos/resource-escrow-decision-core/v1`
- `llmos/resource-escrow-challenge-notice/v1`
- `llmos/resource-escrow-dispute-open/v1`
- `llmos/resource-escrow-adjudication/v1`
- `llmos/resource-escrow-bilateral-settlement/v1`
- `llmos/resource-escrow-expire-intent/v1`
- `llmos/resource-escrow-transition/v1`
- `llmos/resource-escrow-command-rejection/v1`
- `llmos/resource-escrow-state/v1`
- `llmos/resource-escrow-ledger-time-proof/v1`

`LedgerTimeProof.proof_id` 也按该规则计算，且其 purpose/subject/escrow/generation/
nonce/commit domain/log index 均位于 signed unsigned body 内。authorization bundle 的每个
签名覆盖同一个 CommandBodyDigest；CommandId 再绑定 canonical bundle。

`[RESCROW-CANON-001]` v1 的 `H` MUST 固定为 SHA-256；TimePolicyDigest、receipt/proof/decision ID、ExpireRequestId、NoticePreimageDigest、ResourceCommandIntentDigest、CommandBodyDigest、CommandId、ResourceEscrowRecordDigest 与 SettlementAttemptHistoryRoot MUST 由上述 domain-separated deterministic CBOR 规则生成。TimePolicy digest 不得包含自身字段；`command_intent_digest` 必须由 body 内完整 intent 重算一致。receipt/proof/decision/expire intent 签名覆盖自身 ID，authorization 签名覆盖完整 CommandBodyDigest。basis_refs 必须按 `(role_ordinal, type_tag bytes, object_id bytes)` canonical sort；role_ordinal 必须逐位等于 EscrowBasisRole registry 中固定的 `10..90` 映射，每个角色至多出现一次，并使用 `SignedObjectRef{basis_role, role_ordinal, type_tag, object_id}` 同时匹配该角色唯一合法 schema/type tag 与 ID。禁止自定义 ordinal、跨类型/跨角色重放、算法冒充、遗漏字段签名或只签部分 projection；实现 MUST 为下列矩阵每个合法行以及错误 role/type/ordinal/顺序提供 canonical golden vectors。

`[RESCROW-ID-001]` 调用者 MUST 使用 CSPRNG 生成 `open_nonce_128` 并在 hold 前预计算 EscrowId；v0.5 初始 hold_generation 固定为 1。Ledger MUST 对 EscrowId 执行 create-if-absent CAS：同一 EscrowId + open IdempotencyKey + 字节相同 receipt 返回原结果；任何字段不同返回 `E_CONFLICT`。终态 EscrowId 永不复用；修改合同必须使用新 nonce、新 EscrowId 和 generation 1。

`[RESCROW-OPEN-001]` `resource_escrow_open` MUST 验证传入 ID 等于 Receipt 中 ID，使用 Receipt 内 nonce/request 重算相同、generation 为 1、KabiHeader.request_id 等于 open_request_id、payer/payee handles 与 projection 相同、payer authorization 绑定完整 SettlementContractDigest/projection、签名与 capability 有效，并原子执行 `AVAILABLE(payer) -= amount; ESCROW(id) += amount; state=HELD; state_seq=1`。成功返回的 ID/generation 只是确认值，不是首次分配。

`[RESCROW-DEADLINE-001]` Open MUST 验证所有 instant/expiry 受同一 immutable TimePolicy/authority epoch 解释，并以 checked arithmetic 计算：
`decision_registration_deadline = decision_deadline + declared_delivery_margin`；
非零 challenge 时 `notice_registration_deadline = decision_registration_deadline + declared_delivery_margin`，否则二者相等；
`settlement_validity_floor = notice_registration_deadline + challenge_window + declared_delivery_margin`；
并要求 `release_deadline >= settlement_validity_floor`。TimePolicy、agreement policy、timeout、全部 deadline、challenge、delivery margin、notice authority 与这些派生值固化后不得修改。

`[RESCROW-PROOF-001]` `DECISION_COMMIT` proof MUST 绑定
`{source_basis_type_tag, source_basis_digest, escrow_id, hold_generation, purpose, nonce}`，
并由 TimePolicy 接受的 commit domain 在持久提交该 source basis 的同一原子 commit 中签发；
`decision_committed_at` 必须逐位等于 proof.observed_at。`NOTICE_DURABLE` proof MUST
以同样方式绑定 `NoticePreimageDigest`，且 `durable_notice_at` 必须逐位等于
proof.observed_at。Ledger 必须重算 subject、验证 authority/epoch/domain/log index/签名，
拒绝 purpose 替换、跨 escrow/generation 使用、预取后补写、nonce 换绑、回滚和分叉。
`(authority, epoch, purpose, nonce)` 首次出现时 MUST 唯一绑定
`{subject_type_tag, subject_digest, escrow_id, hold_generation, proof_id}`；不同 subject、
receipt、attempt 或 proof bytes 复用该 tuple 一律拒绝。矩阵要求后续命令只读复验当前 record
已登记的同一 ReceiptId + 完全相同 proof bytes（例如 REGISTER_DECISION 后 RELEASE，
REGISTER_NOTICE 后 RELEASE/ABORT）不算 replay；再次登记同一 receipt 仍须拒绝，原
CommandId 的幂等回读除外。

`[RESCROW-DECISION-001]` `REGISTER_DECISION` MUST 消费 resolver-authorized ResourceDecisionCoreReceipt，验证 subject-bound decision proof 与 record 相同、`decision_committed_at <= decision_deadline`、`settlement_validity_floor <= valid_until <= release_deadline`，并使用本次 Ledger apply time 验证登记不晚于 decision_registration_deadline，再以 CAS 将 HELD 变为 DECISION_REGISTERED。该状态阻止 HELD timeout 抢先结算。

`[RESCROW-NOTICE-001]` challenge_window 非零时，`REGISTER_NOTICE` MUST 消费 notice-authorized ResourceChallengeNoticeReceipt，重算 NoticePreimageDigest，逐字段绑定已登记 DecisionCore，验证 `decision_committed_at <= durable_notice_at <= apply_at <= notice_registration_deadline`，并保存 `registered_notice_at = apply_at`、`release_not_before = apply_at + challenge_window`；还必须验证 `release_not_before + declared_delivery_margin <= registered_decision_valid_until`。成功后进入 PENDING_CHALLENGE。challenge_window 为零时 REGISTER_NOTICE 必须拒绝，不能用伪造 notice 改变 release 边界。

`[RESCROW-ABORT-001]` resolver MAY 在 RELEASE/OPEN_DISPUTE 尚未线性化时，以 `ABORT_DECISION` 将 DECISION_REGISTERED 或 PENDING_CHALLENGE CAS 回 HELD，并把 decision/notice 标记为 aborted history；这条恢复边同样适用于 notice 迟到、decision validity 不足或 release 投递失败。只有仍能在 decision deadline 前产生新 subject-bound DecisionCore 时才可重新评估；否则 HELD 在 deadline 后只能走机械 EXPIRE，旧 decision/notice 永不得复用。

`[RESCROW-HISTORY-001]` 每次 decision registration 必须分配从 1 开始、严格递增且无洞的 attempt_seq，以 status=REGISTERED 创建 active history entry；notice 后更新为 NOTICE_REGISTERED，关闭时才写 ABORTED/DISPUTED/SETTLED/TIMED_OUT 与对应 outcome，并 durable 关联 Decision/Notice/各自 Transition、Abort command/Transition。数组必须按 attempt_seq canonical 排序，最多一个 REGISTERED/NOTICE_REGISTERED active entry，且它与 record 顶层 registered fields 逐位一致；SettlementAttemptHistoryRoot 按固定公式重算。恢复不得只保留一组裸 Decision IDs；当前 registered fields 必须能由 record + transition log 唯一重建，旧 attempt 的 notice/authorization 不得跨 attempt_seq 复用。

每个命令的合法状态、basis 和授权是闭集；`apply_at` 永远取本次 Ledger 共识提交注入的
`COMMAND_APPLY` proof，而不是调用者给出的时间：

| command | 唯一合法 before → after | 必需 basis_refs | authorization | 时间条件 |
|---|---|---|---|---|
| REGISTER_DECISION | HELD → DECISION_REGISTERED | `AUTHORIZING_DECISION` | ResolverAuthorization | `apply_at <= decision_registration_deadline` |
| REGISTER_NOTICE | DECISION_REGISTERED → PENDING_CHALLENGE | `REGISTERED_DECISION` + `AUTHORIZING_NOTICE` | NoticeAuthorization | 非零 challenge 且 `apply_at <= notice_registration_deadline` |
| ABORT_DECISION | DECISION_REGISTERED → HELD | `ABORT_DECISION_HISTORY` | ResolverAuthorization | `apply_at <= release_deadline` |
| ABORT_DECISION | PENDING_CHALLENGE → HELD | `ABORT_DECISION_HISTORY` + `ABORT_NOTICE_HISTORY` | ResolverAuthorization | `apply_at <= release_deadline` |
| OPEN_DISPUTE | HELD/DECISION_REGISTERED/PENDING_CHALLENGE → DISPUTED | `AUTHORIZING_DISPUTE_OPEN` | ChallengeAuthorization | HELD 不晚于 decision registration deadline；DECISION_REGISTERED 仅非零 challenge 且不晚于 notice registration deadline；PENDING_CHALLENGE 严格 `< release_not_before` |
| RELEASE | DECISION_REGISTERED → RELEASED | `AUTHORIZING_DECISION` | ResolverAuthorization | 仅零 challenge，且 `apply_at <= min(decision.valid_until, release_deadline)` |
| RELEASE | PENDING_CHALLENGE → RELEASED | `AUTHORIZING_DECISION` + `REGISTERED_NOTICE` | ResolverAuthorization | `release_not_before <= apply_at <= min(decision.valid_until, release_deadline)` |
| RELEASE/REFUND | HELD → RELEASED/REFUNDED | `AUTHORIZING_BILATERAL` | BilateralAuthorization | `apply_at <= decision_registration_deadline`，且 agreement_policy 明确允许该 disposition |
| REFUND | DECISION_REGISTERED → REFUNDED | `AUTHORIZING_BILATERAL` + `ABORT_DECISION_HISTORY` | BilateralAuthorization | `apply_at` 不晚于当前状态的机械 timeout boundary；已有 decision 原子标记 `ABORTED_BY_AGREEMENT` |
| REFUND | PENDING_CHALLENGE → REFUNDED | `AUTHORIZING_BILATERAL` + `ABORT_DECISION_HISTORY` + `ABORT_NOTICE_HISTORY` | BilateralAuthorization | `apply_at` 不晚于当前状态的机械 timeout boundary；已有 decision/notice 原子标记 `ABORTED_BY_AGREEMENT` |
| RELEASE/REFUND | DISPUTED → RELEASED/REFUNDED | `AUTHORIZING_ADJUDICATION` | AdjudicatorAuthorization | `apply_at <= command.valid_until` |
| EXPIRE | HELD/DECISION_REGISTERED/PENDING_CHALLENGE → REFUNDED 或 DISPUTED | 空 | Ledger 在 apply 事务中生成 MechanicalTimeoutAuthorization | 严格晚于当前状态 timeout boundary；after 必须分别等于 immutable `on_timeout=REFUND/DISPUTE` |

表中角色名就是 v1 唯一合法槽位，不存在通用 `AUTHORIZING`、`REGISTERED_REFERENCE`
或 `ABORT_HISTORY` 角色。一个对象即使字节相同，也必须按该命令行要求进入精确角色：
REGISTER_NOTICE 的 Decision 是 `REGISTERED_DECISION`，PENDING_CHALLENGE RELEASE 的
Notice 是 `REGISTERED_NOTICE`，ABORT/协议退款保存的历史分别是
`ABORT_DECISION_HISTORY`/`ABORT_NOTICE_HISTORY`。调用者不能改 ordinal 或用一个通用角色
承载两个 reference。

其中 HELD 的 timeout boundary 是 decision_registration_deadline；非零 challenge 且尚未
登记 notice 的 DECISION_REGISTERED 是 notice_registration_deadline；零 challenge 的
DECISION_REGISTERED 与 PENDING_CHALLENGE 是 release_deadline。EXPIRE 必须在一个 CAS/
双重记账事务里直接执行唯一 on_timeout 后继，不创建可被外部命令竞争的 EXPIRED 中间态。

`[RESCROW-MATRIX-001]` Ledger MUST 先统一验证 `apply_at <= min(ResourceCommandIntent.valid_until, 每个 AUTHORIZING_* basis receipt.valid_until)`（该 receipt 不含 valid_until 时忽略），再完全按上表对应 command 行验证 state/time boundary：EXPIRE 使用严格 `>`，ABORT 使用其独立的 release_deadline 上界，不能套用当前状态的 timeout boundary。随后逐项验证 before/after、精确 basis role/ordinal/数量/type tag、authorization variant、immutable agreement_policy 与 on_timeout；`REGISTERED_*`/`ABORT_*_HISTORY` 只证明当前 record 对应的已登记状态历史，不用其过期时间阻止安全 ABORT，但 RELEASE 的 DecisionCore 必须位于 `AUTHORIZING_DECISION`。不得用较长 command validity 延长较短 authorizing basis validity，表外组合一律拒绝。尤其 EXPIRE 不接受 challenger 代替 Ledger，DISPUTED 终态不接受 bilateral/resolver 代替 adjudicator，bilateral settlement 不得从 DISPUTED 发起，REFUND_ONLY 不得被双方签名升级成 RELEASE。

`[RESCROW-EXPIRE-001]` 外部/semantic caller 请求 timeout 时 MUST 只持久化并提交 stable ResourceEscrowExpireIntent/ExpireRequestId，而不是伪造最终 MechanicalTimeoutAuthorization。Ledger 必须在接纳该 request 的同一 WAL/共识事务中：逐位复制 escrow/generation/settlement digest/expected state+seq，以 `requested_valid_until` 作为 EXPIRE ResourceCommandIntent.valid_until 并构造空 basis body；由 Ledger authority 签 MechanicalTimeoutAuthorization；得到最终 CommandId；生成 subject=CommandId 的 apply proof；执行矩阵 CAS；并 durable 保存 `ExpireRequestId → CommandId → TransitionReceipt|RejectionTombstone` 映射。相同 request/key 返回同一映射；requester signature 只证明请求/限流身份，不授权 timeout 或决定 after_state。

`[RESCROW-BASIS-001]` 独立 RESOURCE_ESCROW 实现 MUST 只解析五类 generic Resource receipt——ResourceDecisionCore、ResourceChallengeNotice、ResourceDisputeOpen、ResourceAdjudication 与 ResourceBilateralSettlement——的机械字段，并验证其 contract/escrow/generation/intent/disposition/validity、role capability、自身签名与最终 authorization bundle 一致。后三类的 `opaque_source_type_tag/digest` 只用于审计链接，不得被 Resource ledger 解释；Semantic Dispute/Manual Receipt 不得直接进入 generic basis_refs，而必须先无损投影为对应 Resource receipt。

`[RESCROW-BIND-001]` 每个 ResourceEscrowCommand MUST 重算并逐字段匹配 intent digest、escrow_id、generation、SettlementContractDigest、expected state/state_seq、command、矩阵指定的 typed basis refs 与 authorization bundle，再以 CAS 提交唯一新 state_seq。CommandIntentDigest 必须先于 basis receipt 构造，CommandBodyDigest 必须先于 authorization 构造；basis receipt MAY 绑定 intent digest，但 MUST NOT 反向绑定包含其自身 ReceiptId 的最终 CommandBodyDigest。

`[RESCROW-CHALLENGE-001]` PENDING_CHALLENGE 上 `OPEN_DISPUTE` 只在 `apply_at < release_not_before` 成立；`RELEASE` 从 `apply_at >= release_not_before` 开始成立，因此等号属于 RELEASE。两者由同一共识日志和 expected_state_seq 排序；窗口内 OPEN_DISPUTE 先线性化则 RELEASE CAS 失败，窗口关闭后 OPEN_DISPUTE 即使先到达也必须被拒绝，不能无限延长托管。

`[RESCROW-TIME-001]` 调用者 MUST NOT 在 ResourceEscrowCommandBody 中提供 apply time proof。Ledger 必须在接纳 CommandId 的同一个共识/WAL 事务内生成 purpose=`COMMAND_APPLY`、subject=`CommandId`、匹配 escrow/generation 的新 LedgerTimeProof，并把它写入 TransitionReceipt 或 RejectionTombstone；两类对象的 `committed_at` 必须逐位等于 proof.observed_at，durable log index 必须等于 proof.committed_log_index。OPEN 后 state_seq=1 时 record 的 last-apply fields 为空；首次成功 apply 起必须存在并逐次单调更新。各副本只使用该日志输入，不得各读 wall clock。除同一 CommandId 的幂等回读外，不得复用旧 nonce/proof。不可比 authority/epoch、clock rollback、skew 超界、加法 overflow 或 proof 分叉一律 fail-closed。

`[RESCROW-RIGHTS-001]` REGISTER_DECISION/ABORT_DECISION 需要 resolver 对完整 CommandBodyDigest 的签名；REGISTER_NOTICE 需要 notice authority；OPEN_DISPUTE 需要 challenger capability；DISPUTED→终态必须由 adjudicator 直接签名；deadline 前 bilateral refund 必须由 payer 与 payee 对同一 body 双签；MECHANICAL_TIMEOUT 只能由 Ledger authority 签发且最终 eligibility 只由本次 apply proof 判断。Semantic adapter 不得代签 adjudicator/payer/payee。

`[RESCROW-IDEM-001]` open/apply MUST 保证“唯一 durable 状态转换 + 使用原 IdempotencyKey/CommandId（EXPIRE 使用 ExpireRequestId）可重复查询”；所有终态金额迁移必须双重记账。重复、stale state_seq、authorization bundle 替换或不同 key 的同一 transition 不得重复支付。已通过认证但永久失败/过期/stale 的 CommandId/ExpireRequestId 必须形成 durable `REJECTED_FENCED` tombstone 或 request→tombstone 映射，保证它以后永不提交。

`[RESCROW-QUERY-001]` 三入口 KABI 的 `resource_escrow_get(EscrowId, EscrowOperationRef?)` MUST 在线性化读点返回当前 record/state_seq 和签名 ResourceEscrowStateReceipt；该 Receipt 的 record_digest、active registered IDs、settlement_attempt_history_root、last transition 与 state/state_seq 必须按固定 digest 公式逐位对应同一读点，使公开接口本身足以权威分类当前状态，而不依赖私有 successor 枚举。EscrowOperationRef 是严格 tagged `CommandId | ExpireRequestId`，不得与通用 OperationId 互换，后者还要返回 resolved CommandId。查询同时返回 `PENDING`、带原 TransitionReceipt 的 `COMMITTED`、带 tombstone 的 `REJECTED_FENCED` 或 `UNKNOWN`。`UNKNOWN` 只是没有稳定 operation 证据，绝不否定 ResourceEscrowStateReceipt 所证明的当前状态，也不等于 NOT_COMMITTED；查询不得要求原 Process 或原 capability handle 仍存活。

`[RESCROW-RECOVER-001]` 崩溃恢复后，HELD、DECISION_REGISTERED、PENDING_CHALLENGE、DISPUTED、终态、Command/ExpireRequest mapping/status/tombstone 及资金位置 MUST 从 durable log 原样恢复。Process/service 消失、outbox 未确认或 wall timeout 本身不得触发退款/释放。恢复者只能查询稳定 CommandId/ExpireRequestId、用原 canonical operation bytes/key 重投，或提交会以同一 expected_state_seq 赢得 CAS 并 fence 旧命令的新授权命令。`REJECTED_FENCED`、已分类后继 TransitionReceipt，或签名 ResourceEscrowStateReceipt 证明 `current.state_seq > command.expected_state_seq`/当前已终态，均能证明该旧 expected-state command 永不再提交；只有 state_seq 仍等于 expected、状态仍兼容且 operation 为 PENDING/UNKNOWN 时才必须继续 RECONCILING。

`[RESCROW-HANDLE-001]` 幂等 identity MUST 只覆盖 signed canonical open receipt/command bytes、稳定对象 ID 与原 IdempotencyKey；KABI transport envelope、slot+generation handle 和本地 handle 编码不得进入该 identity。恢复进程必须通过 stable ID 重新 `ns_lookup/resource_escrow_get` 获得 fresh handles，并验证其解析到同一 account/escrow/receipt/command，再携带原 canonical operation bytes 与 key 重投；旧 handle 不得复用。

## 11. Durable Ledger 与恢复

`[DUR-SCOPE-001]` 以下成功 ACK MUST 表示 durable commit：

- reserve/finalize/transfer；
- Reservation activation/closing barrier；
- advertised `RESOURCE_ESCROW` 的状态转换；
- lease grant/top-up/close；
- spawn 中的资源划拨。

`[DUR-ACK-001]` 单机 ACK 前 MUST 写入完整 WAL 记录、checksum 并完成 `fdatasync/fsync` 或等价 durable barrier；语言级 `flush()` 不构成 durable commit。

`[DUR-ACK-002]` 复制账本 ACK 前 MUST 获得 consensus quorum commit。

`[DUR-GROUP-001]` MAY 使用 group commit，但调用者只能在覆盖其 LSN 的 durable barrier 完成后收到成功。

WAL 至少包含：

```text
record_magic, format_version, record_type, length, lsn,
txn_id, idempotency_key, BEGIN/PREPARE/COMMIT framing,
mutation_payload, object/account ids,
before_digest, after_digest, txn_checksum, record_crc
```

`[DUR-TXN-001]` 跨账户转移 MUST 是同一双重记账事务；未见 COMMIT 的 prepare MUST NOT 对外可见。

`[DUR-RECOVER-001]` 恢复 MUST 验证 framing、CRC、transaction checksum 和 LSN 连续性，从最后一个合法完整 COMMIT 重放，截断 torn tail，并按 TxnId/IdempotencyKey 幂等；before/after digest 不得替代可重放 mutation payload。

`[DUR-SNAP-001]` snapshot MUST 记录 `last_lsn`、state hash、dedup/result table 和已消费 authority Receipt high-water；写临时文件、fsync、原子 rename、fsync 父目录后方可回收旧 WAL。Dedup 记录不得早于其最大 retry/recovery/audit window 被 GC。

`[DUR-FREEZE-001]` 恢复后的全部非终态 Reservation（RESERVED/ACTIVE/CLOSING/UNCERTAIN）默认继续冻结。只有证明一次性 dispatch token 从未消费的 RESERVED 才能安全 release；不得因原 Process 不存在自动退款。

`[DUR-FAILCLOSED-001]` 存储或 quorum 不可用时，新 reserve/transfer/spawn MUST fail-closed；已有 Reservation MAY 在既有上界内继续，但不得扩张额度。

`[LEASE-GRANT-001]` 控制面 MUST 先 durable 扣除全部 face_value，再签发 lease。

节点本地守恒：

```text
face_value
= local_available
+ local_reservations
+ local_spent
+ returned
+ quarantined
```

`[LEASE-SPEND-001]` 节点只能从本地 lease 子账本 reserve，不得在分区中续约、扩额或向其他节点迁移。

`[LEASE-REPORT-001]` usage/reconcile MUST 使用单调 high-water mark 并幂等。

`[LEASE-TTL-001]` TTL 只限制旧节点继续创建调用，不能单独证明额度可安全复用。

`[LEASE-FENCE-001]` fencing token MUST 在明确 fence_scope 内全序单调。重发任何未对清额度前，控制面必须获得该 scope 内全部真实成本 gateway/credential issuer 的 durable fence-barrier ACK；无法完成 barrier 的额度继续 QUARANTINED。

`[LEASE-CLOSE-001]` `ACTIVE → CLOSING` MUST 先 durable 禁止本地新 reserve，再 drain/reconcile；close ACK 之前不得把剩余额度返回全局 AVAILABLE。

`[LEASE-LOSS-001]` 节点失联后的未对清额度 MUST 进入 QUARANTINED；宁可冻结，不得重复签发。

`[LEASE-MIGRATE-001]` 正常迁移 MUST 执行 `drain → close source lease → fence source → grant target lease`。

`[LEASE-RENEW-001]` renew MUST NOT 隐式增加额度；top-up 是新的 durable 转移。

`[LEASE-ENFORCE-001]` ENFORCED_DISTRIBUTED 中，invoke、stream extend 和每个新增计费窗口 MUST 携带并校验 node boot generation、epoch 和 fencing token，不得降为 optional。

`[LEASE-WAL-001]` 节点本地 lease WAL 丢失后 MUST 停止准入、fence 旧 boot generation 并由控制面 reconcile/quarantine；不得从 face_value 猜测 remaining 后重新上线。

`[LEASE-CAPACITY-001]` CapacityLease 的 GLOBAL_RESERVED/TARGET_PREPARED/ACTIVE 数量 MUST 计入 source pool 的 strict committed capacity；target 只有在匹配 boot/controller/group generation 的 host attach Receipt durable 后才能 ACTIVE。pre-active prepare 失败必须走 RETURNING，并在 source authority durable 确认 target 从未激活或已 fence/cleanup 后才 RETURNED；否则 QUARANTINED。expiry 只阻止新 admission，不证明 holder 已停止；FENCING + CLEANING Receipt 完成前不得回到 source allocatable pool。

`[LEASE-CAPACITY-002]` CapacityLease revoke/migrate MUST 执行 `freeze new use → drain/checkpoint or force → fence holder/node generation → controller cleanup/reconcile → return/regrant`。节点失联、meter high-water 不明或 cleanup proof 缺失时进入 QUARANTINED；目标重发不能只依赖 lease TTL 或控制面数据库状态。

`[LEASE-DEVICE-001]` 每个 DeviceId/partition MUST 有线性化 DeviceLeaseHead；新 lease 只能以 head=FREE 的 CAS 安装为唯一 PREPARED holder，不能靠选择不同 exclusivity_epoch 并发占用。pre-active 失败也必须经 RETURNING 和必要 reset/zeroization 后 CAS 回 FREE。迁移或 holder loss 后，全部 device endpoint 必须拒绝旧 fencing token，并取得 fence、queue drain、reset、VRAM/secret zeroization attestation，原 head 才能清空并允许新 epoch；不能证明清理的设备保持 QUARANTINED。

`[LEASE-PREACTIVE-001]` QuotaLease.ISSUED、CapacityLease.GLOBAL_RESERVED/TARGET_PREPARED 和 ExclusiveDeviceLease.DEVICE_RESERVED/HOLDER_PREPARED MUST 都有 idempotent cancel/return/query 路径。只有 authority 证明额度/容量/设备从未 ACTIVE，或已经完成对应 fence/cleanup，才能进入 CANCELLED/RETURNED；ACK 丢失与本地 timeout 保持冻结，不能永久占用也不能猜测释放。

`[LEASE-RECON-001]` QuotaLease、CapacityLease 与 ExclusiveDeviceLease MUST 使用各自 typed query、high-water 和 reconciliation Receipt。Quota reconcile 守恒 face value，Capacity reconcile 证明数量与 holder cleanup，Device reconcile 证明唯一 epoch 与 reset/zeroization；三种 Receipt 不得互换。

可信控制面私有协议至少包含：

```text
lease_grant / lease_cancel / lease_topup / lease_renew /
lease_close / lease_fence / lease_reconcile /
capacity_prepare / capacity_abort_return / capacity_activate / capacity_revoke /
capacity_fence / capacity_cleanup / capacity_reconcile /
device_prepare / device_abort_return / device_activate / device_drain /
device_fence / device_reset / device_reconcile
```

`[LEASE-PROTO-001]` 每个 lease 命令 MUST 携带 schema/version、request/idempotency key、node boot generation、expected state/epoch、AuthorityExpiry 和签名，并返回 durable state seq；状态查询与重复命令必须返回同一已提交结果。

## 14. Artifact、Context 与持久状态

### 14.1 Artifact

Artifact 必须能表达：

- 文档、文件、结构化对象和流；
- content type、版本、所有者、Application 关联；
- share、sync、retention、backup 和 conflict；
- immutable revision 与 mutable head；
- provenance、加密、删除和 legal hold。

`[ART-OWNER-001]` Package 内容与用户可变数据 MUST 分离；卸载 Application 不得默认删除用户 Artifact。

`[ART-VERSION-001]` 高风险 Action 的输入和输出 MUST 绑定具体 Artifact revision/digest，不得只引用可漂移的“latest”。

`[ART-LOCAL-001]` `DeploymentMode=LOCAL_SINGLE_NODE` MUST 以本地 Artifact 为权威并提供 export/backup/restore；其他模式 MAY 采用不同权威布局，但同步冲突、离线语义和远程失败 MUST 显式，不得伪装成透明本地调用。

### 14.2 Context

Context 是一次执行使用的派生视图，可由 Artifact、Semantic Event、Session state 和私有输入构成。

`[CTX-DERIVE-001]` Context MUST 记录 source selectors、captured revisions、构建器版本、quota 和有效期。

`[CTX-NOTDATA-001]` Context eviction 不得删除 Artifact 本体。

`[CTX-PIN-001]` pin 只保证声明范围内的可用性/一致性并产生资源费用，不得被解释为语义真实性。

`[CTX-PRIVATE-001]` 模型隐式推理状态和预训练知识 MUST 标记为系统无法完整捕获的 private context。

# 第六部：语义事件、规格与结算

## 16. 语义数据面的基本原则

核心原则：

> **内容身份、认识论行为身份和 policy-relative 系统视图必须分离；内核记录证据，不保存全局真值。**

### 16.1 ContentDigest 与 EventId

```text
ContentDigest =
  H(
    "llmos/content/v1"
    || deterministic_cbor([media_type, exact_bytes])
  )

EventId =
  H("llmos/semantic-event/v1" || deterministic_cbor(unsigned_event))
```

其中 `unsigned_event` 是完整事件信封移除 `event_id` 与 `signature` 后的结构，仍包含 `schema`、`issuer_execution` 和 `key_id`。

`[SEM-ID-001]` ContentDigest 只表示字节完整性和字面去重，MUST NOT 充当 Assertion、Judgment、Verification、Retraction 或 Spec 的身份。

`[SEM-ID-002]` 两个主体发表完全相同内容时，ContentDigest MAY 相同，EventId MUST 不同。

`[SEM-ID-003]` EventId MUST 覆盖除 event_id 与 signature 外的完整事件信封，包括 schema、event type、完整 payload、issuer、issuer execution、scope、control domain、nonce、time、lineage、validity 和 key_id。

`[SEM-CANON-001]` canonical encoding MUST 使用 deterministic CBOR；禁止重复键、不定长编码、NaN 和浮点时间，时间使用整数 Unix 纳秒。

`[SEM-IDEM-001]` 相同 canonical event 的重试 MUST 幂等返回原 Receipt；相同 EventId 对应不同字节 MUST 触发安全故障并隔离，禁止 `INSERT OR IGNORE` 静默吞掉。

`[SEM-SIGN-001]` signature MUST 签署 `H("llmos/semantic-signature/v1" || EventId)`；它只证明作者和完整性，不证明内容为真。

### 17.1 AssertionEvent


`[SEM-ASSERT-001]` assertion_mode 是生产者声明；仅填写 `FACT_FROM_TOOL` 不得提升权威，必须绑定可信 Driver 的 execution EvidenceRef。

### 17.2 JudgmentEvent

```text
JudgmentEvent {
  relation: EQUIVALENT | CONTRADICTS | ENTAILS | SUPPORTS | REFINES
  source: EventId
  target: EventId
  context?: ContentDigest
  evaluator_evidence: EvidenceRef
  confidence_bp?: 0..10000
}
```

`[SEM-JUDGE-001]` 不同判断者对相同端点和关系的判断 MUST 保留为不同事件。

`[SEM-JUDGE-002]` 内核和 CRDT merge MUST NOT 自动生成 `CONTRADICTS` 或其他语义关系；merge operation 只能返回签名的结构性 ConflictReceipt（对象 revision、冲突字段/操作和 checkpoint），它不是 SemanticEvent，也不判断语义矛盾。

`[SEM-JUDGE-003]` ENTAILS、SUPPORTS 和 REFINES 是有向关系；EQUIVALENT 和 CONTRADICTS 是对称关系，其 source/target MUST 按 EventId 字节序规范化，防止同一判断出现两个编码。

### 17.3 VerificationEvent

```text
VerificationTarget =
  EventTarget {
    kind: EVENT
    event_id
  }
  | CriterionTarget {
    kind: CRITERION
    spec_id
    criterion_id
    artifact_set_digest
    procedure_digest
    evaluation_id

      escrow_id

  procedure_ref: ImmutableArtifactRef | AuthorityPolicyRef
  evaluator_evidence: EvidenceRef
  evidence:[EventId]

```

`[SEM-VERIFY-001]` `SELF` 与 `INDEPENDENT` 是 verifier 与 producer 的派生关系，不是调用者可自报的 method。

`[SEM-VERIFY-002]` `UNVERIFIED` 是“没有足够适用证据”的派生视图状态，MUST NOT 写成事件。

`[SEM-VERIFY-003]` checker 缺失、异常或超时 MUST 产生 `ERROR`，不得伪装为 PASS 或业务 FAIL。

`[SEM-VERIFY-004]` Verification target MUST 恰好匹配 tagged union 的一个分支；Gate 只能接受完整 CriterionTarget，空目标、混合目标、evaluation/procedure digest 不一致 MUST 拒绝。自动 Escrow gate 还必须具有匹配 hold generation 的 settlement_binding。

`[SEM-VERIFY-005]` Artifact gate 的独立性 MUST 针对 ResolvedArtifactSet/ActionReceipt 绑定的全部 producer_control_domains 计算，而不是只比较单个 owner。

`[SEM-CONFIDENCE-001]` confidence_bp 只是证据属性，MUST NOT 单独提升 authority、证明 independence 或满足 gate。

### 17.4 RetractionEvent

```text
RetractionEvent {
  target_event_id: EventId
  mode: WITHDRAW | INVALIDATE
  reason?: ContentDigest
  authority_evidence: EvidenceRef
}
```

`[SEM-RETRACT-001]` WITHDRAW 只能由原 issuer 或其预先委托主体签发。

`[SEM-RETRACT-002]` INVALIDATE 只能由 scope 内持有 adjudication capability 的主体签发。

`[SEM-RETRACT-003]` 普通第三方不得撤回他人事件；它只能追加 VerificationEvent(FAIL)、JudgmentEvent 或在自身 TrustPolicy 中排除。

`[SEM-RETRACT-004]` 撤回只针对 EventId，MUST NOT 针对 ContentDigest；不级联、不物理删除，也不得通过撤回 RetractionEvent 使原事件复活。

### 17.5 SpecEvent

SpecEvent 承载完整不可变 IntentSpecBody，其身份规则见第 20 章。

```text
}

resolve(target, TrustPolicy P, SemanticCheckpoint C):
  1. 读取 C 的各 domain/shard watermark 所覆盖事件
  2. 校验 admission、durability、signature、scope 与 authorization
  3. 按 P 和 C 的 trust snapshots 应用授权撤回及 key policy
  4. 以 C.as_of_ns 应用 effective validity 与 taint 规则
  5. 收集全部仍适用的 VerificationEvent
  6. 按 authority、control domain、independence 和 aggregation 聚合
  7. 输出结果、完整证据集与派生风险标记
```

`[SEM-POLICY-001]` TrustPolicy MUST content-addressed、不可变并完整定义 authority、聚合、独立性、撤回、taint、key revocation、human override 和 unknown handling；漂移的 policy alias 不得用于 Gate。

`[SEM-CHECKPOINT-001]` 分布式 View MUST 使用签名 vector/checkpoint，不得假设存在跨 Cell 的全局标量 log_seq。

```text
AuthorityViewReceipt {
  target
  disposition
  policy_digest
  semantic_checkpoint
  resolver_implementation_digest
  aggregation_algorithm_digest
  canonical_iteration_digest
  derivation_digest
  as_of_ns
  evaluated_at: UtcInstant
  valid_until: AuthorityExpiry
  accepted_evidence:[EventId]
  excluded_evidence:[{event_id, reason}]
  derived_risk_markers
  durability
  signer
  key_id
  signature
}
```

`[SEM-VIEW-001]` 同一事件在不同 TrustPolicy 下得到不同 disposition 是预期行为。

`[SEM-VIEW-002]` `ACCEPTED` 只表示“在 policy P 和 SemanticCheckpoint C 下达到证据门槛”，不得表述为内核证明了世界事实。

`[SEM-VIEW-003]` quorum MUST 按不同 ControlDomainId 计数，禁止同一控制者用多个 key/event 刷票。

`[SEM-VIEW-004]` key 撤销是否追溯、TTL 的 as-of 时刻和 retraction cutoff MUST 由 TrustPolicy 与 SemanticCheckpoint 唯一确定；ViewReceipt 还必须绑定 resolver implementation、aggregation algorithm、canonical iteration 和 derivation digest，才能按 `[CONS-SEM-001]` 重放 disposition/derivation。升级 resolver 必须产生不同 View identity，不能静默改写历史。

### 18.1 验证者独立性

默认独立验证至少要求：

1. verifier 与 producer 的 ControlDomainId 不同；
2. verifier Process 不是 producer 或其受控子进程；
3. verifier 由 Spec/controller 选择，而非 producer 临时指定；
4. evaluator model/harness/tool digest 和执行域可认证；
5. Policy 要求维度未知时按“不独立”处理。

`[SEM-INDEP-001]` 高 criticality Policy MAY 进一步要求不同 provider、模型家族、harness、operator 或执行环境。

`[SEM-HUMAN-001]` Human verdict MAY 被 Policy 赋予最高权威；系统不得全局禁止 Human verifier。

`[SEM-DET-001]` deterministic checker 仍 MUST 绑定代码 digest、input Artifact digest、环境和 execution Receipt；“代码”本身不是无条件真理。

## 19. Provenance、Lineage、Taint、TTL 与 GC

### 19.1 捕获边界

- `declared_parents`：生产者签名声明；
- `captured_inputs`：trap/Driver/系统服务实际观察到的读取；
- `private_context`：系统无法完整证明的隐式状态。

```text
effective_lineage =
  declared_parents ∪ captured_inputs

effective_taint =
  ingress_taint
  ∪ taint(declared_parents)
  ∪ taint(captured_inputs)
  ∪ provenance_incomplete_if_applicable
```

`[SEM-LINEAGE-001]` 新事件只能引用已提交事件或同一原子批次中更早事件；dangling、未来引用和环 MUST 拒绝。

`[SEM-LINEAGE-002]` declared parents MUST NOT 被宣称为完整 provenance。

`[SEM-TAINT-001]` effective taint MUST 包含 ingress、declared parents 和 captured inputs 的 taint；存在 private context、观察旁路或依赖完整性未知时 MUST 加入 `PROVENANCE_INCOMPLETE`，默认单调不减。

`[SEM-DECLASS-001]` 降低 taint 必须由新事件的 `declassification_receipt_id` 引用不可变授权 Receipt；Receipt 必须绑定 holder、scope、source events、允许移除的 label、purpose、expiry 和 nonce。Admission 验证后只影响新事件，原 Event 与 AdmissionReceipt 保持不变。

`[SEM-ANCESTOR-001]` 父事件过期或撤回时，Authority View MAY 动态派生 `ANCESTOR_EXPIRED/ANCESTOR_RETRACTED` 风险标记；不得修改后代 Event/AdmissionReceipt，内核也不得自动追加 `DISPUTED` 语义结论。

### 19.2 Append-only 与事务

权威源至少包括：

```text
content_objects
semantic_events
event_signatures
admission_receipts
durability_receipts
lineage_edges
event_log
```

`[SEM-APPEND-001]` 权威表 MUST 只增不改；UPDATE/DELETE 必须在存储层拒绝。Materialized view 和索引 MAY 更新或重建，但不得成为事实源。

`[SEM-TXN-002]` 一次 append 事务 MUST 原子完成：

1. schema/canonical 校验；
2. digest/EventId 校验；
3. identity、capability、scope、signature 和 key validity 校验；
4. target、lineage、DAG、effective validity、taint 和 declassification 校验；
5. content reference、event、edges、AdmissionReceipt 和 durable outbox 同时提交；
6. 失败时任何部分均不可见。

`[SEM-TXN-001]` Spec 完整结构 MUST 存于 canonical SpecEvent；旁表只能是同事务生成、可重建的投影。

`[SEM-XORG-001]` 跨组织事件 MUST 同时具有生产者签名和接收域 AdmissionReceipt；签名覆盖 scope 以防跨 tenant 重放。

语义服务稳定错误至少包括：

```text
E_CANONICAL_MISMATCH   E_EVENT_ID_COLLISION
E_INVALID_TARGET       E_INVALID_LINEAGE
E_UNAUTHORIZED_RETRACTION
E_INDEPENDENCE_UNKNOWN E_PROVENANCE_INCOMPLETE
E_NON_SETTLEABLE       E_STALE_VIEW
E_INSUFFICIENT_DURABILITY
```

`[SEM-ERR-001]` canonical mismatch、ID collision、无效 target/lineage、未授权撤回、独立性未知、provenance 不完整、不可结算、stale view 和 durability 不足 MUST 可由调用者区分。

### 19.3 TTL 与 GC

`[SEM-TTL-001]` TTL 只表示事件对新 live view 的适用期，不表示真假改变、撤回或物理删除。

`[SEM-TTL-002]` Admission MUST 计算 `effective_valid_until = min(declared_valid_until, scope_policy_limit, key_validity, admission_limit)`，并使用接收域可信时钟；过期事件仍 MUST 可在 audit/as-of view 中查询。

`[SEM-TTL-003]` RetractionEvent 在 admission 时 MUST 拒绝任何 `valid_until`，防止撤回通过 TTL 自动失效。

`[SEM-GC-001]` active Escrow、legal hold、未过期后代或 retention policy 引用的 logical event 不得进入冷归档；logical retention、content payload GC、索引回收和冷归档 MUST 使用不同状态与指标。

`[SEM-GC-002]` GC MAY 删除无引用 content bytes、embedding 和可重建索引，但 MUST 保留 ContentDigest、事件头、lineage、signature、Receipt 和日志/Merkle checkpoint。

`[SEM-PRIVACY-001]` 隐私删除 SHOULD 使用加密内容的 crypto-shredding；读取必须返回 `CONTENT_UNAVAILABLE`，不得假装事件从未存在。

`[SEM-PRIVACY-002]` Event header 中的 issuer、time、lineage 和 signature 也可能是个人数据；实现 MUST 支持 metadata minimization、按 retention domain 分离密钥、账户 export/delete、legal hold 冲突政策和可审计删除证明，不能把“保留 header”误称为无隐私影响。

`[SPEC-ID-001]` SpecBodyDigest MUST 覆盖 goal、全部 acceptance、constraints、criticality、settlement 和 extensions。

`[SPEC-ID-002]` SpecId 还 MUST 覆盖 issuer、scope、nonce、time 和 lineage。

`[SPEC-IMM-001]` 任一字段变化 MUST 产生新 Spec；Spec 不可原地更新，只能用 REFINES Judgment 连接。

`[SPEC-CHECKER-001]` checker/tool/model/prompt MUST 引用 immutable version/digest；漂移的 `latest` 不得用于 hard gate。

`[SPEC-ARTSET-001]` ArtifactSelector MUST 在验收或 Escrow hold 前解析为不可变 ResolvedArtifactSet；全部 Verification、GateDecision 与 Hold MUST 使用同一 artifact_set_digest，selector 后续漂移不影响本次结算。

`[SPEC-WINDOW-001]` 每个 criterion 在开始验收前 MUST 创建不可变 CriterionEvaluationWindow；deadline 等于 `min(started_at + criterion.timeout, Spec deadline, Escrow decision_deadline)`，并由 settlement coordinator 的可信时钟签署。

`[SPEC-WINDOW-002]` 聚合前 MUST 过滤迟到证据：只有被 TrustPolicy 接受的可信 execution completion time 不晚于 window.deadline 才能计数；缺少可信执行时钟时使用接收域 Admission time。及时完成但稍后读取的证据仍可有效，deadline 后才完成或无法证明完成时间的 PASS 不得复活 gate。

`[SPEC-CONSTRAINT-001]` 未知“可执行约束” MUST 拒绝；自然语言黑名单不得宣称为内核可强制约束。

`[SPEC-SPAWN-001]` child Spec 的 Resource、Namespace、deadline 和 Capability 必须机械衰减；无法证明衰减时必须拒绝或显式重授权。

### 20.2 Hard/Soft 与 evaluator kind 正交

`effect` 表示该 criterion 是否阻塞结算，`evaluator_kind` 表示如何产生证据，二者不是同一维度。

- deterministic checker 默认可设为 HARD；
- model/human 默认是 SOFT；
- `[SPEC-HARD-001]` model/human MAY 显式成为 HARD，但必须声明 authority、pass/fail quorum、independence、timeout 和风险 policy；
- HARD 表示 policy 的阻塞语义，不表示世界事实被数学证明。

单 criterion 状态：

```text
PENDING | PASS | FAIL | CONTESTED | ERROR | EXPIRED
```

单 criterion 按以下固定优先级聚合已被 TrustPolicy 接受、且来自不同 ControlDomain 的证据：

```text
1. FAIL       = 存在满足 authority 的 veto FAIL
2. CONTESTED  = pass_count >= pass_quorum
                且 fail_count >= fail_quorum
3. FAIL       = fail_count >= fail_quorum
4. PASS       = pass_count >= pass_quorum
5. EXPIRED    = criterion deadline 已过
6. ERROR      = 所有已计划 verifier 均终态，
                quorum 已不可能达到，且存在 ERROR
7. PENDING    = 其余情况
```

`[SPEC-AGG-001]` pass_quorum 和 fail_quorum MUST 均大于 0；只计数符合 CriterionEvaluationWindow 的及时证据，并去重 ControlDomain。达到 veto 的 FAIL 优先于 CONTESTED，其余状态严格按上述顺序求值。

总 hard gate：

```text
FAIL       = 任一 hard criterion 为 FAIL
CONTESTED  = 无 FAIL，且任一 hard criterion 为 CONTESTED
ERROR      = 无 FAIL/CONTESTED，且任一 hard 为 ERROR/EXPIRED
PASS       = hard 集合非空，且全部 hard criterion 为 PASS
PENDING    = 其余情况
```

`[SPEC-GATE-001]` `AUTOMATIC` settlement 的 hard set MUST 是 acceptance 中全部 `effect=HARD` CriterionId 的规范排序集合，且非空；`hard_criteria_digest` MUST 精确等于该集合的 digest，不得遗漏失败 gate。

`[SPEC-GATE-002]` 空 acceptance、soft-only acceptance 和空 hard set MUST NOT 自动通过；禁止依赖 `all(empty) == true`。

`[SPEC-GATE-003]` 只有 hard gate `PASS` 可驱动自动结算；PENDING、FAIL、CONTESTED、ERROR 和 EXPIRED 全部 fail-closed。

`[SPEC-GATE-004]` `NONE` 或 `MANUAL` MAY 没有 hard gate，但不得产生“自动完成”或“自动释放”；`NONE` 的 hard_criteria_digest 和 challenge_window MUST 为空，`MANUAL` 的任何 release 必须消费独立 Human/Adjudication DecisionReceipt。

`[ESC-DEADLINE-001]` Semantic hold admission MUST 使用 contract 绑定的 resource TimePolicy 以 checked arithmetic 计算并验证 decision/notice registration deadline、settlement validity floor 与 release deadline，把 agreement policy、timeout、time policy、全部派生 deadline、challenge、delivery margin 和 notice authority 无损编译进 ResourceEscrowOpenReceipt；AUTOMATIC 默认只能编译为 REFUND_ONLY，MANUAL 才可在明确 payer/payee 双签策略下编译为 RELEASE_OR_REFUND，NONE 不创建 Escrow。Ledger 不得读取或解释 Spec。

`[ESC-STREAM-001]` Hold 创建时 MUST 注册独立 evidence stream，并把 `Spec + ArtifactSet + hard criteria + transitive evidence dependencies` 映射到 EscrowId/hold generation。用于自动结算的 Verification 必须带 settlement_binding；影响已登记证据的 Retraction、Challenge 或 Verification 在 Admission 时必须原子追加 EscrowEvidenceRef 到对应 stream。

`[ESC-CUT-001]` Settlement checkpoint MUST 是 causal-closed cut，覆盖 TrustPolicy 要求的全部 domain/shard 和当前 durable EscrowEvidenceHead；staleness 不得超过 policy 上界。无法证明 required-domain coverage 或 causal closure 时返回 `E_STALE_VIEW`。

`[ESC-HEAD-001]` SettlementDecision COMMIT MUST 以 expected stream_seq/state=OPEN 执行 CAS，并把 EvidenceHead 置为 DECISION_PENDING_REGISTRATION；head 已变化、存在未覆盖引用或 generation 不符时必须重新计算。pending 之后的新证据进入 post-decision stream，不能被伪装成“checkpoint 之后所以无关”。

`[ESC-BIND-001]` coordinator MUST 逐字段比较 GateDecisionCore 与当前 SemanticSettlementContract，包括 escrow/generation、两个 contract digest、Spec、ArtifactSet、TrustPolicy、hard set、resolver/aggregation/canonical iteration digest 与 TimePolicy。通过后，同一 decision transaction 必须持久写入 GateDecisionCore、subject=`GateDecisionCore.decision_id` 的 GateDecisionCommitReceipt/DECISION_COMMIT proof、引用二者的 ResourceDecisionCoreReceipt、`REGISTER_DECISION` canonical command/outbox；不得让 adapter 事后替换 basis。

`[ESC-BIND-002]` GateDecisionCommitReceipt 的 proof MUST 由 contract TimePolicy 接受的 semantic commit domain 在持久提交 GateDecisionCore 的同一原子 commit 中签发，且 `decision_committed_at = proof.observed_at <= decision_deadline`、`commit_domain = proof.commit_domain`、`committed_log_index = proof.committed_log_index` 均逐位相等。ResourceDecisionCore 必须复用该 proof、以 GateDecisionCore type tag/decision_id 作为 source subject，并满足 `settlement_validity_floor <= valid_until <= release_deadline`；Resource registration 还必须在 decision_registration_deadline 前完成，超出 bounded delivery margin 的 outbox 不得用旧决定释放。

`[ESC-DURABLE-001]` 自动结算使用的 SpecEvent、VerificationEvent、evaluator/execution Receipt、TrustPolicy、identity/key snapshot、SemanticCheckpoint、GateDecisionCore、ResourceDecisionCore 与相关 outbox MUST 全部达到 DURABLE；BUFFERED 证据不得登记 resource decision。

`[ESC-GATE-001]` GateDecisionCore 的 criterion_states MUST 精确覆盖 hard_criteria_digest 对应的全部 HARD criterion，且每项为 PASS；soft-only、遗漏、PENDING、FAIL、CONTESTED、ERROR 或 EXPIRED MUST fail-closed。

### 21.2 结算线性化点

v0.5 采用 **DecisionCore → Notice → Release**：

1. Semantic settlement coordinator 读取当前 EscrowEvidenceHead H；
2. 构造覆盖 H、全部 required domains 且 causal-closed 的新 SemanticCheckpoint C；
3. 在 C 上解析完整 hard gate；
4. 在一个 durable transaction 中 CAS H，写 GateDecisionCore、subject-bound GateDecisionCommit、ResourceDecisionCore 和 REGISTER_DECISION outbox，head 进入 DECISION_PENDING_REGISTRATION；
5. GateDecisionCommit 所证明的该 transaction COMMIT 是语义 verdict 的历史线性化点，不等于资金 release；
6. outbox ACK 后，零 challenge 的 head 可进入 DECIDED；非零 challenge 进入 DECISION_PENDING_NOTICE；
7. 非零 challenge 生成引用 DecisionCore 的 ResourceChallengeNoticeReceipt，经 REGISTER_NOTICE outbox ACK 后 head 进入 DECIDED；
8. challenge window 结束后，用 exact RELEASE command + resolver authorization bundle 申请 release；Ledger 独立验证 registered decision/notice/time/CAS；
9. C 前证据必须参与决策；pending/decided 后的新证据只能驱动 challenge/dispute 或 decision abort/re-evaluation，不能改写历史 receipt。

`[ESC-FINALITY-001]` AuthorityView 查询不是结算决定；GateDecisionCommitReceipt 证明的 GateDecisionCore durable commit 是语义 verdict 的线性化点，ResourceEscrowTransitionReceipt 才是资金状态的线性化结果。两者不得合并成“网络 exactly-once”。

`[ESC-CMD-RECONCILE-001]` REGISTER_DECISION、REGISTER_NOTICE、ABORT_DECISION、OPEN_DISPUTE、RELEASE、REFUND 任一普通 command 在 ACK 丢失、delivery 超时、worker crash 或表面“永久失败”后，coordinator MUST 先用 `resource_escrow_get(EscrowId, CommandId)` 收敛，不能仅据 transport 结果推断未提交。若 operation 为 PENDING/UNKNOWN 且签名 ResourceEscrowStateReceipt 的 state_seq 仍等于 command.expected_state_seq、状态仍兼容，则 head 进入 DECISION_RECONCILING，只允许用原 canonical bytes/key 重投或继续查询；若 current state_seq 已更大或已终态，expected-state CAS 已被权威 fence，即使 operation status 仍 PENDING/UNKNOWN 也必须按当前 state 分类。COMMITTED 证明该 Transition 曾发生，但 Semantic 映射同样以本次线性化查询的 ResourceEscrowStateReceipt 为当前权威，不能把 head 回退到旧 Transition.after_state；按其精确 registered decision/notice 分类：HELD→DECISION_ABORTED/可重开判断，DECISION_REGISTERED→DECISION_PENDING_NOTICE 或 DECIDED（零 challenge），PENDING_CHALLENGE→DECIDED，DISPUTED→DISPUTED，RELEASED→SETTLED_RELEASED，REFUNDED→SETTLED_REFUNDED。REJECTED_FENCED 也必须与同次 ResourceEscrowStateReceipt 一起分类；不同 DecisionCore/Notice、state receipt 验证失败、state_seq 反向或无法分类时保持 RECONCILING 并升级冲突。普通瞬时“未查到”、operation tombstone 单独出现或本地 deadline 均不得制造孤儿 decision、重复 command、状态回退或错误重开。

`[ESC-NOTICE-FAIL-001]` REGISTER_NOTICE 超过 margin 或失败时必须先执行 `[ESC-CMD-RECONCILE-001]`。若该 Notice 已 COMMITTED，或当前 PENDING_CHALLENGE 精确登记同一 DecisionCore/Notice，则 head 进入 DECIDED；若 Resource 已 DISPUTED/RELEASED/REFUNDED/HELD，则直接收敛到对应 Semantic 状态，禁止再 ABORT。只有 NOTICE CommandId 已有 durable REJECTED_FENCED、当前仍为同一 DecisionCore 的 DECISION_REGISTERED 且 notice 尚未登记时，resolver 才可基于最新 state_seq 构造新的 ABORT_DECISION；已经进入 PENDING_CHALLENGE 的 Notice delivery 不得借故撤销。ABORT 也必须按统一协议查询收敛，且 COMMITTED 后才可把 EvidenceHead CAS 为 DECISION_ABORTED、合并 post-decision evidence；只有仍能满足 decision deadline 时才可重新评估，否则标记 NON_SETTLEABLE 并走 timeout。后续新证据若要主动撤销已登记 Notice，必须走独立、显式授权的 policy path，不能伪装成 delivery failure。

`[ESC-REGFAIL-001]` REGISTER_DECISION ACK 丢失、永久失败或超过 registration deadline 时 MUST 使用 `[ESC-CMD-RECONCILE-001]`。COMMITTED 且当前仍登记本 DecisionCore 才继续 notice/release；只有本 CommandId 已有 durable REJECTED_FENCED，或签名 ResourceEscrowStateReceipt 已证明 current.state_seq 大于该 command.expected_state_seq，且当前 record 仍 HELD、没有 registered active decision 时，才可 CAS Semantic head 为 DECISION_ABORTED、合并 post-decision evidence，并在 deadline 仍可满足时重开；否则保持 RECONCILING、进入 NON_SETTLEABLE 或接受权威后继终态。

`[ESC-RELEASE-RECONCILE-001]` RELEASE/REFUND 的 Semantic head 不得在 outbox 发送后永久停留 DECIDED。ACK 丢失时必须执行 `[ESC-CMD-RECONCILE-001]`：同一 CommandId COMMITTED 按 RELEASED/REFUNDED 终结；若 OPEN_DISPUTE、bilateral settlement、EXPIRE 或 ABORT 先赢，则分别进入 DISPUTED、SETTLED_* 或 DECISION_ABORTED/NON_SETTLEABLE；若仍是匹配的 DECISION_REGISTERED/PENDING_CHALLENGE，则只可按原 command 重投或保持 RECONCILING，不得绕过 state_seq 另发释放。

`[ESC-TXN-001]` Semantic Store 与 Ledger 位于同一事务域时 MAY 单事务提交 semantic + resource state，但仍 MUST 保持类型边界。跨服务时 OPEN 和所有普通 Resource command MUST 使用 EscrowCommandOutbox；timeout 使用 APPLY_EXPIRE_INTENT item，保存 ResourceEscrowExpireIntent/ExpireRequestId，并在 ACK/query 后记录 Ledger 解析出的 CommandId。禁止 check-then-act。

`[ESC-IDEM-001]` 每个 outbox item MUST 持久保存 exact canonical signed operation bytes、稳定对象 IDs、普通操作的 CommandId 或 timeout 的 ExpireRequestId、原 IdempotencyKey、expected state_seq 与 result Receipt；transport envelope/handle 不属于 exact identity。恢复时先用稳定 ID 重绑 fresh handles、查询 Resource state/operation id，再用原 canonical bytes/key 重投；ACK 丢失、重复 delivery 和 coordinator 重启必须收敛到同一结果。

`[ESC-CHALLENGE-001]` challenge_window 非零时，Semantic service MUST 在 DecisionCore commit 后按 policy 产生 subject-bound ResourceChallengeNoticeReceipt；notice 引用 DecisionCore，而 DecisionCore 不引用 notice，消除摘要环。Resource 层以 REGISTER_NOTICE 的 apply_at 计算 release_not_before；Semantic UI MAY 显示该值，但不得作为账本权威。

`[ESC-CHALLENGE-002]` OPEN_DISPUTE 的 semantic DisputeOpenReceipt MUST 绑定不含 basis refs 的 ResourceCommandIntentDigest；coordinator 再生成机械 ResourceDisputeOpenReceipt，以前者 type tag/ID 作为 opaque source，最终 ResourceEscrowCommandBody 只引用 Resource receipt。challenger 的 authorization bundle 直接签最终 CommandBodyDigest。两种 receipt、command 与 outbox MUST 在同一 semantic transaction durable 保存后再投递。Resource 已进入 DISPUTED 但 ACK 丢失时恢复者查询/重投；不得出现“Ledger DISPUTED 而 Semantic 无 grounds/evidence”。

`[ESC-CHALLENGE-003]` RELEASE command MUST 精确引用 Resource 层已登记的 DecisionCore/Notice typed IDs，并由 resolver 对完整 ResourceEscrowCommandBody digest 签名；Semantic adapter 不得自填 challenge_open/release_not_before、替换 decision/notice proof 或提供 apply time。

`[ESC-DISPUTE-001]` `DISPUTED → RELEASED/REFUNDED` 的 semantic DisputeDecisionReceipt MUST 绑定 ResourceCommandIntentDigest；coordinator 必须将其机械字段投影成 ResourceAdjudicationReceipt，并以前者 ID 作为 opaque source。adjudicator 必须签两种 receipt，并另在 AdjudicatorAuthorization 中直接签最终 CommandBodyDigest；receipt/command/outbox 同事务保存。adapter 只投递，不能代签。普通 GateDecision 或重新计算的 PASS 不得绕过 adjudication。

`[ESC-REFUND-001]` deadline 前 refund 只有两个互斥授权分支：`DISPUTED` 分支使用匹配 DisputeDecision 投影出的 ResourceAdjudicationReceipt，并只接受 adjudicator 对 receipt 与 AdjudicatorAuthorization/CommandBodyDigest 的签名；协议分支使用由 Manual/Bilateral source 投影出的 ResourceBilateralSettlementReceipt，并要求 payer/payee 对该 receipt 及同一 Resource CommandBodyDigest 双签。两种 authorization union 不得混用，Semantic service 不得代签。机械 timeout 只由 Resource TimePolicy 与 Ledger 注入的 apply proof 决定。

`[ESC-EXPIRE-001]` Semantic service 的 View MAY 从 EXPIRE TransitionReceipt 派生显示 TIMED_OUT，但 Resource ledger 不暴露可竞争的 EXPIRED 中间态。Semantic service 不得构造带 Ledger 签名的 Resource command 或自行修改资源状态；它只能投递 stable ResourceEscrowExpireIntent，以 ExpireRequestId 查询 Ledger 生成的 CommandId/结果，并接受 immutable on_timeout 与可信 apply-time 裁决。

`[ESC-TIME-CAS-001]` Semantic adapter MUST 原样传递 subject-bound decision/notice proof、validity 与 typed basis refs，不得提供/缓存 Resource apply proof，不得通过重签延长 deadline、缩短 challenge 或把 deadline 后 PASS 伪装为及时决定。最终 apply 时间/CAS 裁决由 `[RESCROW-TIME-001]` 执行。

`[ESC-MANUAL-001]` MANUAL settlement MUST 在 Resource state=HELD、agreement_policy=RELEASE_OR_REFUND 且 decision_registration_deadline 尚未关闭时，使用绑定完整 contract、ResourceCommandIntentDigest 与 required signer set 的 durable ManualSettlementReceipt，并投影为只含机械字段、以 Manual receipt ID 作 opaque source 的 ResourceBilateralSettlementReceipt；payer/payee 必须签两种 receipt，并在 BilateralAuthorization 中签完整 CommandBodyDigest，随后直接走矩阵中的 `HELD → RELEASED/REFUNDED`，不伪造 DecisionCore。receipt/command/outbox 同事务提交。若已进入 DECISION_REGISTERED/PENDING_CHALLENGE，双方协议只能 REFUND；若已 DISPUTED，只能由 adjudicator 结算。任何 ReceiptId 都不得反向包含最终 body digest，以免与 basis_refs 形成摘要环；`settlement.mode=NONE` 不得创建 Escrow。

`[ESC-HISTORY-001]` RELEASED 是明确 SemanticCheckpoint 下的历史账本决定；之后的撤回或反证不得改写该状态，只能进入独立 dispute、clawback 或 rebate 流程。

`[ESC-KERN-001]` `SEMANTIC_SETTLEMENT` MUST 通过公开 `RESOURCE_ESCROW` feature 使用资源托管，不得要求基础 KABI 理解 Spec、ArtifactSet、TrustPolicy、Criterion、EventId 或自然语言条件，也不得以服务内私有余额替代通用账本状态机。

`[ESC-RIGHTS-001]` Semantic service 只能持有为该 contract 衰减的 resolver/notice capability；payer、challenger 与 adjudicator 的授权必须保留为 basis-specific signature/capability proof，不能合并成 adapter 万能 capability。

## 22. Watchdog 与控制面降权

### 22.1 三层监督

| 层 | 输入 | 允许的默认动作 |
|---|---|---|
| L0 Kernel | time、CPU、Resource、heartbeat、queue、host state | 限流、deadline、挂起、fence |
| L1 System Service | durable Artifact、checker transition、operation result | 建议 pause/review/retry |
| L2 Semantic/Human | 隔离后的内容和任务语义 | 签名建议或人工裁决 |

`[WD-L0-001]` 只有纯结构、不依赖内容理解的限制才能直接触发内核自动动作。

`[WD-SEM-001]` 文本相似度、embedding 或 LLM judgment MUST NOT 成为内核 kill/suspend 的唯一依据。

`[WD-EMPTY-001]` 双空 content MUST 跳过相似度计算；出现新 captured Artifact、tool result 或 checker transition 时，不得仅因文本重复自动挂起。

`[WD-CAP-001]` 语义监督者默认 MUST NOT 持有 kill、扩权或大额 Budget grant capability；它只输出固定 schema 的签名 Recommendation。

`[CTRL-INJECT-001]` 不可信 payload 与控制命令 MUST 使用不同 channel/schema/taint；内容不得被字符串拼接为 control-plane 指令。

`[CTRL-AUTH-001]` Policy controller 对 Recommendation 的执行仍 MUST 独立检查 capability、budget、deadline 和 deterministic rules。

#### 24.1.1 目标编译、TaskPlan 与自动分解

```text
  → Artifact / Receipt / canonical commit
```

`[PLAN-DAG-001]` TaskPlan MUST 使用稳定 TaskNodeId、显式 dependency edge、输入选择器、输出契约、failure/retry/reducer policy 和资源上界。计划修订 MUST 产生新 revision/digest；已经授权或执行的节点保留原 revision，不能被新计划静默改写。

`[PLAN-LAZY-001]` TaskPlan MUST 支持惰性物化。只有 dependency、authorization、Namespace、ResourceContract 和 fanout gate 全部满足的 TaskNode 才可进入 `MATERIALIZING`；未进入当前 materialization window 的节点只保留 durable metadata，不得占用 Process、模型会话、Context pin、工具连接或 active Agent 槽。

`[PLAN-DEPENDENCY-001]` Package、Skill、Tool、Model、Artifact、Topic 和外部服务依赖 MUST 在计划中以 typed selector 声明，并在执行前解析为带版本/generation 的 handle。Dependency Resolver 不得把搜索结果或 `latest` 直接当成已授权依赖。

`[PLAN-TOPIC-001]` Planner MAY 提议创建 Topic/Channel 和订阅关系，但 broker MUST 独立执行 Capability、payer、retention、fanout、queue 和 predicate-cost admission。自动拆分不得产生无人承担费用或无界订阅者集合的 Topic。

`[PLAN-CHANGE-001]` 用户 MAY 在可信 Task Space 中手工增加、删除、暂停、合并、重排或替换尚未执行的 TaskNode。改变目标语义、授权对象、不可逆副作用、成本上界、deadline 或验收条件的修改 MUST 重新编译并重新授权；纯 placement、显示顺序或不扩大权力的资源降级 MAY 使用受限 ControlCommand。

`[PLAN-OVERRIDE-001]` 自动规划和手工规划 MUST 收敛到同一 TaskPlan/TaskNode schema、AdmissionPlan、Capability 和 Receipt，不得维护一个绕过系统约束的“高级自然语言路径”或“管理员拖拽路径”。

### 24.2 同意与可信 UI

`[TUI-CONSENT-001]` 权限确认 MUST 由 Trusted UI 渲染真实 Application/Principal、目标、purpose、持续时间和成本；不可信应用不得伪造系统提示。

`[TUI-CHOOSER-001]` 文件/Artifact chooser MAY 发现用户可见对象，但只向 Application 返回用户明确选择后的 scoped capability。

`[TUI-EXT-001]` UI Surface/Package schema MUST 为本地化、可访问性、多模态、通知、深链接和内容类型关联保留版本化扩展。

## 25. Task Space 与系统体验

`[TASK-SPACE-001]` NLOS MUST 提供用户可见的持续 Task Space，展示运行、等待授权、暂停、失败、完成和 disputed 的任务。

`[TASK-STATE-001]` Task 状态至少包括：

```text
DRAFT → PROPOSED → WAITING_CONSENT → AUTHORIZED → RUNNING
                                               ↔ WAITING_INPUT
                                               ↔ WAITING_RESOURCE
                                               ↔ WAITING_NETWORK
                                               ↔ SUSPENDED
                                               ↔ RECOVERING
                                               → CANCELLING
                                               → COMPLETING

CANCELLING → CANCELLED | PARTIAL | FAILED
COMPLETING → COMPLETED | PARTIAL | DISPUTED | FAILED
```

`[TASK-VIS-001]` 用户 MUST 能查看每个 Task 的 Application、Process、权限、预算、输入、输出、provenance 和可取消性。

`[TASK-NOTIFY-001]` 后台 Task 的重要状态变化 MUST 通过 Notification service 可见，不依赖原聊天窗口保持打开。

`[TASK-SHELL-001]` 阶段 A/B MUST 提供薄的开发者 Shell 和最小 Task Space；完整桌面不得等到所有分布式能力完成后才首次出现。

`[TASK-REOPEN-001]` 终态 Task 不得原地回到 RUNNING。同一 immutable obligation 的失败重试创建新 TaskAttempt；Intent/Spec、授权目标或义务变化时创建新 Task generation 或 refined Task。两者均 MUST 保留与旧 Attempt/Receipt 的关系。

`[TASK-STATE-002]` Task 的 RUNNING/COMPLETED/PARTIAL 是其 TaskHead、TaskAttempt 和非 detached child group 的聚合状态；单个 AgentInstance/Process 退出不得直接把 Task 写成终态。

### 25.1 海量 Agent 的任务隔离与语义一致性

NLOS 不把“Agent”直接类比成一种新的内核线程。不同对象承担不同职责：

| 现代系统类比 | NLOS 对象 | 被隔离/协调的内容 |
|---|---|---|
| Process / sandbox | Process + IsolationUnit | CPU、memory、address space、FD、network、故障与强杀 |
| thread / actor invocation | AgentInstance | AgentRole 的一次执行与消息身份；共享 Process 时只有 thread-like 隔离 |
| process group / cgroup / structured-concurrency nursery | TaskGroup + ResourceGroup | child admission、资源、取消、失败传播和 bulkhead |
| job execution generation | TaskAttempt | 一次执行的输入快照、Capability、Budget、输出 staging 与提交权 |
| durable job/order | Task | 用户可见义务、历史、重试、验收与长期状态 |
| sandbox / protection domain | IsolationDomain | Namespace、Capability、资源、data、egress、secret、cancel 与 failure domain |
| address-space/read snapshot | TaskSnapshot + Context + Namespace | 一个 attempt 能读到的对象、revision 与语义 checkpoint |
| file/IPC/shared memory | Artifact + Channel + SemanticEvent | 显式共享数据、消息与证据；没有隐式共享“思维” |
| transaction/write set | TaskWriteSet + TaskCommitReceipt | 共享 Artifact head 与 Task 结果的冲突检测/原子提交 |

因此，**任务隔离可以在 ENFORCED profile 下成为进程级强保证；语义一致性是对象级 consistency contract，不是“让所有模型产生同一答案”。**

这些 consistency mode 不是单一强弱梯度：

- `PRIVATE`：仅 attempt 可寻址，不进入共享面；
- `IMMUTABLE_SNAPSHOT`：读取固定 revision/checkpoint，保证可重放输入；
- `CAUSAL`：观察到一个事件时也观察其已声明/captured 的前因；
- `CONVERGENT`：append-only/CRDT 在分区恢复后收敛，不承诺即时同值；
- `SERIALIZABLE_DOMAIN`：声明的单一事务域内提交等价于某个串行顺序；
- `LINEARIZABLE_AUTHORITY`：Capability、Ledger、Task winner、Package head、Gate decision 等少数权威决定存在唯一提交点。

`[CONS-DECL-001]` 每个 SABI 方法/object MUST 声明 requested consistency、实际 achieved consistency、authority/control epoch 与 snapshot/checkpoint。未显式设置 `allow_downgrade=true` 并列出 `accepted_lower_modes` 时，不可满足必须返回可区分错误；允许降级时结果必须使用不同的 non-authoritative 类型/状态，并携带 use restrictions，不能被 Capability、Resource、Task commit、Gate 或不可逆 effect API 接受。

`[CONS-CTRL-001]` EVENTUAL/CONVERGENT 的 index、search、projection、metric 或 recommendation MUST NOT 单独驱动 Capability、ResourceAccount、TaskHead commit、Package update 或不可逆 Action。

`[CONS-SEM-001]` NLOS 的强语义承诺限于：给定已冻结的 SemanticEvents、evaluator output Receipts、TrustPolicy、identity/key snapshot、resolver/aggregation algorithm digest、canonical iteration rules 与 SemanticCheckpoint，确定性 resolver 可重放相同 `disposition + derivation`。它不承诺重新生成字节相同的带时间/nonce/signature Decision Receipt，不承诺随机模型输出一致、结论为真或所有 Agent 观点收敛。

`[CONS-SCOPE-001]` LINEARIZABLE/SERIALIZABLE 保证 MUST 声明 authority object/shard/transaction domain；v0.5 不建立跨 Cell 的全局总序。跨 shard 使用 causal/vector checkpoint、durable outbox/saga 和显式 PARTIAL/UNCERTAIN。

`[CONS-CONVERGE-001]` 对象只有在类型 schema 明确声明 deterministic merge digest、结合/交换/幂等条件、membership、tombstone、冲突暴露、GC 与 version-vector 语义，并通过相应 conformance 时，才能 advertised CONVERGENT；普通 mutable object、任意 LLM reducer 或未定义 merge 的 Blackboard 必须产生 Conflict，而不能借用该标签。

```text
TaskAttempt:
  CREATED → ADMITTED → RUNNING ↔ WAITING
                           ↓
                        SEALING → SEALED → VALIDATING
                                             ├→ CONFLICTED
                                             └→ READY_TO_COMMIT
                                                  ├─CAS loss→ SUPERSEDED
                                                  └─CAS win→ COMMIT_PERMITTED
                                                                  ↓
                                                               EFFECTING?
                                                                  ↓
                                                               FINALIZING
                                                                  ↓
                                                               COMMITTED

  任一 pre-permit state → CANCELLING → CANCELLED | FAILED
  post-permit host/effect uncertainty
    → UNCERTAIN → RECONCILING → COMMITTED | PARTIAL | FAILED

TaskGroup:
  CREATED → OPEN → SEALED → QUIESCING → COMPLETED
              │         └────────────→ FAILED | PARTIAL
              └→ CANCEL_REQUESTED → CANCELLING
                                     → CANCELLED | PARTIAL
  host/effect uncertainty → UNCERTAIN → RECOVERING
                                       → QUIESCING | PARTIAL
  任一非终态 integrity failure → QUARANTINED

IsolationDomain:
  ALLOCATING → ACTIVE → QUIESCING → FENCED → RECLAIMING → CLOSED
                    └─integrity uncertainty→ QUARANTINED
                                             → FENCED | CLOSED

CancellationScope:
  ACTIVE
    → CANCEL_REQUESTED(cancel_epoch++)
    → DISPATCH_FENCED
    → DRAINING | TERMINATING
    → CANCELLED | PARTIAL | EFFECT_UNKNOWN
```

`[TASK-ATTEMPT-001]` 每次 retry、并行候选或 refinement MUST 使用独立 TaskAttemptId/generation 和 immutable TaskAttemptContract。host-loss recovery MAY 保留 AttemptId，但 MUST 创建新 Process/AgentInstance/IsolationDomain incarnation 并 fence 旧 incarnation。旧 attempt 的 Capability、ResourceAllocation、callback 和 commit token 必须按 generation fence；不得通过重写旧记录制造“同一次成功”。

`[TASK-AGENT-001]` AgentInstanceId/incarnation MUST 由 Task/Process authority 在 BirthDecision 中分配并注册，调用者字符串不能成为身份；它具有 `CREATED → READY → RUNNING ↔ BLOCKED → QUIESCING → SUCCEEDED|FAILED|CANCELLED` 生命周期，只有匹配 BirthDecision 的 Process 可进入 READY。host loss 进入 LOST/RECOVERING 并递增 incarnation。共享 Process 的 AgentInstance 只能声称 thread-like fault/security isolation；互不信任或要求独立强杀的实例必须使用不同 Process。

`[TASK-ISO-001]` 一个 TaskAttempt 的强隔离面 MUST 同时包括 IsolationDomain 的 Namespace、Capability root、ResourceGroup、ResourceAccount、TaskSnapshot、Channel endpoints、artifact/semantic staging、Process/AgentInstance generation、secret 与 Device/egress policy。未显式 delegate/import 的 sibling/parent/child 对象不可寻址；仅隔离 prompt 或聊天记录不得称为 task isolation。

`[TASK-ISO-002]` 跨 IsolationDomain 只能通过 typed Channel、不可变 Artifact、显式 SemanticEvent admission 或 Capability delegate/share 传递数据和权力，并产生 Receipt。共享内存只允许在显式 thread-like domain；不同 strong domain 不得通过可变 Blackboard head、模型 session、KV/tool cache 或 scratchpad 暗中共享。

`[TASK-ISO-003]` sibling 默认不得继承彼此的 Capability、Reservation、mutable head、model session/cache 或私有 scratchpad。跨 attempt cache 复用必须按 IsolationDomain/taint/authorization 分区并可证明清理；否则加入 `PROVENANCE_INCOMPLETE` 和 isolation downgrade。

`[TASK-ISO-004]` IsolationDomain 进入 FENCED 后同 generation 不得回到 ACTIVE；stale domain/Process/Agent incarnation 的 message、result、callback、Capability、Driver invoke 和 commit MUST 拒绝。

`[TASK-ISO-005]` 声明 `STRONG_ATTEMPT_ISOLATION` 的每个并行 TaskAttempt MUST 使用独立 DEDICATED_ATTEMPT child IsolationDomain/generation，不得与 sibling 共享 staging、mutable Channel membership、model session/cache、secret 或 provider tenant。共享同一 domain 只可标记 SHARED_THREAD_LIKE，并在 Task Space/Receipt 中降低 fault/security/provider-isolation 声明。

`[TASK-SNAPSHOT-001]` attempt 开始前 MUST 冻结 TaskSnapshot。`PINNED` 执行期间不得把 `latest`、漂移的 TrustPolicy/Settings/Package 或 mutable Context 偷换进读集；`EXPLICIT_EPOCH_ADVANCE` 必须创建新 snapshot id、记录差异并使后续 Action/Receipt 绑定新 snapshot，旧决定保持可重放。

`[TASK-SNAPSHOT-002]` TaskSnapshot MUST 是覆盖当前 TaskHead、durable_effect_history_root/retry_fence_epoch、Artifact revisions、SemanticCheckpoint、identity/key trust、settings、package/schema/spec、group membership 与 causal dependencies 的 causal-closed consistent cut，并取得 durable TaskSnapshotReceipt。Receipt 必须绑定同一 effect history/fence、builder/version、per-authority signed checkpoints、dependency closure root、resolver/canonical iteration digest、achieved consistency、durability 与 authority signature；只有 snapshot digest 而无该证明不能用于授权、Gate 或 canonical commit。无法构造时必须失败，或显式标记 `MIXED_SNAPSHOT/NON_SETTLEABLE`。

`[TASK-SNAPSHOT-003]` 不同 TaskSnapshot 的输出不得静默合并；必须 rebase、重新验证或生成结构化 ConflictReceipt。Search/embedding/eventual index 只发现候选，权威 commit 必须回到 snapshot 中的 revision/checkpoint。

`[CTX-SNAPSHOT-001]` Task Context MUST 绑定 TaskSnapshotId 和精确 source revisions；refresh 创建新 Context revision，并在读集或授权语义变化时创建新 TaskSnapshot/Attempt。

`[TASK-SEM-001]` Semantic consistency 的可承诺内容遵循 `[CONS-SEM-001]`：在冻结事件/evaluator receipts、policy/snapshot、resolver digest 和 canonical iteration rule 下，确定性 resolver 可重放相同 disposition/derivation。系统 MUST NOT 承诺重建同一个签名 Decision、相同模型输出、所有 Agent 持有相同信念或存在全局真值。

`[TASK-SEM-002]` Agent 的结论只能以带 issuer/lineage/taint 的 SemanticEvent 或 Artifact proposal 跨 attempt 传播；接收方必须通过 capability、scope、Admission 和自身 TrustPolicy。共享可变 prompt、隐藏 session memory 或未记录 provider state 不得成为权威协调通道。

`[TASK-WRITE-001]` attempt 输出在获得 CommitPermit 前 MUST 保持在 staging namespace；非 permit holder 不得修改 canonical Artifact/Task/Blackboard head、向公共 semantic scope admission 或触发不可逆外部 effect。

`[TASK-WRITE-002]` TaskWriteSet MUST 绑定 AgentInstance/incarnation、Attempt、IsolationDomain generation、TaskSnapshotReceipt、expected TaskHead、durable effect-history root/retry-fence epoch、IntentSpec、producer ControlDomain、TaskGroup membership root/policy、完整 provenance、精确 read revisions 以及 selector/predicate/range tokens；声称 SERIALIZABLE 时必须检测 phantom 与 write-skew。

`[TASK-WRITE-003]` semantic staging item MUST 声明 target scope、required durability 和预期 admission policy。Task 只有取得每个 required event 的 AdmissionReceipt + DurabilityReceipt 后才能以 COMMITTED 发布；跨 Semantic transaction domain 时，尚未完成的 publication 只能令 Task 处于 FINALIZING/PARTIAL/PENDING_PROJECTION，不能把 outbox intent 当成 durable public SemanticEvent。

`[TASK-COMMIT-001]` CommitPermit MUST 包含上列 PermitId/idempotency、Attempt/Process/Agent/IsolationDomain generation/fence、expected TaskHead、durable effect-history root/retry-fence epoch、membership root/policy、write/effect-set root、authority term/lease、participant registry generation/root、control/cancel/permit epoch、expiry 和 signature；这些 head/history/fence 字段必须与 TaskAttemptContract、TaskSnapshot/Receipt、TaskWriteSet 和当前 TaskControlRecord 逐位相同。TaskAuthority 必须执行线性化 CAS：只有 `active_permit` 为空，或其状态为 CLOSED 且 `outstanding_effect_root` 为空、没有 quarantine tombstone 时才能签发新 permit；同 key/同 bytes 返回原 permit。CAS loser 进入 SUPERSEDED，校验失败进入 CONFLICTED。

`[TASK-COMMIT-002]` permit holder finalize 时 MUST 再验证 TaskSnapshotReceipt/read set、Artifact heads、Capability、Budget/fence、authority lease/control/cancel/permit epoch、participant registry binding 与 membership root。无 PermitAdoption 时 registry generation/root 必须与 CommitPermit 逐位相同；跨 term/control epoch adoption 时，PermitAdoptionReceipt 必须逐位绑定原 Permit 的 registry，证明 `exact_fenced_participant_root` 完整覆盖原 root、current root 来自对应 TakeoverReceipt/new assignment，且 registry_coverage_proof 无遗漏。它必须从 `effect_set_root` 枚举完整、按 `effect_seq` 唯一且无洞的 EffectSlot 集合；每个 planned slot 都必须具有唯一已知终态 `NO_EFFECT`、`CONFIRMED_NO_EFFECT` 或 `EFFECT_CLOSED` 及权威 Receipt，任何 `PERMITTED`、`DISPATCHED`、`RECONCILING` 或 `EFFECT_UNKNOWN` 都禁止关闭 permit。`outcome=COMMITTED` 还要求每个 `required=true` slot：无条件项取得满足 `success_criteria_digest` 的 EFFECT_CLOSED Receipt；带 `required_condition_digest` 的条件项必须取得同样成功，或取得绑定原 TaskSnapshot/条件 digest 的 `CONDITION_NOT_APPLICABLE` 证明。普通 NOT_SELECTED/CANCELLED/EXPIRED/POLICY_SKIPPED 以及事后 CONFIRMED_NO_EFFECT 都不能满足 required slot；`satisfied_required_effect_count` 必须逐槽重算并精确等于 `required_effect_count`。TaskCommitReceipt 必须列出 input snapshot receipt、membership、read/write roots、Artifact/Semantic publication receipts、最终 slot root、计数、每槽 Receipt、durable effect-history root、cost、冲突检查与新 TaskHead；仅在 effect 已知闭合时 active permit 才能关闭。required 未满足且已经发生 effect 时必须按 `[TASK-RETRY-EFFECT-001]` 前进 history；只有全部 planned/pre-permit action 都可证明未发生 effect 时，才可写 TaskPermitClosureReceipt 并保持 TaskHead 不变。绝不能把 skip 写成 COMMITTED。

`[TASK-COMMIT-003]` permit expiry、worker crash、cancel、authority takeover 或 ACK 丢失本身不得清除 active_permit。跨 epoch 收口只能由当前 authority 写 `PermitAdoptionReceipt`；它必须绑定 original/current registry、exact takeover fence root 与 coverage proof，只授权读取旧 participant 的权威 effect 状态、补写 NoEffect/effect-closed 证明或创建 quarantine，不授权新 EffectPermit、dispatch、新 effect、participant 注册或更改原 proposal。只有全部 slot 按 `[TASK-COMMIT-002]` 闭合后，adopted permit 才能产生 TaskCommit/PermitClosure Receipt 并 CLOSED；任一 `EFFECT_UNKNOWN` 必须把 active permit 保留为不可复用的 QUARANTINED tombstone，TaskHead 不前进、不得选择新 winner。replay 原 PermitId 必须返回同一 lifecycle/result。

`[TASK-TXN-001]` 多 Artifact 的原子可见性只能在声明的 transaction_domain 内承诺 SERIALIZABLE；跨 Ledger/Artifact/Semantic/外部系统使用 durable prepare/outbox/saga，并以 PARTIAL/UNCERTAIN + compensation Receipt 暴露。Semantic append 只增不改，CRDT merge 只解决结构冲突，不判定语义真值。

`[TASK-CONFLICT-001]` commit conflict MUST 机器可读地区分 stale Task/Artifact head、read/write、predicate/phantom、Capability revoked、Budget/fence、cancel epoch、membership generation 和 external effect uncertainty；禁止用单一 `FAILED` 隐藏可安全重试条件。

`[TASK-EFFECT-001]` 每个 EffectPermit MUST 绑定 CommitPermit/permit_epoch、`effect_set_root` 中唯一的 effect_slot_id/effect_seq、跨 Attempt 稳定的 LogicalEffectId、retry_fence_epoch、idempotency identity、Action proposal、Operation/Driver/Reservation、Process/Domain incarnation、TaskAuthority term、participant registry generation/root、control/cancel epoch、一次性 dispatch token 与有效期。签发必须以 TaskControlRecord CAS 将该 slot 从 PLANNED 变为 PERMITTED，并更新 issued/outstanding roots；Driver/gateway 在真实副作用前在线校验当前 head/history/fence、epoch 和 registry binding，再原子消费 token并将同一 slot 变为 DISPATCHED。cancel 后迟到的旧 permit必须拒绝；已消费 token 则按真实 effect Receipt reconcile，不能伪装为未执行。

`[TASK-EFFECT-ID-001]` LogicalEffectId 与 idempotency_identity_digest MUST 分别由上列完整 Descriptor/LogicalEffectId 和固定 SHA-256 domain-separated 公式计算；`stable_action_slot` 来自 immutable IntentSpec/Task contract，target 使用权威稳定对象身份，descriptor 禁止包含 AttemptId、ActionId、OperationId、Process incarnation 或随机 nonce。gateway MAY 从托管 secret + LogicalEffectId 确定性派生外部 provider key，但所有 Attempt 必须得到同一 identity commitment。初始 TaskHead 的 history 是固定公式对空 entries 的 digest，retry_fence_epoch=0。之后 TaskEffectHistoryEntry 按从 1 开始、严格递增且无洞的 effect_history_seq canonical 排序，TaskEffectHistoryRoot 按固定公式重算；同一 TaskHead CAS 必须同时提交新 history root 和 retry fence。改变 ActionId/OperationId、retry、hedge 或换 Agent 不得创造新的 LogicalEffectId；真正的新业务副作用必须来自新 Intent/contract 中显式不同的 stable action slot。

`[TASK-EFFECT-002]` `effect_set_root` MUST 承诺完整、按 effect_seq 稳定排序且编号稠密的 planned slot 集；每个 slot 独立经历 `PLANNED → PERMITTED → DISPATCHED → EFFECT_CLOSED|EFFECT_UNKNOWN`，或在可证明 dispatch token 从未消费时由 TaskNoEffectReceipt 进入 NO_EFFECT。TaskNoEffectReceipt 的 CONDITION_NOT_APPLICABLE 只有同时匹配预先绑定的 `required_condition_digest` 与原 TaskSnapshot 上的权威 false proof 才能满足条件 required obligation；其他 no-effect reason 只证明没有启动副作用。执行次序由显式 `dependency_slots` 约束；没有依赖的 slot MAY 并行，系统不得以单个 high-water 或 permit 全局状态替代逐槽证明。每次状态转换必须 CAS `effect_slot_state_root` 并重算 required/satisfied/terminal count 与 issued/dispatched/closed/outstanding roots。

`[TASK-EFFECT-003]` `EFFECT_UNKNOWN` 不是成功、失败或取消的同义词，也不是可关闭 permit 的 effect 终态。它必须产生 TaskEffectQuarantineReceipt，使 active permit 进入 QUARANTINED，并保留冲突 target、unknown slot 和 participant fence 证明；行政层 MAY 把 TaskAttempt/TaskGroup 标记 PARTIAL/EFFECT_UNKNOWN，但不得前进 canonical TaskHead、释放冲突防护或签发另一 winner。后续只能由当前 authority 先签 PermitAdoptionReceipt，将 active permit/对应 slot CAS 为 RECONCILING，再消费 gateway/provider 权威 closure proof 写 TaskEffectReconciliationReceipt，并把 slot 变为 EFFECT_CLOSED、CONFIRMED_NO_EFFECT 或重新 EFFECT_UNKNOWN。这里的 CONFIRMED_NO_EFFECT 证明外部效果权威未发生，不能复用只证明 dispatch token 未消费的 TaskNoEffectReceipt；若仍 unknown，permit 回到 QUARANTINED。全部 slot 闭合后才可按 `[TASK-COMMIT-002]` 收口，且 required slot 的 CONFIRMED_NO_EFFECT 不支持 COMMITTED。

`[TASK-RACE-001]` 多个并行 TaskAttempt MAY 计算候选结果，但 canonical output MUST 由 CommitPermit 选择。只有 permit holder 可从 TaskWriteSet 中已绑定的 planned_action 获得一次性 EffectPermit；产生的 ActionReceipt 必须匹配该 slot，不能改变已许可 proposal。不可逆副作用开始后不得把 permit 转给另一 Attempt，直至原 Operation reconcile。若业务明确允许 pre-permit 投机副作用，每个 Action 必须单独预授权、幂等/可补偿并写入 `pre_permit_action_receipts` 与 durable effect history；它们同样受 `[TASK-RETRY-EFFECT-001]` 约束，`EFFECT_UNKNOWN` 禁止盲重试。

`[TASK-RETRY-EFFECT-001]` TaskPermitClosureReceipt 保持 TaskHead 不变并允许重新竞争的充要 effect 条件是：全部 planned slot 都为 NO_EFFECT/CONFIRMED_NO_EFFECT，且每个 `pre_permit_action_receipts` 都有权威 no-effect proof；任何 EFFECT_CLOSED、部分发生或已知 pre-permit effect 都禁止该路径，也不得标为 CANCELLED。此时必须写 TaskCommitReceipt 的 PARTIAL_EFFECT/FAILED_AFTER_EFFECT，追加含 LogicalEffectId 的 TaskEffectHistoryEntry，令 mandatory retry_fence_epoch 严格递增，并在同一 CAS 前进 TaskHead.commit_seq/effect-history root/fence epoch，或保持 permit 未关闭。后续 TaskSnapshot、AttemptContract、WriteSet 和 CommitPermit 必须继承新 root/epoch；对历史中相同 LogicalEffectId，gateway 只能以原 idempotency identity 回读原结果，或在权威 compensation proof + 显式重新授权后执行，不得因新 Attempt/ActionId/OperationId 再次启动不可逆效果。

`[TASK-GROUP-001]` TaskGroup MUST 构成无环父子树，并绑定 child admission、ResourceGroup、Namespace delegation、failure policy 与 maximum fanout/depth。父级取消默认向全部非终态后代传播；child 失败是 fail-fast、collect、isolate 或 escalate 必须由 group policy 预先决定。

`[TASK-GROUP-002]` membership 变更 MUST 以 content-addressed member set/root + generation CAS，并产生列出 member type/id/generation/ControlDomain 的 Admission/Removal Receipt；child BirthDecision 与加入 membership 必须同事务，或消费同一 prepared membership receipt。只有 OPEN 可新增 child，SEALED 后旧 generation/root 的结果不得计入 ALL/ANY/QUORUM/REDUCE。AttemptContract、TaskSnapshot/Receipt、TaskWriteSet、CommitPermit 与 TaskCommitReceipt 必须绑定同一 membership generation/root 和 group_policy_digest。单纯 LOST 只能使 child 与父组进入 UNCERTAIN/RECOVERING；只有该 incarnation 的 fence barrier 加上全部 EffectSlot/Operation 的 closed-or-quarantined proof 才满足 group quiescence。存在 quarantine 时父组最多以 PARTIAL/EFFECT_UNKNOWN 行政终结，不能标记 COMPLETED。

`[TASK-GROUP-003]` QUORUM 只是工作流完成策略；只有按 TrustPolicy/ControlDomain 去重并满足独立性时才能解释为认识论 quorum。REDUCE 必须绑定 immutable reducer digest；非结合交换 reducer 按稳定 ID 排序，LLM reducer 只能产生带 provenance 的 Judgment/Receipt。分歧候选必须保留，不得 arrival-order/last-writer-wins。

`[TASK-DETACH-001]` detached child MUST 创建新的 TaskGroup、ResourceGroup/Account、deadline、supervisor 与可见 owner，并消费显式 DETACH capability；禁止用“后台继续”逃逸父级取消、预算或用户 Task Space。

`[TASK-CANCEL-001]` 每个 TaskGroup、TaskAttempt 与 AgentInstance MUST 属于 CancellationScope 树；parent cancel 默认传播到全部非 detached child。

`[TASK-CANCEL-002]` cancellation 是结构化状态转换，不是文本消息。系统 MUST 先在 TaskControlRecord 原子递增 cancel_epoch，封锁新 child、Operation、Commit/EffectPermit、I/O 和 delegation，再传播 io_cancel/Driver cancel、等待或 fence effects、finalize 资源，最后使 group QUIESCENT；无法证明关闭的 effect必须记录 PARTIAL/EFFECT_UNKNOWN。

`[TASK-CANCEL-003]` cancel、CommitPermit issuance、每个 EffectSlot 的 permit/dispatch CAS 和 TaskCommit MUST 在同一 TaskControlRecord 的 control/cancel/permit epoch 上线性化：cancel 先提交则禁止新 permit/dispatch，并只对可证明 token 未消费的 slot 写 TaskNoEffectReceipt；effect token 先消费则按真实 effect/result reconcile/finalize。TaskAttempt 只有在全部 planned/pre-permit action 都有权威 NO_EFFECT/CONFIRMED_NO_EFFECT 证明时，才可用 TaskPermitClosureReceipt(CANCELLED_BEFORE_EFFECT/FAILED_BEFORE_EFFECT) 原子关闭 permit 且保持 TaskHead 不变。任一已发生 effect 必须进入 PARTIAL_EFFECT/FAILED_AFTER_EFFECT 并按 `[TASK-RETRY-EFFECT-001]` 持久前进 history；任一 unknown 则 active permit 保持 UNCERTAIN/QUARANTINED，Task MAY 以 PARTIAL/EFFECT_UNKNOWN 行政终结，但不能关闭 permit、前进 TaskHead 或把未知副作用改名为取消/失败成功。

`[TASK-PROVIDER-001]` ENFORCED task isolation 若使用远程模型/provider，MUST 记录其 tenant/session/cache/data-retention 隔离保证与 attestation。共享隐藏状态、训练保留或跨租户 cache 无法排除时，Receipt 必须标记 `PROVIDER_ISOLATION_UNVERIFIED`，系统不得把本地 sandbox 宣称扩大为端到端语义隔离。

`[TASK-SCALE-001]` 海量 Agent 调度 MUST 按 Workspace/TaskGroup/Cell 分片：授权和准入使用本地 handle/generation，跨 Cell 协调用 causal/vector checkpoint、Quota/CapacityLease 和 fencing。全局搜索/索引 MAY 最终一致，但不得位于每次 spawn、message 或 commit 的同步关键路径。

`[TASK-SCALE-002]` 系统 MUST 用 bounded fanout、层级 supervision、bulkhead ResourceGroup、per-group queue 和 failure budget 限制故障放大。quorum/independence 按 ControlDomain 而非 Agent/Process 数量计数，禁止通过复制海量同源 Agent 伪造共识。

`[TASK-VIS-002]` Task Space MUST 区分 Task 与各 TaskAttempt，显示 input snapshot、consistency mode、isolation/enforcement profile、resource group/account、当前 Cell、winner/commit、冲突、取消传播和 provider isolation 状态；“1000 个 Agent 正在思考”不能替代这些可核查状态。

### 25.2 PID 级逻辑 Agent 执行架构

NLOS 的规模目标是管理接近现代系统 PID 空间量级的**逻辑执行实体**，而不是让相同数量的模型调用、宿主进程或 Context 同时驻留。系统必须持续区分：

```text
logical_nodes       # TaskPlan 中持久存在的 TaskNode
materialized_nodes  # 已创建 TaskAttempt/Process/AgentInstance 的节点
runnable_instances  # 当前满足依赖并已获得资源的实例
runnable_fibers     # 已 READY、等待用户态 runtime dispatch 的 Fiber
active_instances    # 正在 CPU/GPU/Driver 上执行或持有稀缺槽位的实例
resident_contexts   # 当前占用内存/KV cache/pinned Context 的工作集
```

实现不得用“已登记 Agent 数”冒充并发执行能力，也不得把 logical node、AgentInstance、Process、IsolationUnit 和 OS PID 统计混成一个数字。

#### 25.2.1 驻留与惰性物化

```text
ResidencyClass =
  METADATA_ONLY   # 只有 TaskNode/AgentRole/依赖和资源声明
  COLD            # snapshot/artifact 位于持久存储
  WARM            # 索引、代码或部分 Context 可快速恢复
  HOT             # 已物化 Process/AgentInstance，等待运行
  RUNNING         # 当前占用执行槽
  PINNED          # 因不可迁移资源/副作用而暂不可回收
```

```text
TaskNode execution:
DECLARED
  → BLOCKED_DEPENDENCY
  → ELIGIBLE
  → WAITING_AUTHORIZATION | WAITING_RESOURCE
  → MATERIALIZING
  → ACTIVE (residency=HOT; runtime=RUNNABLE|RUNNING|BLOCKED)
  → CHECKPOINTED
  → EVICTED (residency=WARM|COLD) | COMPLETED | FAILED | CANCELLED

EVICTED → REHYDRATING → MATERIALIZING
```

`[SCALE-LOGICAL-001]` 未物化 TaskNode/AgentRole binding MUST 只占有有界 durable metadata；它不得预占 OS PID、模型 session、工具连接、pinned Context、文件描述符或 active concurrency slot。

`[SCALE-MATERIALIZE-001]` Materialization Controller MUST 根据 dependency readiness、priority、deadline、ResourceContract、当前 pressure、locality 和 materialization window 创建有限数量的 TaskAttempt/Process/AgentInstance。窗口缩小时必须停止新物化，并按 policy checkpoint/evict 可恢复实例。

`[SCALE-IDENTITY-001]` eviction 不得把旧 AgentInstance/Process incarnation 伪装为仍在运行。rehydrate 必须使用同一 TaskNode/TaskAttempt 的 fenced recovery 或新 Attempt，并按第 8、25.1 节规则生成新 Process/AgentInstance incarnation、拒绝旧 callback/handle。

`[SCALE-CONTEXT-001]` Context Residency Controller MUST 把 Artifact 本体与派生 Context/KV/embedding cache 分离，记录 resident bytes、pin reason、rebuild cost、last-use、deadline 和 reclaim class。pressure 下默认先回收可重建 cache，再 checkpoint/evict Agent 工作集，最后才 kill；不得为了“换页”删除 Artifact 或改变冻结 TaskSnapshot 的逻辑读集。

`[SCALE-PIN-001]` PINNED 不是永久豁免。每个 pin MUST 绑定 ResourceAllocation、owner、reason、上界、expiry/renewal 和 release/fence procedure；无法回收的远程 session、Device 或副作用必须进入独立 bulkhead，并降低实现可声明的规模等级。

#### 25.2.2 Global → Cell → Worker 分层调度

```text
Global Control Scheduler
  └─ Tenant/Workspace/Application policy and global admission
      └─ Cell Scheduler
          └─ TaskGroup/ResourceGroup queues and failure domains
              └─ Worker Scheduler
                  └─ Process/AgentInstance/ExecutionFiber runnable queues
                      └─ CPU/GPU/model/Driver execution slots
```

| 层级 | 主要决策 | 不得承担 |
|---|---|---|
| Global | tenant fairness、Application/Task 优先级、Cell placement、全局 quota lease | 每个 token/chunk 的热路径出队 |
| Cell | 本地 capacity、TaskAuthority、bulkhead、TaskGroup queue、跨 Worker placement | 全局扫描所有 Agent |
| Worker | runnable Process/AgentInstance/Fiber、context affinity、batch、local backpressure | 修改全局授权或 Task canonical state |
| Driver/Runtime | coroutine/event loop、Activation、provider slot、GPU batch、tool connection、stream scheduling | 自授 Budget/Capability 或跳过 admission |

`[SCHED-HIER-001]` 每个调度决定 MUST 由最近拥有足够权威和资源视图的 SchedulerDomain 完成。spawn、wake、message 和 dispatch 的正常路径不得同步扫描全局 Agent 集合、获取全局锁或依赖全局严格总序。

`[SCHED-QUEUE-001]` 每个 SchedulerDomain MUST 使用有界 per-ResourceGroup queue，并公开 requested/effective priority、deadline class、weight、queue position range、throttle reason 和 starvation age。实现 MAY 使用 priority queue、DRR、WFQ、EDF、work stealing 或组合策略，但 MUST 保持父级 hard quota、fair-share 和 cancellation fence。

`[SCHED-STEAL-001]` work stealing/跨 Worker 迁移只能移动可迁移 TaskNode/Attempt；必须检查 Namespace、secret、Context locality、Device affinity、provider tenant、TaskAuthority 和 IsolationDomain fence。窃取不得复制 Capability、Reservation、EffectPermit 或 active Device lease。

`[SCHED-BATCH-001]` 模型或工具请求 MAY 按 provider/model/context-prefix/latency class 批处理，但 batch 只是物理优化。每个成员仍保留独立 Operation、Budget、cancel、deadline、provenance、usage 和 Receipt；一个成员失败不得把其他成员成本或副作用归错。

`[SCHED-BACKPRESSURE-001]` 下游模型槽、Topic、Context residency、存储或 Driver 饱和时，pressure MUST 沿 Worker → Cell → TaskGroup → Planner 反向传播，降低 materialization window 或令节点进入 WAITING_RESOURCE；系统不得继续无界创建“等待中的 Agent”掩盖拥塞。

#### 25.2.3 可声明的规模能力

```text
ScaleProfile {
  profile_id
  hardware_and_host_profile
  max_logical_nodes
  max_materialized_instances
  max_runnable_instances
  max_runnable_fibers
  max_host_threads
  max_active_model_operations
  max_resident_context_bytes
  max_topic_subscriptions
  metadata_bytes_per_cold_node
  scheduler_transition_rate
  recovery_scan_bound
  p50_p95_p99_targets
  overload_and_degradation_policy
  evidence_ref
}
```

`[SCALE-PROFILE-001]` 实现只能按经 benchmark 验证的 ScaleProfile 声称 `10K_LOGICAL`、`100K_LOGICAL`、`1M_LOGICAL` 或更高能力。profile MUST 同时披露 logical/materialized/runnable/active/resident 数量，禁止用冷 metadata 数量宣传为同时推理数量。

`[SCALE-PID-001]` 单机路线的明确目标是达到当前 PC 可承载的 PID 空间同量级逻辑 TaskNode/AgentRole 管理能力，同时将 materialized、runnable、active 和 resident working set 限制在实时资源允许的范围内。该目标属于待验证 requirement，不是 v0.5 已实现的性能事实。

`[SCALE-DEGRADE-001]` 超过 ScaleProfile 时系统 MUST 通过拒绝新 admission、缩小物化窗口、降低 QoS、checkpoint/evict、延迟 fanout 或请求扩容而有界退化；不得 OOM、递归崩溃、丢失 canonical Task 状态或绕过预算。

### 25.3 多层手动调度与系统控制

自然语言是首要界面，但用户必须像使用 Windows Task Manager、macOS Activity Monitor、System Settings 和应用窗口一样，在每个授权层级直接观察和控制系统。手工操作不是调试后门；它与自然语言命令、CLI、GUI 和自动化 API 共用同一类型化控制协议。

```text
ControlCommand {
  control_command_id
  issuer_principal
  source: TRUSTED_GUI | NL_SHELL | CLI | STRUCTURED_API | AUTOMATION
  scope:
    SYSTEM | WORKSPACE | APPLICATION | TASK |
    TASK_GROUP | TASK_ATTEMPT | PROCESS | AGENT_INSTANCE |
    EXECUTION_FIBER |
    RESOURCE_GROUP | CONTEXT | TOPIC | CHANNEL |
    OPERATION | DEVICE
  target_id
  expected_generation_or_revision
  command
  typed_parameters
  requested_priority_or_contract?
  reason
  capability
  confirmation_or_policy_receipt?
  issued_at
  deadline
}
```

| 控制层级 | 用户必须能够执行的典型操作 |
|---|---|
| System/Device | 查看总负载与 pressure；切换电源/性能模式；暂停后台等级；配置系统保留量；触发安全关机/恢复 |
| Workspace/Tenant | 查看和设置授权范围、Quota、默认 QoS、数据边界、并发上限与通知策略 |
| Application | launch/activate/terminate；允许后台运行；设置自启动、网络/设备权限、资源上限和默认优先级 |
| Task | 查看/编辑计划；start/pause/resume/cancel/retry/refine；改变 deadline/优先级/预算；选择或锁定计划 revision |
| TaskGroup/TaskNode | 展开依赖图；seal，或以新 generation 重新打开未执行组；限制 fanout/depth；暂停/恢复分支；为新 plan/group generation 提议 reducer/failure policy；手工物化或驱逐 |
| TaskAttempt | 查看 snapshot、isolation、candidate output 和 effect 状态；cancel/supersede；请求重新验证；不能手工宣称 commit 成功 |
| Process/AgentInstance/Fiber | inspect、suspend、resume、kill/cancel、checkpoint、迁移建议、CPU/model affinity、QoS；显示共享 Process/Fiber 时的 thread/coroutine-like 共享故障域 |
| ResourceGroup/Context | 查看 requested/effective allocation、working set、pin、pressure；调低/申请调高 quota；reclaim/checkpoint/evict |
| Topic/Channel | 查看 producer/subscriber、积压、fanout、payer 和慢消费者；pause/throttle/drain/close；purge 必须显式确认并产生数据损失 Receipt |
| Operation/Device | cancel、retry-if-safe、reconcile、compensate、reset；不可把 EFFECT_UNKNOWN 手工改成成功或未发生 |

`[CTRL-PARITY-001]` “用自然语言暂停某应用”“在任务管理器点击暂停”“CLI 发送 pause”和结构化 API 调用 MUST 编译为语义等价的 ControlCommand，并经过相同 Capability、generation CAS、resource/effect fence 和 Receipt 路径。

`[CTRL-HIER-001]` 上层控制默认作用于其结构化后代，但传播范围 MUST 在预览中明确。例如暂停 Application 可冻结其非系统关键 TaskGroup/Process；取消 Task 默认传播到非 detached child；对单个 AgentInstance 的 kill 不得自动伪造整个 Task 已取消。

`[CTRL-PRIORITY-001]` 用户提交的是 requested priority/QoS/affinity；Resource Manager 返回 effective value。普通用户和 Application 不能手工授予 SYSTEM_CRITICAL、实时调度、系统救援保留量、额外 Capability 或不存在的物理容量。

`[CTRL-SAFETY-001]` 手工控制不得绕过 TaskHead、Commit/EffectPermit、LogicalEffect history、Budget、Capability、Lease、fencing 或 Trusted UI。强杀、purge、reset、强制迁移和不可逆补偿 MUST 显示影响范围，必要时要求确认，并产生逐目标 Receipt。

`[CTRL-PLAN-001]` Task Space MUST 同时提供自动视图和专家视图：普通用户看到 Application/Task 的整体状态；高级用户可下钻 TaskPlan、TaskNode、TaskAttempt、Process/AgentInstance/ExecutionFiber、ResourceGroup、Topic 和 Operation，并在授权范围内手动干预。

`[CTRL-RECOVERY-001]` 控制命令超时或客户端断开时，UI MUST 通过 ControlCommandId 查询权威状态；UNKNOWN 不得当作未执行而盲重发。批量控制必须报告逐目标成功、拒绝、等待和 unknown。

### 25.4 Desktop 系统对象与契约

完整桌面不等于 Task 控制台。`SurfaceProfile=DESKTOP` 至少具有：

```text
UserProfile
DesktopSession
ApplicationLauncher
SystemControlCenter
TaskManagerSurface
ResourceMonitorSurface
Surface
Window
FocusAndInputRoute
ChooserGrant
ClipboardItem
```

最小生命周期：

```text
DesktopSession: LOCKED → ACTIVE ↔ SUSPENDED → CLOSED
Surface:        REGISTERED → CREATED → PRESENTED ↔ HIDDEN → CLOSED
Window:         CREATED → VISIBLE ↔ MINIMIZED → CLOSING → CLOSED
Workspace:      CREATED → ACTIVE ↔ ARCHIVED → CLOSED
```

`[DUI-LAUNCH-001]` Launcher MUST 按 ApplicationId/InstallationId 激活 Application，不得把 PackageId 或某个 ProcessId 当作应用身份。

`[DUI-CONTROL-001]` Desktop MUST 提供可信的 System Control Center/Task Manager Surface，至少支持按 System、Workspace、Application、Task、TaskGroup、Process/AgentInstance/ExecutionFiber 和 ResourceGroup 浏览；它必须使用第 25.3 节 ControlCommand/Receipt，不得通过私有 UI RPC 绕过系统控制协议。

`[DUI-WINDOW-001]` Surface/Window MUST 具有 Application owner、Session、visibility、focus/input route、accessibility tree 和 generation；stale Surface 不得接收新输入。

`[DUI-INPUT-001]` focus、keyboard、pointer、voice 和 automation input MUST 经过 Trusted UI 路由并标明来源；不可信 Application 不得伪造系统级输入或权限界面。

`[DUI-CHOOSER-001]` Open/Save/Share chooser MUST 返回 scoped Artifact Capability，而不是泄露全局路径或整个用户目录。

`[DUI-ASSOC-001]` content type/default Application association MUST 是用户可查看、可撤销的 Settings 数据；Package 只能提议，不能静默夺取默认关联。

`[DUI-CLIP-001]` Clipboard/drag-and-drop MUST 绑定 content type、source Application、taint、expiry 和 user gesture；敏感内容跨 Application 需要 policy/consent。

`[DUI-NOTIFY-001]` Notification action MUST 绑定原 Notification/Application/Task 和一次性 Action token，防止另一 Application 伪造响应。

`[DUI-SESSION-001]` 多用户 Profile、Workspace、Session、Keychain 和 Application data container MUST 隔离；lock/switch user 后旧 Session input/capability generation 必须失效或降权。

`[DUI-SETTINGS-001]` Settings 必须按 system/user/workspace/application scope 分层并支持 compare-exchange/watch；Keychain 只向 Application 提供 use-by-reference handle。

`[DUI-OFFLINE-001]` LOCAL_SINGLE_NODE Desktop MUST 在离线时完成 launcher、Artifact、Task、Settings、Search、Notification history 和本地 Application 基本操作；依赖远程能力的 Action 必须显示 `WAITING_NETWORK/UNAVAILABLE`，不能令桌面整体失效。

# 第八部：分布式、兼容性与路线

## 26. 分布式现代 NLOS

### 26.1 蜂窝式权威

每个 Cell 具有本地：

- Process supervisor；
- capability/name cache；
- Resource lease 子账本；
- Driver gateway；
- durable event/outbox；
- Artifact cache；
- failure detector。

控制面负责：

- Principal/key 与 policy；
- Package/Application trust；
- quota lease、epoch 和 fencing；
- placement 与 migration intent；
- 跨 Cell 名称与服务发现；
- reconciliation 和审计 checkpoint。

```text
TaskAuthorityParticipantRegistry {
  registry_id
  task_id
  task_generation
  assignment_id
  authority_term
  control_epoch
  participant_registry_generation
  prior_participant_registry_root
  participants:[{
    participant_type:
      TASK_STORE | ARTIFACT_HEAD | SEMANTIC_ADMISSION |
```

`[DIST-LOCAL-001]` Cell 在控制面分区期间只能使用已授权、未过期、可本地证明的能力和额度。

`[DIST-FAIL-001]` 远程调用 MUST 显式暴露 deadline、unavailable、partial、uncertain、retry 和 idempotency；位置透明不得隐藏失败语义。

`[DIST-NAME-001]` 稳定对象身份不编码位置；路由绑定 MAY 变化并由 generation/epoch 防止旧实例复活。

`[DIST-TASK-001]` 每个 Task generation MUST 有唯一 durable TaskAuthorityAssignment，并以 TaskAuthorityParticipantRegistry 动态维护该 term/control epoch 已接触的完整 participant 集。任何 endpoint 在接收 task-scoped handle、canonical write prepare、Resource/Ledger reservation 或其他可跨接管存活的 operation 前，MUST 先通过 TaskControlRecord CAS 注册；注册与 operation admission 必须同一 authority transaction，或先形成不可激活的 durable prepare、待 registry generation/root 提交后才激活。TaskWriteSet seal 后，全部 planned EffectSlot 的 Driver gateway、Artifact/Semantic target 与 Resource/Ledger endpoint MUST 在 CommitPermit 前预注册；Permit issuance 的同一 CAS 把 registry 置 FROZEN_FOR_PERMIT，active permit 存续期间禁止新增 participant，所有 EffectPermit 必须绑定与 CommitPermit 逐位相同的 generation/root。若确需新 endpoint，必须先用已知闭合证明关闭旧 permit、创建新 registry generation 并重新 seal/竞争，不能在 permit 背后扩集合。worker MAY 跨 Cell，但 canonical TaskControlRecord/TaskHead/CommitPermit 只能由该 term 的 authority 提交。

`[DIST-TASK-002]` TaskAuthority 迁移 MUST 先用同一线性化 CAS 把旧 assignment 置 TAKEOVER_PENDING、把 registry 置 FROZEN_FOR_TAKEOVER 并截取 generation/root；其后拒绝旧 term 的新注册、prepare 和 dispatch。fence 集必须是“该 frozen registry 当前全集 ∪ 旧 control epoch 的 durable outstanding operation participant”，并以 `exact_fence_set_root` 固定。Task store、Artifact head、Semantic admission、Channel/Topic broker、Driver gateway 和 Resource/Ledger endpoint 的 barrier Receipt 必须逐项覆盖该 exact root，TaskAuthorityTakeoverReceipt 提交后才能激活新 assignment。任一 endpoint 不可 fence 时，只能等待其旧 authority/permit/lease 权威过期并保持 outstanding effect QUARANTINED，不能抢先接管；旧 Cell 的 result、message、permit、callback、effect 和 commit 必须拒绝。分区期间 worker MAY 在未过期 TaskSnapshot/lease 内做纯计算，但无有效 assignment/CommitPermit 时不得发布 canonical output 或启动新不可逆 effect。

`[DIST-TASK-004]` 新 assignment MUST 从已验证的 takeover Receipt 初始化 registry baseline，并递增 participant registry generation；TaskPermitClosureReceipt 在 TaskHead 不变时重新竞争也必须创建新的 OPEN registry generation，不能原地解冻旧 root。旧 registry root、旧 authority term/control epoch 或未在当前 registry 中的 endpoint 不得接受新的 canonical operation。registry 更新、permit freeze、takeover freeze 和 operation admission 必须共享 TaskControlRecord 的线性化顺序，禁止出现“已启用但未进入 fence 集”的参与者。

`[DIST-TASK-003]` 大 TaskGroup MUST 使用层级子组、局部 reducer、Merkle result root 和增量 checkpoint；root coordinator 不得要求每个 Agent 彼此全连接或执行 O(N²) 全状态广播。

`[DIST-FANOUT-001]` spawn/fanout admission MUST 预留并限制 group depth、child/active Agent 数、message count/bytes、Context/read bytes、write bytes 和 external effects；超限进入 WAITING_RESOURCE/backpressure，不得递归失控。

`[DIST-BULKHEAD-001]` tenant、Workspace、TaskGroup 与 provider MUST 有独立 ResourceGroup、并发池、队列和 failure budget；单个 Agent storm、provider stall 或 poisoned group 不得耗尽 Safety TCB 与其他 bulkhead 的系统保留量。

### 26.2 Artifact 与事件同步

`[DIST-EVENT-001]` Semantic Event 同步只合并签名事件集合及 admission 信息；不得通过 CRDT 自动创造语义判断。

`[DIST-ART-001]` Artifact sync MUST 为每种内容类型声明 merge、conflict、authoritative replica 和 deletion semantics。

`[DIST-AUDIT-001]` 跨域接受事件 MUST 保存生产者 signature、接收域 AdmissionReceipt 和 trust snapshot。

### 26.3 Process 迁移

`[DIST-MIGRATE-001]` Process 迁移至少要求：quiesce/cancel、checkpoint、源 fencing、Capability rebind、Lease close/regrant、目标 restore、新 generation 和 Receipt。

`[DIST-MIGRATE-002]` pinned/non-migratable Driver session MUST 导致明确拒绝或降级为 restart-from-artifact，不得假装透明迁移。

## 27. 性能与工作负载类别

NLOS 不能用“LLM 很慢，所以所有系统开销可忽略”作为性能模型。

| 路径 | 例子 | 主要契约 |
|---|---|---|
| Fast | 本地代码、handle、small IPC | 微秒/低毫秒、低复制、宿主抢占 |
| Streaming | token、音视频、机器人、长工具输出 | 增量计量、背压、cancel、bounded buffer |
| Slow | 远程 LLM、人工审批、长任务 | durable operation、deadline、恢复、通知 |

`[PERF-CLASS-001]` 每个 KABI/SABI 操作 MUST 声明其 workload class 和延迟/吞吐/持久性目标。

`[PERF-BENCH-001]` benchmark MUST 包含真实 durability barrier、并发和失败路径；仅内存或仅 `flush()` 结果不得代表 durable 性能。

`[PERF-SCALE-001]` 海量 Agent benchmark MUST 分别测量 logical TaskNode 登记、dependency eligibility、materialization、runnable queue、dispatch、checkpoint/evict/rehydrate、Topic 匹配和 recovery scan；必须报告每节点 metadata、总 RSS/磁盘、状态迁移吞吐、p50/p95/p99、CPU、I/O 和失败注入结果。

`[PERF-SCALE-002]` benchmark MUST 至少覆盖 10K、100K 逻辑节点，并在目标硬件允许时覆盖 1M；active working set 必须独立扫描多个比例。任何 O(N) 全局扫描、全局锁、全量 prompt、全订阅广播或每次 tick 的全量持久化都必须在证据中显式暴露，不能被远程 LLM 延迟掩盖。

`[PERF-CONTROL-001]` 手动控制面 MUST 在大规模下保持可用：列表必须分页/聚合，批量命令有界分片，暂停/取消/限流先作用于权威控制记录再异步传播；UI 不得等待枚举全部 Agent 后才能提交控制命令。

## 28. 路线拓扑

路线不是严格的 A→B→C→D→E 串行瀑布。C 和 D 在 B 之后并行；安全、兼容和证据贯穿全部阶段。

```text
A 启动微内核 + 薄 NL Shell
             ↓
B 单机应用平台 + 最小 Task Space
             ↓
┌──────────────────┬──────────────────┐
│ C 分布式现代系统 │ D 完整自然语言桌面 │
└──────────────────┴──────────────────┘
             ↓
E 兼容性制度化与生态规模化
```

### 28.1 阶段 A：启动微内核

必须交付：

- strict single-node sandbox/egress；
- Process、Capability、Namespace handle；
- ResourceGroup/ResourceContract、宿主 controller binding、pressure/reclaim；
- durable ResourceAccount ledger 与多资源 AdmissionDecision；
- generic I/O 与 Driver；
- 最小 Package envelope；
- Audit/Receipt；
- CLI 与薄 NL Shell。

退出门：

`[ROAD-A-001]` 更换模型 harness、provider 和 Tool adapter 不修改 KABI。

`[ROAD-A-002]` Budget 并发、kill -9、torn WAL、断流、重复 callback 和旁路攻击测试守住声明不变量。

`[ROAD-A-003]` 至少一个真实 provider 和一个 pure-code Process 通过纵切面。

`[ROAD-A-004]` CPU/memory/storage/I/O 至少四类本地 controller MUST 完成 hard limit、pressure、reclaim/OOM、分维 meter 与 explainable Receipt；ResourceAccount 不得冒充 ResourceGroup。

### 28.2 阶段 B：单机通用应用平台

必须交付：

- Application/Installation/Package/Update；
- Artifact 与用户数据 container；
- Identity、Task、Notification、Search 等最小系统服务；
- TaskGroup/TaskAttempt/AgentInstance/IsolationDomain、TaskSnapshot 与唯一 CommitPermit；
- ExecutionFiber/Activation M:N runtime、event loop、异步 Operation 与结构化取消；
- TaskPlan/TaskNode、Dependency Resolver、惰性物化、Context residency 和单机分层 Scheduler；
- SDK、debugger、conformance kit；
- 最小 Task Space、Task Manager、Resource Monitor 与可信权限 UI；
- 自然语言、GUI、CLI 和结构化 API 共用的多层 ControlCommand。

退出门：

`[ROAD-B-001]` 一个不了解内核实现的第三方能开发、安装、更新和卸载未预设 Application。

`[ROAD-B-002]` Application 能拥有 Artifact、后台 Task、UI Surface 和多个 Process，而非只能运行单 Agent chat。

`[ROAD-B-003]` 至少完成双 Attempt 唯一提交、cancel/commit 竞态、跨 Task handle 泄漏、snapshot 漂移、共享 provider cache 降级与投机副作用 fence 测试。

`[ROAD-B-004]` 单机实现 MUST 发布至少一个 ScaleProfile，并完成 10K/100K logical TaskNode、不同 active working-set 比例、pressure/reclaim 与 checkpoint/rehydrate benchmark；未完成前不得声称 PID 级 Agent 容量。

`[ROAD-B-005]` 用户 MUST 能从可信 Task Manager 在 Application、Task、TaskGroup/TaskNode、Process/AgentInstance/ExecutionFiber、ResourceGroup 和 Topic/Operation 层执行授权范围内的 inspect/pause/resume/cancel/kill/throttle/reclaim，并证明其与 NL Shell 走同一 ControlCommand/Receipt。

`[ROAD-B-006]` 单机 runtime MUST 证明有限宿主线程可承载至少 100K dormant/waiting Fiber，阻塞 I/O 不线性占用宿主线程；并通过 cancel/late-callback、structured join/detach、Process crash propagation 与分维 Activation metering 测试。未完成前不得声称 coroutine 级大规模并发。

### 28.3 阶段 C：分布式现代系统

必须交付：

- 多节点 identity/epoch/fencing；
- quota lease 与 reconciliation；
- Artifact/event sync；
- placement、migration、federation；
- TaskAuthority 分片、层级 fanout/reducer、Capacity/Device lease 与 bulkhead；
- Global/Cell/Worker SchedulerDomain、work stealing、context affinity、跨 Cell pressure/backpressure；
- 分区与恢复语义。

退出门：

`[ROAD-C-001]` 分区、重启、迁移和重复消息下有明确一致性、额度冻结和损失上界。

`[ROAD-C-002]` 海量 Agent benchmark MUST 证明 spawn/message/commit 不依赖全局锁或全局总序，并验证 stale TaskAuthority epoch、分区双主、fanout storm、provider stall 与 Cell bulkhead。

### 28.4 阶段 D：完整自然语言桌面

必须交付：

- 完整 Task Space、窗口、通知、设置、搜索；
- 多模态输入输出；
- 可信权限与成本界面；
- System Control Center、Task Manager、Resource Monitor 与各层级手动调度；
- 自动 Planner 计划预览、图形化编辑、手工 override 与重新授权体验；
- 离线/恢复体验；
- 可访问性和本地化。

退出门：

`[ROAD-D-001]` 非开发者无需理解 Agent 编排即可持续使用多个 Application 和后台 Task。

### 28.5 阶段 E：兼容制度与生态

必须交付：

- 长期 SABI/Package/Driver 兼容政策；
- Application Store 与 publisher 治理；
- 认证、迁移、兼容层和生态工具；
- 第三方 Driver/Application 市场。

退出门：

`[ROAD-E-001]` 系统能力增长主要来自第三方生态，升级无需生态整体重写。

## 29. 永久非目标与延后目标

### 29.1 永久非目标

- 不要求替代 Linux/Darwin/Windows 的硬件内核；
- 不绑定单一模型、provider、harness、MCP 或 A2A；
- 不让内核判断自然语言真假、意义或任务价值；
- 不保证 Agent 一定正确或 Task 一定成功；
- 不把 raw natural language 作为唯一编程接口；
- 不隐藏远程调用的部分失败、信任边界和成本；
- 不把定价、组织治理、调度策略或市场规则硬编码进内核；
- 不要求所有 Application 都是聊天界面或单 Agent。

### 29.2 v0.5 延后实现但必须保留接口

- 完整消费级桌面；
- 全球联邦与跨组织清算；
- 生产级 Application Store；
- 完整硬件 Driver 生态；
- 长期二进制兼容承诺；
- 裸机运行；
- “知识变换可表达性”的正式证明。

`[NLOS-DEFER-001]` deferred 不等于 forbidden；未实现不得被解释为从系统对象模型和兼容接口中删除。

## 32. 第一组实施切片

第一组工作拆成两个可独立验收的纵切面，避免把通用 OS 地基绑死在语义结算用例上。

### 32.1 Slice K：通用系统权威

```text
signed Package
  → install Application
  → typed Intent / direct structured launch / ControlCommand
  → bounded TaskPlan + lazy TaskNode materialization
  → TaskSnapshot / TaskAttempt or direct Activity
  → multi-resource AdmissionDecision
  → atomic proc_spawn + ResourceGroup binding
  → AgentInstance/Fiber M:N dispatch + async Operation
  → capability-scoped Driver
  → durable Resource reservation
  → streaming consume/cancel/effect fence
  → Artifact + nested Receipts
  → Shell + minimal Task Space + manual Task/Process/Resource control
  → crash recovery and replay
```

`[SLICE-K-001]` Slice K MUST 同时运行一个 LLM Process 和一个 pure-code Process，并运行一个无 Task/IntentSpec 的后台 System Process，以防设计退化为 LLM proxy 或知识工作流平台。

`[SLICE-K-002]` Slice K MUST 使用至少一个真实外部 Driver，明确其 GuaranteeTier，并包含 Reservation 复用攻击、多资源部分准入、memory pressure/OOM、并发、断流、kill -9、torn WAL、迟到 usage、重复 request、host incarnation 和旧 fencing token 测试。

`[SLICE-K-003]` Slice K MUST 通过薄 NL Shell 和结构化 API 执行同一 typed Intent，并允许结构化 API 直接启动非任务 Application，证明自然语言是首要界面但不是唯一机器接口。

`[SLICE-K-004]` Slice K MUST 运行两个竞争同一 TaskHead 的 TaskAttempt，证明只有一个 CommitPermit/TaskCommitReceipt；同时验证 cancel 先于 permit 与 permit 先于 cancel 两种线性化结果。

`[SLICE-K-005]` Slice K MUST 以有限宿主线程运行大量 waiting Fiber，并验证 Operation completion、late callback fencing、structured cancellation、Process crash propagation 和 Activation 分维计量；不得用一 Fiber 一线程的实现冒充 M:N runtime。

### 32.2 Slice S：语义与结算系统服务

```text
Semantic Events
  → durable Admission/Checkpoint
  → Authority View
  → ResolvedArtifactSet
  → complete Hard Gate
  → GateDecisionCore
  → register decision / durable notice
  → ResourceEscrow release
  → dispute/replay
```

`[SLICE-S-001]` Slice S MUST 只依赖 Slice K 暴露的 SABI/KABI 和普通 Package/Driver 机制实现，证明 Semantic/Gate/Escrow 是可替换系统服务而非内核特例。

`[SLICE-S-002]` Slice S MUST 包含 canonical collision vector、同文多源、Sybil independence、buffered evidence、空/遗漏 hard set、unauthorized retraction、concurrent retraction、Receipt substitution、challenge/dispute 和 outbox replay 测试。

## 33. 规范类型词典与生成约束

| 类型 | 最小含义 |
|---|---|
| EventId / SemanticEventId | 同一名义类型；通用 SemanticEvent 的内容身份 |
| SpecId | SemanticEventId 的受限子类型，event_type 必须为 SPEC |
| IntentId | TypedIntent 的身份，不等于 SpecId；Intent 可在授权后引用一个 Spec |
| TaskPlanId | 一个 Task generation 下版本化执行图的稳定身份；revision/digest 另行绑定 |
| TaskNodeId | TaskPlan 中逻辑工作节点身份；不等于 TaskAttempt、AgentInstance 或 Process |
| TaskGroupId | 结构化并发、child admission、取消与 failure policy 的稳定组身份 |
| TaskAttemptId | 一个 Task generation 下单次 retry/hedge/refinement 的执行身份 |
| AgentInstanceId | AgentRole 在特定 Attempt/Process incarnation 中的一次调度身份 |
| ExecutionFiberId | AgentInstance 内用户态可挂起/恢复执行流的身份；不是强隔离边界 |
| ActivationId | Fiber/AgentInstance 一次 dispatch turn/quantum 的计量身份 |
| SchedulerDomainId | Global/Cell/Workspace/Application/TaskGroup/Worker 某层调度权威与队列身份 |
| ControlCommandId | NL/GUI/CLI/API 共用的可查询、可去重系统控制命令身份 |
| IsolationDomainId | 多维隔离边界的身份；必须另带 generation/fencing token |
| TaskSnapshotId | causal-closed Task 输入切面的 content identity |
| TaskCommitId | 唯一 TaskHead CAS 成功后提交结果的身份 |
| KeyId | Principal key registry 中带用途、generation 和 validity 的稳定引用 |
| ImmutableArtifactRef | `{artifact_id, revision, content_digest, media_type}` |
| ArtifactSelector | 尚未冻结的查询表达式；不得直接用于 Gate/Authorization |
| AuthorityPolicyRef | `{policy_id, version, digest}` 的不可变引用 |
| TrustPolicyDigest | 完整 deterministic TrustPolicy 的 digest |
| ResourceAccountId | fungible credit/费用/账本归属；不等于调度隔离组 |
| ResourceGroupId | host controller 对应的层级调度/容量隔离组；不等于付款账户 |
| SettlementContractDigest | `RESOURCE_ESCROW` 可独立理解的 opaque 固定长度结算合同 digest；不与本地调度 ResourceContract 混淆 |
| UserDataContainer | ApplicationId + Principal/Workspace scope 下的 ACL/加密/备份边界 |
| ReceiptRef | 本域 ReceiptId 或带签名/digest 的 ExternalAttestationRef |
| SystemActivityId | 非 Task 型 daemon、维护、UI 或恢复活动的审计关联 |

`[TYPE-NOMINAL-001]` IDL/SDK MUST 保留上述名义类型，禁止把全部 ID 降成可互换 string。

`[TYPE-SELECTOR-001]` ArtifactSelector、service alias、Package channel 和任何 `latest` 名称在授权/验收前 MUST 解析为带 generation/revision/digest 的不可变引用。

`[TYPE-GEN-001]` KABI struct、SABI/Event schema、错误码、状态机枚举和 canonical golden vectors SHOULD 从同一 IDL/schema registry 生成并在 CI 检查；手写表与生成源漂移必须阻止 conformance release。

`[DOC-REGISTRY-001]` v0.5-alpha MAY 先以本文件的唯一 requirement ID 为规范源；在首次 `AssuranceLevel=CONFORMANT` 发布前 MUST 生成逐条 `claims.yaml`，记录 type/status/scope/profile/test/evidence。`DOC-CLAIM-001` 是 conformance 发布门，不是对当前候选稿已经完成 registry 的虚假声明。

## 结语

v0.5 对 llmos 的重新定位不是缩小愿景，而是让愿景拥有可以生长的系统地基：

> **确定性 Agent 内核是完整 NLOS 的权威执行底座；Application、Principal、Task、Artifact、Package、Driver、Intent、Receipt、系统服务与桌面共同构成完整操作系统。自然语言负责表达意图，类型化契约负责消除歧义，微内核负责不可绕过的边界，证据决定我们能把哪一项设计称为事实。**

当前最重要的工作，不再是继续扩写未经验证的宏大理论，而是实现第一条 strict、durable、可恢复的端到端纵切面，同时保留通向 Windows/macOS 级通用现代 NLOS 的完整对象模型和兼容路径。
