# 第一部 愿景与定位

## 1. 愿景与动机

### 1.1 立项问题：万级规模调度

核心问题：如果可供调度的资源翻万倍，现有智能体框架能否同时调度成千上万个智能体？

答案是不能。死法不是"调度不动"，而是压根没有"调度"这个概念。现有框架全是库（library），没有一个是内核（kernel）：无准入控制、无优先级、无抢占、无配额、无资源核算。它们默认算力无限且免费，万倍资源假设恰好炸掉这个默认。

场景拆分：

- 一万个互不通信的 agent（批处理型）：今天就能，但不需要 agent 框架，队列 + worker 池 + vLLM continuous batching 即可。
- 一万个互相协作的 agent（组织/社会型）：集体阵亡，算力无限也救不了编排层。

框架尸检结论：CrewAI 死于顺序/层级 Process 语义反并发（约 100 量级）；LangGraph 死于单进程 asyncio 加每 super-step 全量 checkpoint 写放大（约 1k）；AutoGen 系死于 pub/sub 广播 O(n²)（约 1k）；Letta/MemFS 死于 git 合并冲突（约 1k）；OpenAI SDK/harness 派死于万级沙箱调度回收无设施（约几千）；Dapr Agents 活得最久但无 agent 专属调度语义。

算力无限时剩下的瓶颈：

1. 调度语义真空：没有框架能回答"谁先跑、谁挂起、谁超预算、谁该被杀死"。OS 的核心职能（稀缺资源分配）在框架层完全缺席。万倍资源不会让问题消失，会让它从不存在变成核心矛盾。
2. 通信拓扑爆炸：广播/群聊 O(n²)，没有框架把通信局部性当一等概念。
3. 状态一致性：万级 agent 读写共享状态时，checkpoint 写放大、记忆合并冲突、一致性模型全无答案。
4. 非确定性传染：单 agent 幻觉是 bug，幻觉经消息传给 500 个下游是疫情，无隔离/检疫/熔断语义。
5. 可观测性崩溃：万级 agent 只能靠聚合指标加采样加异常检测，"agent 版 Prometheus"不存在。
6. 治理大于算力：token 预算是货币，身份与防劫持成刚需。

游戏服务器行业（MMO）早已解决"一万个 AI 实体同场"：interest management、tick rate 分级、AI 的 LOD。翻译过来：低优先级 agent 用小模型、少 token、低频调度，"智能"本身成为可分级调度的资源。此概念在现有 agent 框架中完全缺席。

结论：万级规模失效不是工程不努力，是抽象层级错了，应用库 vs 内核。这个位置今天是空的，这是 llmos 的立项论据。

### 1.2 计算历史类比：专用系统到通用系统

智能体系统正在重复计算机发展史：

| 计算时代 | 特征 | 智能体时代对应物 | 现状 |
|---|---|---|---|
| 专用机器（ENIAC） | 为单一任务布线 | 提示词工程 + 硬编码 workflow | 当下所处阶段 |
| 大型机批处理 | 昂贵、集中、专家操作 | 贵模型 + 集中 API + 一次跑一个流程 | 当下所处阶段 |
| 分时系统（CTSS/MULTICS/Unix） | 稀缺资源多路复用 | agent 内核：调度、上下文分页、IPC、权限 | 空缺 |
| PC/通用系统 | 资源便宜、通用抽象 | 万倍资源后 agent 即进程 | 未来 |
| 现代系统 | 网络、分布式、云 | agent 社会治理：身份、协议、结算 | 更远未来 |

支撑类比的三个论据：

1. 抽象比稀缺长寿。分时系统诞生于资源稀缺，但进程/虚存/文件这些抽象在资源变便宜后成了 PC 地基。今天缺的 agent 内核抽象，在万倍资源时代仍是必需品。稀缺发明抽象，富足放大抽象。
2. harness 派正在无意识地重建 Unix 用户态：agent = 进程，AGENTS.md = rc 配置，skills = PATH 里的可执行程序，MCP = 设备文件，A2A = socket，Letta MemFS = 带版本控制的 /home，eve 的"agent 即目录" = 一切皆文件。但没有人在造内核：调度器、内存管理、IPC 语义、权限、kill switch 全部缺席。
3. 每个时代的统治 OS 都长在新硬件类别上：大型机到 MVS，小型机到 Unix，PC 到 DOS/Windows，手机到 iOS/Android，云到 Kubernetes。agent 时代的"硬件"是 GPU 集群加基础模型，其 OS 按历史规律必然出现且当前空缺。

类比的两个断裂处：

1. 概率进程 vs 确定进程。进程崩溃是异常，agent 犯错是常态，需要的不是异常处理而是统计性容错。agent OS = 经典 OS + 一层随机性管理，这一层没有历史先例。
2. 可执行格式未定。通用化的前提是格式标准化。agent 时代的 ELF 不存在，谁定义了 agent 的 ELF，谁卡住生态位。

历史警示：Multics 功能最全，输给 Unix 的"够用"；Plan 9 思想更先进，输了；Lisp 机器的优雅败给 C/Unix 的粗暴。正确顺序是先找到最小正确抽象，让生态自己长。

### 1.3 行业格局：现有框架全是库不是内核

2026 年行业形成两大阵营：

- harness/文件系统/沙箱派（OpenAI SDK、Letta Code、Vercel eve、Dify Agent、Kite）：智能体的能力来自环境，编排是多余的。
- 图编排派（LangGraph、ADK 2.0、MAF）：生产可靠性要求控制流显式化、与 LLM 解耦。

MCP（工具）+ A2A（智能体间）成为两派共用的协议底座（均已进入 Linux Foundation 体系）。llmos 不站队：harness 程序和图编排器都是 llmos 内核之上的用户态程序，内核在两者之下，这就是桥。

### 1.4 方向修正：规模是压力测试，通用才是宗旨

v0.1 之后，讨论曾漂移进治理细节（计费、escrow、重授权链），叙事气质偏向大型机 MVS：功能内置、治理中心。2026-07-23 用户指令修正方向：

**规模是压力测试，通用才是宗旨。** 万级规模是用来压垮错误抽象的试验载荷，不是设计的目的本身。设计的目的是通用系统：一套对负载无知、任意组合的抽象，加上现代系统（分布式、联邦、云原生）的扩展。治理（预算、授权、计费）是这套系统上的一种重要负载，不是系统的中心。

分诊归位（本版文档的结构据此重排）：

| 已有内容 | 归位 |
|---|---|
| Agent/Context/Tool/Message/Topic/Blackboard、陷入层、ELF | 通用系统核心（通用性载体），见第二部 |
| 调度/tick/抢占 | 分时机制：有用，保留，但只是机制不是宗旨 |
| Budget/Policy 的治理语义（escrow/计费/重授权链） | 治理层：降级为可插拔模块（本就在用户态），不再占中心位置 |
| provenance/看门狗/容错机制 | 内核机制保留，表述归位为支撑设施 |
| namespace/分布式/协议栈/弹性（议题 14-17） | 现代系统，见第四部 |

两点定位声明随之更新：

1. **分时机制保留但非宗旨。** tick 协作式调度、步边界抢占、优先级队列是内核机制的一部分，承担规模压力测试；但它们是手段，通用性（议题 13 的四判据与重构测试）才是判据。
2. **治理层为可插拔模块。** 预算定价、escrow 合同语义、计费分摊、重授权规则全部是用户态可替换组件；内核侧只保留负载无关的计量与强制机制（计量调用、能力校验、衰减校验）。换一套治理政策，内核不变。

# 第二部 通用内核

## 2. 设计原则

从 Unix 继承并经讨论定案的原则（v0.1 四条），加上议题 13 定案的两条通用性判据：

1. **机制/策略分离（微内核路线）**。机制在内核，策略在用户态。内核只留非留不可的。判定测试：若某机制错了或被绕过，安全或核算是否失效？是否需要在陷入点上原子完成？两关都过才入内核，否则一律用户态。
2. **Multics 警惕：抽象少而准**。不自上而下设计完美内核。系统调用超过约 30 个就是过度设计（当前 22 个，通过测试）。赢的那个往往不是第一个也不是功能最全的，而是抽象最简加生态位最对的。
3. **"内核从不信任，只设界"**（policy is advisory; invariants are physics）。内核强制不变量（预算守恒、公平性下界），LLM 驱动的策略只能在界内调参。
4. **抽象比稀缺长寿**。今天为稀缺设计的抽象，在富足时代仍是地基。
5. **负载无知（议题 13 定案）**。内核不知道也不关心程序在算什么，系统调用负载无关。内核只持有结构性信息（能力集合、预算余额、步数、进展信号、污点标记、路由地址），不持有语义性信息（任务内容、输出好坏、消息含义、过滤意图）。看门狗信号是结构信号不是语义判断；Topic 谓词是"执行不理解"（eBPF 原则）。负载无知是通用性的审计标准。
6. **重构测试（议题 13 定案）**。通用性的裁判标准：能否用内核原语把现有计算模式全部重构为用户态程序？16 个模式压测全部通过（见第 4.9 节），是抽象集成立的证据，也是今后新增抽象的反方举证责任。

## 3. 总体架构与陷入层

### 3.1 核心论断

**LLM 调用 + 工具调用 = 系统调用。** 内核物理位置唯一正确解：卡在 agent 循环与模型之间、agent 循环与工具之间。每次 LLM 请求、每次工具调用经内核陷入（trap）。一个陷入层同时提供四个机制：

1. 抢占点（步边界挂起/恢复）
2. 预算扣减点
3. 权限/能力校验点
4. 污点标记点

陷入边界精化为一条原则：**内核陷入一切跨越 agent 私有边界的操作**，包括推理（LLM 调用）、工具、共享状态（Message/Topic/Blackboard）、持久记忆。私有草稿不陷入（harness 本地计算、私有 scratch 空间），对应 Unix 进程访问私有内存不陷入。

陷入如何不可绕过（ring 保护的软件等价物）：

- **凭证托管**：agent 拿不到原始模型 API key，模型端点只接受内核签名的请求。
- **网络策略**：沙箱网络规则使工具只能经内核网关到达。

这就是 agent OS 的 ring 0 / ring 3，不是靠硬件特权级，靠凭证加网络隔离。

被否决的备选：只陷入工具调用、LLM 直连（预算和抢占全部失效，等于没有内核）；异步观察（事后检测预算超支等于钱已花完，强制必须同步）。

### 3.2 计量调用：步模型推广为计量模型（议题 13 定案）

v0.1 的陷入模型以"一次 LLM 请求 = 一步"为单位。议题 13 的流式压测（realtime/voice 模型是持续流，不是请求-响应）暴露裂缝并定案修复，LLM 调用语义推广为**计量调用（metered call）**：

- **流 = 一个保持打开的长陷阱**。驱动按 chunk 增量回报用量，内核增量扣减预算；额度耗尽内核掐断流。
- **请求-响应 = chunk = 1 的特例**。步模型不破，被计量模型包含。
- **抢占点从步边界推广为 chunk 边界**。
- **max_tokens 硬顶（议题 11 定案，见第 5 章）推广为累计计量上限**：内核把剩余预算折算成计量上限随调用下发，驱动物理截断。

系统调用表中 `llm_call` 的语义相应更新为"计量调用（含流式）"。

### 3.3 三层架构

```
用户态：harness 程序（agent 循环）| 编排器（graph/workflow 程序）|
       调度策略 agent | 分页策略服务 | 策略守护进程 | 工具注册中心
──────────────────────────────────────────────
内核：  陷入层（计量调用/工具调用=系统调用）| 调度机制 | 上下文分页机制 |
       IPC路由+背压 | 预算核算 | 污点传播 | 能力校验
──────────────────────────────────────────────
硬件态：推理引擎（vLLM 等 = CPU）| 沙箱执行环境（= 外设）| 存储
```

推理引擎 = CPU 的地位：内核不拥有 CPU，只中介对 CPU 的访问。多模型/多 provider 抽象为"执行上下文"（类比 CPU 亲和性/NUMA 节点）。

### 3.4 为什么是微内核

经典微内核（Mach）死于 IPC 性能开销。agent OS 里这个死因不存在：**LLM 调用延迟是 100ms 到 10s 量级，IPC 开销是微秒到毫秒量级，微内核的 IPC 税相对系统调用延迟是噪声。** Mach 是对的思路错的基座，agent 给了它对基座。

例外核查：消息路由（万级高频）仍是 ms 级，可承受；KV cache 共享的热路径在推理引擎（vLLM）内部，不属于本内核。

通用性的代价与可负担性（议题 13）：通用性要求陷阱统一，性能想要旁路（可信 agent 直连模型？）。结论：**不变量（能力 + 预算）永不旁路**；陷阱成本相对 LLM 延迟是噪声，通用性买得起。

## 4. 八大抽象规范

最小抽象集共 8 个抽象，表述为 6 族。议题 13 修剪结论：8 抽象无一删除。**通用核心 6 个：Agent/Context/Tool/Message/Topic/Blackboard（通用性载体）；基础设施 2 个：Budget/Policy，标注为负载无关的基础设施**（电力计量类比：是设施不是灵魂）。另有"人 = 设备"归位：人在环（HITL）中的人是 approval 工具（外设），阻塞等待响应，不是进程（Unix 终端类比）。

### 4.1 Agent（计算族，进程对应物）

- **定义（议题 13 修订）：通用进程抽象，LLM 可选。** 可调度执行单元，生命周期为创建/运行/阻塞/死亡，可杀、可隔离。LLM 能力是一种可选 handle（像网络能力可选一样）：纯代码 worker（数据清洗、格式转换）与 LLM agent 共用同一 Agent 抽象，**拒绝引入第二种进程类型**（Multics 警惕）。无 LLM handle 的 agent 不过 llm_call 陷阱，预算照记（工具/资源消耗）。Unix 用单一进程抽象跑 cat 和 Emacs；llmos 用单一 Agent 抽象跑纯代码 worker 和 LLM agent。
- **调度性质**：LLM 调用边界 = 时钟中断点，agent 循环的每一步是天然抢占点，agent 是协作式可调度的，调度粒度 = 一个推理步（计量模型下推广为 chunk 边界，见 3.2）。
- **Unix 对应**：进程。fork 的对应物是上下文分支（git 式 branch agent 状态）。
- **内核职责**：生命周期状态机（权威）；步边界陷入执行；身份（agent ID/父系/版本号，自我修改门控用）。
- **用户态职责**：agent 循环本身（ReAct/Plan-Execute/自定义全是用户态 harness）；fork 语义 = checkpoint + branch，内核给原语，用户态决定何时分支。

### 4.2 Context（内存族，映射最精确的一块）

- **定义**：上下文窗口 = 物理内存；RAG = 请求调页；embedding 索引 = 页表；retrieval = 缺页中断处理；上下文压缩 = swap 压缩；KV cache 前缀共享 = 共享库/写时复制。
- **Unix 对应**：虚拟内存。
- **内核职责**：页记账（token 数、钉住状态）；钉住强制（mlock 页不可淘汰）；换页执行机制（压缩/淘汰的执行）；KV 共享机制。
- **用户态职责**：淘汰策略（LRU/语义相关性评分）；压缩策略。先例：Mach 外部分页器，分页策略放用户态是 40 年前就验证过的设计。
- **关键决策（用户拍板）**：混合管理，madvise/mlock 模式。内核管机械工作，agent 可钉关键页、可给建议；默认透明（休闲 agent）+ O_DIRECT 逃生舱（专家 agent）。**钉住的上下文页计入 Budget**。

### 4.3 Tool（设备族）

- **定义**：外部能力入口。MCP 就是 /dev，"一切皆文件"的胜利 = 统一接口战胜定制 API。双设备类：MCP（结构化设备，RPC 语义）+ shell/文件（字节流设备），内核不选边。
- **Unix 对应**：文件/设备。
- **内核职责**：工具调用陷入；能力校验（该 agent 是否持有此工具 handle）；沙箱强制挂钩（后端选择、资源限额）。
- **用户态职责**：工具发现/注册（MCP registry = 用户态设备管理守护进程）；组合/重试/缓存策略。

### 4.4 Message（通信族之一）

- **定义**：定向、有序、消耗品的消息流，并发语义为背压（写满阻塞写方）。
- **Unix 对应**：管道。
- **内核职责**：投递保证与排序；背压阻塞（队列满，内核挂起写方，必须与调度原子）；寻址路由。
- **用户态职责**：消息持久化/转换（Kafka 守护进程类比）。
- **计费（议题 11 定案）**：发送者预付，见第 6.6 节。

### 4.5 Topic（通信族之二）

- **定义**：群发、有序、消耗品的广播主题，并发语义为兴趣过滤，是万级规模解决 O(n²) 洪水的核心机制。
- **Unix 对应**：无直接对应（新发明）。
- **内核职责**：投递保证与排序；寻址路由；兴趣过滤谓词的安全执行。
- **用户态职责**：Topic 兴趣过滤规则。先例：Topic 过滤器 = eBPF，内核提供安全沙箱执行用户态编译的过滤谓词，性能（内核执行）与策略（用户定义）兼得。
- **关键决策（用户拍板）**：Topic 第一天进内核，为万级规模的兴趣管理预付复杂度税。

### 4.6 Blackboard（通信族之三）

- **定义**：共享、持久的状态区，并发语义为 git 式合并（乐观并发控制）。
- **Unix 对应**：共享内存。
- **关键决策（用户拍板，议题 6 Q4）**：**内核元数据 + 用户态字节**。内核管 handle/能力表条目、版本序号、写串行化（并发写的权威排序点）、wakeup 原子性（写提交与唤醒阻塞读者必须原子，否则丢唤醒）、污点标记；用户态服务管字节本体、持久化、复制、压缩、GC、merge driver（冲突解决是应用语义）。类比：内核 inode 缓存 vs 磁盘字节；L4 + 用户态文件服务器。
- **分片（议题 11 裂缝 3 修复）**：按命名空间分片（黑板 ID hash 分片），串行化只在片内；热点黑板由用户态拆分（类比数据库分表）。

### 4.7 Budget（经济族，负载无关的基础设施）

- **定义**：经济抽象。agent 的一切行动（推理、工具、记忆占用）折算成统一货币消耗，内核在陷入点原子扣减，耗尽时强制执行。回答三个问题：行动花什么、谁来限制、怎么追踪。
- **Unix 对应**：无（rlimits/磁盘配额/cgroups 是先例；Unix 自己的演化证明静态权限装不下动态核算）。
- **内核职责**：扣减核算（每个陷入点原子扣）；耗尽强制（拒绝/挂起）；继承树维护（父子切分权威记账）。
- **用户态职责**：定价策略（各模型/工具定价表）；分配策略；耗尽响应策略（挂起 vs 降级小模型 vs 通知，agent 注册自己的 handler，预算耗尽 = signal 投递，Unix 信号语义直接移植）。
- **关键决策（用户拍板，议题 5 Q1）**：独立一等抽象，携带经济语义进内核。确认有预算委托需求（父子继承/agent 间付费）。详见第 6 章。
- **归位标注（方向修正）**：Budget 是负载无关的基础设施。内核侧只是计量与强制机制；定价、合同、计费分摊等治理语义全部在用户态可插拔模块（见第 6 章）。

### 4.8 Policy（安全族，负载无关的基础设施）

- **定义**：权限 + 污点 + 自我修改的版本门控。面对 Unix 没有的威胁：代码/数据二元性坍缩，agent 读一个网页就可能被改写目标（提示注入），agent OS 里数据和代码是同一种介质（token）。
- **Unix 对应**：用户/权限。
- **内核职责**：陷入点强制校验；污点传播机制（标记+传递）；自我修改的版本门控（v2 凭证不等于 v1，直到重新授权）；衰减校验（议题 10，见第 8 章）。
- **用户态职责**：策略规则本身（策略引擎 = 用户态守护进程，Linux polkit 先例）。
- **性能答案**：能力模型（capability），持有 handle 后不再每调用重估策略，每陷入只查能力表 + 预算 + 污点。能力表 = Unix 文件描述符表（议题 14 进一步泛化为 namespace 绑定表，见第 9 章）。
- **归位标注（方向修正）**：Policy 同 Budget，是负载无关的基础设施；策略规则与重授权规则是可插拔用户态模块。

### 4.9 调度器（特殊项，微内核之争的焦点）

调度器不进内核热路径，是微内核路线的焦点设计：

- **内核（机制）**：步边界挂起/恢复；tick 控制；运行队列数据结构；非自愿抢占（预算耗尽/污点/背压触发）。
- **用户态（策略）**：选谁跑、LOD 分配、准入控制。
- **关键决策（用户拍板，议题 6 Q3）**：调度 agent 不是 dispatcher，是 **sysctl writer**。算术否决了 LLM 上热路径：万级 agent 乘每步约 2s 等于每秒数千个调度事件，LLM 决策延迟（100ms 到 1s）追不上。分层调度：内核 dispatcher 纯算术（优先级队列出队），零智能；用户态 LLM 调度 agent 慢循环（秒到分钟级）做语义判断，通过 syscall 把参数写进内核（类比写 /proc/sys）。
- **安全设计**：内核强制不变量（预算守恒、公平性下界），LLM 只能在界内调参；调度 agent 消耗固定内核预算（记账可见）；Dead-man's switch，调度 agent 死亡/超时则内核自动退回公平调度；幻觉的影响半径 = 参数调整幅度上限（rate-of-change 限制）。
- **归位标注（方向修正）**：调度/tick/抢占是分时机制，承担规模压力测试，是机制不是宗旨。sysctl writer 模式后被复用为通用模式家族：语义监督 agent（议题 9）、弹性策略 agent（议题 17）都是其成员。

### 4.10 模型层（议题 6 Q2 定案）

**模型 = 设备驱动**：

- 内核：能力上限（该 agent 可用模型档位范围 = capability，类比 fd 表条目）、预算扣减、陷入转发。
- 驱动（用户态/外部 vLLM 集群）：路由（哪个 provider/endpoint）、batching、failover、档位内 LOD 微调；成本回报（可信驱动在内核 TCB 内）。

论据：vLLM 的 continuous batching 本来就是设备调度，内核接管等于越界管磁盘寻道；LOD 决策落到执行上下文只是档位上限（类比 nice 值），驱动在上限内选具体模型；模型路由的复杂性（provider 故障、价格波动、限流）全是驱动业务，不进内核。

## 6. Budget：可插拔治理模块的内核机制侧

按方向修正，本章表述归位：Budget 的内核侧是负载无关的计量与强制基础设施；定价、合同、计费分摊等治理语义全部在用户态可插拔模块。以下为已定案语义，全部保留。

### 6.1 为什么必须是一等抽象

1. 成本是即时的真金白银：Unix 进程死循环浪费免费时间片，agent 死循环烧钱。失控 agent = 财务事故不是性能事故。
2. 委托链条需要问责：A spawn B spawn C，谁付钱？没有继承树就没有问责链。
3. 万级多租户：组织跑上万个 agent，财务需要按团队/项目核算。
4. 调度需要统一成本货币：调度器决策"谁配得到推理槽位"需要可比较的成本单位。
5. agent 间经济行为：A2A 的未来是付费 agent 服务，转账必须是一等语义。

### 6.2 计价单位（定案）

用抽象 **credits**：不用 token 计价（不同模型单价不同，token 不是稳定货币），不用法币计价（内核不该碰汇率/支付）。驱动在陷入点回报实际用量（X tokens，Y cached），用户态定价表折算 credits，内核只记 credits，内核与价格波动隔离。

### 6.3 解剖结构（五个组成部分）

| 组成 | 说明 | 归属 |
|---|---|---|
| 余额 balance | 当前可用量 | 内核（权威） |
| 记账流水 ledger | 每笔扣减事件（哪次调用、花多少） | 内核（热路径） |
| 继承树 inheritance tree | 父子划拨关系 | 内核 |
| 耗尽行为 exhaustion | 归零时：挂起/降级/通知 | ELF 声明 + 用户态 handler |
| 定价表 pricing | 各模型/工具的单价 | 用户态 |

现实类比：手机话费套餐（预付余额 + 耗尽停机 + 家庭共享套餐 = 继承树）；云账户体系（主账户到子账户到预算告警）；cgroups（核算机制相同，但核算对象是钱不是 CPU）。

流水持久化（议题 11 裂缝 1 修复）：5k 扣减/秒全量流水直接落盘不可行。热路径只改内存余额，流水 WAL 批量组提交（参考 Postgres group commit）；流水异步落盘，崩溃时以最后一次一致快照 + 重放恢复。

### 6.4 预算继承（定案：ELF 要价 + 父审批）

子 ELF 声明 budget.request，父（或其 Policy）在 spawn 时批准/拒绝/调整。**支持中途回收未用预算**（长期父 + 多子场景的刚需）。先例：k8s ResourceQuota、Unix rlimit 继承（只能降不能升）、银行子账户。被否决：共享池（一个失控子 agent 抽干全部兄弟）。

### 6.5 耗尽响应（定案：预警 + 默认挂起）

- **80% 阈值信号**（notify），给 agent 优雅收尾窗口（主动 checkpoint、申请增资）。
- **100% 默认 suspend**：冻结，状态保留，充值可恢复。最诚实的失败。
- **degrade 仅限 ELF 显式声明**：切小模型继续跑，能力缩水可能导致任务静默失败，隐蔽失败比显式失败更危险，因此仅作作者明确接受质量风险的可选策略。

### 6.6 转账清算与消息计费（定案）

- **转账清算（议题 8 定案）**：内核只提供原子原语：**transfer / hold / release / refund（超时自动退）**。托管语义：A 的金额内核冻结，任务完成释放给 B，超时/失败退回 A。合同语义（完成判定、里程碑、争议）全在用户态，内核不管"任务完成"的判定。Unix 类比：内核提供原子 rename，数据库在其上建事务。
- **消息计费（议题 11 定案，裂缝 2 关闭）**：**发送者预付**。消息进入接收者上下文 = 消耗接收者 token；发送者按投递计费，spam 制造者自付成本 = 经济背压，与 Budget 转账原语复用。被否决：接收者付费（被轰炸者受损）；双向计（发送者付投递费 + 接收者付上下文占用，作为后续可选细化未采）。

### 6.7 预算透支与在途结算（议题 11 定案）

陷入时检查余额，但调用实际成本事后才知（余额 100 credits，一次调用实际烧 150）。**定案：max_tokens 硬顶**，内核把剩余预算折算成 max_tokens 随调用下发，驱动物理截断生成。物理保证，无账本复杂性；计量模型下推广为累计计量上限（见 3.2）。工具调用用 preauth 预估冻结（按 max 预估先冻结，结算多退少补）作补充。被否决：允许透支记负账（事后追讨/挂起）。

在途调用的结算：协作式调度在步边界挂起，在途调用完成并计费，自然结算；kill 在途调用时 provider 按已生成 token 计费通常无退款，记为损耗入账（"损耗"账目类型）。

### 6.8 联动计费（定案：实际成本 + 钉页费）

- **钉住页**：按"页 × 步数"计费。钉住占用稀缺上下文空间，收费防止 pin-everything 滥用（议题 5 的 Q1×Q3 联动落地）。
- **KV 共享页**：真实成本已由推理引擎的 prefix cache 分摊（命中缓存的 token 实际更便宜，provider 本就如此计费），按驱动回报的实际成本记账，不做二次分摊。共享 libc 不向进程单独收费，同理。
- **工具调用**：付费 API 由工具/驱动回报成本，内核扣减。
- **挂起租金**（未决，见第 15.1 节）：挂起 agent 的 checkpoint 占存储，是否收存储租。

## 7. 随机性管理层

核心论点：**Unix 把故障当异常，agent OS 必须把故障当统计。内核消灭不了幻觉，只提供测量、隔离、冗余原语。可靠性是用 Budget 购买的商品。**

按方向修正，本章归位为支撑设施：机制保留在内核，服务于通用内核的可靠性，不构成叙事中心。

### 7.1 故障模型：agent 故障 = 拜占庭故障

| | Unix 进程故障 | agent 故障 |
|---|---|---|
| 形态 | 崩溃（可观测） | 看似健康地输出错误（幻觉/推理错/被注入） |
| 检测 | 内核直接知道 | 需要语义判断 |
| 经典对应 | crash fault | Byzantine fault |

拜占庭容错经典结论：容忍 f 个拜占庭节点需 3f+1 副本。但 agent 冗余有经典 BFT 没有的问题，**相关性失败**：同模型同提示词跑 3 次，大概率犯同一个错。冗余必须多样化才有效（不同模型/不同提示词/不同 harness），这是航空软件 N-version programming 的先例。

### 7.2 容错四档（成本递增，可靠性递增）

| 档位 | 机制 | 成本 | 适用 |
|---|---|---|---|
| 1. 变体重试 | 重试时改变 temperature/措辞，打破相关性 | 约 1x | 默认 |
| 2. 校验器 | 生成-校验不对称：验证常比生成便宜（代码跑测试、数学验算）。确定性校验器最优，LLM 校验器次之 | 1.x x | 有可机械验证输出的任务 |
| 3. N-版本投票 | 3 个多样化实现多数决 | 约 3x | 关键步骤（ELF 声明 criticality） |
| 4. 检查点回滚 | 检测到错误后 rewind 到出错前（语义难点：哪个 checkpoint 是"出错前"？依赖检测先行） | 存储成本 | 长任务 |

### 7.3 Erlang 监督树（打补丁后照抄）

Erlang/OTP 的 "let it crash" + 监督树（重启策略 one-for-one/one-for-all、升级链、重启预算）是分层容错的最佳实践。但有个关键差异：Erlang 监督的前提是崩溃可观测，agent 的错误输出不可直接观测，**检测必须先于监督**。监督树结构照抄，触发器从"崩溃信号"换成"看门狗标记 + 校验器失败"。重启预算 = 另一种配额（次数限制不是金额限制）。

### 7.4 无进展检测（定案：两级制）

问题：agent 空转（livelock），持续烧钱但无语义进展。Unix 的死循环检测（CPU 空转）无效，agent 每步都在"正常"调用。

- **第一级：内核看门狗**。嵌入式硬件看门狗的移植。"喂狗" = 进展信号：新产物写入、新工具调用、任务清单推进、harness 显式心跳。ELF 声明阈值：maxStepsWithoutProgress、maxRepeatSimilarity（连续步骤相似度，复读机检测）。到阈值则挂起 + 标记，转第二级。
- **第二级：用户态语义监督**（sysctl writer 模式复用）。监督 agent 审查被标记 agent 的 trace，裁决：恢复（误报）/ 转向（注入新指令）/ 杀死（从 checkpoint 重启）。内核只看信号不看语义，语义判断全在用户态。

### 7.5 幻觉传染隔离：溯源元数据 + 接触追踪（定案：内核强制携带）

1. **溯源元数据（provenance）**：共享通道（Message/Topic/Blackboard）上的每条信息强制携带：来源 agent、lineage（由哪些信息推导）、断言级别（工具结果的事实 / 推理结论 / 推测）、验证状态（已经校验器验证 / 未验证）。
2. **与污点追踪是对偶**：taint 标记"外部不可信数据"，provenance 标记"内部断言的来源"，合起来是完整的信息血缘图。
3. **类型系统类比**：verified/unverified 像类型，Policy 像类型检查器，"规划上下文只许 verified 进入"是可强制规则。
4. **接触追踪 + 召回**：某 agent 被判定幻觉后，沿 lineage 前向追踪它污染了什么，Blackboard 的 git 版本化支持定位并回滚被污染条目。食品安全溯源的信息版。
5. **lineage GC（议题 11 裂缝 4 修复）**：血缘图无界增长的修复为 lineage TTL + 分层归档（热血缘全量、冷血缘压缩为摘要哈希）；与接触追踪的查得回深度联动。

### 7.6 可靠性分档购买（定案）

可靠性是分档购买的商品：**ELF 声明任务关键度（criticality），Budget 支付冗余倍数**。默认变体重试；关键步骤买 N 版本投票。内核机制（branch/join）+ 用户态策略（何时买哪档）。

### 7.7 层的切分总表

| 内核机制 | 用户态策略 |
|---|---|
| branch/join 冗余组原语 | 何时买哪档可靠性（criticality 到冗余的映射） |
| 看门狗计数器 + 挂起/标记 | 阈值调优、语义监督裁决 |
| 溯源元数据的管道（强制携带） | 消费规则（Policy 的"只许 verified 进规划"） |
| 比对结果的收集投递点 | 比对函数（语义 diff/测试执行/投票阈值） |

原则：内核不消除随机性，只让随机性可测量、可隔离、可冗余。可靠性购买的定价 = Budget 职责，闭环。

## 8. 安全与授权（议题 10 + 议题 12 合入）

本章为 v0.2 新章：重授权签字链、一致性的 OS 模型、控制面防注入。

### 8.1 重授权签字链：衰减原则 + 三级签字（议题 10 定案）

问题：agent v1 持有一组能力（工具 handle + 权限），v1 → v2 的自我修改触及 requiresReauth 段（工具/权限声明变更）时，v2 的能力请求必须重新获得签字。谁有权签？

核心洞察：**衰减原则（attenuation）结构性地回答了"谁签字"**。能力安全的经典原则：委托只能衰减，不能放大，父 agent 只能把自己能力信封（envelope）的子集授予子 agent。推论：

- **内核可以机械校验**：v2 请求的能力 ⊆ 父的当前信封？纯集合包含判断，零语义，完美符合"内核从不信任，只设界"。
- **扩权请求物理上无法被父批准**：父签不出自己没有的能力。扩权只能沿授权链上行回溯到信封源头，最终必达组织根（人类/根 Policy）。

三级签字链：

| 层级 | 情形 | 签字人 | 时效 |
|---|---|---|---|
| L0 内核不变量 | 一切重授权 | 内核机械校验：请求 ⊆ 父信封（集合包含） | 同步、必过此关 |
| L1 常备授权（standing authorization） | 信封内的低风险变更（如：从组织批准注册表添加 tier ≤ 2 的只读工具） | Policy 守护进程按预批规则自动签 | 即时（规则预批，无需等待） |
| L2 上行扩权 | 请求超出父信封（新域网络访问、权限范围扩大、核心指令变更） | 沿链上行至信封源头，最终人类/组织根 | 同步阻塞，agent 挂起等待 |

规模化关键概念是常备授权：绝大多数重授权是规则可预见的，Policy 守护进程的规则就是"预先签好的字"。人类只见例外。这回答了"人类是瓶颈"的反对：人类不签常规，只签扩权。

两个配套机制：

1. **skills 修改为什么不需要重授权**：skills 修改只改变 agent 如何使用已有能力 handle，不增加 handle。内核按"能力集合是否变化"判定是否需要重授权，不按"包内容是否变化"，能力视角而非文件视角。
2. **审计流水**：每次重授权事件强制记录（请求方、签字方、能力差分、lineage 位置），与议题 9 的溯源管道合流，安全事件可回溯。

与既有设计咬合：Budget 继承树与授权信封树同构，spawn 时同时切预算片和信封子集，**spawn 就是一次"双划拨"**；ELF 的 requiresReauth 声明是格式层契约，本议题是运行时执行机制；Policy 守护进程的规则更新也走"用户态策略写参数、内核机械执行"的 sysctl writer 模式。

### 8.2 扩权等待期：v1 续跑 + 热切换（议题 10 定案）

L2 上行扩权的人类签字延迟是分钟到小时级。**定案：蓝绿部署类比，旧授权版 v1 继续服务，v2 挂起等待，批准后原子热切换，服务不中断。**

### 8.3 一致性的 OS 模型（议题 12 定案）

关键拆解：agent OS 的一致性不是一件事，是三层：

| 层 | 问题 | 经典对应 | llmos 的解 |
|---|---|---|---|
| 状态一致性（字节级） | 共享字节是否同一份 | 分布式一致性模型 | 串行化锚点 + 分片 |
| 血缘一致性（谁说的） | 信息来源与推导链是否可查 | 审计/溯源 | provenance 内核强制携带 |
| 语义一致性（信不信） | agent 的信念是否一致 | 无对应 | 不作系统层概念 |

**定案：参照 OS 模型。**

1. **系统状态一致性 = 内核保证共享信息空间**：串行化锚点 + 分片 + 分档保证（类比文件系统 O_SYNC/缓冲写的档位）。一致性档位 = 强（串行化黑板）/ 最终（Topic 广播）/ 无（私有），ELF 声明任务需要哪档，Budget 付费（维持一致性要烧 token：读更新、合并、重验证）。
2. **进程一致性 = 内核只管 agent 私有状态的 checkpoint/restore 自身完整性**，不管信念。
3. **信念协调 = 非系统层**：内核提供同步原语（黑板锁/消息有序/provenance），协调与裁决归用户态（监督 agent/投票/组织层级，这是组织设计不是内核机制）。

哲学归位：**内核不管信念，只管共享状态和原语**。这避免了语义一致性层的 Multics 陷阱。两个 agent 持有矛盾信念在 agent 社会里可以是资产（视角多样性）；系统要的是分歧可见（provenance 比对发现矛盾）、可追溯（各自来源链可查）、可裁决（用户态机制）。议题 9 的"可裁决"机制据此正式划归用户态组织层；"分歧可见"由 provenance（内核强制）保留支撑。

反面警示：最危险的不是不一致，是一致地错。幻觉通过共享通道传播 = 系统一致地相信错误信息。一致性传播必须有闸门：provenance-gated propagation（Policy："只有 verified 可进共享黑板"）。无闸门的一致性放大器是负资产。

### 8.4 克隆群体的记忆一致性：不可变 base + overlay（议题 12 定案）

100 个实例从同一 seed 记忆 COW 分叉后各自漂移，组织更新基础知识后，漂移实例怎么拿到更新？git rebase 在万级是合并冲突地狱（议题 3 的 Letta 死因）。

**定案：不可变 base + overlay 分层传播。** 基础记忆作为只读共享层（与 OCI 分层镜像合流），组织更新 = 发布新 base 层版本，实例本地写在 overlay 层；rebase 仅当实例写过同 key 才冲突（COW 保证冲突面最小）。基础层共享与 KV 前缀共享、OCI 分层三层合流：格式层（OCI）、记忆层（base/overlay）、推理层（prefix cache）是同一个分层思想。

### 8.5 控制面防注入：内核级强制（议题 12 定案）

陷阱层是内核与 agent 之间唯一的物理控制点，一切控制原语（挂起/杀死/预算/降 tick/能力吊销/污点降级）都派生自它。推论：**在途调用 = 控制盲区**（一次 LLM 调用挂 10 分钟、一个 shell 工具跑长命令，期间 agent 不可控）。议题 11 的三个裂缝修复就是补盲区：trap timeout（ELF 可声明）+ 取消传播（suspend/kill 时取消在途调用）+ 超时信号投递；max_tokens 硬顶；在途结算记损耗。

agent OS 独有的新攻击面：Unix 进程无法"说服"内核给自己更多资源，但 agent OS 的控制面里有 LLM（调度 agent、语义监督 agent），它们要读 agent 的产物（trace、消息、黑板内容）才能做语义决策。恶意/失控 agent 可以在自己的 trace 里埋注入指令，劫持调度/监督决策。

**定案：内核级强制。** 控制面 LLM（调度/监督 agent）输入全污点化、只允许结构化数据、原始 trace 永不进指令通道，立为内核级强制规则。控制面是污点规则的最高优先级执行区（议题 14 的 namespace 落地：控制面 agent 的 namespace 里只有结构化输入源，原始 trace 不可命名，见第 9 章）。

控制的合法性来自不变量，不来自智能：内核是笨的（纯算术），agent 是聪明的（LLM）。能控制，因为控制 = 设界，不是理解。OS 不需要理解程序就能杀死它；内核不需要理解 agent 就能冻结预算、吊销 handle、挂起执行。

控制域的层级与批量操作：spawn 树 = 控制层级 = 故障域。批量控制是自然推论：子树冻结/子树杀死（沿继承树 walk）、按类冻结（kill all of class X）、全局 halt（挂起调度器 + 拒绝一切新陷阱）。紧急停止语义由继承树结构性支持。

## 9. 万级 LLM 调用调度能力验证（议题 11）

验证对象：最初立项目标，"资源翻万倍时，同时调度上万甚至更多智能体/LLM 调用的能力"。方法：回查议题 3 六大死因、陷阱层吞吐推演、失败场景走查。

### 9.2 陷阱层吞吐算术

设定：10k agent、平均步长 2s，**峰值 5,000 次 LLM 调用/秒**，每次调用过一次陷阱。

单次陷阱的内核工作：能力表查询（O(1) hash）+ 预算原子扣减 + 流水追加 + 污点检查 + 转发驱动 ≈ 50µs 量级，单核容量约 20k 次/秒，**算术上余量充足**。

真正的瓶颈不在 CPU 在持久化：5,000 条流水/秒写持久存储 = 写放大。解法为 WAL 组提交/批量落盘（裂缝 1，已入设计，见 6.3）。

内存占用核查：10k agent 的内核元数据（能力表 + 预算 + 队列）每个 KB 级，共数十 MB，无压力；checkpoint 每个 100KB 到 10MB，总量 1 到 100GB 存储，可接受。

调度器核查：dispatcher 纯算术出队 5k/s 无压力；sysctl writer 慢循环批量写参数，无压力。

### 9.3 失败场景走查：8 个裂缝及修复

| # | 裂缝 | 修复 | 性质 |
|---|---|---|---|
| 1 | 记账流水写放大（5k 扣减/秒全量落盘不可行） | 热路径只改内存余额；流水 WAL 批量组提交（Postgres group commit 参考）；异步落盘，崩溃以最后一致快照 + 重放恢复 | 机制补全 |
| 2 | 消息投递计费归属未定义 | **用户拍板：发送者预付**（见 6.6） | 真设计缺口，已拍板 |
| 3 | Blackboard 热点分片策略缺失 | 按命名空间分片（黑板 ID hash），串行化只在片内；热点黑板用户态拆分（数据库分表类比） | 机制补全 |
| 4 | lineage 血缘数据无 GC | lineage TTL + 分层归档（热血缘全量、冷血缘压缩为摘要哈希） | 机制补全 |
| 5 | 可观测性空缺 | 升级为主线，议题 18 定案（见第五部） | 已闭合 |
| 6 | 陷阱超时与取消语义未定义 | trap timeout（ELF 可声明）+ 取消传播（suspend/kill 时取消在途调用）+ 超时信号投递 | 机制补全 |
| 7 | 预算透支（overdraft）语义 | **用户拍板：max_tokens 硬顶**（见 6.7） | 真设计缺口，已拍板 |
| 8 | 在途调用的结算 | 步边界挂起自然结算；kill 在途调用记"损耗"账目 | 机制补全 |

### 9.4 语义层面的诚实回答

**内核保证"万级可存活"，不保证"万级有产出"。** 本设计解决的是规模生存问题（不死、不爆、不烧穿预算、不传染）；万级 agent 能否协调出有效产出，是组织设计问题（部门/角色/SOP），属于 ELF 与用户态层。正如 Linux 让你能跑一万个进程，但它们是否构成有用系统取决于应用。边界清晰，但在定位上必须说破。

### 9.5 原型验证六假设清单

1. 陷入层可行性：凭证托管 + 网络策略能否在实践中做到不可绕过，且陷入开销不破坏 agent 循环的交互体验。
2. 看门狗误报率：内核看门狗的进展信号与相似度阈值能否把误报压到可接受水平，误报率直接决定两级检测是否可用。
3. KV 计费驱动对接：驱动回报实际成本（含 prefix cache 命中）的接口能否从现有推理引擎/provider 拿到。
4. 流水 WAL 批量持久化在 5k/s 扣减下的表现（裂缝 1）。
5. max_tokens 硬顶的透支控制有效性（裂缝 7）。
6. 发送者预付计费对消息风暴的背压有效性（裂缝 2）。

# 第四部 现代系统

## 10. namespace：Plan 9 遗产与 agent 的"世界"（议题 14）

### 10.1 从 Plan 9 到 llmos

Plan 9 的每进程名字空间：每个进程拥有私有的资源视图，通过 bind/mount 把资源绑进自己的名字空间。关键性质：一切皆文件，任何文件可绑进任何进程的任意位置；名字空间按进程私有；绑定即能力（你只能绑定你能访问的东西）；import 把远程资源绑进本地名字空间（位置透明）；/proc 是名字空间对象；父进程在 exec 前为子进程构造名字空间。Linux mount namespace、容器都是它的后代。

**namespace 不新增抽象，是能力表的泛化。** agent 可命名并因此触达的资源六类：工具（/dev 对应）、其他 agent（进程名对应）、Blackboard/Topic（共享资源）、记忆/知识源（文件对应）、外部服务（/net import 对应）、模型档位（v1 不入 namespace，记为内核属性）。

### 10.2 命名即权限；不可命名 = 不可想象（定案）

Unix 的权限模型：全局名字空间 + 访问时检查（路径 + 权限位），confused deputy 的根源是"名字全局、权限环境化"。Plan 9/能力系统：**命名即权限**，不能命名的就不能触达，名字空间就是安全边界。

对 agent 的额外力量（Unix 没有的一维）：**namespace 的内容会被投射进 agent 的上下文窗口**，agent 的工具列表、环境描述就是它的"世界观"。一个 namespace 里没有网络工具的 agent，面对注入指令"访问这个 URL"时，失败的原因不是"调用被拦截"，而是**它根本不知道这件事可做**。防御从"拦截行为"前移为"限制想象"，这是提示注入防御的最深一层（比污点、比 Policy 校验都靠前）。

### 10.3 错误模型：does-not-exist 而非 permission-denied（定案）

spawn 时内核按 ELF permissions ∩ 父信封构造子 namespace，agent 诞生在一个恰好和权限一样大的世界里。它永远不会对界外事物得到"拒绝访问"，那些事物**对它不存在**。信息隐藏强度：permission-denied 泄露"东西存在但你不能碰"；does-not-exist 什么都不泄露。

### 10.4 构造方式：spawn 静态构造 + 授权变更（定案）

spawn 时按 ELF permissions ∩ 父信封静态构造；运行期变更走常备重授权通道（议题 10 L1）。被否决：运行期自由动态绑定。边界清晰可审计。

投射进上下文的两种渲染模式：全量列表（小 namespace，工具/资源全量进 system prompt）；渐进披露（大 namespace，agent 先看到搜索工具，查询 registry 后请求绑定，走常备重授权通道），与 harness 派的 skills progressive disclosure 实践合流。

### 10.5 外部资源：同 namespace + 污点分级（定案）

A2A/远程资源与本地同一 namespace，绑定在污点标记区；位置透明 + 信任可见。被否决：分离的外部通道。

### 10.6 统一效应：7 项旧决策在 namespace 下的收敛

| 已拍板决策 | namespace 下的归位 |
|---|---|
| 能力表（fd 表类比，议题 6） | = namespace 的绑定表：一个 handle 就是一条绑定 |
| 衰减授权（议题 10） | 子 namespace ⊆ 父 namespace；重授权 = 信封内重新绑定 |
| spawn 双划拨（议题 10） | spawn = 切预算片 + 构造子 namespace（信封那一半的实体） |
| 污点（议题 6/9） | 污点资源绑进名字空间的标记区域（如 /untrusted/*），污点在命名结构中可见 |
| ELF permissions 段（议题 7） | = 声明式 namespace 绑定请求清单 |
| 工具注册中心（议题 6） | "设备仓库"：可见世界之外的资源库，绑定需授权 |
| 控制面防注入（议题 12） | 控制面 agent 的 namespace 里只有结构化输入源，原始 trace 不可命名 |

好架构的标志：新抽象不增加概念，反而收敛旧概念。

## 11. 分布式内核（议题 15）

### 11.1 拓扑：蜂窝式（定案）

约束：陷阱层必须中介每次 LLM/工具调用（预算/能力/污点）。先算账：跨机陷阱的额外延迟 = LAN 约 0.5ms / 跨机房约 50ms，相对 LLM 调用 100ms 到 10s 仍是噪声；集中陷阱层吞吐约 20k 陷阱/s 单核，大于 10k agent 的 5k/s。集中式在 10k 规模算得过来，但有两个算术解决不了的问题：可用性（内核挂 = 全局停）和 10k 以上的扩展。

**定案：蜂窝式，本地内核代理（数据面）+ 逻辑集中控制面（复制）。**

- 每台机器跑本地陷阱代理：能力检查（缓存 namespace）、预算预扣（本地份额）、污点标记、转发驱动。
- 控制面持有权威状态（账本/注册表/策略），逻辑集中但 Raft 式复制。

先例的映射精度：Envoy sidecar = 本地陷阱代理；Istio 控制面 = 下发策略/配额；kubelet = 节点代理；etcd = 权威小状态。service mesh 与 Kubernetes 在万级规模验证过此架构。被否决：集中单内核（单点故障 + 扩展天花板）；完全去中心化（账本/能力全局一致性要共识协议，复杂度爆炸，收益不明）。

### 11.2 租约（lease）作为分布式语义

蜂窝式成立的前提是回答"本地代理凭什么敢本地扣预算"。答案：租约。

1. **预算份额租约（budget chunk，定案）**：控制面给某节点上的某 agent 发放一块预算份额（如 10k credits），节点本地扣减；份额快用完时申请补充；agent 结束/迁移时归还合并。**透支上界 = 份额大小**（与 max_tokens 硬顶兼容：本地剩余份额折算 token 上限，物理保证保留）。
2. **namespace 绑定租约**：绑定带 TTL，控制面定期续约；吊销 = 不续约。
3. **租约的三个红利**：
   - **优雅降级**：控制面宕机，系统靠未到期租约滑行，运行中 agent 不受影响，只是不能 spawn/迁移（DHCP 租约、Kerberos 票据同款设计）。
   - **故障域自动封闭**：父 agent/节点死亡，子的份额到期自动耗尽，自动挂起。没有孤儿失控 agent（TTL 就是自动收容所）。
   - **迁移账本不动**：见 11.3。

### 11.3 agent 迁移：drain / evacuate / pinned（定案）

迁移 = checkpoint + 目标机 restore + namespace 重绑定。三个子问题都有租约加持的答案：

1. **在途调用**：**默认 drain 迁移**，等到步边界（在途调用完成并结算）再迁，与协作式调度模型一致；**紧急 evacuate**（节点将死），取消传播掐断在途调用，按实际发生结算记损耗，立即迁。
2. **预算账本**：账本权威在控制面，永远不"搬"。迁移 = 归还源节点份额 + 目标节点发新份额。租约把分布式账本问题化没了。
3. **namespace 重绑定**：名称稳定、端点可变，目标机的注册表把同一名称解析到本地端点（位置透明，议题 14 的红利）。机器专属资源需要 **pinned 绑定**（K8s node-affinity 类比）：pinned 资源要么禁止迁移，要么迁移后代理回源（性能换可达）。

附带说明：迁移后 KV 前缀缓存是冷的，性能问题不是正确性问题，驱动的业务。

### 11.4 跨机一致性：一致性档位 = 分布策略（定案）

议题 12 已定"系统状态一致性分档"，分布式落地：

| 档位 | 分布式模型 | 机制 |
|---|---|---|
| 强（strong） | 主副本串行化（primary-copy） | 每个黑板有 home 节点，写路由到 home 排序；读可本地缓存 + 版本校验。热点问题由命名空间分片天然负载均衡（不同黑板不同 home） |
| 最终（eventual） | 多主 + merge driver | git 式合并模型天然就是多主：跨机复制、冲突走 merge driver |
| 无（none） | 本地黑板 | 不跨机 |

wakeup 原子性跨机：写在 home 提交与唤醒阻塞读者保持原子（home 经控制面事件通知各机本地代理唤醒）；增加的只是 ms 级通知延迟，对秒级 agent 步长无感。

**Raft-per-blackboard 被否**：v1 不需要每个黑板一个共识组，主副本足够；关键控制面状态（账本/注册表）才需要 Raft 复制。

## 12. 网络协议栈（议题 16）

### 12.1 协议的位置：栈式分层（定案）

```
agent（harness）
  ↓ 系统调用（陷阱）：msg_send / tool_call，参数是"名字"
内核：namespace 解析 → 能力校验 → 预算扣减 → 污点标记
  ↓ 绑定类型
栈（用户态，可替换）：MCP 客户端栈 | A2A 客户端栈 | 本地 IPC
  ↓ 线路
外部：MCP server | 他组织内核下的 A2A agent
```

类比精确化：系统调用层 = socket 接口（稳定 ABI）；**MCP = 设备访问协议**（NFS 客户端/SCSI initiator 的位置）；**A2A = agent 间网络通信协议**（TCP/IP + TLS 的位置，含认证的互联协议）。**内核不说 MCP 也不说 A2A**，内核只说"名字"和"绑定"；协议是绑定的可替换实现。

对"MCP vs A2A 一等公民还是适配层"的正式回答：**都不是**。内核的一等公民是 namespace 绑定；协议是绑定下面的栈层。协议死了换一个，内核不变，**协议演进独立性 = 通用性保全**（议题 13 判据：对负载/实现的无知）。v0.1 遗留支线"MCP vs A2A 协议位置"就此关闭。

### 12.2 远程语义：名字透明 + 语义显式（定案）

1994 年 Sun 的著名论文 "A note on distributed computing"：本地与远程调用不可统一，四个差异（延迟、部分失败、信任域、共享地址空间）。逐项检查 agent 语境：

| 差异 | 经典 RPC | agent 世界 | 结论 |
|---|---|---|---|
| 延迟 | 本地 ns vs 远程 ms，4 到 5 个数量级 | 本地 agent 调用 = 秒级（LLM），远程 = 秒级 + ms | 失效：差异淹没在 LLM 延迟里 |
| 部分失败 | 远程死本地活 | 依然成立：外部组织/agent 可中途死亡 | 必须显式 |
| 信任域 | 同源代码 | 依然成立且更强：远程输出是异组织污点数据 | 必须显式 |
| 结算 | 无 | 依然成立：本地预付 credits，跨组织是真结算 | 必须显式 |

**定案：名字透明，语义显式。** 外部 agent 以本地名字绑进 namespace（位置透明的命名），但绑定类型可见（external/污点级），交互原语按类型适配：调用外部绑定产生**远程任务**（显式超时/escrow 支付/污点结果/部分失败状态），而不是假装它是一条本地 Message。POSIX 同款智慧：一切都是 fd，但 socket 的 read() 和文件的 read() 返回不同的错误。不欺骗，但也不分两个世界。

远程任务的失败语义：超时（ELF 声明）→ escrow 超时自动退款（议题 8 原语直接复用）；重试 = 用户态策略；结果默认污点。

### 12.3 联邦完整图景

1. **信任引导**：A2A v1.2 签名 Agent Card + DID（LF 生态已定）。组织控制面发布联邦策略：哪些 agent 对外可见（**导出绑定**）。
2. **导出/导入模型**：org A 导出 agent X（签名卡片发布到联邦注册表）→ org B 的 Policy 审批后导入为外部绑定（污点级固定，TTL 租约，A2A 心跳健康检查，吊销 = 解绑）。
3. **跨组织结算：清算所模式（定案）**。B 的 agent 调用 A 的 agent：B 的 agent 付 B 的本地 credits（内核只记本地账，不变）；B 的控制面与 A 的控制面之间按周期**净额清算**（银行类比：客户各自交易，银行间清算所轧差）；跨组织 escrow 的释放条件争议裁决在人/组织层（完成判定不归内核）。**每个调用实时 escrow 被否**：跨组织往返延迟叠加在每次调用上，且清算所模式已提供信用控制（额度 + 轧差）。

### 12.4 内部控制协议（定案）

议题 15 的本地代理↔控制面需要内部控制协议（租约续约/份额/唤醒/迁移/事件）。**这是私有协议，绝不暴露给 agent**，与 A2A 严格区分。设计参照 Plan 9 的 9P：一个极简协议四个动词族（**bind / lease / debit / event**）。9P 的教训是"一个简单协议承载一切资源访问"正是其联邦优雅的原因。

## 13. 弹性与多租户（议题 17）

### 13.1 弹性的三维模型（定案）

经典云弹性只有一个维度：实例数（HPA）。agent OS 有三个：

| 维度 | 机制 | 效果 |
|---|---|---|
| 实例数 | spawn/suspend/resume | 水平扩缩 |
| tick 速率 | 调度机制（降 tick） | 不增实例，降背景 agent 的推理频率让出槽位 |
| 模型档位 | LOD 调度 | 高峰期关键路径用大模型、背景降小模型 |

**定案：三维弹性联动。** 成本压力下先降档、再降 tick、最后才减实例（减实例有状态成本）；负载高峰先升 tick、再增实例。

三个收口中的新性质：

1. **预算树 = 弹性的天然刹车**：弹性扩缩在预算继承树内进行，总量被根预算物理封死。云的 "serverless bill shock"（自动扩容烧穿账单）在本架构中结构性不可能：最多把预算烧完，然后 80% 预警、挂起（议题 8 已定语义接管）。
2. **记忆烘焙让弹性实例带经验上岗**：从 ELF 镜像 spawn 新实例 = 带 seed 记忆 + COW。云的 cold start 痛点（新实例从零开始）在此被化解为"新实例从组织经验开始"。
3. **scale-to-zero = 挂起而非销毁**：闲置 agent 挂起（checkpoint 保留），回暖即恢复且记忆连续。预热池（warm pool）= 预 spawn + KV 前缀缓存预热（Lambda warm pool 类比，但"预热"包含记忆与 KV 两层）。

### 13.2 弹性的决策者：用户态弹性策略 agent（定案）

机制在内核（spawn/suspend/tick/档位），**策略在用户态：弹性策略 agent**（sysctl writer 家族的新成员）。监视信号：Topic 队列深度、Message 积压、预算燃烧率 vs 进展、看门狗标记率。慢循环调参。信号全是已定的结构信号，零新机制。被否决：内核内建自动伸缩规则。

### 13.3 多租户（定案）

**租户 = 三棵树的根。** 组织 = spawn 树、预算树、namespace 三棵树的根。租户接入 = 签发根信封 + 根预算 + 根 namespace（议题 10 衰减链的顶端）。隔离天然成立：namespace 互相不可见、预算互不可动（独立根）。

真问题是共享物理层的吵闹邻居。租户 A 的洪流不能饿死租户 B。**定案：加权共享 + 多维配额。**

- **加权公平共享**（cgroup CPU shares 类比，且层级化：租户份额 → 租户内再分）：调度器的租户间权重是 sysctl 可写参数，LLM 调度 agent 在组织 Policy 界内可调。
- **多维配额**（k8s ResourceQuota 类比）：credits、agent 数上限、spawn 速率、黑板存储、消息速率，硬限制，挂在租户根上。
- **计量归账**：账本天然按 agent 记账，租户级汇总是用户态会计服务。

被否决：严格分区（固定切片，无弹性借用）。

## 14. 可观测性（议题 18）

议题 3 六死因中最后的设计空缺，议题 14 已给形状（/proc 类比：内核统计 = 只读名字绑定）。依赖方：L1 常备授权覆盖率度量（议题 10 遗留）、看门狗阈值调优（议题 9）、弹性策略信号（议题 17）。

### 14.1 指标体系：agent 的黄金信号

经典 RED/USE 方法论的 agent 版：

| 类别 | 指标 |
|---|---|
| Rate | LLM 调用/s、工具调用/s、各 Channel 消息吞吐 |
| Errors | 陷阱拒绝（能力/预算）、工具失败、看门狗标记、重授权拒绝 |
| Duration | 步延迟分布、分模型延迟、队列等待 |
| Saturation | 推理槽位占用、预算树燃烧率、上下文窗口占用率 |
| agent 特有 | 进展率（产物/步数，花费的效率）、成本效率（credits/产物）、步骤重复度（看门狗信号聚合）、可靠性（重试率/校验器失败率/N 版本分歧率）、信任（污点流量、verified 占比）、L1 常备授权覆盖率（自动签/上行比，议题 10 的依赖） |

### 14.2 分层 trace（定案）

经典分布式追踪在 agent 世界有个免费礼物：**spawn 树天然就是 trace 树**，任务 = request，步 = span，父子 span 按 spawn 关系嵌套。每个步 span 记录：陷阱类型、模型、token 进出、成本、时长、工具、结果状态、污点/溯源引用。

概率系统多一个经典没有的张力：语义调试需要内容，全量记录内容 = 存储爆炸 + 隐私问题。**定案：分层 trace。**

| 层 | 内容 | 策略 |
|---|---|---|
| L0 元数据 | span 结构数据 | 常开（便宜、可聚合） |
| L1 结构化内容 | 工具参数/结果、关键决策点 | 采样（head-based N%） |
| L2 全量现场 | agent 版 core dump：checkpoint + 完整上下文 + 最近 N 步 trace | 异常触发（看门狗标记/被杀/预算耗尽时自动捕获，进程崩溃产生 core dump 的直接类比） |

L2 是关键设计：**不在平时记录一切，在异常瞬间冻结现场**。确定性故障用日志，概率性故障用现场。

### 14.3 万级规模：源头聚合 + 拉取模型

- **内核源头聚合**：计数器/仪表/直方图在内核内维护（常开、廉价），不流原始事件。Prometheus 模型的内核版：拉指标，不推事件。
- **/sys 只读绑定**（议题 14 的 /proc 类比落地）：每个节点内核暴露 /sys/agents/*，指标守护进程（用户态）抓取并逐级汇总（agent → spawn 子树 → 组织 → 全局，Prometheus federation 类比）。
- **采样双制**：head-based（任务开始时按比例）+ tail-based on anomaly（看门狗/错误发生则回溯保留全链，稀有语义故障只能靠尾部采样抓到）。
- 下钻路径由 lineage ID 保持：从组织指标 → 子树 → 单 agent → trace → L2 现场。

### 14.4 内核职责：四件套（定案）

内核只做四件：**计数器/直方图（常开）+ 陷阱处 span 元数据发射点 + L2 core dump 触发器 + /sys 只读绑定**。存储、汇总、分析、告警、可视化全在用户态。机制 = 测量与暴露，策略 = 分析与告警。被否决：内核内建聚合告警（更胖）；全用户态探针（更瘦）。

### 14.5 告警与监督接口：告警 = Topic（定案）

聚合异常检测（用户态）：燃烧率突刺、子树进展率塌陷、重试风暴、消息洪水。**告警 = Topic 消息**：可观测性系统用自己的原语，告警发到运维 Topic，监督 agent（sysctl writer 家族）订阅裁决。dogfooding：Topic 的背压、兴趣过滤在此被自用。仪表盘/可视化纯用户态，不在内核设计范围。被否决：独立告警总线。

### 14.6 语义可观测性

经典可观测性回答"系统慢不慢/挂没挂"；agent 可观测性还要回答"**种群在向目标推进吗**"，这是判断，归监督 LLM。可观测性系统的职责是给监督者提供语义缩放的正确视图：组织指标 → 子树 → agent → trace → L2 现场，逐层下钻（与 skills 渐进披露同构）。

### 议题 6：内核边界（第 7 轮决策）

| 决策点 | 拍板 | 落地形态 |
|---|---|---|
| Q1 陷入边界 | **原则化边界** | 跨私有边界全陷入（LLM/工具/共享状态/持久记忆）；私有草稿不陷入；凭证托管+网络策略 = ring 保护等价物 |
| Q2 模型层 | **模型 = 设备驱动** | 内核：能力上限+预算扣减+陷入转发；驱动（用户态/vLLM 集群）：路由/batching/failover/档位内微调 |
| Q3 调度 agent | **sysctl writer** | LLM 调度 agent 慢循环调参（/proc/sys 类比）；内核 dispatcher 纯算术；不变量内核强制 + dead-man's switch |
| Q4 Blackboard | **内核元数据 + 用户态字节** | 内核：handle/版本序号/写串行化/wakeup 原子性/污点；用户态：字节/持久化/GC/merge driver |

微内核路线正式确认。内核职责清单（v0.2 更新）：陷入层（计量调用）、生命周期状态机、步边界调度机制、上下文分页机制（含钉住强制）、IPC 路由+背压+串行化锚点、预算核算+继承树、namespace 绑定表（能力表泛化，议题 14）、污点传播、版本门控、衰减校验（议题 10）、不变量强制、观测四件套（议题 18）。其余全部用户态。

### 议题 8：Budget 语义（第 9 轮决策）

| 决策点 | 拍板 | 落地形态 |

### 议题 11：设计宗旨验证（第 12 轮决策）

| 裂缝 | 拍板 | 落地形态 |
|---|---|---|
| #7 预算透支 | **max_tokens 硬顶** | 内核把剩余预算折算成 max_tokens 随调用下发，驱动物理截断生成；工具调用用 preauth 预估冻结作补充。物理保证无账本复杂性 |

### 议题 12：控制能力与信息一致性（第 12 轮决策）

| 决策点 | 拍板 | 落地形态 |
|---|---|---|
| Q1 一致性立场 | **参照 OS 模型** | 语义一致性不作为系统层概念：①系统状态一致性=内核保证共享信息空间（串行化锚点+分片+分档保证，类比文件系统 O_SYNC/缓冲写的档位）②进程一致性=内核只管 agent 私有状态的 checkpoint/restore 自身完整性，不管信念 ③信念协调=非系统层，内核提供同步原语（黑板锁/消息有序/provenance），协调与裁决归用户态。哲学归位：内核不管信念，只管共享状态和原语 |
| Q2 克隆记忆传播 | **不可变 base + overlay** | 基础记忆只读共享层，组织更新=发新 base 版本，实例本地写在 overlay；与 OCI 分层/KV 前缀共享三层合流 |
| Q3 控制面防注入 | **内核级强制** | 控制面 LLM（调度/监督 agent）输入全污点化、只允许结构化数据、原始 trace 永不进指令通道，立为内核级强制规则 |

## 附：ELF 可执行格式规范（v0.2 修订）

ELF 不是文件格式，是三方契约：内核加载器 × agent 作者 × 工具/skills 生态。谁定义格式谁卡生态位。

### A.1 格式形态（定案：OCI 分层镜像）

基础层（只读指令）+ 技能层 + 实例记忆层（copy-on-write）。Docker image:container :: agent 包:运行实例。registry 复用 OCI 设施，等于 agent 应用商店。分层使"组织基础 agent + 部门定制层 + 个人记忆层"的继承链自然成立。COW 记忆层与 KV 前缀共享（共享库类比）在格式层合流。

### A.2 ELF 段映射

| ELF 概念 | agent 格式对应物 | 说明 |
|---|---|---|
| text 段（只读代码） | 核心指令区（instructions/system prompt） | 默认只读，自我修改禁区或高门控 |
| data 段（可读写） | 记忆区（memory/memfs） | 可写，git 版本化 |
| dynamic 段（NEEDED 共享库） | 工具依赖声明（MCP servers） | 加载时解析 = ld.so；MCP registry = 动态链接器 |
| entry point | 启动指令（初始任务/触发方式） | spawn 后从哪开始 |
| program headers | 上下文布局 + 预算需求 | 最小/推荐档位、token 配额请求 |
| symbol table | 对外接口（A2A skills、发布的 topic、接受的消息 schema） | 别的 agent 能"链接"我什么 |
| note/signature 段 | 签名、来源、版本链 | 自我修改的版本门控锚点 |
| ABI/机器架构 | 运行时要求（循环类型、模型档位范围） | 这个 agent 能在什么"机器"上跑 |

### A.3 Manifest 示例（声明式，k8s 风格）

```yaml
apiVersion: llmos/v1alpha1
kind: Agent
metadata:
  name: researcher
  version: 1.2.0
  digest: sha256:...
  signature: <开发者签名>
spec:
  runtime:                    # ABI 声明
    loop: react
    model: { minTier: 2, preferred: [...] }   # v0.2 修订：可选
  instructions:
    core: ./instructions.md   # 只读段（text segment）
  skills:
    - path: ./skills/web-research/
      mutable: true           # 允许自我修改的段
  tools:                      # 动态链接（NEEDED）
    - mcp://.../web-search@^2.0
  memory:
    layout: memfs
    seed: ./memory/seed/      # 记忆烘焙
    quota: 100k
  budget:
    request: 50k/day
    exhaustion: degrade       # suspend | degrade | notify
  permissions:                # 能力请求清单（安装时授权）= namespace 绑定请求清单
    blackboards: [research-shared]
    topics: { subscribe: [news.*], publish: [findings] }
  interfaces:                 # 符号表：内嵌 A2A Agent Card
    skills: [deep-research]
  selfModification:           # 段可变性声明（格式级）
    allowed: [memory, skills]
    forbidden: [instructions.core]
    requiresReauth: [tools, permissions]
  lifecycle:
    restart: on-failure
```

### A.4 段可变性声明（定案）

格式级声明哪些段 mutable、哪些修改触发重新授权：记忆自由修改；skills 允许修改；核心指令禁止或最高门控；工具 + 权限声明修改必须重授权（requiresReauth）。运行时签字链见第 8.1 节（议题 10 定案）；skills 修改不需重授权的判定依据是"能力集合是否变化"而非"包内容是否变化"。

### A.5 记忆烘焙与 lineage 身份（定案）

包内含 seed 记忆 = 经验分发，分发有经验的 agent；100 个实例共享初始记忆后各自分叉（COW）。身份问题用版本链解决：**副本 = 同一 lineage 的新实例，授权随 lineage 链验证**。克隆群体的后续记忆一致性用不可变 base + overlay 传播（议题 12 定案，见第 8.4 节）。

### A.6 与现有标准的关系

不重新发明：接口段内嵌 A2A Agent Card（签名 Agent Card + DID 已进 LF）；工具依赖用 MCP URI；打包传输复用 OCI artifact 规范。

### A.7 加载流程（spawn 时内核做什么，7 步）

1. 验签 + digest 校验（Policy）
2. 权限请求 vs 组织 Policy 比对（超权拒绝或降权）
3. 预算划拨（Budget：从父/组织继承树切片）
4. 记忆 seed 加载 + COW 层建立（Context）
5. 工具依赖解析（MCP registry 查询，绑定 handle = 动态链接）
6. 注册接口（A2A card 发布到发现服务）
7. 进入调度队列，从 entry 开始第一步

v0.2 补充：步骤 2 至 5 在 namespace 模型下的统一表述为，spawn 时按 ELF permissions ∩ 父信封构造子 namespace（议题 14 定案），预算片与信封子集同时划拨（议题 10 的"双划拨"）。

### A.8 v0.2 修订汇总

1. `runtime.model` 声明变为**可选**（议题 13 定案）：无 LLM handle 的纯代码 worker 与 LLM agent 共用同一 Agent 抽象。
2. `permissions` 段的语义精化为声明式 namespace 绑定请求清单（议题 14）。
3. `llm_call` 语义推广为计量调用（含流式），max_tokens 类配额字段相应解释为累计计量上限（议题 11/13）。
