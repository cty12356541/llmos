## 零、最高优先级北极星：Windows/macOS 级通用现代 NLOS

### 0.1 不可被阶段性建议覆盖的终局

llmos 的最终目标不是：

- 一个 Agent 编排框架；
- 一个 LLM API 代理；
- 一个预算或权限治理中间件；
- 一个语义知识库；
- 一个 Kubernetes 控制器；
- 一个只能运行预设工作流的垂直平台。

它的最终目标是：

> **为自然语言驱动的智能工作负载建立一个达到 Windows/macOS 级别的通用现代操作系统：拥有稳定的系统抽象、内核与系统服务、应用模型、开发者平台、用户交互界面、兼容性承诺和可持续演进的应用生态。**

本评估中“当前还不是一个已实现的 OS”“先实现 reference monitor”等判断，只描述当前成熟度和正确的启动顺序，不改变项目身份，也不构成永久缩窄产品范围的建议。

### 0.2 “Windows/macOS 级别”的准确含义

这里的“级别”不要求 NLOS 在第一天重写硬件驱动、文件系统或取代 Linux/Darwin，而是要求它最终具备同等级别的系统完整性：

1. **通用性**：第三方可以开发设计者事先没有预见的 NLOS 应用，而无需修改内核。
2. **系统权威性**：进程、身份、能力、资源、通信、存储和生命周期由系统统一裁决，而不是依赖每个应用自觉遵守。
3. **现代性**：原生支持多设备、分布式、云边协同、多租户、联邦身份、迁移、恢复和持续升级。
4. **人机界面完整性**：拥有自然语言桌面、Shell、多模态交互、通知、权限确认、任务管理和可视化系统状态。
5. **开发者平台**：拥有稳定 ABI/API、SDK、调试器、包格式、驱动模型、测试工具和文档。
6. **应用生态**：拥有可发现、安装、组合、授权、升级和卸载的应用/Agent/Skill 生态。
7. **兼容性与演进**：旧应用能够跨版本继续运行，系统升级不要求生态整体重写。
8. **长期运行品质**：安全、隐私、性能、可访问性、故障恢复、审计和运维达到真正系统软件的标准。

Windows/macOS 的壁垒从来不只是内核；稳定契约、系统服务、开发工具、用户体验和应用生态同样属于 NLOS 的终局范围。

### 0.3 NLOS 的完整系统分层

推荐以如下完整分层作为长期架构地图：

```text
自然语言桌面 / Shell / 多模态交互
任务空间 · 窗口与通知 · 权限确认 · 系统设置
                    ↓
应用与用户态生态
Agent 应用 · Workflow · Harness · Skills · 第三方软件
                    ↓
现代系统服务
身份 · 包管理 · 搜索 · 语义存储 · 审计 · 更新 · 联邦
                    ↓
NLOS 通用内核
Agent 进程 · Context · IPC · Topic · Blackboard
Capability · Namespace · Budget · 调度 · 隔离 · Checkpoint
                    ↓
设备与驱动
模型 · Tool · 数据库 · 浏览器 · 人类 · 机器人 · 外部服务
                    ↓
宿主基础设施
Linux / Darwin / Windows / Cloud / Kubernetes / GPU / Network
```

在早期，NLOS 可以作为 hosted OS 运行在现有操作系统和云基础设施之上。它不必先取代 Linux/Darwin，关键是成为智能工作负载的系统权威：统一应用模型、资源模型、权限模型、设备模型和用户体验。

随着抽象和生态成熟，NLOS 可以逐步拥有更深的宿主控制权，但“是否裸机”不是判断其是否为自然语言操作系统的首要标准。

### 0.4 启动内核不是最终边界

确定性执行与审计层是 NLOS 最先必须成立的部分，因为没有它：

- 应用无法互相信任；
- 预算和资源没有系统级上界；
- 权限只能靠 prompt 约定；
- 第三方应用不能安全共存；
- 语义状态无法审计和恢复；
- 上层桌面与生态没有可信地基。

因此：

> **agent reference monitor / deterministic control plane 是 NLOS 的 bootstrap kernel，不是最终产品定义。**

短期实现可以窄，但核心抽象和兼容契约必须为未来完整系统保留演化路径。不能为了做出 MVP 而把 Agent、Context、IPC、Topic、Blackboard、package/ELF、系统服务和用户态生态永久降格为外部附属物。

### 0.5 北极星轨道与证据轨道必须并行

项目需要同时维持两条不可互相替代的轨道：

#### 北极星轨道

- 维护完整通用现代 NLOS 的系统地图；
- 评估每次局部决策是否封死未来通用性；
- 定义长期 ABI、应用模型、驱动模型和用户体验；
- 持续回答“第三方应用如何在这个系统上生长”。

#### 证据轨道

- 严格区分愿景、规范、原型和生产事实；
- 从最小内核纵切面开始兑现不变量；
- 通过并发、崩溃、攻击、真实 provider 和分布式测试逐级晋升；
- 不把终局愿景提前写成当前已经实现的能力。

正确原则不是缩小终局，而是：

> **终局保持完整，实施保持克制；架构面向 Windows/macOS 级系统，证据从最小可信内核逐层累积。**

## 一、执行摘要

llmos 的不可变终局是 Windows/macOS 级通用现代 NLOS。当前仓库尚未实现这一终局；它目前最成熟的成果是一套原创性很强的“概率智能体确定性运行时宪法”，这是完整 NLOS 的启动内核。

当前阶段最有价值的不是单独依赖 OS 类比，而是已经找到一条能够长成完整系统的内核原则：

> **模型负责理解和提出行动；内核只在不可绕过的边界上强制能力、成本、生命周期和知识来源。**

成熟度评估：

| 维度 | 评价 |
|---|---|
| 核心思想与研究价值 | 强，且有明确辨识度 |
| 架构主轴自洽性 | 较强 |
| 研究方法 | 良好，但存在过早“定案” |
| 规范一致性 | 中等偏弱，最新版内部已有冲突 |
| 实验证据 | 局部实现较扎实，外部有效性较弱 |
| 工程完成度 | 组件原型阶段 |
| 生产可用性 | 尚未达到 |

建议坚定保留完整 NLOS 终局，同时暂时停止扩大尚无证据支撑的“超级框架/语义完备性”理论边界，先把最核心的运行时纵切面做实，再沿系统服务、现代分布式能力、自然语言桌面和应用生态逐层扩张。

## 二、项目真正的核心哲学

### 2.1 概率智能属于用户态，确定性不变量属于内核态

“内核从不信任，只设界”是整个项目真正的轴心，而不是某个具体的 Agent 编排模型。

证据：

- [架构总纲的核心原则](./04-架构设计总纲-v0.4.md#13-四条设计原则)
- [内核边界的机制/策略判据](../discussions/06-内核边界.md)

其隐含公式是：

```text
智能    = 不可信用户态
权力    = capability + namespace
资源    = reserve / settle ledger
知识    = immutable claim events + attestations
委托    = spawn(资源、权限、义务)
```

不要期待 LLM 自觉遵守预算、权限和审计规则，而应让系统边界成为 reference monitor。这是 llmos 最坚实的哲学地基。

### 2.2 控制不需要理解

项目最漂亮的洞察之一是：

> **控制 = 设界，而不是理解。**

内核不需要知道 agent 为什么调用工具，只需判断：

- 它是否拥有相应 handle；
- 预算是否充足；
- 调用是否越过 namespace 或污点边界；
- 状态迁移是否合法；
- 请求是否需要被挂起、拒绝或审计。

调度 LLM 因而不是 dispatcher，而更像低频的 sysctl writer。它可以建议策略和调参，但不能自行改写不变量。

这比“把 LLM 当 CPU”准确得多。llmos 更接近一个面向随机执行主体的能力安全运行时。

### 2.3 形式化知识的社会学，而不是形式化意义本身

语义层最有原创性的命题是：

> **内核不判断一段自然语言是真是假；它只记录谁说的、基于什么产生、谁验证过、用什么方法验证、何时被质疑或撤回。**

“内核可以对信封执法，不可以对信封思考”是很好的宪法边界。

证据：

- [符号主义边界](../discussions/24-符号主义边界.md)
- [语义原子](../discussions/21-语义原子.md)
- [语义规范化](../discussions/22-语义规范化.md)

这实际上把知识系统从“全局真假字段”改造成：

- 不可变断言事件；
- provenance DAG；
- 验证与争议事件；
- 并存而非强制统一的关系图；
- 面向不同使用者的可信视图。

这套认识论模型比普通 RAG/知识库设计成熟得多，也是整个项目最可能形成长期护城河的部分。

### 2.4 委托同时是资源、权限和义务的划拨

`spawn` 不应只是创建子 agent，而应同时划拨：

1. Budget；
2. namespace/capability；
3. 子 IntentSpec。

这个“三划拨”把递归委托从 prompt 技巧升级成可审计的制度关系，是项目最值得优先工程化的抽象之一。

证据：

- [Agent 与三划拨](./04-架构设计总纲-v0.4.md#41-agent计算族进程对应物)
- [意图规格](../discussions/23-意图规格.md)

### 2.5 可靠性、验证强度与一致性都是可购买档位

项目没有假装随机智能能够获得绝对正确性，而是主张用预算购买：

- 重试；
- 多版本执行；
- 确定性 checker；
- 独立 verifier；
- 人工审批；
- 更强的一致性档位。

这是比“agent 自己反思一下”更诚实的系统思想。

### 2.6 分歧应显式存在，而不是被强制统一

两个 agent 持有矛盾信念，在智能体系统中可能是常态，甚至是资产。内核应保证：

- 分歧可见；
- 来源可追踪；
- 判断者及判断方法可审计；
- 错误判断可以通过事件撤回；
- 用户态可以构造不同可信视图。

内核不应构造一个虚假的全局真理状态。

## 三、思想演进与方法论

### 3.1 思想演进

项目的演进路径大致是：

1. **框架比较**：从 LangGraph、AutoGen、CrewAI 等框架发现分歧本质是“控制流归谁”。
2. **万级压力测试**：发现现有系统大多是 library，而不是负责资源、不变量和隔离的 kernel。
3. **v0.1 OS 骨架**：形成 Agent/Context/Tool/Message/Topic/Blackboard/Budget/Policy、trap、ELF、随机性管理等骨架。
4. **v0.2 方向修正**：明确“规模是压力测试，通用才是宗旨”，把治理从项目灵魂归位为基础设施。
5. **v0.3 实验主义**：危险假设先做最小原型，再回写设计。
6. **v0.4 语义扩张**：加入 SemanticAtom、LinkAtom、IntentSpec、八原语和形式化宪法。
7. **议题 25 反例修订**：O*NET 反例迫使“全部知识工作”收窄为“知识变换成分”。
8. **v0.4.1 外部评审修订**：补入预算五元组、hard/soft gate、verified 防伪、控制面纵深和 CRDT merge。

其中最健康的转折是 v0.2 的“规模是压力测试，通用才是宗旨”；风险最大的跃迁是 v0.4 从运行时设计扩大为语义计算理论。

### 3.2 方法论优点

项目采用了六种主要方法：

1. 历史类比迁移：区分照抄、变换和新发明；
2. 极端规模压力测试；
3. 机制/策略双问测试；
4. 现有模式的用户态重构测试；
5. 先写判定标准，再做实验；
6. 外部敌对评审和反例驱动修订。

尤其值得肯定的是，O*NET 反例迫使理论从“任意审慎型知识工作”收窄为“其中的知识变换成分”：

- [构造性证明的修订版定理](../discussions/25-构造性证明.md#六onet-广泛任务普查与定理边界修订)
- [O*NET 普查证据](../discussions/onet-census.md)

这说明项目具备真实的自我修正能力，而不是只寻找支持性例子。

### 3.3 方法论的系统性缺陷

当前最大问题是证据等级塌缩：

> “设计上存在对应机制”“模型内不变量成立”“mock 测试通过”“真实系统已验证”经常被统一写成“已定案、已闭合、全部通过”。

这导致概念闭合速度明显快于协议、ABI、实现和证据闭合速度。

项目自己的风险清单已经意识到这个问题：

- [风险清单的证据状态](./04-设计问题与理论风险清单.md#一问题分级说明)
- [设计覆盖不等于验证闭合](./04-设计问题与理论风险清单.md#o-05-议题-3-六死因全部闭合)

但总纲、实验索引和网站没有完全执行这套证据纪律。

另一个问题是重构测试较难证伪：通用 `Agent`、`Tool` 和宽泛的 `generate` 足以容纳几乎任意模式。它能证明“可以描述”，但不能证明该抽象是最小的、高效的或具有独立解释力。

## 四、实验与证据审计

### 4.1 测试复核

准确合计为 **158 项测试通过**：

| 实验 | 测试结果 |
|---|---:|
| exp1-trap-layer | 26 passed |
| exp2-watchdog | 14 passed |
| exp3-kv-billing | 26 passed |
| exp4-msg-backpressure | 11 passed |
| exp5-contamination-sim | 尚无测试与可运行实验 |
| exp6-topic-fanout | 25 passed |
| exp7-semantic-atoms | 56 passed |

绿色测试说明局部实现忠实于作者定义，但不能自动证明外部世界命题。

| 实验 | 实际支持的结论 | 尚不能支持 |
|---|---|---|
| exp1 | 顺序、mock 场景下代理、扣账、硬顶可运行 | 并发物理预算、durable WAL、真实 provider |
| exp2 | 能识别作者脚本生成的几类模式 | 真实 agent 的低误报率 |
| exp3 | usage 字段归一化和计费公式正确 | 真实 provider 一定提供可靠成本数据 |
| exp4 | 有限预付状态机最终封顶 | 真实多智能体经济会稳定 |
| exp5 | 仅有领域模型草图 | 污染传播防御有效性 |
| exp6 | 谓词选择性的解析数学正确 | Topic 扇出、CPU 成本、延迟和背压 |
| exp7 | 声明的结构不变量被测试锁定 | 身份、授权、持久化和真实认识论安全 |

### 4.2 exp1：预算并不“物理守恒”

exp1 在调用 provider 前根据余额计算 cap，直到 provider 返回后才结算，中间没有：

- reservation；
- in-flight debit；
- 每账户并发锁；
- 流式逐 chunk 扣减。

证据：

- [请求与结算路径](../../experiments/exp1-trap-layer/trap_layer/proxy.py)
- [BudgetManager.settle](../../experiments/exp1-trap-layer/trap_layer/budget.py)

运行时探针复现：

- 账户余额 120；
- 两个并发请求都读取同一余额；
- 两者都获得 cap=119；
- provider 实际成本合计 239；
- 本地账户只扣到 0。

因此当前系统只保证“账面余额不为负”，不能保证“供应商实际支出不超过预算”。

流式路径也只在流结束后的 `finally` 中统一结算，并非逐 chunk 扣减。

#### WAL 结论同样过强

当前 WAL 只有 `write + flush`，没有：

- `fsync`/`fdatasync`；
- 崩溃恢复协议；
- torn write 检测；
- 幂等 replay；
- 有界 pending queue。

而基准热路径明确排除了磁盘成本：

- [WAL 实现](../../experiments/exp1-trap-layer/trap_layer/wal.py)
- [WAL 基准定义](../../experiments/exp1-trap-layer/scripts/benchmark_wal.py)

所以它目前是异步审计日志或批写器，不是能抵抗进程/主机崩溃的 durable WAL。

#### exp1 的实际结论

- API 代理形态可行：支持；
- 顺序 mock 场景下的 cap 与结算：支持；
- 生产级物理预算隔离：不支持，且有已复现反例；
- durable WAL：不支持；
- 5k/s 内存追加微基准：支持，但结论必须缩窄。

### 4.3 exp2：看门狗存在现实误杀路径

双空文本被定义为相似度 1，而相似度触发和“有新工具调用/新产物”是独立 OR 条件：

- [相似度实现](../../experiments/exp2-watchdog/watchdog/similarity.py)
- [看门狗状态机](../../experiments/exp2-watchdog/watchdog/core.py)

运行时探针复现：

- 连续四步；
- 每步都有全新工具调用和全新结果；
- 每步 `progress=True`；
- tool-call 响应的文本 content 为空；
- 第 4 步仍被 `repeat_similarity` 挂起。

这对 tool-heavy agent 是现实且高概率的误杀路径。

此外：

- task 标签直接决定脚本 provider 的 normal/stuck/slow 模式；
- 数据生成器和检测器共享同一假设；
- 14 个测试实际只覆盖相似度函数，没有覆盖核心状态机；
- 阈值表 16 格全部零误报，报告文字却称 0.80 已开始误杀，数据与固定文案矛盾。

因此 exp2 支持“状态机能区分作者构造的模式”，不能支持真实总体误报率低于 10%。

### 4.4 exp3：计费转换成立，真实前提未验证

exp3 的模块边界是四个实验中最干净的：

```text
不可信 usage dict
→ 类型化字段探测
→ 统一 cached token 语义
→ 纯函数计费
```

它证明了：

- DeepSeek/OpenAI/无缓存字段三种 mock 形态可归一化；
- 缺字段或缺价格时可以保守回落全价；
- 计费公式在 mock 中正确。

但真实 provider 尚未运行，报告也明确承认这一点：

- [exp3 报告](../../experiments/exp3-kv-billing/results/report.md)

因此危险假设“provider 能稳定回报可用于真实计费的缓存成本”尚未验证。

此外，usage 只回报 token 数；“实际成本”仍由本地价格表推导，不能把二者混为一谈。

### 4.5 exp4：验证了状态机，不是经济系统

exp4 的停止条件直接写在模拟器里：

```text
有限余额 + 每个 delivery 先扣 1
→ 余额耗尽后停止
```

- [预付与 fan-out 实现](../../experiments/exp4-msg-backpressure/msgstorm/engine.py)
- [结果数据](../../experiments/exp4-msg-backpressure/results/summary_mean.csv)

实验很好地验证了实现没有破坏这个不变量，也展示了队列排空和流量类别占比恢复。

但它没有独立证明：

- 真实 agent 会因价格改变策略；
- 多主体经济会稳定；
- 预付优于配额或限速；
- 广播公平性成立；
- 有充值、收入和多 rogue 时仍会收敛。

而且 fan-out 按固定订阅顺序进行，余额不足完整广播时低 ID 订阅者系统性优先，当前没有公平性指标。

### 4.6 exp5：尚未形成实验

exp5 目前只有：

- 领域模型；
- 四臂 Defense 枚举；
- 参数配置；
- 指标结构。

尚无：

- World/engine；
- 污染生产与传播；
- verifier、审计与召回算法；
- 四组 runner；
- 参数扫描；
- 测试；
- 结果；
- README；
- lockfile。

所以 exp5 目前是实验设计草图，不能产生“provenance gating + tracing 已有效”的结论。

未来还必须同时测量 clean throughput、等待时间和有效产出，否则可能把“拒绝一切内容导致零污染”误判成防御成功。

### 4.7 exp6：只完成了谓词数学基础

exp6 已证明：

- category × intensity 谓词语义；
- 任意目标选择性可以解析编译；
- Uniform/Bimodal/PowerLaw 三类选择性分布可复现；
- 经验通过率与解析值匹配。

证据：

- [Topic 谓词模型](../../experiments/exp6-topic-fanout/topicfan/model.py)
- [Topic 模型测试](../../experiments/exp6-topic-fanout/tests/test_model.py)

但尚无：

- N 订阅者路由器；
- 广播基线；
- 发布频率；
- 投递计数；
- 路由 CPU 成本；
- 延迟、队列和背压；
- 热点与订阅重叠；
- 参数扫描和失效区。

必须区分：

- `Σ selectivity` 是期望投递量；
- 如果仍逐个执行所有订阅谓词，路由 CPU 成本依然是 O(n)。

没有谓词索引、IR 或分组执行机制，就不能声称 Topic 已解决规模问题。

### 4.8 exp7：结构原型有价值，但身份与授权模型有 P0 缺陷

exp7 是语义哲学最清晰的代码落地：

- content 保持不透明；
- 原子不可变；
- 修改通过新原子和 lineage；
- 撤回通过 tombstone；
- verdict 通过事件流 fold；
- 关系判断本身也是原子；
- IntentSpec 把自然语言目标和结构化验收结合。

56 项测试确实锁定了作者声明的窄口径不变量。

但其关键未测缺陷直接伤及核心认识论。

#### 4.8.1 Content identity 与 assertion identity 被错误合并

claim ID 只哈希 kind 和 content，写入使用 `INSERT OR IGNORE`：

- [ID 计算](../../experiments/exp7-semantic-atoms/sematom/model.py)
- [claim 写入与 INSERT OR IGNORE](../../experiments/exp7-semantic-atoms/sematom/store.py)

结果是两个独立来源发表完全相同的文本时：

- 第二来源的独立证据消失；
- 只保留首写 source、assertion、lineage、TTL、signature；
- 接触追踪会错误归因；
- 恶意首写者可以污染后续同文本事件的身份。

必须拆成：

```text
content_digest
  = hash(content)

assertion_event_id
  = hash(content_digest
         + provenance
         + assertion
         + lineage
         + validity
         + signature/nonce)
```

LinkAtom 也有同类问题：同一关系和端点的多个独立判断者会被去重。

#### 4.8.2 IntentSpec 身份没有覆盖完整规格

同 goal、不同 acceptance/constraints 的规格获得同一个 ID，第二次写入触发唯一键错误。

结构字段还放在没有不可变触发器保护的 `specs` 旁表中，裸 SQL 可以改变所谓不可变规格。

- [IntentSpec 实现](../../experiments/exp7-semantic-atoms/sematom/spec.py)

规格身份应覆盖完整 canonical envelope，并在单个事务中原子写入。

#### 4.8.3 hard gate 真空通过

当前：

```python
all(o.passed for deterministic outcomes)
```

在没有 deterministic criterion 时返回 True。

因此：

- 空 acceptance；
- 只有失败的 LLM judge；
- 只有待定 human criterion；

都会令 `escrow_releasable=True`。

应要求至少一个 hard gate，或要求规格显式声明并授权 `allow_vacuous_hard_gate`。

#### 4.8.4 “独立验证”只是自报枚举

`record_verdict()` 只检查 method 是否属于允许集合，不检查：

- verdict writer 是否与生产者不同；
- writer 是否拥有 verifier capability；
- 是否有签名；
- verifier 是否被当前 Policy 授权。

生产者只要自称 `independent-verifier` 就能给自己写 verified。

#### 4.8.5 撤回和 verdict 缺少授权语义

任何 source 都能 tombstone 任意 atom；低信任写入者也能通过 latest-wins verdict 覆盖较高信任的确定性结果。

需要：

- writer capability；
- issuer/owner/authority policy；
- 方法与主体绑定；
- 权威等级或证据集合视图；
- 追加事件不可更新/不可删除；
- 有授权的 tombstone 与反 tombstone/恢复语义。

#### 4.8.6 文件存储不能正常重开

主 schema 使用裸 `CREATE TABLE/CREATE TRIGGER`，构造器每次都重新执行。首次创建、关闭后第二次打开同一路径会报 `table atoms already exists`。

现有 fixture 全部使用内存数据库，因此没有发现。

## 五、规范与理论层面的主要问题

### 5.1 系统调用 ABI 并未闭合

最新总纲声称约 22 个系统调用，但表中实际是：

```text
进程 7
+ 内存 4
+ 设备 3
+ IPC 7
+ 经济 3
+ 安全 3
= 27
```

- [系统调用表](./04-架构设计总纲-v0.4.md#5-系统调用表)

同时正文依赖但表中没有：

- `join`；
- `hold/release/refund`；
- 语义原子 CRUD、lineage、TTL；
- 带 namespace 和 IntentSpec 的完整 spawn。

所以“22 个调用通过 Multics 测试”目前只是修辞性计数，不是稳定 ABI。

而且“少于 30 个”本身不是最小性的证明。真正的测试应该是：

- 每个 syscall 是否对应必须原子完成的不变量；
- 删除它是否导致不可避免的旁路或竞态；
- 能否由其他原语无损组合；
- fast path 成本是否可接受。

### 5.2 最新规范没有归一化

当前文件名是 v0.4，内容却是 v0.4.1，并通过不断叠加修订注维护。

已经出现直接冲突：

- 一处说 escrow 默认只绑定 hard gate；
- 后文仍说 acceptance 全部通过才释放；
- 一处说 watchdog 只计确定性和结构进展；
- 后文仍以全部 acceptance 的通过比例定义进展；
- 修订引入 self-attested；
- schema 仍只有 unverified/verified/disputed；
- 议题 25 已收窄理论边界；
- 最新总纲仍写“任意审慎型知识工作”。

这说明需要一份重新编译的规范，而不是继续叠加修订注。

### 5.3 “语义图灵完备”应降级为工作流可表达性命题

当前证明使用非常宽的 `generate`、通用 Tool 和 `decompose`；对象又被限定为“可被人类组织分解的任务”。

这接近循环论证，也很难被反例证伪：

- 原子任务由 acquire/generate/verify 完成；
- 复合任务由 decompose 分解；
- 可讨论对象又被定义为可分解任务。

八原语仍然是一套有用的工作流指令集，但目前更准确的名称是：

> **审慎型知识工作的知识变换工作流可表达性假说。**

它还不是与 Church–Turing 同等级的完备性定理。

要形成严格理论，至少还需要：

- 对任务和状态的操作语义；
- 原语的形式定义；
- 合法 Tool 的边界；
- 表达等价关系；
- 编译/构造算法；
- 非循环的覆盖证明；
- 反例和效率界。

### 5.4 “意义 = 压缩”是启发式，不是语义理论地基

压缩可以解释规律发现和预测，但不能自动给出：

- 指称；
- 真值；
- 意图；
- 规范性；
- 社会语境；
- 说话者承诺。

- [意义等于压缩的主张](./04-架构设计总纲-v0.4.md#172-三条地基结论)

可以保留为设计直觉，但不宜作为项目理论合法性的证明。

### 5.5 更准确的“零语义”内核边界

“内核零语义、永不读 content”目前表述过强，因为系统已经设想或实现：

- n-gram 相似度；
- embedding fingerprint；
- 向量索引；
- assertion/verification/关系标签过滤；
- acceptance method 的结构执行。

更稳健的宪法应该是：

> **内核不得生成、推导或裁决语义主张；但可以机械存储、索引和执行带明确来源的结构标签。**

同样，“不可命名 = 不可想象”应改为：

> **不可命名 = 不可寻址、不可行动。**

模型仍可能知道、猜测或被提示 namespace 外的对象。

### 5.6 Provenance 是 attestation，不自动等于事实

强制每个输出携带 lineage，并不能保证：

- 生产者列出了所有实际读过的输入；
- 私有 scratch 中的信息没有被洗白；
- agent 没有伪造 source；
- 多源融合后的 taint 正确；
- declassification 合法。

因此当前 provenance 更准确地说是“强制来源声明与可审计事件”，而不是自动真实的信息流证明。

如果要支撑“幻觉疫情接触追踪”，需要进一步设计：

- I/O 边界自动捕获；
- taint lattice；
- 显式 declassification；
- capability-bound signer；
- provenance completeness 的可验证范围。

### 5.7 OS、BFT、Rice、ELF 等类比应保持为启发式

这些类比有很高的发现价值，但不能自动继承原理论的结论：

- agent 像 Byzantine 节点，不等于可以直接套用 `3f+1`；
- 一般验收困难与 Rice 定理有相似直觉，不等于自然语言验收直接满足 Rice 定理前提；
- Agent package 类似 ELF，不等于已经存在稳定 loader/ABI；
- LLM 调用类似 syscall，不等于 trap 是唯一实现形态。

更准确的说法是“结构同构与设计迁移”，而不是逻辑证明。

## 六、工程与项目成熟度

### 6.1 当前实现边界

仓库目前没有真正实现：

- 权威 scheduler；
- 宿主执行隔离；
- 不可绕过的网络 egress；
- 稳定 syscall ABI；
- Agent ELF loader；
- checkpoint/restore；
- Topic 路由器；
- Blackboard 分片；
- 分布式预算租约；
- 多节点控制协议；
- 完整 semantic data plane；
- 端到端 agent kernel。

现有实现是若干机制原型，而不是可运行的操作系统。

### 6.2 通用化削弱了原有性能论据

项目最初用“LLM 调用是秒级，微内核开销可忽略”论证 trap 成本。

但 v0.2 后 Agent 已包含：

- 纯代码 worker；
- 短工具调用；
- 高频 Message；
- 流式 chunk；
- Topic fan-out。

这些路径可能是微秒或毫秒级，不能继续统一使用 LLM 延迟作为性能豁免。

纯代码 worker 如果在私有循环中死循环，也没有 LLM trap 抢占点；仍需依赖宿主 OS 进程/容器调度与 kill。llmos 必须明确自身与宿主内核的分工。

### 6.3 可信计算基比“笨微内核”更大

真正的 TCB 至少包括：

- trap proxy；
- provider/tool driver；
- 宿主 sandbox；
- 网络策略；
- budget ledger；
- identity/capability 服务；
- verifier registry；
- semantic store；
- checkpoint 与恢复组件；
- 控制面协议。

如果这些组件中的任一个可以伪造 usage、绕过 egress、冒充 verifier 或修改事件表，“内核物理保证”都会失效。

### 6.4 站点与当前项目叙事脱节

静态站点仍停留在 v0.2，继续宣传：

- 18 议题全部定案；
- 22 个调用通过测试；
- 六大死因全部闭合；
- max_tokens 是物理透支保证；
- serverless bill shock 结构性不可能；
- 不可命名即不可想象。

但这些表述已经被 v0.3/v0.4/v0.4.1、议题 25/26 和当前实验反例部分修正。

站点作为 v0.2 历史摘要尚算忠实，作为当前项目对外入口则已经构成叙事风险。

另外，站点当前的 Three.js、极光、玻璃面、glow、大圆角视觉实现与 `docs/site/DESIGN.md` 中的克制细线、无装饰渐变等约束已经明显漂移。

### 6.5 工程工作流仍不完整

当前 GitHub Actions 只部署 Pages，没有：

- exp1–7 测试矩阵；
- Python 版本矩阵；
- 静态检查；
- schema/ABI 检查；
- Markdown 链接检查；
- 实验结果再现检查。

此外：

- exp1–3 要求 Python 3.13，exp4–7 要求 3.12；
- exp5 无 lockfile；
- 根目录缺少统一 README、状态说明、许可与贡献约定；
- 公开站点没有呈现证据等级和已知反例。

## 七、风险优先级

### P0：直接阻塞核心主张

1. **Budget 无并发 reservation，provider 实际消耗可以突破余额。**
2. **ContentId 与 AssertionEventId 合并，独立 provenance 会被去重吞掉。**
3. **IntentSpec 身份不覆盖 acceptance/constraints，规格不可变性不成立。**
4. **空 hard gate 真空通过，失败的 soft-only 规格仍可释放 escrow。**
5. **verified 独立性仅靠调用者自报枚举，未与主体身份和 capability 绑定。**
6. **任意 source 可 tombstone 任意原子，缺少授权模型。**

### P1：进入 v1 前必须关闭

1. WAL 无 durable commit 与崩溃恢复。
2. trap 的不可绕过性尚未通过网络隔离和工具 egress 验证。
3. watchdog 会误杀空文本的多步工具调用。
4. Topic 只有谓词数学，没有路由复杂度与失效区实验。
5. exp5 污染传播机制尚无实验。
6. 分布式预算租约、断网双花和恢复清算没有协议。
7. syscall ABI 与总纲正文不一致。
8. 最新规范内部互相冲突。

### P2：影响理论可信度和生态定位

1. “语义图灵完备”表述过强。
2. “意义 = 压缩”被当作理论地基。
3. OS/BFT/Rice/ELF 类比被赋予超过证据的证明力。
4. Tool/generate 使重构测试难以证伪。
5. 网站与当前证据状态脱节。
6. 缺少统一 CI、根 README、版本与实验状态规范。

## 八、建议的下一阶段路线

### 8.1 总路线：从启动微内核走向完整现代 NLOS

路线必须以完整 NLOS 为终点，而不是在 MVP 成功后停留于控制中间件。

#### 阶段 A：启动微内核

目标：建立系统权威和最小可信计算基。

- 稳定最小 syscall ABI；
- Agent 生命周期与宿主执行隔离；
- capability/namespace；
- 原子 Budget reserve/settle；
- Message/基础 IPC；
- 不可绕过的模型与工具驱动；
- checkpoint、审计和 replay；
- AssertionEvent、verdict、IntentSpec 的正确身份与授权模型。

完成标志：单机端到端纵切面在并发、崩溃、取消和恶意输入下仍守住不变量。

#### 阶段 B：单机通用 NLOS

目标：从“内核原型”升级为第三方可以编写应用的操作环境。

- Agent ELF/package 与 loader；
- SDK、CLI、自然语言 Shell；
- Context/Memory 系统服务；
- Blackboard 与 Topic；
- 包管理、安装、升级和卸载；
- 用户、会话、权限确认与密钥管理；
- 调试器、trace viewer、任务管理器；
- 多种 harness 和纯代码 worker 共享稳定 ABI。

完成标志：陌生第三方可以在不修改内核的情况下开发、分发和运行此前未预设的 NLOS 应用。

#### 阶段 C：分布式现代 NLOS

目标：达到现代系统而非单机 runtime 的能力层级。

- 本地数据面与分布式控制面；
- 多节点 namespace 与身份；
- quota lease、联邦清算与断网恢复；
- checkpoint 迁移、弹性和故障域隔离；
- 多租户、组织策略和审计；
- 云、边缘和个人设备协同；
- Topic/Blackboard 的分片、复制与一致性档位；
- 协议栈、远程设备和跨组织应用。

完成标志：应用能跨节点、设备和组织运行，系统在分区、重启、迁移和升级中维持明确的一致性与损失上界。

#### 阶段 D：自然语言桌面与完整系统服务

目标：形成面向普通用户的完整操作系统产品，而不只是开发者 runtime。

- 自然语言桌面与任务空间；
- 多模态输入输出；
- 通知、窗口、后台任务和系统设置；
- 权限请求与可理解的安全提示；
- 全局搜索、文件/知识/应用统一寻址；
- 用户可见的预算、隐私和执行状态；
- 个人、团队和组织级系统体验；
- 可访问性、国际化和离线/弱网模式。

完成标志：用户可以像使用 Windows/macOS 一样持续使用 NLOS 完成广泛任务，而不需要理解底层 Agent 编排。

#### 阶段 E：平台兼容性与应用生态

目标：建立真正的系统级护城河。

- 长期 ABI/API 兼容政策；
- 应用商店或可信包仓库；
- 开发者签名、审核和权限透明度；
- 应用间组合与系统级 automation；
- 驱动、模型、工具和 Skill 市场；
- 迁移工具与旧版本兼容层；
- 完整开发文档、示例、认证与生态治理。

完成标志：NLOS 的能力增长主要来自第三方生态，而不再依赖核心团队亲自实现每一种应用。

这五个阶段是递进关系，不是相互替代：

```text
可信微内核
→ 通用单机系统
→ 分布式现代系统
→ 自然语言桌面
→ 长期应用生态
```

### 8.3 优先修复三个 P0 数据模型

#### 原子预留预算

调用前：

```text
estimate upper bound
→ atomic reserve
→ provider execution
→ incremental debit
→ settle/refund
```

需要覆盖：

- 多请求并发；
- 流式输出；
- prompt/tools/hidden token；
- 客户端断流；
- provider 取消；
- provider 少报或迟报；
- 重复 callback；
- 进程崩溃；
- 分布式 quota lease。

#### 分离内容与断言事件身份

至少引入：

- `ContentDigest`；
- `AssertionEventId`；
- `JudgmentEventId`；
- `VerdictEventId`；
- `RetractionEventId`。

任何 provenance、判断者或验证者的独立事件都不能因文本相同而消失。

#### 完整 IntentSpec 身份和 gate 语义

- ID 覆盖完整 canonical envelope；
- 原子和结构字段同一事务写入；
- specs/verdicts 同样不可更新、不可删除；
- 至少一个 hard gate，或显式允许无 hard gate；
- verifier 与 capability/identity 绑定；
- human、deterministic、independent verifier 的权威关系明确；
- latest-wins 改成授权感知的证据视图。

### 8.4 实现一个端到端纵切面

最推荐的 MVP 不是一次实现八大抽象，而是跑通：

```text
spawn
  ├─ 划拨 budget lease
  ├─ 衰减 capability/namespace
  └─ 绑定 child IntentSpec
        ↓
所有外部 I/O 经不可绕过的 driver
        ↓
原子 reserve / 流式计量 / settle
        ↓
输出 AssertionEvent + provenance
        ↓
deterministic hard gate
        ↓
escrow release/refund
        ↓
完整 replay 与审计
```

先单机、一个 provider、一个工具、一个父子委托场景即可。

这个纵切面一旦在并发、kill -9、重复回调、客户端断流和恶意调用下仍守住不变量，项目才第一次拥有“内核”的工程实质。

### 8.5 重新设计实验纪律

每个核心命题都应区分：

1. 模型内是否成立；
2. 实现是否满足模型；
3. 模型假设是否符合真实工作负载；
4. 替代机制是否更简单或更有效；
5. 故障和攻击下是否仍成立。

下一批实验应优先覆盖：

- Budget 并发 property test；
- kill -9/WAL torn-write 恢复；
- provider usage 少报、迟报、矛盾回报；
- 真实 agent traces 上的 watchdog ROC；
- Topic 的 predicate CPU、索引成本、延迟与背压；
- exp5 中污染率与 clean throughput 双指标；
- 多节点 quota lease 的分区与恢复；
- provenance 遗漏、伪造、洗白和 declassification。

### 8.6 给 NLOS 终局设置可检验的系统级门槛

至少应满足：

- 多种 harness 能运行在稳定 ABI 上；
- 所有副作用路径能够被证明不可绕过；
- 并发和故障下预算损失有严格上界；
- 生命周期、抢占、恢复不依赖模型配合；
- capability、identity、provenance 能被系统而非调用者自报强制；
- Topic 相比广播在路由 CPU、投递量、延迟上有明确优势；
- 多节点租约在分区和恢复后不双花。

这些条件不是放弃 OS 身份的理由，而是项目从“正在构建 NLOS”晋升到“已经形成可用 NLOS”的工程门槛。

阶段 A 的 reference monitor、deterministic control plane 和微内核必须明确标注为：

> **完整 NLOS 的启动内核与第一阶段实现。**

它们不是替代终局的产品定位。任何短期架构选择都应回答：它是否保留了通向通用应用、现代系统服务、自然语言桌面和第三方生态的兼容演进路径。

### 8.7 推荐的对外产品表述

推荐：

> **llmos 的终极目标是构建达到 Windows/macOS 级别的通用现代 NLOS（自然语言操作系统）。当前阶段正在实现它最小但不可替代的确定性微内核：模型负责语义，内核在不可绕过的边界上强制能力、预算、生命周期和知识来源。**

对外叙事必须同时包含“终局”和“当前阶段”，既不能把项目缩成治理中间件，也不能把尚未完成的终局写成已经实现。

当前暂时避免：

- “Agent OS 必然出现”；
- “语义图灵完备已经证明”；
- “max_tokens 使透支物理不可能”；
- “六大死因全部闭合”；
- “Topic 已解决万级通信”；
- “不可命名即不可想象”；
- “意义等于压缩，因此语义计算已有理论地基”。

## 九、最终评价

项目最重要、最高优先级的目标已经明确：

> **构建达到 Windows/macOS 级别的通用现代 NLOS。**

这个终局不应被当前工程成熟度、MVP 范围或阶段性产品表述覆盖。确定性控制层不是项目最终形态，而是完整操作系统赖以生长的启动内核。

项目值得继续，而且其核心研究命题是真正有价值的：

> **面对概率性智能，系统不应试图把模型变成可靠内核；应让模型保留开放语义能力，同时用确定性执行层约束它能够触及什么、消耗多少、如何委托，以及其知识主张从何而来。**

这是 llmos 最强、最原创、也最可能形成长期护城河的部分。

当前应主动把项目从“宏大理论扩张期”切换到“规范归一化和核心不变量兑现期”，随后按照单机通用系统、分布式现代系统、自然语言桌面和应用生态的路径继续扩张。

端到端纵切面的成功不是终点，而是 NLOS 第一次获得可持续生长的系统地基。后续所有路线判断都应同时接受两个问题：

1. 当前阶段是否用证据兑现了它声称的不变量？
2. 这个选择是否保留了通向 Windows/macOS 级完整 NLOS 的演进路径？
