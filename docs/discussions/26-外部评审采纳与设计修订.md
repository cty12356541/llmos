## 修订 1：Budget 守恒五元组（修订 B-01，议题 8/11）

原表述"max_tokens 硬顶 = 物理保证无透支"仅对 completion 维度成立。**完整预算守恒 = 五元组**：

1. **max_tokens 硬顶**（completion 维度的充分上界，已 exp1 验证）
2. **prompt 预扣**：按 prompt 估算预冻结，结算时多退少补（预扣误差有界：prompt token 数在陷入时可精确计数）
3. **tool preauth**：工具调用按预估成本预授权（议题 11 已定方向，此处明确为守恒必要件）
4. **流式计量**：chunk 增量扣减 + 流末统一结算（议题 13 已定），驱动必须增量回报，缺失回报时按 chunk 数保守估算
5. **驱动可信回报 + 负余额拒绝**：驱动在 TCB 内（议题 6）；结算若超余额记负账并立即挂起（负余额账户拒绝一切新调用直到充值）

**对外表述**：max_tokens 是"completion 维度的充分上界"，完整守恒靠五元组，禁止单独宣传硬顶。

## 修订 2：内核进展信号只计确定性轨（修订 F-03，议题 9/18/23）

问题：进展=验收通过数时，若验收走 llm-judge，语义判断经此漏进内核看门狗，破防火墙。
**修订**：内核进展信号 = **确定性 checker 通过数 + 结构产物计数**（新工具调用/新原子产出）两项；llm-judge 的验收结果单独标记（进观测流水），**不进内核 watchdog 计数**。与议题 24 Q3 精化（机械触发只写进程状态）自洽：llm-judge 结果若影响控制，必须经用户态监督流程。

## 修订 3：hard gate / soft gate 分离，escrow 只绑 hard gate（修订 B-07/C-04，议题 8/23）

IntentSpec 的 acceptance 按验证方法分两类：
- **hard gate**：deterministic checker（代码可判定）——escrow 的释放条件**默认只绑 hard gate**
- **soft gate**：llm-judge / human（概率性判断）——不做金钱结算的硬条件；soft gate 结果影响验收评价与信誉记录（用户态），escrow 释放若以 soft gate 为条件必须显式声明并接受概率性 SLA

理由：Rice 定理语义版——一般验收不可判定，把合约绑在概率判断上等于把结算变成赌博。

## 修订 4：verified 写入限制（修订 F-06，议题 9/23/24）

**verified 状态只能由独立验证者或确定性 checker 写入**；生产者自检的 verified 标记默认无效，除非 Policy 显式授予该 agent 自检权限（与议题 23 验证独立性四档对齐：自检档不产生 verified，只产生 self-attested）。防止生产者伪造 verified 击穿"只许 verified 进规划"的闸门。

## 修订 5：控制面纵深防御（修订 R-02，议题 12）

议题 12 已定"控制面输入全污点化、原始 trace 不进指令通道"。补充三层：
1. **输入 schema 固定**：控制面 LLM 的输入为固定结构字段（计数/状态枚举），字段级校验（类型/范围/长度），拒绝 schema 外内容
2. **物理 namespace 隔离**：监督/调度等控制面 agent 运行在与普通 agent 隔离的 namespace 分区——普通 agent 的任何资源（黑板/消息）默认不在控制面 namespace 可命名范围内，输入只经内核中介的结构化管道
3. **关键决策 human L2**：涉及杀死/扩权/预算大调的裁决保留人工通道

## 修订 6：最终一致档限 CRDT 式原子 merge（修订 D-02，议题 12/15）

语义 merge 一般不可判定。最终一致档 Blackboard 的跨机合并规则收敛为：
- **tombstone 优先**（撤回战胜内容，防复活）
- **原子本体不可变**，无合并需求（议题 21 的红利）
- **link atom 不自动合并**：冲突（对同一对端点的矛盾关系断言）不裁决，共存并在共享视图产出 **CONTRADICTS link**——分歧显式化（议题 12 的 OS 一致性模型在合并层的落地）
- 用户态 merge driver 只允许在这三条之上做呈现层裁决，不改写原子流
