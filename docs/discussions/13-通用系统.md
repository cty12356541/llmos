# 议题 13：通用系统——通用性的判据与压测

> 轮次：第 13 轮（2026-07-23）
> 来源：方向修正后的主线第一题——"设计通用系统"
> 方法：通用性判据正式化 → 负载无知审计 → 重构测试（16 个计算模式压测）→ 抽象修剪

## 一、通用性四判据（Unix 通用性的来源）

1. **抽象正交性**：抽象各自独立、任意组合。通用性不来自抽象数量，来自组合自由度
2. **对负载的无知性**：内核不知道也不关心程序在算什么，系统调用负载无关
3. **可组合性优先于功能**：pipe 没有"功能"，但让一切功能可组合
4. **机制下限，生态上限**：系统提供最少机制，通用性由生态组合涌现（MVS 反面：功能内置，越全越专用）

## 二、负载无知审计——内核知道什么、不知道什么

| 内核知道（结构性、负载无关） | 内核不知道（语义性） |
|---|---|
| 能力集合、预算余额、步数 | 任务内容、目标 |
| 进展信号（新产物/新工具调用——结构信号） | 输出"好不好"、对话语义 |
| 污点标记、路由地址 | 消息的含义 |
| 兴趣过滤谓词的**执行**（eBPF 原则：执行不理解） | 兴趣过滤的**意图** |

审计结论：负载无知性成立。看门狗信号是结构信号不是语义判断， Topic 谓词是"执行不理解"，均未越界。

## 四、两个通用性裂缝与修复方向

### 裂缝 A：流式/实时语义
问题：realtime/voice 模型是持续流，不是请求-响应的"步"。步边界协作调度模型对流失效。
**修复方向：计量流陷阱（metered stream）**——流 = 一个保持打开的长陷阱，驱动按 chunk 增量回报用量，内核增量扣减预算；max_tokens 硬顶推广为"累计计量上限"（额度耗尽内核掐断流）；抢占点从"步边界"推广为"chunk 边界"。**步模型不破，推广为计量模型**：请求-响应是 chunk=1 的特例。

### 裂缝 B：Agent 的定义——通用进程，LLM 可选
问题：纯代码 worker（数据清洗、格式转换）不该被迫过 LLM。
**修复方向：Agent = 通用进程抽象，LLM 能力是一种可选 handle**（像网络能力可选一样）。Unix 用单一进程抽象跑 cat 和 Emacs；我们用单一 Agent 抽象跑纯代码 worker 和 LLM agent。**拒绝引入第二种进程类型**（Multics 警惕）。
推论：ELF 的 runtime.model 声明变为可选；无 LLM handle 的 agent 不过 llm_call 陷阱，预算照记（工具/资源消耗）。

## 五、通用性的代价与可负担性

Unix 的通用性有代价（一切皆字节流不是总最优，所以后来有 io_uring/内核旁路）。我们的陷阱在一切操作的关键路径上，通用性要求陷阱统一，性能想要旁路（可信 agent 直连模型？）。结论：**不变量（能力+预算）永不旁路**；陷阱成本相对 LLM 延迟是噪声（议题 6 已定），通用性买得起。

## 六、修剪结论

8 抽象无一删除。通用核心 = Agent/Context/Tool/Message/Topic/Blackboard；Budget/Policy = 负载无关的基础设施（电力计量类比）——是设施不是灵魂。两处定义修订（流式计量、LLM 可选）+ 一处归位（人=设备）。
