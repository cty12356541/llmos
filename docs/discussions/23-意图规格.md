# 议题 23：意图规格——语义计算的类型系统

> 轮次：第 23 轮（2026-07-25）
> 前置：议题 21（语义原子）、议题 22（语义规范化，L1/L2 判定设施可复用）、议题 20（构造性证明待完成公理）
> 本轮任务：定义意图规格的结构、验证架构、与系统各部位的咬合

## 一、什么是意图规格

经典类比：函数签名+类型是"这个函数承诺什么"的机器可检查契约。语义计算里对应物缺失：agent 接到的"任务"是一段 NL，完成了没有、完成得好不好，没有可检查的基准。

**意图规格 = 任务成功结果的机器可检查描述**——语义计算的"类型"。它回答：一个变换（原子集→原子集）的产出，满足什么条件才算"型别正确"。

没有它的后果已在设计里以遗留形式出现：议题 8 的 escrow"任务完成判定"悬空（合同语义在用户态但没有规格格式）；看门狗只检测"无进展"检测不了"偏离目标"；可靠性分档购买（议题 9）的 criticality 没有声明对象；监督 agent 裁决没有依据。**生成-验证不对称（验证比生成便宜）只有在有规格可验证时才兑现。**

## 二、规格结构（逃生口复用：结构归信封，内容归 NL）

```
IntentSpec {
  id:          原子 id（规格也是原子，见决策 3）
  goal:        NL 目标描述（内核不解析）
  acceptance:  [  // 验收标准列表，三轨异构
    { criterion: NL 判据,              method: llm-judge },
    { checker:   tool://test-runner,   method: deterministic },  // 确定性检查走代码
    { criterion: NL 判据,              method: human }           // 高风险走人工
  ]
  constraints: { budget_cap, deadline?, forbidden: [动作/资源黑名单] }  // 全结构字段，内核可强制
  criticality: 议题 9 的可靠性档位声明
  provenance:  签发者（父 agent/编排器/人）
}
```

**三轨异构是核心设计**：验收标准不是同质 NL 列表——能确定性检查的（测试通过/文件存在/数值在界内）走代码（最强、免费、可信）；只能语义判断的（摘要是否忠实）走 L2 模型判定（议题 22 设施复用）；最高风险的走人工。这与经典软件"类型系统抓能抓的、测试判行为"的双层结构同构：**确定性检查 = 类型检查，NL 判据 = 行为契约**。

**constraints 是全结构字段**：预算上限、禁止动作、资源黑名单——内核可直接强制（与 Policy/Budget 机制咬合，不涉及语义）。

## 三、验证独立性分档（与议题 9 多样化原则咬合）

| 档位 | 验证者 | 强度 | 适用 |
|---|---|---|---|
| 自检 | 生产者自己 | 最弱（相关失败） | 低 criticality 的第一步 |
| 独立验证者 | 不同模型/harness 的验证 agent | 中（多样化破相关） | 默认 |
| 确定性检查 | 代码 | 最强 | 有可机械验证输出的任务 |
| 人工 | 人 | 最终权威 | 高 criticality |

映射规则：criticality 声明（ELF/规格内）决定验证档位组合——与议题 9"可靠性分档购买"同构：**验证强度也是分档购买的**。

## 四、规格即原子

规格进入信念流：有 provenance（谁签发的）、可争议（垃圾规格→verified garbage 的永恒需求问题，至少可被发现和标记）、可被 **REFINES link 精化**（议题 22 的关系枚举直接复用：v2 规格 REFINES v1 规格）。**规格的版本链 = 需求演化链**，与自我修改的版本门控（议题 7）同构。

## 五、与系统各部位的咬合（本轮的收敛清单）

1. **escrow 关闭**：议题 8 遗留的"任务完成判定" = 规格的 acceptance 全部通过（验证档位按 criticality 配）——托管释放条件从"用户态约定"升级为"规格判定"
2. **看门狗进展信号**：进展 = 已通过的验收标准数/总数——从"有无新产物"升级为"向规格推进了几格"，且仍是结构信号
3. **监督 agent 裁决依据**：恢复/转向/杀死的判断对照规格做
4. **Budget**：criticality → 冗余与验证档位的购买依据
5. **spawn 双划拨扩展**：spawn 时父传子的第三样东西（预算片、namespace 之外的第三样）= **子规格**（父规格的分解）
6. **构造性证明公理完成**（议题 20）：公理 B 升级为**带型变换**——产出原子集须满足规格（变换的"型"）；公理 C 的组合要求**规格兼容**（父验收 ⊇ 子交付的合取，精化链由 REFINES 记录）——语义计算的"类型化"完成

## 六、陷阱检查

规格内容保持 NL（无本体语言）；结构字段闭集（method 三选一、constraints 有限键）；确定性 checker 是工具引用（Tool 抽象复用）；判定归模型与代码，内核只管结构字段强制。**"谁规格规格"的问题如实存在**——规格质量是需求工程问题不是框架问题；框架的职责是让规格可表达、可追溯、可争议、可强制其结构部分。
