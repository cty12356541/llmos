# 议题 6：内核边界——机制在内核，策略在用户态

> 轮次：第 6 轮（2026-07-19）
> 前置：议题 5 已定 8 抽象/6 族（Agent/Context/Tool/Message/Topic/Blackboard/Budget/Policy）
> 本轮任务：划分每个抽象的内核/用户态边界；拍板微内核路线

## 一、核心论断

**LLM 调用 + 工具调用 = 系统调用。** 内核物理位置唯一正确解：卡在 agent 循环与模型之间、agent 循环与工具之间。每次 LLM 请求、每次工具调用经内核陷入（trap）。一个陷入层同时提供四个机制：

1. 抢占点（步边界挂起/恢复）
2. 预算扣减点
3. 权限/能力校验点
4. 污点标记点

**推论（化解议题 2 阵营之争）**：harness 派（agent 循环）和图编排派（LangGraph 式编排器）都是本内核之上的**用户态程序**。内核在两者之下，不站队——这就是桥。

**边界判定测试**（每个候选机制过两关）：
- 若它错了/被绕过，安全或核算是否失效？→ 是则入内核
- 它是否需要在陷入点上原子完成？→ 是则入内核
- 否则一律用户态（Multics 警惕：内核只留非留不可的）

## 二、微内核路线的决定性论据

经典微内核（Mach）死于 IPC 性能开销。但 agent OS 里这个死因不存在：

**LLM 调用延迟 = 100ms~10s 量级，IPC 开销 = µs~ms 量级——微内核的 IPC 税相对系统调用延迟是噪声。** Mach 是对的思路错的基座；agent 给了它对基座。

例外核查：消息路由（万级高频）仍是 ms 级，可承受；KV cache 共享的热路径在推理引擎（vLLM）内部，不属于本内核——划界时注意不越界去管推理引擎内部事务。

## 三、三层架构

```
用户态：harness 程序（agent 循环）| 编排器（graph/workflow 程序）|
       调度策略 agent | 分页策略服务 | 策略守护进程 | 工具注册中心
──────────────────────────────────────────────
内核：  陷入层（LLM调用/工具调用=系统调用）| 调度机制 | 上下文分页机制 |
       IPC路由+背压 | 预算核算 | 污点传播 | 能力校验
──────────────────────────────────────────────
硬件态：推理引擎（vLLM 等 = CPU）| 沙箱执行环境（= 外设）| 存储
```

注：模型推理引擎 = CPU 的地位——内核不拥有 CPU，只中介对 CPU 的访问。多模型/多 provider 抽象为"执行上下文"（类比 CPU 亲和性/NUMA 节点），模型路由是内核机制 + 用户态 hint。

## 四、逐抽象切分

### 1. Agent（进程）
- **内核**：生命周期状态机（权威）；步边界陷入执行；身份（agent ID/父系/版本号——自我修改门控用）
- **用户态**：agent 循环本身（ReAct/Plan-Execute/自定义全是用户态 harness）；fork 语义 = checkpoint + branch（内核给原语，用户态决定何时分支）

### 2. Context（内存）
- **内核**：页记账（token 数、钉住状态）；钉住强制（mlock 页不可淘汰）；换页执行机制（压缩/淘汰的执行）；KV 共享机制
- **用户态**：淘汰策略（LRU/语义相关性评分）；压缩策略（怎么摘要）
- **先例**：Mach 外部分页器（external pager）——分页策略放用户态是 40 年前就验证过的设计

### 3. Tool（设备）
- **内核**：工具调用陷入；能力校验（该 agent 是否持有此工具 handle）；沙箱强制挂钩（后端选择、资源限额）
- **用户态**：工具发现/注册（MCP registry = 用户态设备管理守护进程）；组合/重试/缓存策略

### 4/5/6. Message / Topic / Blackboard（IPC）
- **内核**：投递保证与排序；背压阻塞（队列满 → 内核挂起写方，必须与调度原子）；寻址路由
- **用户态**：Topic 兴趣过滤**规则**；Blackboard 合并策略（冲突解决是应用语义，类比 git merge driver）；消息持久化/转换（= Kafka 守护进程类比）
- **先例**：Topic 过滤器 = **eBPF**——内核提供安全沙箱执行用户态编译的过滤谓词。性能（内核执行）与策略（用户定义）兼得

### 7. Budget（经济）
- **内核**：扣减核算（每个陷入点原子扣）；耗尽强制（拒绝/挂起）；继承树维护（父子切分权威记账）
- **用户态**：定价策略（各模型/工具定价表）；分配策略（父如何分给子）；**耗尽响应策略**（挂起 vs 降级小模型 vs 通知——agent 注册自己的 handler）
- **先例**：预算耗尽 = **signal 投递**，handler 在用户态——Unix 信号语义直接移植

### 8. Policy（安全）
- **内核**：陷入点强制校验；污点传播机制（标记+传递）；自我修改的版本门控（v2 凭证 ≠ v1，直到重新授权）
- **用户态**：策略规则本身（策略引擎 = 用户态守护进程，Linux polkit 先例）
- **性能答案**：能力模型（capability）——持有 handle 后不再每调用重估策略，每陷入只查能力表 + 预算 + 污点。能力表 = Unix 文件描述符表

### 9. 调度器（微内核之争的焦点）
- **内核（机制）**：步边界挂起/恢复；tick 控制；运行队列数据结构；非自愿抢占（预算耗尽/污点/背压触发）
- **用户态（策略）**：选谁跑（语义决策——**可以由特权调度 agent 用 LLM 做**）；LOD 分配（模型档位）；准入控制
- **递归设计**：调度策略 agent = init 类比；内核保留固定规则兜底（调度量子到期必唤调度 agent，类比 Unix swapper/0 号进程）

| 类别 | 调用 |

## 六、留给用户的挑战点

1. **是否接受"LLM 调用 = 系统调用"作为唯一陷入边界？** 备选：只中介工具调用、LLM 调用直连——但那样预算扣减和抢占全部失效，等于没有内核
2. **模型路由归内核还是归"模型设备"？** 内核内（热路径快）vs 内核外（把推理引擎整体当外部设备，内核只发"执行请求"）
3. **调度 agent 递归**（特权 agent 做语义调度）——优雅还是过度聪明？风险：调度 agent 自己也消耗预算、也可能幻觉——内核固定规则兜底到什么程度才够？
4. Blackboard 存储本体：内核管（VFS 路线）还是用户态服务管（FUSE 路线）？

## 七、挑战点深析（第 7 轮）

### 挑战点 1：陷入边界的精化——不是两件事，是一条原则

初版表述"LLM 调用 + 工具调用 = 系统调用"不够精确。精化后：

**原则：内核陷入一切跨越 agent 私有边界的操作**——推理（LLM 调用）、工具、共享状态（Message/Topic/Blackboard）、持久记忆。**私有草稿不陷入**（harness 本地计算、私有 scratch 空间）——对应 Unix 进程访问私有内存不陷入，内核只在缺页时介入。

**陷入如何不可绕过**（ring 保护的软件等价物）：
- **凭证托管**：agent 拿不到原始模型 API key；模型端点只接受内核签名的请求
- **网络策略**：沙箱网络规则使工具只能经内核网关到达
- 这就是 agent OS 的 ring 0 / ring 3——不是靠硬件特权级，靠**凭证 + 网络隔离**

被否决的备选：
- 只陷入工具调用、LLM 直连 → 预算在 LLM 调用处烧掉，无扣减点；抢占点在 LLM 边界，无挂起点。等于没有内核
- 异步观察（eBPF 式只观测不强制）→ 事后检测预算超支 = 钱已花完。强制必须同步

### 挑战点 2：模型层 = 设备驱动

**切分**：
- **内核**：能力上限（该 agent 可用模型档位范围 = capability，类比 fd 表条目）；预算扣减；陷入转发
- **驱动（用户态/外部 vLLM 集群）**：路由（哪个 provider/endpoint）、batching、failover、档位内 LOD 微调；成本回报（可信驱动在内核 TCB 内）

论据：
1. vLLM 的 continuous batching 本来就是**设备调度**——内核若接管等于越界管磁盘寻道
2. LOD 决策由用户态调度 agent 做出（挑战点 3），落到 agent 执行上下文上只是一个**档位上限**（类比 nice 值）；驱动在上限内选具体模型
3. 内核保持小——模型路由的复杂性（provider 故障、价格波动、限流）全是驱动业务，不该进内核

### 挑战点 3：调度 agent 不是 dispatcher，是 sysctl writer

**算术否决了 LLM 上热路径**：万级 agent × 每步 ~2s = **每秒数千个调度事件**，LLM 决策延迟（100ms~1s）追不上。所以分层调度：

- **内核短期调度（dispatcher）**：每步决策 = 纯算术（优先级队列出队），零智能
- **用户态 LLM 调度 agent（慢循环，秒~分钟级）**：做语义判断——准入、优先级调整、LOD 分配——然后**通过 syscall 把参数写进内核**（类比写 /proc/sys）

**安全设计**：
- 内核强制不变量（预算守恒、公平性下界），LLM 只能在界内调参——**"内核从不信任，只设界"**（policy is advisory; invariants are physics）
- 调度 agent 消耗固定内核预算（记账可见）
- Dead-man's switch：调度 agent 死亡/超时 → 内核自动退回公平调度（类比 Unix 无 init 时的内核恐慌避免）
- 幻觉的影响半径 = 参数调整幅度上限（rate-of-change 限制）

### 挑战点 4：Blackboard = 内核元数据 + 用户态字节

**必须在内核的**：handle/能力表条目；版本序号；**写串行化**（并发写的权威排序点）；**wakeup 原子性**（写提交与唤醒阻塞读者必须原子，否则丢唤醒）；污点标记
**放用户态服务的**：字节本体、持久化、复制、压缩、GC、merge driver（冲突解决是应用语义）

类比：内核 inode 缓存 vs 磁盘字节；L4 + 用户态文件服务器。万级规模下 Blackboard 操作是 ms 级——用户态存储服务完全够，内核只留非留不可的一致性锚点。

## 八、用户决策（第 7 轮，2026-07-19）——内核边界定案

| 决策点 | 拍板 | 落地形态 |
|---|---|---|
| Q1 陷入边界 | **原则化边界** | 跨私有边界全陷入（LLM/工具/共享状态/持久记忆）；私有草稿不陷入；凭证托管+网络策略 = ring 保护等价物 |
| Q2 模型层 | **模型 = 设备驱动** | 内核：能力上限+预算扣减+陷入转发；驱动（用户态/vLLM 集群）：路由/batching/failover/档位内微调 |
| Q3 调度 agent | **sysctl writer** | LLM 调度 agent 慢循环调参（/proc/sys 类比）；内核 dispatcher 纯算术；不变量内核强制 + dead-man's switch |
| Q4 Blackboard | **内核元数据 + 用户态字节** | 内核：handle/版本序号/写串行化/wakeup 原子性/污点；用户态：字节/持久化/GC/merge driver |

**微内核路线正式确认。** 内核最终职责清单（全量）：陷入层、生命周期状态机、步边界调度机制、上下文分页机制（含钉住强制）、IPC 路由+背压+串行化锚点、预算核算+继承树、能力表、污点传播、版本门控、不变量强制。其余全部用户态。
