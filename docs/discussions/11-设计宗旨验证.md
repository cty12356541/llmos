# 议题 11：设计宗旨验证——万级 LLM 调用调度能力

> 轮次：第 12 轮（2026-07-23）
> 验证对象：最初立项目标——"资源翻万倍时，同时调度上万甚至更多智能体/LLM 调用的能力"
> 方法：①回查议题 3 六大死因（llmos 是否逐一有解）②陷阱层吞吐推演（关键路径算术）③失败场景走查（找裂缝）

## 一、六大死因回查

| 议题 3 瓶颈（现有框架死因） | llmos 的解 | 判定 |
|---|---|---|
| 1. 调度语义真空 | tick 协作式调度 + 优先级队列 + LOD + sysctl writer 分层 | ✅ 有解（纸面） |
| 2. 通信拓扑 O(n²) | Topic 兴趣过滤（内核执行谓词）+ 背压 | ⚠️ 机制有，计费缺口（裂缝 #2） |
| 3. 状态一致性 | Blackboard 串行化锚点 + wakeup 原子性 + git 合并 | ⚠️ 热点分片未定（裂缝 #3） |
| 4. 非确定性传染 | provenance 强制携带 + 接触追踪 + 召回 | ⚠️ lineage 无 GC（裂缝 #4） |
| 5. 可观测性崩溃 | **未设计**（一直在支线清单） | ❌ 仍是空缺（裂缝 #5） |
| 6. 治理（预算/身份） | Budget 全语义 + ELF 签名 + 衰减授权链 | ⚠️ 流水写放大（裂缝 #1） |

## 二、陷阱层吞吐推演（关键路径算术）

设定：10k agent、平均步长 2s → **峰值 5,000 次 LLM 调用/秒**，每次调用过一次陷阱。

单次陷阱的内核工作：能力表查询（O(1) hash）+ 预算原子扣减 + 流水追加 + 污点检查 + 转发驱动 ≈ **50µs 量级** → 单核容量 ~20k 次/秒，**算术上余量充足**。

**但真正的瓶颈不在 CPU 在持久化**：5,000 条流水/秒写持久存储 = 写放大。解法已知（数据库 WAL 组提交/批量落盘），但必须进设计——这是裂缝 #1。

内存占用核查：10k agent 的内核元数据（能力表+预算+队列）每个 KB 级 → 数十 MB，无压力；checkpoint 每个 100KB~10MB → 总量 1~100GB 存储，可接受。

调度器核查：dispatcher 纯算术出队 5k/s 无压力；sysctl writer 慢循环批量写参数，无压力。

## 三、失败场景走查发现的 8 个裂缝

### 裂缝 1：记账流水写放大
5k 扣减/秒全量流水直接落盘不可行。**修复方向**：热路径只改内存余额，流水 WAL 批量组提交（参考 Postgres group commit）；流水异步落盘，崩溃时以最后一次一致快照+重放恢复。

### 裂缝 2：消息投递的计费归属未定义 ⚠️ 真设计缺口
消息进入接收者上下文 = 消耗接收者 token。谁付钱？不定这个，Topic 的背压只有机制没有经济约束。
- 选项 A：**接收者付费**——spam 自限（轰炸别人先榨干自己的投递预算？不，接收者付意味着被轰炸者受损）
- 选项 B：**发送者预付**（按投递次数计费）——spam 发送者自付成本，真正的经济背压
- 选项 C：双向计（发送者付投递费 + 接收者付上下文占用）
- Sisyphus 倾向 B 或 C：成本应归于制造负载的一方

### 裂缝 3：Blackboard 热点分片策略缺失
写串行化 = 单一排序点。万 agent 抢一个热点黑板 = 串行化瓶颈。**修复方向**：按命名空间分片（黑板 ID hash 分片），串行化只在片内；热点黑板由用户态拆分为多个（类比数据库分表）。机制已在（锚点），缺分片策略声明。

### 裂缝 4：lineage 血缘数据无 GC
溯源元数据强制携带 → 血缘图无界增长。**修复方向**：lineage TTL + 分层归档（热血缘全量、冷血缘压缩为摘要哈希）；与接触追踪的查得回深度联动。

### 裂缝 5：可观测性仍是空缺
议题 3 的六瓶颈之一，至今在支线。**建议升级为主线下一议题**——它同时是 L1 常备授权规则覆盖率度量（议题 10 遗留）的依赖。

### 裂缝 6：陷阱超时与取消语义未定义
LLM 调用可挂分钟级；provider 故障时陷阱挂起怎么办？**修复方向**：trap timeout（ELF 可声明）+ 取消传播（suspend/kill 时取消在途调用）+ 超时信号投递。

### 裂缝 7：预算透支（overdraft）语义 ⚠️ 真设计缺口
陷入时检查余额，但调用实际成本事后才知——余额 100 credits，一次调用实际烧 150，怎么办？
- 选项 A：预估冻结（信用卡 preauth：按 max 预估先冻结，结算多退少补）
- 选项 B：允许透支记负账（事后追讨/挂起）
- 选项 C：**max_tokens 硬顶**——内核把剩余预算折算成 token 上限随调用下发，驱动物理截断生成。**Sisyphus 推荐 C：物理保证，无账本复杂性**；A 可作为 C 的补充处理工具调用

### 裂缝 8：在途调用的结算
与 7 联动：协作式调度在步边界挂起（在途调用完成并计费，自然结算 ✅）；但 kill 在途调用时，provider 按已生成 token 计费通常无退款 → 记为损耗入账（需要"损耗"账目类型）。

## 四、语义层面的诚实回答

**内核保证"万级可存活"，不保证"万级有产出"。** 本设计解决的是规模生存问题（不死、不爆、不烧穿预算、不传染）；万级 agent 能否协调出有效产出，是组织设计问题（部门/角色/SOP），属于 ELF 与用户态层——正如 Linux 让你能跑一万个进程，但它们是否构成有用系统取决于应用。边界清晰，但必须在定位上说破。

## 五、验证结论

设计宗旨在结构层面成立：六大死因五个有解一个已知空缺，关键路径算术余量充足。但 8 个工程裂缝必须进入设计 backlog，其中 #2（消息计费）和 #7（透支语义）是真设计缺口需要拍板，其余为机制补全。
