# 议题 27：v0.5 规范化与核心不变量修订

> 轮次：第 27 轮（2026-07-28）
> 触发：[全项目深度评估与路线建议](../design/05-项目深度评估与路线建议.md)
> 产出：规范性总纲 [llmos 架构设计总纲 v0.5](../design/06-架构设计总纲-v0.5.md)
> 性质：设计修复定案；不代表实现或生产验证已经完成

---

## 一、最高目标不变，启动路径纠偏

llmos 的最高目标保持为：

> **构建达到 Windows/macOS 级别的通用、现代、系统级 NLOS（Natural Language Operating System，自然语言操作系统）。**

本轮不把项目收缩为 Agent 网关、reference monitor 或治理中间件。相反，本轮确认：

- 确定性控制层是完整 NLOS 的启动微内核；
- 单机纵切面是第一项实现，不是最终产品边界；
- Application、Package、Task、Artifact、系统服务、自然语言桌面和第三方生态均属于长期系统范围；
- 每项近期修复既要守住当前不变量，也不能封死通往完整 NLOS 的兼容演进路径。

新增概念：**NLOS 主权域**。

NLOS 可以作为 hosted OS 运行于 Linux、Darwin、Windows、云或 Kubernetes 之上。只要在其主权域内，应用的执行、身份、能力、资源、通信、系统可见持久状态、生命周期和外部副作用均由 NLOS 统一裁决，它就不是普通 SDK。是否裸机不是 NLOS 身份的首要判据。

## 二、修订 1：停止叠加修订注，建立唯一规范源

### 2.1 定案

v0.5 是当前唯一规范性架构基线：

- v0.1–v0.4.1 保留为历史设计与 rationale；
- 议题文档保留决策过程、反例和被否方案；
- 实验文档只记录证据；
- v0.5 正文只保留一个当前答案，不再插入“旧正文 + 新修订注”；
- 出现冲突时，v0.5 的带编号规范条款优先；
- 实现与 v0.5 不一致时，必须标记为实现缺口，不能由现有代码反向改写规范。

### 2.2 规范、理论与证据分离

| 类别 | 内容 | 禁区 |
|---|---|---|
| Normative Spec | MUST/SHOULD/MAY、状态机、事务、错误和兼容语义 | 历史类比冒充证明 |
| Rationale/ADR | 选择理由、替代方案和权衡 | 把拍板等同于已验证 |
| Theory | 定义、假说、定理、反例和证明义务 | 未形式化即称完备证明 |
| Evidence | 环境、代码、数据、复现方法和局限 | 用 mock 结论推广生产事实 |

被否方案：继续直接在 v0.4.1 中追加 v0.5 修订注。原因是它已经造成 hard/soft gate、watchdog、原子不可变性和理论边界等多处互相冲突。

## 三、修订 2：重构系统对象模型

### 3.1 问题

原“八抽象”把平台一等概念和必须驻留内核的机制混为一谈，且 `Agent` 同时承担程序、包、应用、人格、发布者和运行实例等含义。

这对 Agent runtime 尚可，对 Windows/macOS 级系统不够。

### 3.2 定案

v0.5 分离以下身份和生命周期：

| 对象 | 定义 |
|---|---|
| Principal | 用户、组织、系统服务、应用、设备等权威主体 |
| Application | 安装、授权、更新、卸载和用户数据所有权单位 |
| Package | 不可变、可签名、可分发的制品 |
| Executable | Package 内可被加载的执行组件 |
| Process | 调度、隔离、故障与生命周期单位 |
| Agent Role | 自主语义角色，可由一个或多个 Process 实现 |
| Task | 用户可见、可持续、可委托的义务，不随聊天窗口或单个 Process 消失 |
| Artifact | 用户或应用持久拥有的文档、文件、结构化对象和结果 |
| Context | 为一次执行构造的派生视图，不是 Artifact 本体 |
| Workspace | 用户/组织数据、应用和 namespace 的协作边界 |
| Session | 用户交互和桌面状态 |
| Device/Driver | 外部能力及其可替换实现 |

身份必须分离：

```text
PrincipalId
ApplicationId
PackageId
ExecutableId
ProcessId
AgentRoleId
TaskId
ArtifactId
DeviceId
```

这些 ID 不得互相复用，也不得编码物理位置。

### 3.3 对原八抽象的处理

Agent、Context、Tool、Message、Topic、Blackboard、Budget、Policy 继续是重要的平台概念，但“一等抽象”不再等同于“必须成为 syscall 或驻留微内核”。

其中：

- Tool 精化为 Device + Driver；
- Agent 的内核运行对应物精化为 Process；
- Context 是 Artifact/Memory 派生的执行视图；
- Message 建立在内核 Channel 上；
- Topic、Blackboard、Policy 是稳定系统服务；
- Budget 的守恒账本进入内核，定价和经济策略留在服务层。

## 四、修订 3：平台抽象与微内核驻留分离

### 4.1 五项内核驻留测试

一个机制只有同时满足以下条件才进入微内核：

1. 被绕过会破坏隔离、授权、核算或生命周期正确性；
2. 必须与权威状态迁移原子完成；
3. 不要求理解自然语言内容；
4. 与模型、协议、provider 和应用类型无关；
5. 无法由更小的内核原语无损组合。

### 4.2 内核保留

- Principal 与 Process 的身份绑定；
- Process 生命周期、隔离、取消、等待和故障域；
- Capability 的派生、委托、撤销和检查；
- Budget 的原子预留、消费、结算、转账和租约；
- Channel 的排序、背压、阻塞与唤醒；
- Checkpoint 的一致性锚点；
- 不可伪造的内核审计事件；
- Device/Driver 调用的不可绕过边界。

### 4.3 稳定系统服务

- Identity、登录、目录与联邦；
- Namespace 的发现、绑定和用户授权界面；
- Package/Application 安装、更新、回滚和卸载；
- Task 与 Intent；
- Artifact、Context/Memory、Search；
- Topic broker、Blackboard；
- Semantic Store、可信视图、向量索引；
- Escrow、定价、合同和信誉；
- Scheduler policy、Observability；
- Notification、Shell、Desktop 和系统设置。

Topic、Blackboard 和 Semantic Record 仍可是一等 NLOS API，但不再以此为由扩张微内核。

### 4.4 被否标准

“系统调用少于约 30 个”不再作为正确性或最小性的证明。评价标准改为：

- 是否对应必须原子完成的不变量；
- 是否正交、可组合；
- 是否有清晰失败语义；
- 是否能形成 conformance test；
- 是否同时覆盖 slow、streaming 和 fast path。

## 五、修订 4：Budget 从事后钳账改为原子预留账本

### 5.1 问题

exp1 的 `authorize → await provider → settle` 允许并发请求读取同一余额。`charged=min(cost,balance)` 只能保证本地账面不为负，不能限制 provider 已经产生的实际成本。

### 5.2 定案

所有有成本上界的动作统一使用：

```text
quote
→ atomic reserve
→ invoke
→ monotonic consume
→ finalize(actual) / release
```

强制规则：

- 未成功获得 Reservation，Driver 不得发起外部副作用；
- reserve 必须原子减少 available；
- 并发请求不得共享同一份 available；
- usage report 必须单调；STRICT 的 observed actual 不得超过 Reservation，低保证 Driver 的 observed actual 若超限只能由预留 RiskAccount/域外 liability 承担，用户 charge 不得超过 Reservation；
- finalize 只能执行一次，重复回调必须幂等；
- 未消费部分返还 available；
- 不允许用负余额修补并发竞态；
- 无法给出成本上界的调用默认拒绝，或显式进入 bounded-loss 风险池。

Reservation 必须一一绑定 CallId、OperationId、DeviceId、DriverId 和 QuoteId；`io_submit` 在 dispatch 前以一次性 CAS durable 激活。finalize 必须消费 endpoint 的 `effect_closed + final_usage` Receipt，防止崩溃退款和迟到扣费。

### 5.3 三种保证等级

| 等级 | 含义 |
|---|---|
| OBSERVED | 只保证 NLOS 内部观察与核算 |
| BOUNDED_RISK | 通过预付子账户、短期 credential 或 gateway 声明最大外部损失 |
| STRICT | provider/本地执行器能物理强制全部计价维度的成本上限 |

只有 STRICT Driver 可以宣传“外部支出物理不超 Reservation”。内部账本守恒与外部账单保证必须分开表述；请求 STRICT 时不得静默降级。

### 5.4 流式调用

- Driver 必须报告单调累计 usage；
- 发出下一批可计费 chunk 前必须确认 Reservation 仍有额度；
- 额度不足时进入 cancel/drain；
- 客户端断流不等于 provider 已停止，Driver 必须继续取消或结算；
- 流末报告只做最终 reconciliation，不能取代增量消费。

### 5.5 Durable acknowledgement

Budget reserve/consume/finalize 的成功响应必须对应 durable commit：

- 使用 checksum、单调 sequence 和 idempotency key；
- group commit 可以降低开销；
- `flush()` 不等于 durable commit；
- hard accounting 不得在 `fsync`/等价持久化之前确认成功；
- snapshot 只覆盖已提交序号；
- 崩溃后以 snapshot + WAL replay 恢复；
- torn write、重复 replay 和部分事务必须有明确恢复规则。

### 5.6 分布式 quota lease

- 根账本签发唯一 LeaseId、额度、holder、epoch 和期限；
- 签发时额度立即从根 available 隔离；
- 节点离线时只能消费本 lease 剩余额度，不能自行扩额；
- lease 到期只禁止新消费，不自动证明额度未被旧节点使用；
- 根账本只有在旧 holder 被 fenced 且完成 reconciliation 后才能重发未用额度；
- 安全优先于分区期间的无限可用性。

## 六、修订 5：语义内容身份与断言事件身份分离

### 6.1 问题

`id = hash(kind + content)` 会把相同文本的不同来源、时间、lineage、assertion 和 signature 折叠为同一事件，破坏独立证据和接触追踪。

### 6.2 定案

至少分离：

```text
ContentDigest
AssertionEventId
JudgmentEventId
VerificationEventId
RetractionEventId
SpecEventId
```

`ContentDigest` 只负责字面内容寻址和去重：

```text
ContentDigest = H(
  "llmos/content/v1"
  + deterministic_cbor([media_type, exact_bytes])
)
```

事件 ID 覆盖完整规范化信封：

```text
EventId = H(
  schema_version
  + event_type
  + issuer_principal
  + issuer_execution
  + control_domain
  + scope
  + nonce
  + issued_at
  + body
  + declared_parents
  + validity
)
```

签名对 EventId 签署，但不作为 EventId 的输入，以避免签名算法差异改变事件身份。`captured_inputs` 是接收域在 admission 时观察到的事实，写入单独的签名 AdmissionReceipt；它不能在生产者签发原事件后再反向改变 EventId。

相同 ContentDigest 可以对应任意多个独立事件；任何独立 provenance 都不得因内容去重而消失。

## 七、修订 6：验证、判断和撤回全部改为授权事件

### 7.1 不再原地写 verified

原子本体不含可变验证状态。验证结果是不可变 `VerificationEvent`。

“verified”是某个 ViewPolicy 对一组事件的派生结果，不是全局唯一字段。

### 7.2 独立性必须由身份和能力证明

- `method=independent-verifier` 只是声明，不能证明独立；
- verifier principal 必须持有当前 Policy 授予的 verifier capability；
- 默认要求 verifier principal/process 与 producer 不同；
- self-attested 永远保留为独立类别；
- deterministic checker 必须记录 checker digest、输入 Artifact digest 和执行环境；
- human 可以在 Policy 授权下成为最高权威验证者；
- 低权威事件不能用 latest-wins 覆盖高权威证据。

### 7.3 撤回不是全局删除

- 原发布者可以 withdraw 自己的 assertion；
- namespace 管理者可以在其作用域 quarantine；
- 第三方只能 dispute，不能冒充原作者撤回；
- RetractionEvent 必须携带 authority basis；
- Store 永久保留审计事件；
- View 根据当前 Policy 决定隐藏、警告或继续展示。

CRDT 合并只合并事件集合。内核不得自动生成 `CONTRADICTS` 语义关系；结构冲突只能产生非语义 `MergeConflictEvent`，关系判断仍由授权用户态判断者写入。

## 八、修订 7：IntentSpec 完整身份与 fail-closed gate

### 8.1 完整规格身份

SpecEventId 必须覆盖：

- schema version；
- goal ContentDigest；
- 全部 acceptance criteria；
- constraints；
- criticality；
- issuer；
- parent spec；
- delegation scope；
- release policy；
- idempotency key。

goal 相同但 acceptance、约束或发行者不同的规格必须是不同事件。

规格及其结构字段必须在同一 append-only 事务中写入，不得使用可裸改的旁表作为权威源。

### 8.2 Gate 状态

每个 criterion 使用：

```text
PENDING | PASS | FAIL | CONTESTED | ERROR | EXPIRED
```

`effect=HARD|SOFT` 与 `evaluator_kind=MODEL|DETERMINISTIC_TOOL|HUMAN` 是两个正交维度。deterministic checker 默认可作 hard gate；LLM judge 和人工评价默认为 soft evidence，但在显式声明 authority、pass/fail quorum、independence、timeout 和风险策略时也可成为 hard gate。这里的 HARD 表示“阻塞结算”，不表示世界事实被数学证明。

### 8.3 禁止真空通过

- `settlement.mode=AUTOMATIC` 时，hard set 必须等于全部 `effect=HARD` criterion 的规范集合，且非空；
- 空列表的 `all()` 不得解释为通过；
- 任一 required gate 为 PENDING/FAIL/CONTESTED/ERROR/EXPIRED 时不得自动释放；
- 没有 hard gate 的探索性 Task 可以存在，但 settlement 必须使用 MANUAL 或 NONE；
- model/human 若被显式提升为 HARD，其概率性风险必须在 immutable policy 中声明。

### 8.4 Escrow 状态机

```text
UNBOUND → HELD
HELD → DECISION_REGISTERED | RELEASED | REFUNDED | DISPUTED
DECISION_REGISTERED → PENDING_CHALLENGE | RELEASED | HELD | REFUNDED | DISPUTED
PENDING_CHALLENGE → RELEASED | HELD | REFUNDED | DISPUTED
DISPUTED → RELEASED | REFUNDED
```

每次迁移必须授权、幂等并产生 Receipt。EXPIRE 不暴露可竞争的 EXPIRED 中间态，而是在同一 CAS/双重记账事务中严格按 immutable `on_timeout` 进入 REFUNDED 或 DISPUTED。Escrow 是 Budget 原语之上的系统服务，内核不理解 acceptance 文本。

更准确地说：基础 KABI 不含 Escrow 特例；可协商的 `RESOURCE_ESCROW` 扩展只提供 `open/get/apply`，理解 opaque `SettlementContractDigest`、金额、TimePolicy/LedgerTimeProof、状态/CAS 和 basis-specific authorization bundle，schema 不出现 Spec、Event 或 TrustPolicy。IntentSpec、AuthorityView 和条件解析属于 `SEMANTIC_SETTLEMENT` 系统服务。

自动结算采用 `DecisionCore → subject-bound commit proof → register decision → durable notice → release`。Resource 账本具有 `DECISION_REGISTERED/PENDING_CHALLENGE` 状态，合法 deadline 前 decision 一经登记就不会被 timeout 抢跑；challenge 的 `< release_not_before` 与 release 的 `>= release_not_before` 由同一次 Ledger apply proof 精确分界。Decision/Notice proof 绑定 purpose、subject、Escrow、generation、nonce 和 durable commit domain；命令 apply proof 由 Ledger 在共识提交时注入，调用者不能拿旧 proof 回填 deadline。

Gate/Dispute/Manual 与 Resource receipt 全部使用 v1 固定 SHA-256、完整 ASCII type tag、domain-separated deterministic CBOR ID/signature。Dispute/Manual receipt 先投影为纯机械 Resource basis，并只绑定不含 basis IDs 的 CommandIntentDigest；最终 authorization 再签完整 CommandBodyDigest，避免摘要环。每个命令的 basis 使用固定 role/ordinal/type 槽位，Decision/Notice 的登记引用、授权引用和 abort history 不得混成一个通用角色。MANUAL 双签可按 immutable agreement policy 从 HELD 直接 RELEASE/REFUND。timeout caller 只提交 stable ExpireIntent，Ledger 在 apply 事务内生成最终签名 command/CommandId。hold 保存完整 HoldSaga；outbox 固定 canonical signed operation bytes、stable IDs 与原 key，重启后以 fresh handles 重绑。`get(EscrowId, CommandId|ExpireRequestId?)` 区分 PENDING/COMMITTED/REJECTED_FENCED/UNKNOWN，并在线性化读点返回带 canonical record/history digest 的签名 ResourceEscrowStateReceipt；UNKNOWN 不能当作“未提交”，但 state_seq 已推进或终态可权威 fence 旧 expected-state command。Notice、Release 和其他普通命令必须按当前 StateReceipt 收敛，不能因旧 ACK/Receipt 回退 Semantic head。Semantic adapter 只能持 resolver/notice capability，不能代签 payer、challenger 或 adjudicator。

## 九、修订 8：Provenance 明确为可分级 attestation

Provenance 分为：

- `captured_inputs`：由内核、Driver 或系统服务在受控边界自动记录；
- `declared_inputs`：由生产者自声明；
- `private_context`：系统无法证明完整性的私有推理状态。

事件必须标记 completeness：

```text
CAPTURED_BOUNDARY | DECLARED_ONLY | MIXED
```

强制携带 provenance 不等于保证 provenance 完整真实。对外只可声称已捕获边界内的依赖。

Taint 从 captured inputs 机械传播；declassification 必须由授权 Principal 产生签名事件。

TTL 只影响默认可见性，不等于从审计历史删除。内容 blob 可以在 retention 条件满足后 GC，但 EventId、ContentDigest 和删除证明必须保留。

## 十、修订 9：明确 TCB、不可绕过条件与宿主抢占

### 10.1 TCB 分域

| TCB | 组成 |
|---|---|
| Safety TCB | 宿主内核、NLOS 微内核、sandbox/egress、capability、ledger、identity key store、enforcement driver |
| Epistemic TCB | 事件 canonicalizer、append-only store、签名验证、verifier registry、View engine |
| Update TCB | Package 验签、安装器、更新器、回滚锚点 |
| Trusted UI TCB | 登录、权限提示、密钥确认、系统 chooser 和安全状态展示 |

### 10.2 不可绕过不是只托管 API key

一个运行域只有同时满足以下条件才能称为 strict：

- 真实 credential 不进入不可信 Process；
- 网络 egress 默认拒绝，只允许受控 Driver；
- 文件、socket、数据库和工具 handle 通过 capability 授予；
- 宿主进程/容器隔离禁止直接访问被保护资源；
- Driver 的取消、计量和 usage proof 满足声明契约。

不满足以上条件的部署必须标记为 cooperative domain，不能宣传“物理不可绕过”。

### 10.3 抢占

- LLM/tool 边界是有用的 cooperative safe point，不是普适时钟中断；
- pure-code Process 必须依赖宿主 OS 的 preemptive scheduling、CPU quota 和 kill；
- 长流式调用必须支持可取消 OperationId；
- suspend 不保证外部 provider 自动停止，in-flight 操作必须进入 cancel/drain/settle；
- 无法 checkpoint 的 Driver session 必须显式声明 pinned/non-migratable。

### 10.4 Profile 适用性必须可计算

EnforcementProfile、SurfaceProfile、AssuranceLevel 和 DeploymentMode 是四个正交维度，不能再压成一个“生产级”标签。每条 requirement 由有序、闭合的 prefix registry 映射为布尔 applicability；FeatureRegistry 和 OperationRegistry 是版本化输入。正文中的 `if ENFORCED`、`STRICT` 等只表示已适用条款内部的条件分支，不是隐藏的适用例外。CI 必须为每个 requirement ID 输出 `APPLIES` 或 `DOES_NOT_APPLY` 及命中规则，不能让模型解释“适当安全条款”之类的自然语言集合。

## 十一、修订 10：重建 KABI 与系统服务 ABI

### 11.1 三类兼容契约

- **KABI**：微内核与可信系统服务之间的对象能力 ABI；
- **SABI**：第三方应用使用的稳定系统服务 API；
- **Package/Driver ABI**：安装、加载、设备协商与应用生态契约。

原“约 22 个 syscall”表废止。v0.5 不以数量作为胜利条件。

### 11.2 KABI 只容纳原子机制

v0.5-alpha 的基础 KABI 候选统一为 27 个入口；编号要到纵切面和 IDL conformance 后才能冻结：

| 编号 | 调用族 | 候选入口 |
|---:|---|---|
| 1–8 | Process | `proc_spawn`, `proc_exit`, `proc_wait`, `proc_suspend`, `proc_resume`, `proc_kill`, `proc_checkpoint`, `proc_restore` |
| 9–13 | Object view mapping | `view_map`, `view_unmap`, `view_pin`, `view_unpin`, `view_advise` |
| 14–17 | Namespace/Handle | `ns_lookup`, `ns_delegate`, `ns_revoke`, `handle_close` |
| 18–22 | Generic async I/O | `io_submit`, `io_write`, `io_read`, `io_poll`, `io_cancel` |
| 23–24 | Resource | `budget_query`, `budget_transfer` |
| 25–27 | Trusted metering | `meter_reserve`, `meter_consume`, `meter_finalize` |

其中 25–27 只允许具有 `RIGHT_METER_DRIVER` 的可信 Driver/reference monitor 调用。另有可协商的 3-entry `RESOURCE_ESCROW` 通用扩展：`resource_escrow_open/get/apply`；它不是基础 KABI，也不认识语义类型。restore 只用于同一 ProcessId 的 fenced 接管；branch 必须以 Checkpoint 为初始状态执行一次新的 LaunchGrant，产生新 ProcessId 和独立 Capability/Resource。语义 `join` 由 wait + 用户态聚合服务组合。Topic、Blackboard、Semantic CRUD、Package 安装、LLM 和 Tool 通过 typed handle + generic I/O 或 SABI 实现；quota lease 使用可信控制面私有协议。27 只是当前组合结果，不是最小性证明。

第三方应用的 SABI 同时定出最小服务族：ServiceDirectory、Package、Application、Task、Artifact、Context、Intent、Operation/Receipt、Notification、Search、Settings、Keychain、Device、UI Surface、Workspace 和 Session。所有长操作统一继承 capability、version negotiation、idempotency、deadline、cancel、partial failure 和 Receipt；这使“完整 NLOS”不再只存在于路线口号中。

### 11.3 Spawn 三划拨

`spawn` 接收结构化 `LaunchGrant`：

```text
launch kind
principal
package/executable handle
capability root
budget account or lease
activity context（Task/Application/SystemActivity/Session 之一）
intent spec obligation（仅 delegated task 必填）
execution limits
correlation
```

capability 衰减、Budget/Resource 划拨、可选 obligation 和 Process identity 必须在 child 进入 RUNNABLE 前形成一个 durable BirthDecision。delegated task 还原子绑定 AttemptContract、IsolationDomain generation/fence、TaskSnapshotReceipt、staging、CancellationScope、group membership 与系统分配的 AgentInstance；普通 Application、daemon、UI 和系统服务不必伪装成知识 Task。

### 11.4 海量 Agent：线程/进程类比的正确落点

不能把一个含糊的 Agent 对象同时当线程、进程、任务和语义主体。v0.5 明确：

| 对象 | 类比与职责 |
|---|---|
| AgentRole | 角色/程序逻辑，不是隔离边界 |
| AgentInstance | thread/actor 式一次执行；共享 Process 时只有 thread-like 隔离 |
| Process + IsolationUnit | 可由宿主抢占、限额、强杀的执行安全边界 |
| Task | 用户可见、可持续的义务 |
| TaskAttempt | 一次 retry/hedge/refinement 的输入、权限、资源、写集与提交隔离单位 |
| TaskGroup + IsolationDomain | structured concurrency、层级取消、bulkhead 与多维安全边界 |
| TaskSnapshot | Artifact/Semantic/Identity/Settings/Package 的 causal-closed 读切面 |
| TaskControlRecord + Commit/EffectPermit | 多候选 winner、取消、真实副作用与 canonical commit 的共同线性化点 |
| EffectSlot + PermitAdoption | 每个外部副作用独立签发、dispatch、闭合；跨 epoch 只可 reconcile，未知 effect 进入隔离墓碑 |
| TaskAuthorityParticipantRegistry | 动态登记所有可跨接管存活的 endpoint，并在 permit/takeover 前冻结精确 fence root |

这套模型可以控制海量 Agent 的可观察输入、Capability、资源、通信、取消、失败与唯一发布，但不承诺所有模型产生同一文本、持有同一信念或结论天然为真。TaskSnapshotReceipt 证明跨 authority 的 causal-closed cut；membership root 从 Attempt 贯穿 WriteSet/Permit/Commit；所有 Task 通信由 runtime 注入 Domain/authority epoch 并按 recipient 去重。CommitPermit 未关闭时不能换 winner，多个 EffectPermit 由完整、无洞的 EffectSlot root 逐槽排序；required slot 必须满足预绑定成功条件，普通 skip 不能冒充 COMMITTED。跨 Attempt 的同一业务副作用使用不含 AttemptId 的 LogicalEffectId；TaskHead、Snapshot、WriteSet 与 Permit 贯穿 durable effect-history root/retry-fence epoch，换 ActionId 不能绕过重复效果防线。`EFFECT_UNKNOWN` 不关闭 permit、不前进 TaskHead，只能通过 PermitAdoption 和权威 closure proof 从 QUARANTINED 进入 RECONCILING。LOST 也不等于 child 已终结。

共享结果按对象选择 PRIVATE/SNAPSHOT/CAUSAL/CONVERGENT/SERIALIZABLE/LINEARIZABLE 契约，降级必须由调用者显式允许；搜索和 embedding 的最终一致结果不得直接驱动授权、资金或不可逆副作用。跨 Cell 通过 TaskAuthorityAssignment、动态 ParticipantRegistry、takeover fence barrier、vector checkpoint、lease/fencing 和层级 reducer 扩展；planned effect endpoint 必须在 CommitPermit 前注册并冻结，接管覆盖 frozen registry 全集与 outstanding operation participants，不能依赖全局 prompt、全局锁或 O(N²) 广播。

### 11.5 现代资源管理不等于 Budget

ResourceAccount 与 ResourceGroup 被正式分离：

- ResourceAccount 管可转移 credit、外部费用和权威账本；
- ResourceGroup 类似 cgroup/job object，管 CPU、memory、I/O、network、accelerator 的层级调度、容量和 pressure；
- ResourceContract 使用 Cpu/Capacity/Rate/Cumulative/Exclusive 等 tagged demand，声明 requested/effective demand、scheduling class、保证、回收与失败策略；
- ResourceAllocation/Reservation/QuotaLease/CapacityLease/ExclusiveDeviceLease/Meter 分别表达本地容量、外部费用、分布式额度、物理容量、排他设备和累计用量。

现代系统的抢占、fair-share、quota、working set、pressure/reclaim/OOM、I/O backpressure、network QoS、GPU/VRAM allocation、energy/thermal policy 和分布式 placement/fencing 均有 NLOS 对应物；NLOS 还增加模型 token/context/KV cache、外部成本、Topic fanout 和人类注意力。多资源工作在 RUNNABLE/dispatch 前形成覆盖完整 proposal root 的 durable AdmissionPlan/typed PreparedReceipt/唯一 Decision；plan-level fence 拒绝迟到 PREPARE，COMMIT 后补偿必须以更高 epoch 覆盖全体 participant，完成 fence/cleanup 前不得复用容量。父子 strict capacity 以权威事务防超卖；controller manifest、forced fence/cleanup 与 Quota/Capacity/ExclusiveDevice 三类 lease 分别闭合，DeviceLeaseHead CAS 加 fence/reset/zeroization 防止跨 epoch 双 holder。只靠 meter、告警或 Agent 自律的维度最多叫 OBSERVED，不能宣传 hard quota。

## 十二、修订 11：看门狗和控制面降权

### 12.1 三层监督

| 层 | 输入 | 默认动作 |
|---|---|---|
| L0 内核 | 时间、CPU、Budget、heartbeat、队列等纯结构状态 | 限流、超时、挂起 |
| L1 系统服务 | durable Artifact、checker transition、调用结果等结构进展 | 建议 pause/review |
| L2 语义监督/人 | 被隔离的内容与任务语义 | 输出签名建议或人工裁决 |

文本相似度、embedding 和 LLM 判断不得作为微内核自动 kill 的唯一依据。

双空 content 不参与相似度；发生新的 captured Artifact/tool result 时，重复文本计数不得单独触发挂起。

语义监督者不直接持有 kill、扩权或大额 Budget grant capability。它只能通过固定 schema 输出建议，由确定性 Policy controller 或人类执行。

## 十四、路线修订：兼容性从第一天开始，桌面不等待分布式完成

路线拓扑改为：

```text

             ↓
B 单机应用平台 + 最小 Task Space
             ↓
┌──────────────────┬──────────────────┐
│ C 分布式现代系统 │ D 完整自然语言桌面 │
└──────────────────┴──────────────────┘
             ↓
E 兼容性制度化与生态规模化
```

兼容性、安全、证据纪律贯穿所有阶段，不是 E 阶段才开始。

每阶段必须同时通过：

1. **证据门**：当前实现是否兑现所声称的不变量；
2. **演进门**：是否保留通往通用应用、完整桌面和第三方生态的路径。
