# 议题 30：阶段 B 技术栈讨论

> 状态：讨论中
>
> 基线：[阶段 B 技术选型](../management/stage-b-technology-selection.md)
>
> 原则：技术栈服务于 NLOS 对象模型；任何库、runtime、数据库或 UI 框架都不得反向成为 KABI/SABI 的身份和语义来源。

## 1. 讨论顺序

按“越底层、越难替换、越先讨论”的顺序：

1. 核心语言与异步/Fiber runtime；
2. Process/IsolationUnit 与第三方代码沙箱；
3. 本地权威状态、WAL 与 Artifact；
4. IDL、canonical encoding 与本地 IPC；
5. Resource Controller 和平台适配；
6. Package/Application/Driver 格式；
7. 可观测性与测试基础设施；
8. CLI、Task Manager 与桌面技术。

桌面框架必须晚于 SystemControl typed API；否则 UI 的私有 RPC 会反向污染系统契约。

## 2. 第一项：核心语言

### 2.1 候选

| 候选 | 安全/正确性 | 并发与性能 | 跨平台/生态 | 与 NLOS 的主要关系 |
|---|---|---|---|---|
| Rust | 强类型、ownership、无 GC；unsafe 仍需审计 | async、低层控制、可预测 | Windows/macOS/Linux，系统生态较强 | 最适合 Safety TCB、nominal ID、状态机和 adapter |
| Go | 内存安全、实现简单 | goroutine/runtime 成熟；GC 和 runtime policy 较强 | 服务端生态强 | 适合服务，但宿主控制和 runtime 语义更难完全封装 |
| C++ | 控制力强 | 性能成熟 | 系统生态最广 | TCB 内内存安全与并发风险较大 |
| Java/Kotlin | 类型和工具链成熟 | virtual thread/GC 强 | 企业服务生态强 | 桌面/服务可用，但 native supervisor/嵌入路径较重 |
| Python | 开发快 | 核心规模、隔离和可预测性弱 | Agent 生态最强 | 适合 SDK、Planner、实验，不适合 Safety TCB 主体 |

### 2.2 当前建议

采用“双层语言政策”：

```text
Rust
  → kernel/runtime/supervisor/resource/store/driver-host/CLI

Python + 其他语言
  → Planner、Agent application、实验、SDK、Wasm/native child
```

选择 Rust 不是因为“Rust 自动安全”，而是它让以下要求更容易被代码结构强制：

- `ApplicationId`、`ProcessId`、`AgentInstanceId`、`ExecutionFiberId` 名义类型分离；
- Capability/handle ownership 和 generation；
- 状态机的穷尽匹配；
- Resource/Receipt 的 checked integer；
- Tokio、Wasmtime、SQLite 和 platform API 的统一宿主；
- future C ABI、WIT 或 RPC SDK。

### 2.3 不接受的做法

- 把 Rust struct memory layout 冻结成 KABI；
- 让应用直接依赖内部 crate；
- 到处暴露 Tokio/SQLite/Wasmtime 类型；
- 用 `unsafe` 绕过 Capability、lifetime 或并发控制；
- 因 Python Agent 生态丰富而把 credential/ledger/supervisor 放入 Python TCB。

### 2.4 待定点

1. Rust 是否作为整个阶段 B 的唯一核心实现语言，还是允许 Go 承担部分非 TCB 系统服务？
2. Python SDK 第一版采用本地 RPC，还是同时提供 Wasm component 编译路径？
3. 是否从第一天建立稳定 C ABI，还是先冻结 IDL/WIT，延后 C ABI？

当前推荐：

- 核心实现只用 Rust，先降低多语言构建和故障复杂度；
- Python 先通过 typed local RPC 接入；
- 不冻结 C ABI，优先冻结 schema/WIT 和行为 conformance。

## 3. 第二项：Fiber runtime

### 3.1 必须区分的五层

```text
Task/TaskAttempt       # 持久义务和提交隔离
AgentInstance          # thread/actor-like 执行身份
ExecutionFiber         # coroutine/fiber
Activation             # 一次 dispatch turn
Tokio Task             # 当前实现引擎的 runtime-local 对象
```

前四层是 NLOS 语义；Tokio task 只是候选实现，不得进入 durable state、Capability、Receipt 或公开 API。

### 3.2 候选

| 候选 | 优点 | 风险 | 结论 |
|---|---|---|---|
| Tokio | 跨平台 I/O、work stealing、生态成熟 | 调度、公平、取消不是 NLOS 语义；容易被业务直接 spawn 绕过 | 首选 PoC |
| async-std/smol | 较轻、更容易理解 | 生态和长期主流度较弱 | 对照候选 |
| 自研 executor | 完全控制 queue/Activation | 研发成本、并发 bug、安全风险极高 | 阶段 B 不首选 |
| 一 Agent 一线程 | 模型简单 | 规模和资源不可接受 | 排除 |
| 一 Agent 一进程 | 强隔离 | 不能承载 PID 级逻辑实体 | 仅用于不互信边界 |

### 3.3 推荐结构

```text
NLOS SchedulerDomain
  → admission/materialization/priority/deadline/resource policy
    → RuntimeAdapter
      → per-Worker bounded runnable queues
        → Tokio executor
          → host threads
```

`RuntimeAdapter` 最小职责：

- `spawn_fiber`
- `yield_now`
- `await_operation`
- `cancel_scope`
- `suspend/resume`
- `meter_activation`
- `inspect`

禁止业务模块直接持有全局 Tokio runtime handle。内部需要 spawn 时必须携带：

```text
FiberContext {
  fiber_id
  agent_instance_id
  process_incarnation
  task_attempt_id?
  cancellation_scope
  resource_group
  scheduler_domain
  deadline
}
```

### 3.4 Tokio PoC 的否决门

任一情况成立就不能直接接受：

- 100K waiting Fiber 的内存超过目标 ScaleProfile；
- cancel/control path 会被 CPU-heavy Fiber 长时间饿死；
- 无法可靠阻止 bypass spawn；
- Activation 计量开销或误差不可接受；
- runtime shutdown 遗留无法归属的 Operation；
- platform I/O 差异导致核心语义不一致。

PoC 失败后的顺序不是立刻自研 executor，而是：

1. 调整 facade、队列和 worker 分区；
2. 将 CPU-heavy/pinned workload 移到 Process pool；
3. 对比 smol/其他 Rust runtime；
4. 只有证据证明通用 runtime 无法满足不变量时才讨论自研。

## 4. 初步结论

当前建议进入 PoC、尚未 ACCEPTED：

```text
核心 TCB：Rust
异步引擎：Tokio
系统边界：RuntimeAdapter
规模策略：大量 logical/Fiber + 有限 Process/host thread
多语言：typed local RPC / Wasm component
```

## 5. 下一轮讨论

下一项是 Process/IsolationUnit 与沙箱组合，核心问题包括：

- native Process、Wasm component、容器分别承担哪一层；
- macOS/Windows/Linux 如何提供最低共同强制语义；
- Wasmtime 放在 kernel Process 内还是独立 sandbox host；
- Package 中如何声明 trust、runtime 和 resource profile；
- native third-party Application 是否允许，以及进入哪个 GuaranteeTier。

这些问题决定阶段 B 是否真的能运行“不受信任的第三方应用”，而不只是运行自己编写的 Agent。

## 6. 第三项：Process、IsolationUnit 与 Wasmtime

### 6.1 必须分开的对象

```text
NLOS Process
  = 稳定身份、生命周期、资源、故障和控制对象

Host IsolationUnit
  = OS process / Job / cgroup / sandbox / container / VM

Wasm Instance
  = 某个 IsolationUnit 内的语言级 sandboxed component instance
```

三者不是一一同义：

- 一个 NLOS Process 在恢复后可以绑定新的 Host IsolationUnit generation；
- 一个 Host IsolationUnit 可以承载同一信任域内的多个 AgentInstance/Fiber；
- 一个 sandbox host 可以承载多个 Wasm Instance，但不能因此假装它们具有独立 Process 故障域；
- 互不信任、独立强杀、独立 secret 或独立资源上界通常要求不同 Host IsolationUnit。

### 6.2 安全结论

> **Wasm 是内层代码沙箱，OS Process 是外层故障与强杀边界；阶段 B 默认采用组合隔离，而不是二选一。**

原因：

1. Wasmtime 能限制 guest memory/table/instance，并支持 fuel、epoch interruption 和 capability-oriented WASI import；
2. Wasmtime 或 host adapter 自身仍可能存在漏洞、panic、宿主内存和 credential 错误；
3. in-process Wasm Instance 共享宿主进程的崩溃域和宿主权限；
4. OS Process 可以由宿主最终终止并绑定平台级资源控制；
5. NLOS reference monitor 仍必须位于所有文件、网络、模型、工具和 secret 路径上。

### 6.3 推荐的信任档位

```text
T0 SYSTEM_TCB
  Rust native dedicated Process
  + 最小宿主权限
  + 不允许第三方代码动态进入

T1 TRUSTED_SERVICE
  signed native/Wasm dedicated Process
  + 平台 sandbox/resource controller
  + 受控 Driver/IPC

T2 THIRD_PARTY_WASM（阶段 B 默认）
  dedicated sandbox-host Process
  + Wasmtime/WASI Component
  + deny-by-default imports
  + per-Application data/container

T3 THIRD_PARTY_NATIVE（显式高风险）
  dedicated native Process
  + 最强可用平台 sandbox
  + 无原始 credential
  + 降级 GuaranteeTier

T4 LEGACY/UNCONFINED
  仅通过外部 Driver/automation 边界交互
  + 明确 UNVERIFIED/COOPERATIVE
  + 不得宣传为受控 NLOS Application
```

阶段 B 的第三方默认目标是 T2。T3 不是完全禁止，因为通用系统最终必须处理 native 应用，但第一版必须经过显式用户授权和降级声明。

## 7. Process 与 Wasm Instance 的映射

### 7.1 推荐默认值

```text
1 Application security domain
  → 1..N NLOS Process
    → 默认每个强隔离 Process 绑定 1 sandbox-host OS process
      → 1..N Wasm Instance（仅同 Application/IsolationDomain）
```

允许在一个 sandbox host 中复用多个 Wasm Instance 的前提：

- 同一 Principal/Application security domain；
- 同一 secret、network、filesystem 和 Device policy；
- 接受共享 crash domain；
- ResourceGroup 能提供有效的 per-instance soft accounting；
- 任一 instance 不需要独立 OS 强杀。

否则必须拆分 Host IsolationUnit。

### 7.2 不采用“一 Wasm Instance 一 OS Process”为固定规则

固定一一映射虽然简单，但会：

- 把 logical/Fiber 规模错误推成 OS PID 规模；
- 增加启动、内存和上下文切换成本；
- 阻止同一 Application 的可信轻量组件共享 runtime；
- 让 Process 对象模型被当前 Wasm 实现绑死。

系统以 IsolationContract 决定映射，而不是用对象名称猜测：

```text
IsolationContract {
  trust_tier
  required_kill_boundary
  crash_domain
  namespace_profile
  secret_profile
  network_profile
  resource_guarantees
  native_or_wasm
  co_residency_policy
}
```

## 8. 三平台宿主适配

### 8.1 Linux

首选候选：

- cgroup v2：层级 CPU、memory、I/O、PID 等资源控制；
- user/mount/PID/network namespace；
- seccomp；
- Landlock 或等价文件访问收缩；
- pidfd、signal 和受控 supervisor；
- 必要时独立容器/VM profile。

Linux cgroup v2 本身就是“层级组织进程并分配系统资源”的机制，适合映射 NLOS ResourceGroup，但 namespace、seccomp、filesystem 和 credential custody 仍需单独组合。[Linux cgroup v2 官方文档](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html)

### 8.2 Windows

首选候选：

- Job Object：进程树、CPU/memory limit、终止、notification 和 accounting；
- restricted token / AppContainer；
- named pipe + ACL；
- Windows Filtering Platform 或受控 gateway；
- 必要时 Windows Sandbox/Hyper-V profile。

Windows Job Object 可以把进程组作为整体管理、施加资源限制并聚合 accounting，适合 ResourceGroup/IsolationUnit binding；但其安全限制不能替代每个进程的 token/ACL/sandbox。[Microsoft Job Objects 文档](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)

### 8.3 macOS

首选候选：

- App Sandbox entitlement/container；
- XPC service 作为 privilege separation；
- code signing、Hardened Runtime；
- Endpoint/network access 通过 broker；
- Resource limit 能力不足部分由 NLOS admission/metering 降级声明。

Apple App Sandbox 通过 entitlement 限制文件、网络和设备，并为应用建立 container；Apple 也明确把 XPC 作为 privilege separation 的首选技术之一。[Apple App Sandbox](https://developer.apple.com/documentation/security/app-sandbox)、[配置说明](https://developer.apple.com/documentation/xcode/configuring-the-macos-app-sandbox)、[sandbox inheritance/XPC](https://developer.apple.com/library/archive/documentation/Miscellaneous/Reference/EntitlementKeyReference/Chapters/EnablingAppSandbox.html)

macOS 是阶段 B 的关键难点：公开资源控制能力不像 Linux cgroup/Windows Job 一样统一。实现必须按资源维度报告 `HARD_ENFORCED / METERED / COOPERATIVE / UNSUPPORTED`，不能为了跨平台 API 对称而虚构强制保证。

## 9. Supervisor 架构建议

```text
NLOS Kernel/System Authority
  └─ Process Supervisor
      ├─ LinuxHostAdapter
      ├─ WindowsHostAdapter
      └─ MacOSHostAdapter
           ↓
        IsolationUnit
           ↓
        Sandbox Host
           ↓
        Wasmtime Component
```

Supervisor 必须拥有：

- spawn-before-run barrier；
- process tree ownership；
- stdout/stderr/diagnostic pipe；
- suspend/freeze/terminate/kill；
- exit/host-loss notification；
- resource binding 和 usage query；
- inherited FD/handle allowlist；
- environment/working-directory 清洗；
- credential absence attestation；
- generation、PID reuse 和 stale callback fencing。

Application 不得直接获得 supervisor control socket。

## 10. 当前建议与待 PoC

### 当前建议

1. **默认第三方格式**：WASI Component；
2. **默认隔离组合**：独立 sandbox-host OS Process + Wasmtime；
3. **同域优化**：同一 Application/IsolationDomain 可在证据支持时共享 host；
4. **native 应用**：允许，但必须独立 Process、显式授权并降级 GuaranteeTier；

## 11. 本轮初步结论

本轮建议进入 PoC、尚未 ACCEPTED：

```text
NLOS Process ≠ OS PID ≠ Wasm Instance

第三方默认：
NLOS Process
  → dedicated OS sandbox-host Process
    → Wasmtime/WASI Component

高规模：
```

## 12. 第四项：本地权威状态与 SQLite

### 12.1 先按语义分类，而不是按数据类型分类

阶段 B 至少有四类持久状态：

| 类别 | 示例 | 要求 | 推荐介质 |
|---|---|---|---|
| Canonical authority | TaskHead、Attempt、Capability generation、Resource allocation、Ledger balance、Receipt、idempotency | 原子、durable、可恢复、CAS | 单机 authority database |
| Immutable content | Artifact revision、Package、checkpoint、Evidence bytes | content digest、版本、fsync、GC | content-addressed file store |
| Rebuildable projection | search index、embedding、materialized view、UI cache | 可丢弃重建、带 source checkpoint | 独立 projection database/cache |
| Ephemeral runtime | runnable queue、Fiber stack、socket、provider session | 有界、可重建或明确不可恢复 | memory/runtime |

不能把四类都塞进同一数据库，也不能为了“event sourcing”把大对象复制进 WAL。

### 12.2 当前建议

阶段 B 使用：

```text
authority.db
  SQLite WAL + synchronous=FULL
  单一 Authority Writer
  canonical tables + append history + outbox

artifacts/
  content-addressed immutable bytes
  staged write → fsync → rename → DB reference commit

projections/
  search.db / embedding cache / UI cache
  可按 authority checkpoint 重建

runtime/
  bounded queues / Fiber / Operation live state
```

### 12.3 为什么阶段 B 首选 SQLite

- 单机部署无需外部数据库 daemon；
- transaction、constraint、index、backup 和 migration 工具成熟；
- WAL 允许 writer 与 readers 并发；
- Rust 能通过成熟 binding 使用；
- 100K logical metadata 规模远未证明需要分布式数据库；
- 阶段 C 可以把 AuthorityStore trait 映射到复制状态机，而不是让阶段 B 先承担集群运维。

SQLite 官方说明 WAL transaction 通过 commit frame 生效，checkpoint 与 transaction commit 是不同动作；`synchronous=FULL` 在 WAL 模式下会在每次 transaction commit 后增加 WAL sync，而 `NORMAL` 可能保留一致性但丢失最近 durable commit。[SQLite WAL](https://www.sqlite.org/wal.html)、[synchronous pragma](https://sqlite.org/pragma.html)

所以：

> 阶段 B 的 durable ACK 路径不能使用 `synchronous=NORMAL` 冒充 durable commit。

### 12.4 单库还是多库

当前推荐：

- 所有需要原子联动的 canonical authority 状态进入一个 `authority.db`；
- search、embedding、telemetry 和 UI projection 使用独立数据库；
- Artifact bytes 不进入 `authority.db`；
- secret material 不进入普通 SQLite，由平台 Keychain/credential broker 托管。

把 canonical 状态拆成多个 SQLite 文件会引入跨文件 commit、恢复顺序和 backup checkpoint 问题；尤其 WAL 下不能默认假设任意多文件业务事务都有符合 NLOS 要求的统一 durable ACK。因此阶段 B 先选择单 authority file，以逻辑 schema/module 分域。

单库不表示单体架构：Task、Resource、Package、Receipt 等仍由独立 service/module 和 repository interface 拥有，只共享 commit authority。

## 13. Authority Writer

推荐单写入权威：

```text
many Process/Fiber clients
  → bounded typed command queue
    → Authority Writer
      → BEGIN IMMEDIATE
        → validate expected revision/generation
        → append events/receipts
        → update current heads
        → append outbox
      → COMMIT + durable ACK
```

优点：

- 写入顺序和 busy handling 更明确；
- 便于实现 CommandId/idempotency；
- 避免每个 Agent/Application 直接打开数据库；
- 便于故障注入、审计和迁移；
- 未来可把 Writer 替换为阶段 C 的 replicated log leader。

约束：

- Writer queue 必须有界并按 ResourceGroup/backpressure；
- 长时间计算、网络或模型调用不得在 transaction 内发生；
- read pool 使用明确 snapshot/checkpoint；
- 高风险操作先在事务外准备 immutable input，再在短 transaction 内 CAS；
- DB 文件权限只授予 Authority service，Application 不得直接访问。

## 14. Canonical schema 模式

### 14.1 Immutable log 与 current head 并存

```text
task_history       append-only facts
task_head          current revision + CAS
receipts           immutable
idempotency_result stable request → result
outbox             committed but not yet delivered
```

只使用 event log 会让每次热路径恢复成本上升；只使用 mutable rows 会丢失历史和 reconciliation。因此阶段 B 采用“不可变 history + 可验证 current projection”的组合。

### 14.2 原子命令事务

同一个系统命令需要在一个 transaction 中完成：

1. 验证 Capability/generation/expected revision；
2. 验证 idempotency key；
3. 追加不可变事实；
4. CAS 更新 current head；
5. 更新 Resource/Ledger 守恒状态；
6. 写入 Receipt；
7. 写入 durable outbox；
8. 保存 idempotency result；
9. COMMIT 后才返回成功。

任何外部副作用不能放进数据库 transaction 假装原子。它必须使用 Operation、Reservation、EffectPermit、outbox 和 reconciliation。

### 14.3 类型与约束

推荐：

- SQLite `STRICT` tables；
- ID 存储为固定长度 BLOB 或严格编码，不用可混淆自由字符串；
- authority amount 使用 checked integer；
- foreign key、unique、check constraint；
- monotonic `state_seq` 和 expected revision；
- immutable table 通过 trigger/authorizer/application guard 禁止 UPDATE/DELETE；
- schema version 和 migration digest；
- 不信任的 payload 存 digest/ref，不让 SQL trigger 解释自然语言。

数据库 constraint 是纵深防御，不能代替 Rust nominal type、Capability validation 和 conformance test。

## 15. Ledger 是否直接使用 SQLite

### 15.1 建议

阶段 B Ledger 使用 `authority.db` 内的专用 append-only journal + balance/materialized state，不另写一套自研文件 WAL。

理由：

- SQLite 已提供 transaction、WAL、recovery 和 fsync 路径；
- 另写 WAL 会产生双日志 commit、恢复排序和重复 durable boundary；
- Resource reservation、Task birth、EffectPermit 和 Receipt 经常需要同一 transaction；
- 阶段 B 的首要任务是证明守恒和恢复，不是先实现数据库内核。

### 15.2 必须保留的 Ledger 不变量

- 每次 transfer/reserve/finalize 双重记账；
- integer checked arithmetic；
- transaction 内验证 before/after；
- stable TxnId/IdempotencyKey；
- append journal 不允许原地更新；
- balance 是 journal 的可验证投影；
- startup 执行 consistency/invariant check；
- kill/torn-write/disk-full/duplicate request 测试；
- ACK 只能在 SQLite durable commit 返回后发出。

### 15.3 何时考虑独立 Ledger engine

只有 PoC 证明以下问题不能通过 schema、batch/group commit 或 storage adapter 解决时：

- durable write throughput 不满足 Stage B ScaleProfile；
- authority.db 写放大阻塞 Task/Control path；
- Ledger 需要与其他 canonical state 不同的复制/保留模型；
- SQLite VFS/平台 durability 无法达到声明等级；
- 独立审计或加密边界是硬要求。

即使拆分，也必须先设计跨 Authority 与 Ledger 的 prepare/commit/reconcile，而不是双写。

## 16. Artifact 原子提交

Artifact bytes 和 DB row 无法靠一个普通 transaction 覆盖，采用“先 durable 内容、后提交引用”：

```text
write temp blob
  → hash while writing
  → fsync temp
  → atomic rename to ContentDigest path
  → fsync parent directory
  → DB transaction commits Artifact revision/reference
```

崩溃语义：

- DB commit 前崩溃：留下无引用 content blob，可由有宽限期的 GC 回收；
- DB commit 后：引用的 digest 对应 blob 必须已经 durable；
- DB 引用存在但 blob 缺失：进入 corruption/quarantine，禁止伪装成正常 `NOT_FOUND`；
- 相同 digest 的并发写入必须幂等；
- 删除只删除引用，物理 GC 要证明无 active revision/snapshot/hold。

这样选择“允许安全 orphan”，而不是“允许已提交引用指向不存在内容”。

## 17. WAL、checkpoint 与 backup

### 17.1 配置候选

```sql
PRAGMA journal_mode = WAL;
PRAGMA synchronous = FULL;
PRAGMA foreign_keys = ON;
PRAGMA trusted_schema = OFF;
```

其他 pragma 必须由 benchmark 和平台能力决定，不能复制博客配置。

checkpoint policy：

- 由 Authority service 管理，不让每个 client 随机 checkpoint；
- 监控 WAL bytes、oldest reader、checkpoint latency；
- 长读 snapshot 不能无限阻塞 WAL 回收；
- pressure 下节流 writer 或终止非关键 stale reader；
- checkpoint 失败不等于已提交 transaction 丢失，但必须影响 storage pressure。

SQLite 把 `-wal` 视为数据库持久状态的一部分；数据库活动期间分离或随意删除 WAL 可能丢失已提交 transaction 或导致损坏。[SQLite WAL 文件规则](https://www.sqlite.org/wal.html)

### 17.2 Backup

一致备份必须覆盖：

- authority database 的一致 snapshot；
- Artifact manifest 和对应 content blobs；
- schema/build/version；
- encryption/key references；
- backup checkpoint/digest；
- restore validation report。

禁止直接复制活动中的 `authority.db` 单文件并称为完整备份。使用 SQLite backup API/受控 snapshot，再按 manifest 复制 Artifact；restore 必须在隔离目录演练后才替换当前 authority。

## 18. Durability GuaranteeTier

SQLite 的保证仍依赖 OS、filesystem、VFS、device 和 flush 行为。SQLite 官方原子提交文档明确列出对 fsync、文件删除、sector 和硬件的假设。[SQLite Atomic Commit](https://www.sqlite.org/atomiccommit.html)

因此 build/runtime manifest 必须声明：

| 等级 | 含义 |
|---|---|
| MEMORY_ONLY | 仅测试，不声明 crash durability |
| PROCESS_CRASH_DURABLE | 通过 kill -9/restart |
| OS_CRASH_DURABLE | 在声明平台/filesystem 完成故障测试 |
| POWER_LOSS_EVIDENCE | 有真实/仿真 power-cut 与硬件证据 |

不能因为设置了 `synchronous=FULL` 就自动声明所有硬件上的 power-loss durability。

## 19. SQLite PoC 否决门

PoC-0003 至少验证：

1. 10K/100K/目标上限 TaskNode metadata；
2. single writer command throughput 和 p99；
3. concurrent readers、长 snapshot 与 WAL growth；
4. kill -9 at commit boundary；
5. disk full、I/O error、corrupt/torn WAL；
6. duplicate CommandId/IdempotencyKey；
7. Ledger 守恒 property test；
8. Artifact durable-before-reference；
9. migration interruption和 rollback/forward recovery；
10. backup/restore 后 state hash、Receipt 和 blob 完整性。

以下任一发生则重新评估：

- 无法满足阶段 B durable latency/throughput；
- Writer 成为控制面不可接受的单点停顿；
- WAL/reader pressure 无法有界控制；
- 核心 schema 无法保持模块边界；
- 三平台 durability 差异无法合理分档。

## 21. 第五项：IDL、编码与本地 IPC

### 21.1 三种格式分工

不采用“一种序列化统治全部边界”：

| 用途 | 选择 | 原因 |
|---|---|---|
| Service/RPC | Protobuf + Buf | 多语言生成、schema evolution、breaking check |
| Wasm Component ABI | WIT/WASI Component Model | 跨语言 component interface、resource handle |
| 签名、哈希、Receipt、Event | RFC 8949 deterministic CBOR + CDDL/golden vectors | 字节身份稳定、可验证 |

Protobuf 官方明确说明 deterministic serialization 不是 canonical，序列化字节可能随 schema、build 或 library 改变，因此 protobuf bytes 禁止直接充当 ContentDigest、ReceiptId 或签名正文。[Protobuf 非 canonical 说明](https://protobuf.dev/programming-guides/serialization-not-canonical/)

CBOR 采用 RFC 8949 core deterministic encoding，并额外固定：

- 禁止 duplicate map key；
- 禁止 indefinite length；
- 禁止 float/NaN 进入 authority arithmetic；
- map key 使用确定性排序；
- integer 使用最短表示；
- schema name/major/minor 进入签名 body；
- decoder 必须重新编码比对 deterministic bytes。

[RFC 8949](https://www.rfc-editor.org/rfc/rfc8949.html)提供确定性编码基础，但具体 NLOS schema 仍必须定义自己的允许类型和约束。

### 21.2 canonical object 不做 protobuf round-trip

RPC 传递 canonical 对象时使用：

```text
CanonicalEnvelope {
  type_tag
  schema_major
  canonical_cbor_bytes
  content_digest
  signature?
}
```

接收方验证 CBOR、digest 和 signature 后再投影成内部 view。禁止把 CBOR 解析为 protobuf、再由 protobuf 重新编码后计算身份。

### 21.3 IPC

协议与 transport 分离：

```text
Typed Service Envelope
  → framed RPC/multiplexing
    ├─ Unix Domain Socket（Linux/macOS daemon）
    ├─ Windows Named Pipe
    ├─ macOS XPC adapter（需要 privilege separation 时）
    └─ in-process test transport
```

阶段 B 使用 Protobuf service schema + Rust generated client/server。transport library 先以 tonic/prost 候选实现；若 named pipe/XPC 集成导致大量私有 extension，再保留同 schema、替换 transport adapter。

IPC 边界要求：

- peer identity 从 UDS credential、Windows token/pipe ACL、XPC audit identity 或受信 session 注入；
- client 自报 Principal/ProcessId 不构成身份；
- frame size、stream count、queue、deadline 和 rate 有硬上界；
- connection close 不等于 Operation 未发生；
- request 使用 stable RequestId/IdempotencyKey；
- streaming 有 credit/backpressure；
- unknown major/critical field fail closed；
- opaque Capability handle 绑定连接、holder、rights 和 generation。

### 21.4 结论

```text
Protobuf/Buf = 服务兼容性
WIT          = Wasm 组件边界
CBOR/CDDL    = 权威字节身份
UDS/Pipe/XPC = 可替换本地传输
```

## 22. 第六项：Resource Controller 与平台适配

### 22.1 结构

```text
Resource Manager policy
  → ResourceController trait
    ├─ LinuxCgroupV2Controller
    ├─ WindowsJobController
    ├─ MacOSProcessController
    ├─ WasmtimeController
    └─ Model/DriverController
```

统一的是 contract、状态机、Receipt 和 capability discovery，不统一虚构的宿主能力。

每个 controller 返回：

```text
ENFORCEMENT =
  HARD_ENFORCED | RESERVED | METERED |
  COOPERATIVE | UNSUPPORTED
```

### 22.2 首批资源维度

阶段 B 第一批只实现：

1. CPU time/share；
2. memory working set/hard limit；
3. storage bytes；
4. file/stream I/O bytes；
5. Process/Fiber/concurrency slots；
6. model token/cost reservation；
7. network request/byte rate。

GPU、energy、human attention 保留 schema 和 controller 接口，但不阻止首个纵切面。

### 22.3 技术选择

- Linux：直接操作 cgroup v2 文件接口，避免把 container runtime 设为硬依赖；
- Windows：Win32 Job Object/token API，通过窄 FFI adapter；
- macOS：公开 Process/App Sandbox/XPC 能力 + NLOS admission/metering；不能硬限的维度显式降级；
- Wasmtime：fuel/epoch、memory/table/instance limit；
- model/tool：credential-holding Driver shim 负责 reservation、meter 和 fence。

## 23. 第七项：Package、Application 与 Driver 格式

### 23.1 Package 结构

采用 NLOS manifest + OCI Image Layout 风格内容寻址层：

```text
NlosPackage
  manifest.cbor          # 签名权威对象
  manifest.toml          # 可选人类源文件，不是权威身份
  blobs/sha256/...       # component/native/assets/schema
  signatures/
  sbom/
```

`manifest.cbor` 至少声明：

- Package/Application/Executable stable identity；
- version、target platform/arch；
- executable kind：WASM_COMPONENT / NATIVE / SYSTEM_SERVICE；
- WIT world 或 native adapter protocol；
- requested Capability/Resource/Device；
- data migration、update、rollback；
- trust tier、IsolationContract；
- UI surfaces、background services；
- package layers 和完整 digest root；
- signer、signature、SBOM/provenance。

OCI 兼容用于分层、CAS 和分发，不让 OCI config 取代 NLOS Application/Capability/Task 语义。

### 23.2 安装与运行

```text
acquire
→ verify digest/signature
→ inspect manifest without executing
→ resolve compatibility
→ user/policy authorization
→ stage immutable blobs
→ atomic Installation record
→ activate version
→ launch via Process Supervisor
```

更新采用 side-by-side version + atomic active pointer；migration 在独立受控 Process 中运行；失败回滚代码版本，但不可假装已经发生的外部副作用或不可逆数据迁移自动消失。

### 23.3 Driver

Driver 采用进程外 adapter 为默认：

- core 只依赖版本化 Driver protocol；
- provider credential 留在 Driver shim/Keychain；
- MCP/A2A/OpenAI-compatible/CLI/browser 都是 adapter；
- in-process plugin 只允许 T0/T1 且需明确 ABI；
- 第三方 Driver 首选 Wasm component 或独立 native Process。
