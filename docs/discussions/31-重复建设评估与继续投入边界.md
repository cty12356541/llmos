# 议题 31：重复建设评估与继续投入边界

> 状态：评估结论已定；阶段 B 实施顺序调整待管理基线另行采纳
>
> 日期：2026-08-03
>
> 适用基线：[架构设计总纲 v0.5](../design/06-架构设计总纲-v0.5.md)、[阶段 B 技术选型](../management/stage-b-technology-selection.md)、[阶段 B 权威进度单](../management/stage-b-progress.md)
>
> 议题范围：判断 NLOS 是否正在重复建设已有 Agent OS/runtime，明确必须自持、应当复用和暂缓建设的边界，并为继续投入设置可证伪的验收门。本议题不把外部项目说明当作实现证据，也不自动改变阶段 B 当前工作项顺序。

## 1. 问题与结论

问题不是“是否使用了别人也使用的 Process、Capability、WAL 或 Fiber”，而是：

1. NLOS 的核心哲学是否已有公开先例；
2. 哪些机制构成 NLOS 的系统身份，必须由项目掌握；
3. 哪些只是成熟基础设施，继续自研会扩大维护面；
4. 项目在什么证据出现后才值得继续扩大到桌面、分布式和生态。

结论：

> **NLOS 存在重复建设风险，但仍值得有条件地继续。值得继续的是“通用 AI 原生 Application 的提交、副作用、资源与控制权威层”，不值得继续的是横向重建另一个包办 Agent、RPC、沙箱、工作流、桌面和分布式基础设施的 Agent OS。**

具体判断：

- “概率模型位于不可信用户态，确定性内核在不可绕过边界强制权限、资源和副作用”已有多个公开先例，不能作为独占创新或“世界首创”声明；
- Capability、可消耗 Budget、Checkpoint/Replay、Agent Process、Context paging、调度、Wasm/V8 隔离和 durable workflow 均有成熟机制或近邻项目，默认应复用、适配或兼容；
- `TaskAttempt → CommitPermit → LogicalEffect/EffectPermit → Operation → Receipt → reconcile` 的组合，以及它与 pure-code/LLM Application、统一 ControlCommand、多维 Resource Manager 的衔接，仍是项目应重点验证的差异；
- 差异目前主要处于 `DESIGN`，只有完成最小 Slice K 和故障矩阵后，才能晋升为已实现能力；
- 若该纵切面可由现有 durable execution 引擎加薄适配完整满足，项目应转为其上的 NLOS authority extension，而不是维护完整独立 runtime。

由此可以确认：

```text
不可信 LLM 用户态
+ 确定性微内核
+ capability/budget
+ checkpoint/replay
+ context paging
+ Agent 调度
```

这一组合本身已经有强近邻。NLOS 不得仅靠更换术语或扩大功能清单声称架构独创。

## 3. NLOS 必须自持的系统语义

“自持”不要求从零实现所有底层算法，而是要求 NLOS 拥有公开契约、权威状态、失败语义和 conformance；底层可以由成熟组件承载。

### 3.1 TaskAttempt 与唯一 canonical commit

NLOS 必须证明：

- 同一 Task 可以安全运行 retry、hedge 或候选 Attempt；
- 每个 Attempt 具有独立 Snapshot、generation、资源与取消域；
- 只有一个 Attempt 获得 CommitPermit 并推进 TaskHead；
- losing/cancelled/stale Attempt 不能污染 canonical Artifact 或状态；
- “cancel 先于 permit”和“permit 先于 cancel”只能产生规范允许的线性化结果。

这不是普通 workflow retry 的别名，而是海量 Agent 并发、候选执行和唯一结果提交的共同权威。

### 3.2 LogicalEffect、EffectPermit 与外部未知状态

外部系统可能已经接受邮件、付款、文件写入或设备命令，而 NLOS 在记录结果前崩溃。该裂缝不能被简单改名为 `FAILED`，也不能只靠 replay 消除。

NLOS 必须自持：

```text
LogicalEffect identity
  → per-slot EffectPermit
  → Operation generation / cancel epoch
  → provider idempotency or explicit GuaranteeTier
  → durable Receipt / effect history
  → NO_EFFECT | COMMITTED | PARTIAL | UNKNOWN
  → reconcile / compensation / human decision
```

当前 Operation、callback fence、durable authority 和 Outbox 已提供局部地基，但 `EffectPermit`、跨 Attempt effect history、permit adoption/quarantine 尚未实现，不得提前宣称该差异已经兑现。

### 3.3 多维 Resource 权威

NLOS 应保持以下分离：

- `ResourceAccount`：费用、token、可转移信用和账本守恒；
- `ResourceGroup`：CPU、memory、I/O、network、accelerator 等宿主容量与压力隔离；
- `ResourceController`：真实强制器及其 `HARD_ENFORCED / METERED / COOPERATIVE / UNSUPPORTED` 能力；
- `AdmissionPlan/Decision`：dispatch 前的多资源 prepare/commit/abort 与恢复。

不能用余额冒充物理隔离，也不能用 scheduler counter 直接改写信用账本。实现应先选最小资源集合验证，不为完整分布式资源平面预付复杂度。

### 3.4 通用 Application 与统一控制路径

NLOS 的验收对象不能只有 Agent：

- 同一系统必须运行 LLM Process、pure-code Process 和无 Task/IntentSpec 的后台 System Process；
- Application、Package、Installation、Executable、Process、AgentRole、Task、Artifact 必须保持身份分离；
- NL、GUI、CLI、API 必须收敛到同一个 typed Intent/ControlCommand、Capability、Resource 和 Receipt 路径；
- 自然语言是首要界面，但不是权限后门或唯一机器接口。

这些要求把 NLOS 从安全 Agent wrapper 推向通用 AI 原生应用平台，也是 Slice K 必须保留的边界。

## 4. Build / Reuse / Avoid 边界

| 类别 | 当前边界 | 原因 |
|---|---|---|
| **NLOS 必须拥有契约和权威** | nominal ID/generation、TaskAttempt/TaskSnapshot、CommitPermit、LogicalEffect/EffectPermit、Operation/Receipt、unknown-effect reconcile、ResourceAccount/Group 语义、ControlCommand、Artifact ownership | 这些定义 NLOS 的系统身份和失败语义 |
| **复用成熟实现并包适配层** | Tokio、SQLite、Wasmtime/WASI、Protobuf/Buf、成熟 CBOR/crypto、宿主 Process/Job/cgroup/sandbox、Tauri、OpenTelemetry、内容寻址与文件系统原语 | 避免重建 executor、数据库、虚拟机、编码器、密码学、窗口壳和观测后端 |
| **优先兼容或对照现有系统** | Temporal/Restate/Dapr durable execution、gRPC/Connect/现有本地 RPC、OS 服务发现、现有 package/OCI/WIT | 先证明现有系统无法无损承载 NLOS 不变量，再扩大自研表面 |
| **Slice K 前暂缓** | 完整桌面、应用商店、分布式 consensus/数据库、跨节点迁移、完整语义结算、海量语言 SDK、通用插件市场 | 防止横向建设掩盖核心纵切面未成立 |
| **禁止默认自研** | 通用 async executor、数据库/WAL、Wasm VM、通用 CBOR/Protobuf、密码算法、通用 RPC/服务发现平台 | 安全和维护成本高，且不能直接形成 NLOS 差异 |

约束：如果成熟组件缺少 NLOS 所需语义，应优先增加 facade、adapter、sidecar、conformance 和故障测试；只有证据证明组合无法满足不变量时，才新建底层实现。

## 5. 对阶段 B 当前进展的诊断

阶段 B 采用 Tokio、SQLite、Protobuf/Buf 和候选 Wasmtime/Tauri，说明技术路线并非默认从零重写底层。当前 Operation、Outbox、fault injection、cross-language IPC 也产生了真实局部 Evidence。

风险在于 `B-SCHEMA` 已连续扩展 framing、Unix socket、Windows named pipe、ServiceDirectory、三语言 client、协商、重连、幂等、deadline 和 OperationControl，而最能区分 NLOS 的 `B-TASK`、`EffectPermit` 和 `B-SLICE-K` 尚未开始。若继续横向扩张通用 RPC、服务发现和语言 SDK，项目会在证明存在价值前先承担平台维护成本。

因此形成以下边界结论：

1. Rust/TypeScript/Python 已足以证明当前跨语言协议可行；
2. Go/C# generation/golden 与独立 IPC PoC 仍有冻结前价值，但“增加第四种语言”不能证明 NLOS 核心成立；
3. Go/C# 不应推动 SABI 在 Task/Effect/Receipt 语义稳定前过早冻结；
4. 是否把 Go/C# PoC 后移到最小 Task/Effect 纵切面之后，属于阶段 B 权威进度单的顺序变更，必须另行更新 management canonical object，不能由本讨论静默生效；
5. `nlos-ipc` 应保持 NLOS 控制语义的薄承载层，不发展为通用 gRPC、服务网格或跨网络服务发现替代品。

## 6. 继续投入的最小证据门

在扩大桌面、分布式、生态和更多 SDK 前，Slice K 至少必须完成以下可复现路径：

1. 创建一个真实用户 Task 和冻结输入的 TaskSnapshot；
2. 同时启动两个竞争同一 TaskHead 的 TaskAttempt；
3. 只有一个 Attempt 获得 CommitPermit；
4. 两个 Attempt 请求同一个 LogicalEffect，只有合法 EffectPermit 持有者可 dispatch；
5. 在外部调用前、调用中、调用成功后写 Receipt 前分别强制崩溃；
6. 重启后区分 `NO_EFFECT / COMMITTED / PARTIAL / UNKNOWN`，未知状态进入 reconcile，不冒充失败；
7. 迟到 callback、旧 generation 和 cancelled Attempt 不能污染新执行；
8. 形成可查询的 Artifact、nested Receipt 和 TaskCommitReceipt；
9. CLI 与至少另一个入口产生等价 ControlCommand/Receipt；
10. 同时运行一个 LLM Process、一个 pure-code Process 和一个非 Task 后台 System Process；
11. 用相同故障场景对照至少一个成熟 durable execution 方案，记录哪些 NLOS 不变量可直接复用、哪些需要 authority extension；
12. 所有结论按 Evidence profile 限定，不把单机 PoC 外推为生产或分布式保证。

### 6.1 继续、收缩与转向条件

```text
最小 Slice K 证明独立权威语义
  → 继续扩大 Process / Resource / Control / SDK / Desktop

成熟 durable engine + 薄 adapter 可完整满足同一不变量
  → 收缩为 NLOS authority extension，复用其执行底座

无法证明 unique commit / effect fence / recovery
  → 停止横向扩张，修正或否决当前核心架构
```

这是一道可证伪的投资门，不是预设项目必然成功。

## 7. 对外定位与声明边界

当前不应使用：

- “首次把 LLM 当作不可信用户态”；
- “首个 Agent 微内核”；
- “首个 capability/budget Agent OS”；
- “已经具备 Windows/macOS 级系统能力”；
- “已有完整副作用 exactly-once 保证”。

更准确的候选定位是：

> **面向通用 AI 原生 Application 的系统权威层：在并发 Attempt、真实外部副作用、多维资源和多入口用户控制之间提供可持久、可恢复、可审计的统一语义。**

该定位仍是目标声明。只有 Slice K 的实现、故障证据和竞品对照完成后，才能晋升为能力声明。
