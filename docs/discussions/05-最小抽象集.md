# 议题 5：agent OS 的最小抽象集（钉抽象）

> 轮次：第 5 轮（2026-07-19）
> 方法：以 Unix 最小抽象集为参照，逐个判决"照抄 / 改造 / 新发明"，目标收敛到 ~6 个内核抽象
> 原则：Unix 赢在抽象少而准；警惕 Multics 陷阱——不要自上而下设计完美内核

## 一、逐个判决

### 1. 进程 → Agent 实例【改造】
- 可照抄：生命周期（创建/运行/阻塞/死亡）、可杀、可隔离
- 差异：创建成本（fork 微秒级 vs agent 冷启动需加载上下文/预热 KV cache）；状态不完全可捕获（模型内部状态不透明）
- **关键洞察：LLM 调用边界 = 时钟中断点**。agent 循环的每一步（一次 LLM 调用）是天然抢占点——agent 是协作式可调度的，调度粒度 = 一个推理步。游戏的 tick rate 概念自然成立：低优先级 agent 降 tick（少调用/用小模型）
- fork 的对应物：上下文分支（git 式 branch agent 状态）。LangGraph 时间旅行、MemFS worktree 已是雏形

### 2. 虚拟内存 → 上下文管理【改造，映射最精确的一块】
- 映射表：上下文窗口 = 物理内存；**RAG = 请求调页（demand paging）**；embedding 索引 = 页表；retrieval = 缺页中断处理；上下文压缩 = swap 压缩；**KV cache 前缀共享 = 共享库/写时复制**（多 agent 共享 system prompt = 多进程共享 libc，vLLM 已实现）
- 设计分叉：透明分页（内核决定换入换出，agent 无感）vs 显式管理（agent 自己 memory tools）
- Sisyphus 倾向：内核透明分页兜底 + agent 可给 hint（类比 madvise）

### 3. 文件/设备 → 工具【照抄，MCP 已赢】
- "一切皆文件"的胜利 = 统一接口战胜定制 API；MCP 就是 /dev
- 但注意语义差异：Unix 文件是字节流语义，MCP 是 RPC 语义；harness 派证明 LLM 对 shell/文件比对 JSON RPC 更亲（训练分布原因）
- 判决：双设备类——MCP（结构化设备）+ shell/文件（字节流设备），内核不选边

### 4. IPC → agent 间通信【大部分新发明】
- 管道胜利的原因：组合无需 schema 协商。agent 的"字节流" = 自然语言，但 NL 丢失结构 → schema 协商回归（A2A Agent Card ≈ 接口定义）
- **真正缺失的概念：背压**。Unix 管道满了阻塞写方；agent 消息队列无背压 → 议题 3 的 O(n²) 洪水
- signals：kill 之外需要更丰富中断语义（降预算/立即 checkpoint/降级模型）
- 共享内存 = 共享上下文/黑板；MemFS git 合并 = 乐观并发控制

### 5. 调度器【全新发明，无先例】
- 调度资源不是 CPU 时间，而是：推理槽位（GPU）、上下文空间、token 预算、工具并发度
- 优先级是语义的（任务重要度）不只是 nice 值；每步烧钱 → 调度器必须做经济核算
- LOD 调度：关键路径大模型、背景 agent 小模型——"智能"分级
- **最硬的骨头：livelock 检测**。进程死循环好检测（CPU 空转），agent"无进展空转"是语义判断——可能需内核内置小模型做语义监督（机制人写，策略可用 AI）

### 6. 用户/权限 → 安全模型【新发明，面对 Unix 没有的威胁】
- **代码/数据二元性坍缩**：Unix 安全假设代码完整性——读文件不会改写进程代码。agent 读一个网页就可能被改写目标（提示注入）。agent OS 里数据和代码是同一种介质（token）
- 推论：权限模型必须含污点追踪（不可信内容流经 agent 时降权）、权限分离（规划者不执行、执行者不规划）、ADK 式路由/语言解耦

### 7. shell/组合 → 编排【照抄思想】
- 管道组合、cron（定时 agent）、init/systemd（agent 监护：重启策略、依赖声明、资源限额）
- "agent 版 systemd unit"非常具体：`Requires=`、`Restart=on-failure`、`TokenBudget=`

## 二、Unix 完全没有的三块新大陆

1. **随机性执行管理**：统计性容错（冗余/投票/校验），不是异常处理
2. **自我修改**：Unix 进程不重写自身二进制；agent 必须重写自己的记忆/技能/提示词。内核要回答："自我修改后的 agent 还是原来授权的那个吗？"——agent 版本化 = 授权的版本化（MemFS mods 是雏形）
3. **经济资源模型**：token = 货币不是时间。调度器 = 会计 + 央行

## 三、最小抽象集提案（Sisyphus 初稿）

内核只钉 6 个：

| # | 抽象 | Unix 对应 | 职责 |
|---|---|---|---|
| 1 | Agent | 进程 | 生命周期 + 步边界协作式调度 |
| 2 | Context | 内存 | 透明分页 + hint；KV 共享 |
| 3 | Tool | 设备 | MCP + shell 双通道 |
| 4 | Channel | IPC | 带背压的消息 + 共享黑板 + signal |
| 5 | Budget | （新） | token 配额、核算、父子继承 |
| 6 | Policy | 用户/权限 | 权限 + 污点 + 自我修改的版本门控 |

**重要架构决策：调度器不进内核。** Unix 调度器在内核态，但 agent 调度策略太语义化——建议微内核路线：**机制在内核**（步边界挂起/恢复/降 tick），**策略在用户态**（甚至调度策略本身由一个特权 agent 执行——init agent 用 LLM 做语义调度决策，内核只提供机制）。

## 四、待讨论（三个问题的展开版）

### 问题 1：Budget 是否够格当一等抽象？（vs 并入 Policy）

**决策点**：内核抽象清单里，Budget（token 配额/核算/继承）独立存在，还是并入 Policy（"权限即配额"）？

**关键背景——Unix 自己的演化史**：Unix 原本也没有预算抽象，但演化方向是"长出来"：rlimits（随进程凭证）→ 磁盘配额（独立子系统）→ cgroups（CPU/内存独立核算子系统）。Unix 自己发现"静态权限"装不下"动态核算"。

- **A. 并入 Policy**：语义="允许调用 LLM，累计 ≤ 10k tokens"。优点：抽象更少；授权单点完成。缺点：生命周期错配——权限是静态布尔，预算是动态递减的数量；父子继承（spawn 时切一块预算给孩子）用权限语言表达很别扭；调度器每步读余额 → 与权限系统耦合
- **B. 独立一等抽象**：Budget 是独立内核对象：余额、消耗速率、继承树、耗尽行为（挂起/降级/死亡）。优点：生命周期匹配；调度器直读；支持经济语义（A 付钱给 B = 预算转移）；quota/cgroup 先例。缺点：抽象+1
- **C. 折中**：机制独立（核算在热路径）+ 授权接口统一（Policy 发预算，Budget 管怎么花）

**Sisyphus 倾向 B/C。改主意的条件**：目标场景是蜂群型（同质短命）→ 继承/转移用不上，A 够用；组织型（长期层级委托）→ 预算继承是刚需，必须 B

### 问题 2：Channel 拆不拆？

**决策点**：agent 间通信是一个抽象（统一 Channel）、两个（消息流 + 黑板）、还是三个（+广播主题）？

**关键背景——Unix 统一在哪一层**：管道（消息）和共享内存（共享状态）是**不同抽象**，但共享 fd 接口。Unix 的统一在**接口层**，不在**语义层**。真正的问题不是"一个还是两个"，而是"统一在哪一层"。

三种通信的本质差异：
| | 消息（管道对应） | 黑板（共享内存对应） | 主题/广播 |
|---|---|---|---|
| 定向性 | 定向 | 共享 | 群发 |
| 顺序 | 有序 | 无序 | 有序 |
| 持久性 | 消耗品 | 持久 | 消耗品 |
| 并发语义 | 背压（写满阻塞） | 合并（git/CRDT） | 兴趣过滤（议题3的O(n²)问题） |
| 故障模式 | 消息丢失 | 合并冲突 | 风暴 |

- **A. 单一 Channel**：优点：概念最简单，权限模型统一。缺点：消息丢失 vs 合并冲突是两种故障，一个抽象盖不住；黑板模式下背压语义不存在
- **B. 两个抽象（Message + Blackboard）**：语义各自干净；对应 Unix 管道/共享内存分立
- **C. 三个（+Topic）**：为万级规模预留兴趣管理；但现在就付复杂度税？

**Sisyphus 倾向 B**：Topic 作为 Message 的订阅组模式而非独立抽象；接口层统一（都是 Channel handle，统一寻址/权限），语义层分立——正是 Unix 的 fd/管道/共享内存关系

### 问题 3：Context 透明分页 vs 显式管理

**决策点**：上下文窗口里放什么，谁说了算——内核（透明）、agent（显式）、混合（透明+提示）？

**关键证据**：
- 透明派：Unix 进程不管页表；内核全局视角可跨 agent 去重共享页；小模型 agent 没能力管记忆
- 显式派：Letta/MemGPT 实证——自己编辑记忆的 agent 长期行为更好；**语义相关性是任务相关的，agent 才是理解任务的那个**；LRU 启发式会在最坏时刻换出"5 万 token 前的关键约束"；agent 不能控制记忆 → 自我修改/学习无从谈起（议题 4 新大陆 #2）
- **最锋利的类比——数据库的 O_DIRECT**：数据库绕过 OS 页缓存，因为 DB 比 OS 更懂自己的访问模式；但 Unix 仍默认给普通程序提供页缓存。结论形态：默认透明 + 专家逃生舱

- **A. 全透明**：地板高天花板低；且要求内核内有语义判断（内核塞小模型？机制复杂度爆炸）
- **B. 全显式**：天花板高（Letta 路线）地板低；内核无法跨 agent 优化
- **C. 混合（madvise/mlock 模式）**：内核管机械工作（压缩、淘汰未引用未钉住页）；agent 可钉关键页、可给建议；默认透明（休闲 agent）+ O_DIRECT 逃生舱（专家 agent）。缺点：两套语义并存；**agent 钉太多页 → 内存压力谁负责？需要配额配合——与问题 1 联动**

**Sisyphus 倾向 C，且注意联动：钉住的上下文页应计入 Budget**
