# B-TASK-008C2G-IPC：TakeoverControl 跨进程签名 barrier 提交服务

状态：`PARTIAL_PASS`（2026-08-22）

## 1. 结论

本切片把 `record_authority_takeover_barrier_receipt_signed` 从进程内 API 提升为真实本地 IPC 服务：新增 `nlos.sabi.TakeoverControl` v1.0（payload 家族 + 64 KiB bound，registry 第 5 个 schema），新 crate `nlos-takeover-control` 提供零状态 handler（持有 `&SqliteTaskAuthority + &IdentityAuthority + pluggable TakeoverControlAuthorizer`），单一 MUTATION 方法 `submit_barrier_observation` 经 `validate_sabi_request_context(MUTATION)`（idempotency key 强制）后委托既有 store 验签路径。与 SystemControl 的 `caller==issuer` 检查刻意解耦：签名属于远端 participant principal，IPC caller 由 capability authorizer 单独授权——这是本切片的显式信任模型决策。同时偿还 B-TASK-006L 明示的债：`TakeoverControlError::to_sabi_failure` 提供完整 typed 错误→SabiFailure 映射表，失败以带 SabiErrorCode/RetryDirective 的合法响应信封跨 IPC 返回而非裸 transport 错误。2026-08-19 增量再加入 feature-gated `takeover-control-conformance` server：TypeScript/Python 客户端通过生成的 TakeoverControl payload 真实提交签名 observation，在同一 handler 上完成第二连接的 durable replay；Unix socket 与 Windows named-pipe 均复用同一 server 入口。随后并发增量在两个独立 IPC caller 上并行提交同一 signed observation，验证单 writer 序列化、单 durable row 和 verified record 一致性。最新故障增量又在同一实际 IPC handler 上注入 SQLite VFS `IOERR`/`ENOSPC` 写失败：失败均返回 typed `DURABILITY + RETRY_SAME_IDEMPOTENCY_KEY` 且不落 durable row，解除注入后用同一 key 重试恢复为一个已验签、`LocallyCovered` 的记录；再增加 `PowerLossAfter` 静默丢写模型，证明 IPC 返回的幻影记录在重开后不可见、同 key 重做恢复为单行 durable 记录。第十二增量又加入受控的“提交完成、响应尚未发送”进程崩溃窗口：服务端在 `TakeoverControl::handle` 成功返回后发出 `COMMIT_READY` 并暂停，TypeScript/Python 客户端 kill 服务进程，随后以同一 authority/identity 数据和同一 request/idempotency key 重启，验证 durable record 恢复且第二次 replay 逐字节一致。第十三增量把 feature-gated server 的真实端点连接数配置为 2–32，并让 Unix socket/Windows named pipe 并发接收 8 个独立 caller；不同 request/correlation/caller identity 共享同一 idempotency key 时，所有响应的 durable signed record 逐字节一致，服务退出前仍只保留一行 `LocallyCovered` 记录。第十四增量再在同一真实 IPC handler 上加入 test-only SQLite WAL 尾部撕裂：提交后服务端截断最后一个 commit frame 的中段并发出 `WAL_TORN_READY`，TypeScript/Python kill 进程、清理共享内存索引后重启同一 authority/identity；恢复路径丢弃撕裂尾部，随后同 key 重做收敛为单行、逐字节可 replay 的 `LocallyCovered` signed record。第十五增量加入测试专用多轮端点压力：服务端每轮接收 32 个真实 Unix/named-pipe 连接，连续 4 轮共 128 个会话；客户端在每轮保持连接后并发提交不同 request/correlation/caller identity、共享同一 idempotency key，所有 verified durable record 逐字节一致，最终仍为单行 `LocallyCovered`。第十六增量补上信号级进程崩溃矩阵：测试专用 server 新增 `NLOS_TAKEOVER_CONTROL_HOLD_BEFORE_COMMIT` 提交前保持钩子（发出 `PRE_COMMIT_READY` 后暂停），与既有提交后 `COMMIT_READY` ## 4. 明确限制

- 当前已覆盖 TypeScript/Python 的 TakeoverControl payload/response conformance；尚未提供长期发布的 npm/PyPI SDK facade 或版本承诺。
- 防重放 = SABI idempotency key + store exact-replay 语义；**无时间窗 anti-replay**（trusted clock 是独立未来 authority），`observed_at_ms` 的 wall-clock 真实性未强制（identity key validity 已有界）。
- `ExactPeerAuthorizer` 绑定 OS 凭证（pid/uid/gid），还不是 NLOS principal 级双向 peer auth/attestation；`TakeoverControlAuthorizer` 测试中为受控 stub，未接真实 Capability authority。
- 错误映射中 CorruptRecord 按 store 静态消息串区分 CONFLICT vs STATE——串是 authority 内 `'static` 稳定值，但属结构耦合，store 侧消息变更需同步。
- 覆盖 TakeoverControl 单方法、两个 duplex caller 的并发线性化、8/32 个真实 Unix/named-pipe 并发 caller、32 个端点 × 4 轮 bounded soak、两次串行 caller 连接、Windows named-pipe round-trip，IPC 入口的 SQLite `IOERR`/`ENOSPC` typed failure/recovery、`PowerLossAfter` 静默丢写模型、受控 kill-after-commit/restart recovery、测试专用 WAL 撕裂尾部恢复、提交前/后确定性信号矩阵与固定 seed 随机延迟崩溃矩阵；分钟级长时运行由独立 `takeover_control_long_soak.{ts,py}` 入口覆盖。仍无随机外部时刻进程崩溃、真实断电与时间窗 anti-replay，`TakeoverControlAuthorizer` 仍为测试 stub 而非真实 Capability authority，`ExactPeerAuthorizer` 仍非 principal 级双向 peer attestation。以上 transport 故障矩阵仍属后续门。
