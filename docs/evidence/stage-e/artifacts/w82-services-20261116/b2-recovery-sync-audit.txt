## 已有保护路径

1. `crates/nlos-driver-llm-http/src/reservation_journal.rs:165–172`：可选截去合法 torn tail 后，执行 seek，随后**无条件** `file.sync_all()`。它并不位于 `if used.bytes < file_len` 内；即使文件结尾是完整且校验合法的 Settle/Reject/其他 terminal 帧、完全不需要截断，也必须先成功通过恢复同步屏障。同步失败在 172 行映射为 `GatewayError::Durability` 并返回，不会走到 180 行 `Ok(Self { ... })`。
2. `crates/nlos-driver-llm-http/src/llm_gateway.rs:461–466`：解析回调只把事件应用到本次 load 的局部 State。该 State 虽在同步前构建，但尚未对调用方发布。Journal::open 返回成功后才构造 Gateway；`490–493` 又要求 recover 成功，最后才返回 Gateway。因此完整 terminal 帧不会在恢复同步屏障之前进入可调用的结果缓存。
3. 原实例中的 append 同样有保护：`reservation_journal.rs:256–271` 在写完 header/body/checksum 后同步；`247–249` 遇到写入或同步错误会 poison 并返回失败。`llm_gateway.rs:391–397` 只有 journal append 成功后才 apply 内存状态；`496–499` 拒绝继续读取 poisoned journal。没有依靠原实例在失败后继续发布结果的旁路。
4. 对仍需恢复推进的 intent，`llm_gateway.rs:1388–1401` 的 recover 进入原 finish_settlement 或 append 路径。Settle 在 `1352` 经同一 journal append/sync 后才完成；`Gateway::load` 不会在该恢复失败时返回可用对象。对于已经完整恢复成 terminal 的状态，虽然 recover 无需新增写入，前述 Journal::open 无条件同步已足够，无须依赖“碰巧写入下一条记录”。
5. 首个受保护 chat replay 在 `llm_gateway.rs:1024–1045` 经过可用 journal/账户检查、恢复和当前授权后调用 chat_reply。可取得 Gateway 的时间本身已晚于上述恢复同步屏障；本次风险没有穿过该路径。
