## 正确性核查

1. **获得锁后立即接管。** `WriterLock::acquire` 将原 `try_lock` 与 WriterBusy/Durability 映射原样保留；只有成功持锁才构造 guard。guard 紧接原 open 建立，早于 metadata、容量/记录验证、恢复 apply、文件同步及 Unix 目录同步，故所有后续 `?` 或错误 return 都有受控析构，非持锁错误不会执行 unlock。
2. **最后逻辑 owner 才释放。** guard 是 Journal 的私有文件字段，无新增 Clone 或共享可变入口；Deref/DerefMut 仅让原 I/O 调用继续使用该 File。Arc owner 未归零时 Journal 不析构。最后 owner 销毁时显式 unlock 先于 File 字段自动 close，不再依赖被动 OS 引用都已关闭。
3. **Unix PID 护栏正确。** 成功获得锁时记录 creator PID。fork 副本在其他 PID 执行析构时跳过显式 unlock，随后字段仍正常关闭，避免子副本主动解除原进程的共享锁。这一 cfg(unix) 分支仅做静态接受，尚无本轮 Unix 运行证据，也不声称做过 fork 实验。
4. **后继 writer 与失败语义。** 新 writer 仍必须完成真实 try_lock；被动旧 File close 不拥有新打开对象的锁。Drop 忽略 unlock 的返回值，没有生成成功 ACK；如果底层释放失败，后续 open 仍会返回原 typed error，没有把 Busy 吞掉或重试。
5. **持久语义保持。** 除文件私有 owner 类型和获得/释放动作，本 delta 未改变记录格式、校验、恢复回调、同步/截尾次序、容量、poison 或外部接口。没有解锁后仍执行 journal 写入的新增路径，没有 Busy sleep/retry。
