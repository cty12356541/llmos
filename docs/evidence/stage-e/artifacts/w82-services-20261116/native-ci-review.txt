## 审查重点

1. **失败传播与旧门。** Helper 每条命令保留 argv/实际退出码及原始合并日志；启动失败记录 returncode=null，失败或 skipped 均将最终退出码置为 1，独立探针仍继续。workflow 在 workspace 前采集，`continue-on-error: true` 只让后续旧门继续；最后 `always()` 条件检查原始 outcome==failure 并 exit 1，而非读取已转换的 success conclusion。该区别与 [GitHub steps context 官方定义](https://docs.github.com/en/actions/reference/workflows-and-actions/contexts#steps-context) 一致。前置普通步骤失败造成采集未运行时，作业已由该前置失败变红，不会因此成为绿色。
2. **原有配置保持。** 独立移除三个新增 step 后，workflow 与 HEAD 逐字文本相同（统一换行比较）；既有 job、矩阵、平台条件、workspace tests/Clippy、MSRV 1.97 all-targets check、fmt、阈值、timeout 和 workload 均未改。没有新增路径过滤或跳过旧检查。
3. **上传与归属。** Artifact 上传使用 `always()`，目录与 helper 的 RUNNER_TEMP 输出一致；名称绑定 OS、GitHub SHA、run ID、attempt。Helper 同时记录 checkout HEAD，并在 GITHUB_SHA 存在时要求相等，保存 runner 白名单元数据及 rustc/cargo 版本。旧步骤后续失败不取消已收集证据的上传机会；runner 强制中断仍属于运行时结果，不能预先承诺上传成功。
4. **Linux 原生与 fallback。** Cargo JSON 只接受指定 manifest、blob_open integration-test target、唯一 executable，避免 glob 选错旧二进制。正常及注入模式执行同一完整测试 exe，两者均检查关键真实测试通过。正常 trace 必须出现含 RESOLVE_BENEATH 的 openat2 非负返回；注入 trace 必须出现实际 syscall 行、ENOSYS 与 `(INJECTED)`，普通 ENOSYS 或 metadata 不足以过门。`-ff` 分离线程日志，模式与 [strace 官方注入输出](https://strace.io/#perform-a-syscall-fault-injection) 一致。缺 tracer 或缺 exe 标 skipped 并令总门失败，没有伪造 fallback 覆盖。
5. **Windows 实际夹具。** B3 的 windows_symlink marker 使用词边界，windows_symlink_unavailable 不匹配；父 junction 与 hardlink marker 另外要求。B4 使用明确 `--exact --ignored` 调用平台忽略测试，还要求该确切测试 ok、link-leaf swaps>0、exterior_or_unexpected=0。定向读取当前 B3/B4 测试名与 marker 输出位置确认兼容；未重复审查服务实现，也没有本机权限/开发者模式修改。
6. **latency。** 三平台实际 measurement 入口、macOS 平台名称转换、warm catalog、20 samples、invoke+spawn+run+durable_result、p50/p95 记录要求与当前 B3 输出一致；没有把 50ms 或合成 fixture 的 65.50/123.45ms 设成失败阈值，也未引入 persistent host。
