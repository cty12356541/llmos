## 调用链与验证边界

- 测试先把 WAL 填至大于 64 frame 窗口，通过另一连接保持已建立读快照。测试 wall=100 ms、mono=100,000,000 ns，两值稳定。请求可信 deadline 为 120,000,000 ns。生产 `begin` 映射为从调用开始附近计的 20 ms 本地 `Instant` 界。测试 stopwatch 覆盖解码、时钟、authority/identity、文件及格式读、SQLite 写前和 checkpoint 等完整链。
- `blob_ledger.rs` 的 `with_blob_writer_settings` 将 SQLite busy timeout 置零，关闭 cache spill，并在 action 结果后恢复原配置。高水位 `trim_wal` 首先执行 SQLite `TRUNCATE` checkpoint，busy 则恢复配置、释放 authority mutex，再按 `Timing::pause` 剩余预算重试。正常路径每次动作或 commit 前有 deadline 检查，失败后无应答字节。
- 锁定 `libsqlite3-sys 0.38.2` 的 `sqlite3/sqlite3.c` 69543 的 `walBusyLock` 仅在有 busy handler 且锁忙时反复尝试。69635 以后 `walCheckpoint` 可在持读快照时同步 WAL、将安全 frame 写入主库并同步主库（约 69712、69750、69764）。随后在 69796–69810 尝试阻止 WAL 重启的 reader 锁并可能返回 BUSY。SQLite no-wait 条件限定 busy 重试，不约束已进入 OS 的同步回填、刷新和线程调度。Blob 文档本就把这些阶段与本库能控制的排队区分。
- 因此现失败能证实截止后拒绝和 wall-clock 测量越界，同时不能证实旧固定 SQLite 等待恢复、重试预算被放宽或出现新增读计数。

## 建议的最小修复，待编排确认

1. `crates/nlos-capability/tests/blob_reference.rs`。仍创建并一直持有真实读快照。用观察连接的 no-wait TRUNCATE 校验 `busy=1`、frames 已回填且 WAL 仍高于窗口，再进入服务调用。保留原 20 ms 精确 `DeadlineExpired`、零 receipt、释放锁后同键重试与 release。整段 API 的 `Instant.elapsed` 打印诊断值，将受控等待的门交给以下两项确定性测试，无放宽阈值。
